# 上下文摆放与缓存命中：用已有真实调用做的对照（2026-11-16）

范围：只读分析，没有新的模型调用，没有改代码。数据是 11-01 和 11-05 两批真实模型评测（MiniMax-M3，OpenAI 兼容接口）留下的 2,811 次有用量的模型调用，以及本机 `.local/real-eval-2026110{1,5}/wire/` 里的实际请求体。请求体不进仓库，本目录只有汇总数字。

复现：`scripts/s0_load.py <pickle 路径>` 先生成数据，其余脚本读它；原始输出在 `output/`。

## 1. 没命中缓存的输入来自哪里

两批合计输入 5,380 万 token，缓存读取 74.0%，未命中 1,401 万。

| 来源 | 未命中 token | 占未命中 | 说明 |
|---|---:|---:|---|
| 每次运行的第一次主循环调用 | 867 万 | 62% | 该类调用命中率 11%–14% |
| 隔离子任务的调用 | 301 万 | 21% | 子任务首次调用命中 18%，后续 64% |
| 运行内新增的内容 | 219 万 | 16% | 每条新消息必然先未命中一次 |
| 运行内已缓存内容失效 | 24 万 | 2% | 974 次里 17 次；其中换工具 5.5 万、缩减与清理 0.6 万 |

运行内部已经接近最好：主循环第二次调用起，命中的 token 数正好等于上一次请求的全部输入，间隔 5 分钟以内 99%–100%，5–10 分钟 97%，超过 10 分钟 60%。

## 2. 第一次调用为什么不命中

- 第一次调用的输入中位数约 4 万 token，其中系统提示加工具定义约 3.75 万，和前一次运行逐字节相同（`output/s2.txt`：按“系统提示 → 工具 → 消息”的顺序，可复用前缀占 84%–89%）。
- 实际命中的中位数只有 184 token。命中时都是 37,504 token（正好是系统提示加工具定义），但只发生在约 18% 的首次调用上，和距上次调用的间隔无关（0–120 秒内各档都是 14%–24%）。
- 服务商文档写的匹配顺序是“系统提示词-工具定义-历史对话内容”，没有写留存时间，也没有缓存路由参数。
- 结论：内容是稳定的，不稳定的是服务商是否复用。原因从记录里判断不出来，要用真实探针确认（§6）。

## 3. 摆放顺序能多复用多少

用实际请求体重排后，量“系统提示加工具定义”之后还能与上一次运行共用多长的前缀。字段顺序在一批上按“相邻两轮完全相同的比例”学出来，在另一批上检验。

| 摆放 | 11-01 批（预载一份技能正文） | 11-05 批（不预载技能） |
|---|---:|---:|
| 现状：信封（问题在最前）→ 技能正文 | 约 16 token | 约 17 token |
| 技能正文 → 信封 | 约 3,975 | 约 17 |
| 再把信封里稳定的字段排前、问题和 `context_ref` 排最后 | 约 4,384 | 约 432 |
| 再把历史改成旧的在前 | 约 4,571 | 约 680 |

同一会话相邻两轮之间，稳定的只有技能正文、品类、产品、个人偏好这几项；历史（约 1.9k）、工作状态（约 1.1k）每轮都整段重写，稳定比例为 0。

所以摆放顺序能争取的上限是每次运行 0.4k–4.6k token；第 2 节那 3.75 万 token 是它的 8 倍以上。

## 4. 对成本和速度的影响

- 成本：两批按价卡合计 12.09 美元，其中输入侧 6.89 美元。首次调用若都能复用系统提示加工具定义，缓存读取升到 85.3%，总成本降 12.6%；再把技能正文放到信封前，再降 2.3%。
- 速度：总时延主要由输出决定，每 1k 输出 token 约 9–10 秒。缓存命中与否的系数在两批之间互相检验时不稳定（一批拟合、另一批检验，主循环的未命中系数从 −342 到 +42 毫秒/1k）。直接比较首次调用：命中时中位 12.5 秒（30 次），未命中 11.4 秒（163 次），看不出差别。
- 现有记录没有每次调用的首字时间，所以“命中缓存更快”在这个服务商上还没有被证实，也没有被否定。

## 5. 失败与重复

- 主循环 1,499 次工具调用里 394 次失败（26.3%）。失败结果都留在上下文里，清理也不会清掉错误结果。
- 394 次失败里有 102 次（25.9%）是同一次运行里同一工具、同一失败码的再次出现，集中在 `assistant.extract`（117 次失败里 57 次是重复）。失败后下一次调用仍是同一工具的有 66 次。
- 同一工具连续调用 5 次以上的运行有 9 个，7 个以 partial 结束。
- 同一会话里，上一轮 completed 时本轮 completed 占 40%，上一轮 partial 时占 20%。这只是相关，难题本来就集中在某些会话。
- 这些是 11-01、11-05 的数字，之后的修复（参数校验、工具按范围下发、最后一轮指令）没有重测。

## 6. 需要真实调用才能定的事

探针用系统提示、工具定义和合成问题，不带业务数据，约 80 次调用、输入不超过 400 万 token。

1. 基线：不同问题的首次调用，顺序发送，看命中率是否仍约 18%。
2. 稳定的首条消息：把技能正文或固定说明放在第一条用户消息，问题放第二条，看命中是否变稳定、变长。
3. 固定开场：每次运行都从同一段固定的“用户说明 + 固定回复”接着写，看首次调用能否稳定命中。
4. 留存时间：隔 1、5、10、20 分钟重发。
5. 每次调用记录首字时间，比较命中与未命中。
