## 1. 做了什么

### 字段（`memory_note_versions`，迁移占位号 `s0_0900`）

| §5.7 字段 | 个人条目 | 取值与校验 |
|---|---|---|
| `occurred_at` 事情发生的时间 | 新增，可空 | 不能晚于记下的时间（服务器和数据库都查），和范围条目同一规则 |
| `valid_from` 生效起点 | 新增，必填 | 不填时：新建取“现在”（= 本人确认这一版的时间，与 `created_at` 同一时刻）；修改已生效的条目取“现在”，修改尚未生效的条目沿用原起点 |
| `valid_to` 生效止点 | 沿用已有的 `valid_until` | 须晚于生效起点和现在（与范围条目同一句校验）；替代时由服务器写 |
| `confirmation` 业务确认状态 | 新增，必填 | 与范围条目同一套取值；个人条目只有 `member_confirmed`，页面写“本人确认” |
| 证据链接 | 新增 `evidence`（版本上的 JSON 数组，≤10 条） | 与 `scope_note_evidence` 同形状、同取值：来源（运行 / 讨论 / 回执 / 原件 / 业务对象）、对象种类、版本、片段定位、片段摘要、根来源、立场；复用范围条目的 `EvidenceInput` 请求模型；只存片段的摘要，不存原文；每条按本人当前权限现读，别人的对话不能作来源 |
| 关系 | 新增 `relations`（版本上的 JSON 数组，≤10 条）：冲突、重复 | 取值是范围条目 `RELATIONS` 的子集；替代用已有的 `replaced_by`（被替代的一方） |

数据库里加了三条检查约束（`memory_note_contract_time`、`memory_note_evidence`、`memory_note_relations`），JSON 里的来源、立场、对象种类、关系种类、摘要格式都在库里再查一遍；`test_values_are_the_scope_notes_values` 核对个人取值等于或包含于范围条目的取值。

证据和关系放在版本行上、不另建表的理由：个人条目的内容只存在版本里，本人删除（P94）一次删掉全部版本，证据和关系随之清除，只留删除记录；行级权限、不可改触发器、删除策略都沿用 s0_0865，不必为两张新表再写一套“只有本人、AI 身份不能写、删除时清除”的策略。范围条目是业务记录、要回执和按运行撤回，所以用独立表；两边字段与取值相同，物理存放不同。

### 不加的字段及理由

| §5.7 字段 | 为什么个人条目不加 |
|---|---|
| `claim_key` + 部分唯一索引 | 个人条目的重复由本人按相似度在“合并 / 替换 / 都保留”里决定（P86 第 4 项）；唯一索引会让“都保留”无法成立 |
| `subject_ref` | 已有叫法的 `target_*`（对象、版本）就是主语对象；其他种类的“可能过期”按 P86 只看引用对象，不扩大 |
| `value`（原文、数值、单位） | P86 定为自由文本 ≤200 字，不抽数值 |
| `applicability` | 范围条目经验类、决策背景类的要求；个人条目已有作用域（全局 / 品类 / 产品 / 提案 / 项目） |
| `source_authority` | 个人条目永远是本人的陈述，不是依据、不能引用（P86 第 1、6 项）；从证据算权威性会让它看起来能当依据 |
| `epistemic`（可信状态） | “已核实”要具名核实人和独立来源（§5.6.5），是团队流程；个人条目恒为“本人这样说” |
| `generated_by` | 已有 `origin`（本人填写 / 经提议确认 / 合并）表达同一件事 |
| `model_confidence` | 个人候选不按模型把握排序 |
| `review_due_at` | P87 第 4 项的团队复核；个人条目默认不过期，可自设有效期（P86 第 1 项） |
| `sensitivity` | 个人条目只有本人可读（行级权限），恒为“个人” |
| `created_by` / `confirmed_by` / `receipt_id` | 个人条目只能由本人写和确认，不是 T0/T1/T2 命令，没有回执（P86 第 10 项） |
| 确认状态的 `discussion` / `proposed` / `formal_linked` | 讨论、提议阶段的东西是候选，不是条目（本人点“记住”才写入；P121 第 8 项的“只是讨论”作废候选）；个人条目不是业务记录，不会“已关联正式记录” |

### 替代按生效时间

- **替换旧的**：旧条目在新条目的生效起点结束（`valid_until = 新起点`，标“已替换”）。新条目起点在将来时，旧条目一直有效到那天，页面写“将被替换于 …”，新条目标“未生效”。
- **补录**：新条目的生效起点早于要替换的条目时，它是旧信息，只进历史：写成“已替换”、`replaced_by` 指向现有条目、`valid_until` 为现有条目的起点；现有条目一个版本都不加。接口返回 `effect: "history_only"`，页面提示“只记入了历史”；冲突核对接口提前给出每条的 `replace_effect`。
- **合并**：改写旧条目，起点按修改的规则；两边的证据和关系都保留。
- **都保留**：可同时把它们标为“冲突”或“重复”；标为冲突的两条口径都只进背景区，并注明。
- **相似判定**多了一条：两条的生效区间不重叠就不算冲突（`memory-note-similarity/v2`）。
- **修改**：已生效的条目不能把起点改到将来（要从将来某天起换说法，请新建一条并选择替换）。

### 带入与检索（不扩大范围，不超过 1,000 token）

- 常驻注入只带“现在生效”的条目：未生效、已被替换、补录进历史的都不带入（`notes.state` 先看生效时间）。
- 标为冲突的口径降到背景区，并写明“你把这条和另一条记忆标为冲突”。
- 条目带了发生时间的，信封里给 `occurred_on`（日期）；它和正文一样不存在运行行上，每次从版本表读（D481）。
- `memory.search` 的条目卡片加 `valid_from`、`confirmation_label`，有发生时间时加 `occurred_at`；冲突口径同样降为背景。
- `as_of` 改为按生效时间：取当时“起点已到”的最新版本；在起点之前就被改掉的版本从未生效；补录的旧条目在它覆盖的那段时间里能查到（背景、标明现在已替换）；替换标记只表示上一版在何时结束。未生效的条目从不返回。
- 工具定义、提示词、冻结前缀都没改；改的是追加在上下文末尾的个人记忆信封结构（`personal_memory` 的 `_ENTRY` 多一个可选的 `occurred_on`）。

### 迁移一次（默认值与理由）

| 字段 | 默认值 | 理由 |
|---|---|---|
| `valid_from` | 每一版自己的 `created_at`；“已替换”标记版沿用它所结束那一版的起点 | 那就是本人确认这一版的时间；这样旧条目的列表、带入、检索和 `as_of` 答案与迁移前完全一样（测试 `test_migrated_rows_behave_as_before`） |
| `occurred_at` | 空 | 从来没问过，不能猜 |
| `confirmation` | `member_confirmed`（本人确认） | 现有每一版都是本人写的或本人点“记住”确认的 |
| `evidence` | `[]` | 从未登记过证据；来自提议的条目仍由 `candidate_id` 指向那次提议，不复制一份 |
| `relations` | `[]` | 从未记过冲突或重复；已有的替换仍在 `replaced_by` |

**降级**：只要有任何一版带着 s0_0892 表达不了的数据就拒绝（错误 `Personal note contract fields require s0_0900`）：填了发生时间、有证据链接、有关系、或生效起点不是迁移默认值（将来才生效、往前补的起点、补录进历史的条目）——因为 s0_0892 会把它们当成从记下时就生效。只有默认值时允许降级，旧列逐字节不变。

### 页面与接口

- “我的记忆”每条显示：本人确认日期、生效起点（与确认日不同或未生效时）、有效期或“将被替换于”、发生时间、依据（来源、立场、是否已有新版本）、关系（替代了 / 被替代 / 冲突 / 重复）；状态多了“未生效”。
- 新建和修改表单可以编辑本人该编辑的部分：生效起点、有效期、事情发生的时间、证据链接（选本人可读的品类 / 产品 / 提案 / 项目，选“支持 / 反对 / 背景”；已有的对话、讨论、原件链接可查看、移除）、关系（和本人另一条记忆标冲突或重复）。修改时没动的字段不发，服务器保持原值；页面重发证据时不带片段原文，服务器保留原摘要。确认状态由服务器定，页面不能改。
- `contracts/openapi.json` 由 `tools/export_contracts.py` 重新导出（只多了 `NoteDraft` 的四个字段和 `EvidenceInput`、`RelationRef` 两个结构），`tools/validate_contracts.py` 通过。
