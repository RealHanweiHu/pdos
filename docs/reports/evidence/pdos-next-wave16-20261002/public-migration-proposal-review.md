### 实际 proof 的双向配对

不使用 xmin/top xid 比较，避免拒绝合法 SAVEPOINT。

1. 三操作专用 Confirmation BEFORE guard：新行只能 consumed=false；UPDATE 只允许其它持久字段完全不变的 false→true；已消费禁止任何 UPDATE/DELETE，禁止从其它 operation 改成三操作。未消费预览可删除。
2. Confirmation 的 deferred UPDATE guard：本次实际 false→true 在事务末必须且仅对应一个同 tenant/product/actor/operation 的新 IssueVersion 或 Link。
3. 目标 deferred guard反向要求真实 consumed proof、Product 水位、层级、有效期、具名 human、实质 snapshot 对应，并跨 IssueVersion/Link 只使用一次。
4. 升级先锁 Confirmation 并拒绝任何已有 consumed=true 的三操作历史，不悄悄采用“已消费但无 atom”的旧行。由此建立不变量：旧 proof 已有一个 immutable 目标；若再次使用必形成第二个目标而拒绝。一个新消费缺目标、目标缺消费或消费后尾部故障，均不能提交。约束事件跟随 SAVEPOINT 回滚，不依赖顶层 xid 猜测。

上述论证适用于 trigger 正常启用、迁移前置检查通过且留存行不可修改的应用路径。Root 的迁移管理员能力仍属于受控可信边界；不宣称能防止管理员关闭 trigger 或改写历史。

## SQL 能保证与宿主仍负责的边界

SQL 可核真实持久行、一次消费转移/目标配对、Scope/actor/op/Product 水位、CAS、结构/取值、保存对象与确认 snapshot 的 JSONB 实质相等、完整读集的固定对应/继承、receipt/audit/outbox 原子组和留存不可改。

SQL **不模拟** Python `digest/material_digest`。Python 使用排序、UTF-8、紧凑 JSON；`jsonb::text` 的空白与数字/文本表示不等价。所有 source/basis/action/completion/policy/intent/token SHA 的真实性仍由现有 host/owner 验证，SQL 的摘要形状或同字段相等不能冒充重新算出完整摘要。

以下仍由真实同 Session host marker 与当前端口办理，并应覆盖 PG 负例：

- 确认 token 和完整 command/payload/read-set 摘要、实际 false→true consumer marker、rollback 后 marker 失效；SQL 不验证签名密钥，也不把 consumed=true 当人的批准行为。
- 固定原失败原报告 bytes/hash、每次跨 I/O 后所有 source/issuer/security/政策/专业 epoch 的当前重核；旧失败与测量内容不得被改写。
- 完成事实原文严格九字段 JSON、精确 line/SHA、IANA、微秒时刻，以及 investigation 与真实批准实施 owner proof；SQL 只核存储组与当次 review 的对应和时序，不授专业资格。
- Link 输出引用必须是真实 immutable owner 行，区分 logical ID 与版本行；action/basis 摘要、实际输出适用和完整 owner 读取来自 B 的端口。缺 owner/完成/独立复验/观察期仍 UNKNOWN。
- 私有 ACL、专业角色与用途当前授权独立于 tenant RLS；Product write 和 snapshot 中的 qualified 字段不构成自授权限。
