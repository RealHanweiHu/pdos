## 0. 结论摘要

1. **工程体量已接近一个中型 ERP，但正式验收为零。**
   - 规模：后端 19.1 万行，测试 20.4 万行，211 张 ORM 表，148 个迁移，141 条登记命令，137 个小Pai 工具。

   - S0 是唯一登记通过的阶段，结论是“通过（带 1 项已知性能例外）”（清单:16）。
2. **没有真人，也没有真实模型在用。**
   - 项目自 2026-08-10 开工，至今约 2.5 个月，期间没有真人试用（K9“暂无真实用户”）。
   - 系统只能在本机用合成会话登录：`web/src/app/api/local-session/route.ts` 只放行 localhost；后端没有登录、邀请或 SSO 端点。

### 前端如何组织四个全局入口

- **只有一个页面。** `/` 只渲染 `<AppShell/>`（`web/src/app/page.tsx`）。全局入口不是路由，而是 `?area=work|projects|programs|knowledge|category|cockpit|settings` 查询参数，由客户端状态切换（`web/src/lib/global-navigation.ts:7-15`）。
  - 主干是“我的工作 / 项目 / 组合与资源（`planned: true`）/ 知识”，另有“品类开发”（`group: "product_management"`，按服务器下发的 `capabilities.product_management` 显示）、“项目工作区”（深链）和“设置”。这符合 v1.1:217（P15）。
- **两套导航并存。** 全局壳之下，“品类工作台”还有一套 `?bench=products|projects|knowledge|settings&view=...&task=...`（`web/src/lib/workspace-navigation.ts`）。它在 `components/workspace.tsx` 中挂载约 20 个面板：定义、变体、计划、build、start、execution、supply、cost、verification、professional、handoff、launch、results、quality、field、accounting、originals、lifecycle、sources、activity。
  - 全局“项目工作区”的“办理”按钮都通过 `projectWorkbenchHref()` 跳回 `?area=category&bench=projects&view=plan...`，即旧的品类工作台。
  - 结果是：**全局“项目”主要是读视图，实际 S2–S5 的办理表单仍在“品类 → 型号”上下文的工作台里**。
- **`/plan` 是开发进度页。** 它直接读仓库里的唯一清单，混在产品路由中（`web/src/app/plan/page.tsx`）。

### 3.4 结论

- 今天真实用户能独立完成的是“表单式记录系统”的一部分：任务承诺、外部等待、风险、测试交接与结果、问题记录、发布包。
- 有三类断点，它们决定“能不能用起来”：
  1. **入口与账号**：登录、成员、资格三项都需要后台。
  2. **AI-native 的核心**：小Pai 起草提案、研究、分诊都依赖还没启用的模型；提案甚至没有非 AI 的入口。
  3. **管理者视角**：阶段门禁、健康度、组合、预测、外部系统都是空的。

### 4.2 单个功能的证据与验证开销

一个典型闭环（以 M3“本人案例审阅与具名试点资格”为例，`docs/reports/evidence/pdos-next-m3-20261016/skill-qualification/`）：

- 约 45 个证据文件：日志、JSON、截图、迁移往返、空库复验、收尾 JSON。
- 验证项：139 个后端病例（分 6 组）、57 项前端/BFF、类型、lint、Ruff、构建、设计目录对应。
- 4 个迁移（0766–0769）各自升降往返，空库复验，ORM 对齐，普通角色权限检查。
- 浏览器：桌面亮色、320px 暗色、“成功响应替换为 503 后刷新恢复同回执”。
- 收尾：停服、过期合成登录、备份。

这套仪式在几乎每份 result.md 中重复出现（“320px”在 result.md 中出现 64 次；当前队列中“往返”22 次、“320px”22 次、“真实模型”23 次）。

结果是：

- 每个闭环中位 25 个证据文件；
- 最近 60 次提交里证据新增约是生产源码新增的 **4.8 倍**（272,464 行对 56,901 行，server 加 web）；
- 证据文本还要反复声明“不累加 / 不冒充 / 不宣称”。
- 在大量单元级通过之上，**S1 的整组回归依旧有失败**：
  - 10-17 S1 检查点：24 项失败；
  - 10-18 记录：“既存 141 项失败集中在 SQLAlchemy 测试替身层”（清单:33）；
  - 10-18 agent_kernel 全量：1,715 通过 / 181 失败（清单:84）；
  - b07e548：419 个 DB 用例没有运行。
- **自 S0 冻结后再没有一次整仓完整回归通过。**

## 6. “交付速度与价值兑现”层面的优化候选

每条给出：现象、证据、建议。排序按对价值兑现的影响。

### O1. 2.5 个月没有真人使用：先让“一个真人 + 一个真实模型 + 一个真实品类”跑通，再扩展任何阶段

- **现象**：K9“暂无真实用户，先把产品做好”被理解为“先把所有阶段做完”。真人和真实模型的阻塞（第二评审人、模型启用链）放了一周以上，同期 S2–S5 全面开工。
- **证据**：
  - 首次提交 2026-08-10，原工程 10-08 归档（第一次重建）；
  - 清单:88“待用户处理”中的 G0 第二真人人选；
  - MiniMax key 10-19 已提供，冒烟成功，但启用链未走（清单:86）；
  - 10-17 一天内 S2–S5 依次开工（3d6cb71、fafc493、555aa1a、2985e4a）；
  - 业务指标记录为 0。
- **建议**：
  - 把 S1 出口重新定义为“真实最小闭环”：
    - 1 个 PM（用户本人）和 1 个真实评审人（同事），用真实账号登录；
    - 1 个真实品类（汽车充气泵种子已具备，`docs/design/category-seeds/`）；
    - MiniMax 跑通“对话 → 研究 → 提案候选 → G0 → 项目”；
    - 记录 §09.5 的操作次数、主动时间和 AI 草稿保留率。
  - 在此之前冻结 S3–S5 的新命令和新表（P21 自动续工暂停）。

### O2. 补齐“入口三件套”：登录、成员、资格，否则真人无法进入

- **现象**：系统只能本机合成会话登录；成员授权、专业签发资格只能通过 CLI 或可信导入。
- **证据**：`web/src/app/api/local-session/route.ts`；`pdos-next/tools/acceptance_account.py`；`category.member.grant` 没有前端入口；`professional_import.py` 文件头。
- **建议**：
  - 优先做企业日常入口：钉钉扫码或企业内账号登录，或者最简的邀请链接加口令。
  - 品类成员管理页、专业资格登记页（T2 具名）。
  - 部署一套持续存在的内网预览环境，代替每轮新建、每轮收尾的临时环境。

### O3. 不依赖 AI 的人工路径要先通，然后 AI 才是“加速”

- **现象**：立项提案只能经小Pai 候选创建；模型不可用时 PM 卡在路径 A 第二步。设计自己要求模型失能时人工业务可用（AT-45、v1.1 §01.7“对话不能绕过页面权限，页面也不应因为未使用AI而额外多一套流程”）。
- **证据**：`proposal.create` 在 `web/src` 只出现在 `lib/domain-candidate.ts`；原工程 10-06 有意移除了提案新建表单（清单历史段落，清单:96）。
- **建议**：恢复“空白提案 / 从模板新建”的手动 T1 入口。小Pai 候选作为第二入口；两者落同一个命令。

### O4. 验证仪式按风险分层，横切能力只验一次

- **现象**：每个功能闭环都重复“实库加纯检查、BFF、类型/lint/构建、桌面亮色加 320px 暗色、503 丢响应恢复、迁移往返、ORM 对齐、普通属主、有历史拒退、收尾备份”。证据量是代码量的数倍，阶段验收却没有前进。
- **证据**：
  - 证据 488 MB、8,505 个文件；每个闭环中位 25 个文件；
  - 最近 60 次提交中证据占新增行数的 58%，web 源码占 1.5%；
  - 142 个一次性验证脚本，41,911 行；
  - AGENTS.md:10-11 本已要求“低风险文案/展示不新增镜像实现的测试”和“集中到闭环检查点”，执行中没有落实。
- **建议**：
  - 把“原请求恢复 / 回执重放 / 亮暗与 320px / 迁移往返”做成**公共层的一次性合同测试**，按组件或迁移模板自动跑，不再逐功能写报告。
  - 读视图、文案和布局只保留自动化截图对比。
  - 证据目录只入库 result.md 和 manifest，原始日志放外部归档（已有 `~/pdos-evidence-archive/` 先例）。
  - 一次性 wave 脚本归档出 `tools/`。

### O5. 唯一清单与设计文档需要“限长”，状态要可机读

- **现象**：
  - “当前队列”约 97 KB，M3 一个表格单元格有 30,873 字符，读者无法判断“现在能用什么”。
  - 冻结后的 v1.1 在 10 天内追加了 26 条决策（P1–P26），另有 UI 补遗 290 行、design-qa 110 行长段。
  - 状态出现漂移：真实模型“0 次”与 10-19 冒烟并存；operations.json 的实现标记与代码不一致；`/health` 硬编码 `model_available: False`；执行计划与队列的里程碑编号错位，M4/M5/生态从队列消失。
- **证据**：清单:16-23 行长；`docs/design/2026-10-08-pdos-next-design-confirmation.md:412-628`；`pdos_next/api.py:448-468`；`contracts/operations.json` 中 `provider.agreement.register`、`my_work.query` 的标记。
- **建议**：
  - 每个里程碑一行，不超过 300 字，固定为“可用能力 / 阻塞 / 下一步”三栏；细节只放证据链接。
  - 能力矩阵（命令 × 已实现 × 有 UI × 真实模型 × 真人用过）由脚本从 contracts 和代码自动生成，代替手写状态。
  - 设计“冻结”后的改动改成按版本发布的 changelog（v1.2），不再在冻结稿里原地修订。

### O6. 范围与形式化收敛：数据库触发器、命令数和工具数都在快速增长

- **现象**：
  - S0 冻结后 9 天新增 83 个迁移；数据库中有数百个 plpgsql 守卫；
  - 命令 141 条，内部错误原因 458 条；
  - 工具数 10 天增长 29%（106 → 137），而且“这不是一次性优化，是需要随领域增长不失效的机制”（工具面决策稿:38）；
  - capa_effectiveness 一个领域 1.38 万行，对应的核心决定命令却还没实现。
- **证据**：§1 规模表；确认稿 C6 原本就把“过度形式化”列为必须收敛的项。
- **建议**：
  - 在有真人和真实数据之前，**停止为每个细节新增表、触发器和迁移**。新规则优先放在 Python 领域服务里，单测覆盖；数据库只保留范围根 RLS、幂等与不可变约束。
  - 按“用户会用到的 20 条命令”排优先级，其余命令保持不实现，不进入工具注册表。
  - 工具面按工具面决策稿推荐的方案 C 加 B 固化，并给“工具总数、单技能可见数”设预算上限。

### O7. 前端投入与信息架构收敛：把项目做成真正的“主干”

- **现象**：
  - 用户 10-13 和 10-16 多次明确“产品主体是项目管理”（清单:37 起 UI 记录），但项目工作区多数标签是占位或链接，实际办理仍在“品类 → 型号”工作台的约 20 个面板里，形成两套导航。
  - 后端与前端的代码比约 7.6 : 1（19.1 万对 2.5 万）。
- **证据**：`project-workspace.tsx:55-70`；`lib/workspace-navigation.ts`；`components/workspace.tsx:219-272`；最近 60 次提交中 web 新增只有 7,292 行；约 140 个前端文件未提交。
- **建议**：
  - 下一阶段的主要投入从“新增后端闭环”转到：
    - 阶段模板与门禁的服务器合同（P22 已把 B5 列为“最易返工的先行约束”）；
    - 健康度规则投影（P17）；
    - 把 Build、测试、问题等办理面板迁到项目工作区标签下；
    - 删掉旧品类工作台的项目区。

### O8. AI-native 的价值验证要有评测和读取端口，而不只是写入守卫

- **现象**：
  - 内核把大量投入放在“AI 不能越权写”（可信调用证明、披露链、资格阶梯）上，“AI 能帮上什么”却没有任何测量。
  - S2–S5 技能包只能写，读不到 Build、Issue、Run。
- **证据**：清单:31 剩余缺口第 ① 条；仓库中没有 golden/eval/rubric 文件；§09.4 和 §06.12 要求按维度打分。
- **建议**：
  - 先为 3 个高频场景各做 10–20 个合成或自有评测案例，并做领域只读端口：
    - 品类研究（引用可核率）；
    - RFQ 抽取（字段与单位正确率）；
    - 测试失败分诊（去重与假设标注）。
  - 用真实 MiniMax 跑基线，同时记录时延、轮数和费用。这同时满足 M2 出口和 T0 资格依据。

### O9. 提交纪律与并发施工：先把工作树收敛到可回溯状态

- **现象**：82 个文件已修改、189 个未跟踪（含迁移 0808–0811、约 140 个前端文件、10-17 到 10-19 的 UI/S5/M3 证据），最近一次提交在 10-18。同一分支多会话并发，“HEAD 既有失败”和“另一会话未提交改动所致”的归因反复出现（清单:78、84）。
- **证据**：`git status --porcelain` 统计；提交 b07e548 说明中“three uncommitted change.* commands that no skill authorizes yet”。
- **建议**：
  - 一个闭环一次提交。
  - 并行会话改用独立 worktree 或分支，迁移号分段（S0 计划 §4.1 已有规则）。
  - 任何“通过”只针对已提交的哈希登记。

### O10. 外部系统与通知是“企业能否真正用起来”的前置，优先级应高于 S4 外部移交回执的细节

- **现象**：用户业务的日常协同在钉钉，客户沟通在 GoodJob CRM，生产在 ERP/MES。PDOS 内部没有任何连接器或推送。S4 却已经实现了“固定外部移交 / 独立回执 / 未知对账”这类细节。
- **证据**：grep 结果为 0；执行计划 M7“生态”已从队列消失；清单:21 记录外部移交“无网络发送”。
- **建议**：
  - 先做两个只读或推送型集成：钉钉工作通知（“我的工作”注意项推送）和钉钉登录。
  - 再做 ERP 物料与库存只读 MCP（齐套判断，对应 AT-20）。
  - 写入型外部集成留到真人使用之后。

## 7. 方法与限制

- 只读核查，没有运行测试、服务或数据库，所以“能否走通”依据的是前端源码入口、契约实现标记与证据 result.md，不是现场操作。凡写“未找到入口”的，都是指在 `pdos-next/web/src` 源码中检索不到，不排除有未提交的分支实现。

- “前端 2.5 万行”指 `web/src` 中非测试的 tsx 和 ts（16,055 + 8,909 行），不含 CSS。后端 19.1 万行不含测试和迁移。
