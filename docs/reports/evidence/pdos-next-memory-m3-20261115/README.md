## 权限与写入边界（数据库层，迁移 `s0_0920`）

- `memory_review_items` 只有两条写入路径：本人以本人身份写自己纠正的分流（插入策略要求执行者等于请求人、是在职真人，引用的纠正记录属于本人且就是这次运行的情景）；“待复核”和“复核转交”只能由两个系统规则函数写入，任何人直接插入都被拒。读：被指派的人和提出的人。
- `memory_review_decisions`：只有被指派的人以本人身份写，每项一次。
- `skill_revision_candidates` 只能由汇总函数写入；候选与决定只给当前租户管理员读写，决定行写不进 `activated`。
- `memory_system_rule_settings`：管理员本人写；读取开关经 `memory_system_rule_enabled`。
- `memory_maintenance_ledger`：只经 `memory_ledger_record` 写入，任务名是封闭列表。
- 六张表全部只追加（不能改、不能删）。AI 写入身份对这些表和业务表都没有任何写入路径；测试里用 AI 身份直接插入被拒。

带库测试覆盖的判据：

- 每一路分流只产出候选或提示：固定两路之后，个人条目、团队备忘、品类和产品的版本都没变；个人卡点“记下”后才有条目，团队卡没有经 `scope_note.save` 记下的条目不能标采纳；别人看不到也处理不了。
- AI 身份不能直接写分流项；本人也不能直接插入“待复核”类的系统项。
- 改版后标记是确定性的：同一事件处理两次，第二次不新增标记、不新增台账；被标的范围条目和个人条目的版本与条数都不变；无关条目不被标。变更生效按产品判断。作者离开后每天一次转交，同一天重复不再转交。
- 程序性汇总：同类 5 次生成 1 条候选，未审核时不重复生成，采纳后旧信号不再计数；非管理员读不到候选，也调不了汇总函数；采纳只写草稿版本号。
- 经验沉淀：技能是草稿时触发一律 held，端口不被调用；管理员停用规则后 held 原因变为 `rule_stopped`；规则内容不能改写。
- B6：默认关闭；T27 三条条目只有后两条得到提示，第一条没有，条目原样；T28 只给建议、条目原样，管理员只能拿到数量。

## B6 消融怎么开关

B6 没有任何对用户的入口，也没有定时任务；`curation.DEFAULT_SWITCHES` 为空，不传开关就抛 `Closed`。评测里按目标架构 §8.4 一次只关一样：

1. **条目核对**：对照组不调用；实验组对同一条时间线调用 `curation.entry_check(notes, switches={"entry_check"})`（只有不调用模型的第一步），或 `switches={"entry_check", "entry_check_model"}` 并传入 `judge`（第二步）。判别器须经注册执行图调用模型（见 D586），评测脚本只把它的回答当作 `(是否支持, 摘出的原句)` 传入；摘句不在片段里的回答会被丢弃。比较 T27 与“被植入错误条目的时间线”上的发现率和误报率（提示被确认人忽略的比例）。
2. **常驻升降建议**：对照组不调用；实验组调用 `curation.residency(notes, usage, switches={"residency"})`，把评测里“本人接受建议”的操作按建议改条目后，在同样的常驻预算下比较约定遵守率和任务完成率（T28 与长时间线）。
3. **节奏与预算**：`curation.due`、`curation.paused` 是排队和暂停规则，随前两项一起评；不单独消融。

增益不为正：从目标架构里去掉，或在对应场景的配方里降预算。为正才由你决定对用户打开（届时补用户入口和管理员只看数量的统计接口）。
