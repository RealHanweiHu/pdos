# Wave15 实际页面演练步骤

依据当前冻结 `BuildQualityLoop` / `build-quality-loop-view`、quality_execution / change_execution DTO 和服务规则整理。仅供主线执行；本次未操作页面、HTTP、数据库或构建，不表示演练已通过。使用主线另行准备的**确定失败合成 Run**与新具名 actor，保留原 Wave14 indeterminate Run。

## 0. 进入并选择固定范围

入口：**项目 → 问题与变更**，组件标题为“**失败调查、措施与双线变更**”。

1. 如页面存在“原提交回执尚待核对”等恢复卡，先处理“**按原请求恢复**”；不要清本机草稿或另点一个新动作替代未知请求。
2. “**明确选择试制轮次**”（aria-label：质量闭环试制轮次）明确选择本轮 Build；等待读取完成后，在“**固定测试运行**”（aria-label：质量闭环测试运行）选择本轮 logical Run。不会默认按时间选运行。
3. 核对“**固定原运行与判定**”中的 Run 当前版本、中文结果和原测量范围。原运行的开测、资源占用与样件消费仅在折叠项中回读，不被本页改变。
4. 确定失败必须来自服务器 `failures`，且该行 available / 当前操作 capability 为真。若仍显示“当前没有服务器核验且可办理的确定失败”，停在调查提示；不得把 indeterminate、unknown、invalid 或 pass 建为失败单。

各按钮只取当前服务器能力。新 actor 需要主线已导入的当前精确 project / purpose / operation 职责与专业资格、有效质量政策及可读证据；产品写权限不补专业资格。页面没有自授资格或风险降级入口。合成演练提示应保留。

## 1. fail → Issue

卡片“**1 · 从确定失败建立问题**”：

- “**精确测量 / 样件 / 测试项**”：选择实际服务器核验的固定失败；核对原值、单位、条件、判据、样件及配置，不重填读数。
- “**固定结果事件**”：明确选择“服务器验证的结果事件 N”。事件来自同一固定 Run / Projection / Measurement 的真实证明；不可输入自造事件 UUID，也不可拿 Run 版本行 UUID 当 logical run_id。
- “**可见范围（不能扩大私人依据）**”：通常先保留“仅本人”；只有全部依据和权限允许时选“产品内当前授权人员”。
- “**问题标题**”：填写具体非空标题，最多 2000 字。例如标题应表达本次固定失败，而非声称根因已确定。
- 点击“**核对固定失败并建立问题**”。该动作为 T0：先读服务器 inputs，再保存；**不会弹出 T1 确认框**。

成功后，应出现“建立固定失败问题已保存或读取原回执……”提示，并自动选中回执对应的 logical Issue / 当前可读版本；继续等待本 Issue 的变更引用也读取完毕。在“**2 · 当前问题与独立历史**”核对“**真实问题**”“**问题版本**”。全新问题通常为 v1 / 待具名分诊；语义去重可能读取已有问题，以实际回执和 current pointer 为准。

**注意：从无 Issue 切换到新 Issue 会切换本机草稿作用域。** 此前在 Run 下选过的人工依据 / 表单不要假定自动带入；下述遏制与 CAPA 的依据应在当前 Issue 作用域重新选择。

## 2. T1 分诊

展开“**具名分诊与问题归并**”：

1. 查看当前具名分诊职责 / 资格、风险与独立验证政策；风险由服务器提供，页面不选择 low 或免验证。
2. “**分诊 / 归并原因**”填具体非空原因（最多 2000 字），本次只分诊，不需要勾选归并来源。
3. 点“**核对分诊，一次确认**”。等待服务器返回实质预览；标题为“**具名分诊 · 一次实质确认**”。核对“保存前 / 将保存”的同一 Issue、旧版与新 revision、真实风险 / 原因和 effect。
4. 仅在上述内容准确时点“**确认并提交本次固定内容**”。成功后回读当前新问题版本，应为“已具名分诊”。历史版本仍可选且只读。

每次 T1 用服务器 returned command 原封提交；页面已绑定原命令、读集、版本和 token。不要通过重新点击动作制造第二个确认。版本 / 来源 / 政策 / 职责漂移时旧预览废弃，需要重核。

## 3. 先准备精确人工依据，再记 T1 遏制

页面下方“**本次人工内容的精确原文依据**”：

1. “**当前可读原文**”选当前 actor 能读取的有效 Artifact；若来自上传原件，须已完成主线真实上传 / 扫描 / 解析并满足当前安全决定。
2. “**完整原文行**”选该 Artifact 派生正文中的实际行，查看下方完整内容；点“**加入完整行依据**”。原文 option 只截显前 100 字，所加入摘要仍来自完整行。
3. 需要多条依据时重复。变更读取提供的“**加入服务器固定依据 N**”也可直接加入，不改服务器 SourceRef。不要加入无关大量来源；同一 Artifact 两版本不能混入，一次完整读集最多 20 份且不能截断。

再展开“**记录已经发生的遏制行动**”：

- “**实际执行内容（执行人固定当前本人）**”：填写这个 actor 已发生的行动，不填未来计划，也不代他人报告执行。
- “**实际发生时点，带 UTC 偏移**”：使用真实合成事件中的已发生时点，例如格式 `2026-10-02T10:15:00-07:00` 或同一 instant 的 `...Z`；示例只说明格式，不能拿示例或当前钟替代事实。无偏移时间和未来时间会拒绝。
- “**原 IANA 时区**”：例如 `America/Los_Angeles` / `UTC`，与事实所保留的原时区一致；不可填 `-07:00` 当 IANA。
- “**独立事件出处**”：从已经加入的行动依据中，**另行明确选择**证明这次事件的完整行。加入下方来源不会自动选中该字段。
- 点“**预览实际遏制，一次确认**”，核对标题“记录实际遏制行动 · 一次实质确认”、行动内容 / 当前本人 / 整行证据 / 独立事件时间后，点“**确认并提交本次固定内容**”。服务器保存 / 接收时间由服务器记录，不由用户填写。

回读：新的 Issue 版本应为“措施办理中”，原遏制追加到独立历史。此处事件依据是精确 Artifact 行；**并无让用户强制编造 JSON 事件行的要求**。原测量报告则继续使用既有服务器核值证明，不重新提交原值。

### Locator 的准确含义

当前质量页面不提供手填 `position`、页号或 cell 的输入。helper 从所选 **Artifact 正文完整行 UTF-8 字串**自动生成 `kind=artifact`、固定 id / revision 和 `line:N;quote_sha256:<整行 SHA-256>`；不要只截取子句、改空格、翻译原行或手写哈希。

上传原件的 page / sheet-cell / original-line 属于解析器 locator_map：需要时在资料 / 原件入口核对其对应的派生正文行。**不要把原件页号、PDF 页内行号或工作表 cell 当成此 select 的 Artifact 行号。** 此 wrapper 显示的是 Artifact 行定位，不自行声称原件页 / cell 已核验。来源状态、版本、安全 epoch 或私人权限变化，应刷新；不能沿用旧定位或扩大受众。

## 4. CAPA 草稿（T0）

展开“**纠正与预防措施草稿**”；当前 Issue 必须已分诊 / 措施办理中，且尚无旧 CAPA。已有 CAPA 不覆盖：

1. 点“**增加有来源的假设**”，填写“**根因假设 1（不是具名根因结论）**”；在该条“**此条内容的精确依据（至少一项）**”里明确勾选已经加入的原文。只在下方加入来源而不勾选这一假设，仍不能提交。
2. 点“**增加具名措施草稿**”；填写“**措施类型**”（纠正 / 预防）、“**具名责任人（不授专业资格）**”（实际可选具名人，首版通常当前本人）、“**计划措施内容，尚未执行**”。至少一条假设、一项措施。
3. 填“**后续有效性验证方法**”“**有效性验收要求**”“**独立观察截止时间，带 UTC 偏移**”。文字非空、最多 2000 字；截止为独立观察计划的 aware 时间，不拿遏制发生钟或服务器保存钟代填。
4. 点“**核对并保存 CAPA 草稿**”。T0 无确认弹窗，inputs 仍核对政策 / 资格 / 完整来源。全部固定 failure identities 由当前 Issue 自动映射，不手填或漏选。

回读当前 Issue 新版本，读取 CAPA 假设、责任措施和有效性要求；每个 action completion 仍为 null，root_cause / effectiveness / close 未办理。保持“措施办理中”不意味着 CAPA 已完成。必须先读到含 CAPA 的当前 Issue 版，再建下一步 Change，避免固定旧 Issue 缺失 CAPA。

## 5. Change → 固定图 → Impact（T0）

卡片“**3 · 工程与制造双线提案**”：

1. 填“**变更提案标题**”“**提案原因（两条线分别核对，不是批准或生效）**”，核对“**提案可见范围**”。仍须至少一条已选原文依据。
2. “**选择真实影响根与引用**”：最小演练可将当前 `Issue vN` 勾“**作为影响根**”，将 `CAPA 草稿（固定 Issue vN）` 勾“**作为固定引用**”；也可按真实范围选择服务器其他选项。至少一个 root，根 / 引用合集中至少有该 Issue 或 CAPA；不手填配置、工装或图 UUID。
3. 点“**核对来源并建立变更提案**”。T0 无确认弹窗。成功后自动选回执对应的“**真实变更提案**”“**变更版本**”，通常首版为 draft；查看固定 Issue / CAPA 版与来源。
4. 填“**固定图捕获原因**”（至少 3 字），点“**从真实权威对象捕获固定图**”。这是独立 capture 请求，成功提示“服务器固定图已保存……尚无批准或发布”，并自动选 captureId。必要时在“**明确选择已保存图快照**”手动选本变更当前版本、未过期的快照。
5. 展开“**所选固定图的已知对象、依赖与未知范围**”。第一轮可不填影响假设；若点“**增加有来源的影响假设**”，每条必须填内容且在自身依据复选框至少勾一项。假设不能补造图依赖或证明图完整。
6. 点“**核对工程 / 制造路径及未知**”。T0 无确认弹窗，保存固定 impact 后回读 Change 新版本，状态为“已有影响核对，未批准发布”。检查 engineering / manufacturing 路径与显式 unknown，而非期待全绿。

**从 CAPA 后的当前 Issue 建 Change 后，本次演练不要再修改 Issue。** 当前缺独立旧 Issue / CAPA 再核端口，Issue 续版会使旧固定 Change 依据需重核；这是保护边界，不能拿旧图继续计算。Impact 后 Change 也已续版，旧 capture 不应当作新版图反复提交。

## 6. 回读、恢复与证据留点

- 每次成功都等“已保存或读取原回执”以及当前版本回读完成后继续。Issue / CAPA 回执 subject 是不可变 Issue version row；Change / Impact 是不可变 Change version row，页面会映射其 logical 身份，用户无需重输入 ID。
- 已取得成功回执但出现“随后刷新失败”：只点“**刷新当前事实**”回读，不重发业务动作。若“原提交回执尚待核对”，只点“**按原请求恢复**”，保留本机同 command / key / payload。
- 普通读取失败不等于提交发生；READ_SUPERSEDED 是已知旧读取消，不用另造操作。权限 / 来源 / 政策 / 资格失效、版本冲突或预览过期按当前缺项处理，不从旧历史 capability 推断可写。
- 主线宜记录：固定失败与对应原值 / scope；Issue 建立、分诊前后预览、遏制事件前后预览、CAPA 全部失败覆盖；Change 固定根 / 来源、图范围与 impact unknown；各 current / 历史版及同原请求恢复。版本以实际数据为准，不把按钮提示当作验证通过证据。
- 最终“**下一轮回到已有权威入口**”只是办理需求，未自动新建定义 / 双配置 / Build / 样件 / Run。工程批准、制造切换、正式发布、根因决定、措施完成、独立有效性和关闭均不在本次已开放页面中。
