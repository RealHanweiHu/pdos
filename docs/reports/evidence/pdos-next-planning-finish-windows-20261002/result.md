# 排程完成约束区间 · 独立增量交付

2026-10-02。已完成纯排程包的 FF/SF 及完成时间外部等待区间计算。原先遇到非精确工时或完成约束便返回 `finish_constraint_range_not_supported`；现在返回保守的开始、工作完成和总完成区间，保留未知、实际事实及来源。本轮只改 `forecast.py`、相关排程测试和本证据/清单，不占用主线当前供应、品质、文件安全的公共接线文件。

## 行为与范围

- 同一零/正工时分支内，用较长工时/等待反求最早可行开始，用较短时长反求最迟开始。零工时不吸附工作日，正工时会吸附；区间含零时分别考虑零和最小正有效分钟，避免遗漏周末之后的开始日期。
- 完成日期不简单取最小/最大时长两个场景。日历空档可能让中间时长产生更晚的完成值，因此再按开始与时长范围扩张工作完成/总完成区间。`finish_constraint_envelope` 是非阻断说明：各边界可能无法在同一场景共同达到，也不是最紧区间或概率分布。
- 固定时长仍使用精确日历反求；完成约束给出范围时保留对应端点。已有 Actual 开始/完成不移动；已开工节点使用明确 remaining 估时，分别应用完成约束上下界。
- 无有限工时、等待或完成约束上界时不生成确定交期；完全未知仍保留原因，不以零代替。日历/预测窗口耗尽仍返回缺口，不能拿 horizon 端点当交期。保守范围可能比真实可达范围宽，也可能更早触发窗口限制。
- 即使分钟取整恰好使日期重合，耦合区间说明仍保留；此类候选不计算浮时，不据此认证资源精确占用。容量/预约优化、资源资格和正式承诺继续由业务层办理。

[合成示例](example.json)：UTC 工作日9–17点，工时60–120分钟、外部完成约束12–14点，得到开始10–13点、完成12–15点的保守包络。不能将15点解释为最晚可达日期的精确解，更不能将其作为已承诺日期。
