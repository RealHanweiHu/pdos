# 执行速度与下一轮排程

本记录用于后续排程，不修改当前冻结生产候选，不宣称已实现性能优化或测得加速比。

施工按 A 资源/样件、F Run/请求、C 界面独占并行；公共注册、迁移与验证集中到主线。联合检查上限六个独立进程，夹具租户互不相同；修改公共表结构的生命周期检查在最后单独运行。当前选集和分组见 [joint-shards.json](joint-shards.json)，其结果仍以主线最终汇总为准。

开测夹具的窗口起点是创建资源事实后的真实五分钟，检查等待实际时间进入窗口；未移动 Python/PostgreSQL 时钟。01:55 左右的进程观察也显示墙钟时间明显大于 Python CPU 时间，因此不能将全部耗时称为规则计算开销。一次本实例数据库状态观察为 22 条 idle、5 条 idle-in-transaction、1 条约 17 秒的 transactionid 锁等待；这些瞬时观察不代表全程剖析或已定位全部慢点。

定向源码审阅发现，一次 Run `_load` 经正式请求样件读取、资源整版读取与原 BuildStart 证明会重复深核；inputs/preview/execute 的多个 phase 进一步叠加。资格、来源和占用不允许跨这些 phase 缓存。后续如优化，仅在同一显式 Session/事务/phase 内复用完整绑定的已核证明，并继续查当前权限、版本、有效期与安全 epoch；GET-only ReadContext 不能直接用于命令。当前没有实施该优化。

下一轮排程应先将真实时钟等待、六次事务故障回滚等长用例放入空闲进程，再填充短检查；用本轮分组耗时调整重量，避免只按函数数平均。参数化节点只有在隔离与覆盖不变时才拆分，禁止重叠执行、漏掉参数或用模拟结果代替真实事务。结果返回已消费 Run，不再进行新资源分配，可将原值核验、领域事务和界面按冻结接口并行施工。

收口实际结果：普通联合组上限六个进程，另有失败修正专项并行；所有常规/修正 PG 进程结束后才恢复结构检查。外部修正期间暂停的是编排进程，已派发子进程继续；[隔离屏障](lifecycle-external-check-barrier.json)已解除。原编排总墙钟 3950.38 秒包含修正等待，部分分组的编排 elapsed 也包含延迟收集，不能当作测试计算耗时。子进程真实 pytest 耗时从各日志读取，例如重放所在原组 2223.58 秒、定向三参数重放 1269.99 秒、最终六故障 748.79 秒；最终去重为1598项，不把专项重复计入。

下一轮尤其应将三个独立重放参数、撤回/实际开始等待及故障组提前排程。经唯一节点身份核对后可按独立参数拆分，保留各自租户与真实时钟，不必将整个参数函数放在同一串行进程；拆分后必须验证无遗漏/重复。当前未改冻结编排源码，未实现应用性能缓存，也未测得加速比。
