## D483：隐藏的轮次不再带出提问

问题：`conversation.history` 读本人其他会话时，某一轮的出站类别（私有、客户）比当前运行宽，回答按规则不发送，但那一轮的提问原样返回了。提问里可能带着前端拼接的页面资料。

改动（`server/pdos_next/agent/memory/history.py`）：

- 出站类别不覆盖的轮次只返回运行编号、状态、“未发送”的说明和原始记录的编号，不返回提问。
- 其余轮次的提问只返回本人原话（`work_state.user_goal`），页面资料不返回。情景记录本来就只存原话，这里对齐。

没有改：同一会话内的历史读取。

测试：`test_cross_session_history_returns_no_page_material_and_no_words_of_an_uncovered_turn`。经注册的处理函数读两个历史会话（一轮带页面资料标记，一轮是私有运行且带同一标记），返回内容序列化后查不到标记，也查不到私有轮次的原话。

## D481：条目变了，用它的运行要停；运行行上不留正文

问题有两处：

1. 运行开始时带入的个人条目，之后被修改、替换或过期，运行继续用旧文字；只有删除会拦。
2. 条目正文冻结在运行行上（`AgentRun.versions.memory_notes_context`，叫法在 `memory_aliases`）。删除条目时清不到这份副本；删除回执写的“最迟 30 天内随检查点清除”也管不到它，因为它在业务库里，不在检查点里。

改动（`server/pdos_next/agent/memory/assemble.py`）：

- `recheck`：每次模型调用前，逐条对照最新修订和有效期。删除、修改或替换（有更新的版本）、过期、范围不可读，任何一种都停下，提示里写明是哪一种，`detail.reasons` 按条目给出原因。模型已经看过旧文字，所以是停下让本人重新发起，不是悄悄换成新文字。
- 运行行上只存条目 ID、版本和所在的区，不存正文、叫法的词和含义。每次组装上下文时从版本表读正文；版本不在了（条目已删除）就不带入。
- `frozen_aliases` 同样改为从版本表读，两个调用处（`recall.search`、`enterprise_search/assistant_adapter.py`）跟着改了参数。

为什么不在删除时回头清运行行：已结束的运行不可改（数据库触发器 `kernel_run_guard`），要清就得放宽这个守卫。不把正文存进去更简单，也不动内核守卫。

没有做的：

- 纠正只记去向、没有代码消费（D481 第三条，即 D475 第 2 条）。这是设计 §14.9 的四路分流，归 M3 / B6，依赖范围条目和修订候选审核页。
- 这次改动之前建的运行，行上仍有当时冻结的正文。读取时已不再使用，但行清不掉。pdos-next 目前没有真实数据。
- 新登记 D484：模型在运行里用 `memory.search` 查到的个人条目卡片（含正文）和叫法展开，会留在工具调用记录 `agent_tool_calls.result` 里；模型的回答里也可能转述。这是从代码读出来的，没有逐行验证。删除条目后这些副本是否要清、怎么清，需要你定。

测试（`test_memory_notes_pg.py`）：

- `test_the_run_row_keeps_no_note_words_so_a_deleted_note_leaves_none_behind`：带入一条口径和一条叫法后，运行行整行序列化查不到正文和叫法；运行结束后删除两条，再读回是空的。
- `test_a_revised_replaced_or_expired_note_stops_the_run_that_took_it`：修改、替换、过期三种情况各自停下；条目没变时不拦；之后的新运行带入新文字。

## D482：按结论里的词能找到旧记录

问题：情景的关键词索引只收本人原话。用户只记得结论里的说法时找不到（无模型回放 0/3；真实模型 TL-08 q1 搜 4 次、读 6 次历史仍没找到）。P121 第 1 项已批准把回答摘要等收进索引。

改动：

- 迁移 `s0_0888`（`server/migrations/schema_s0_0888.py`）：`memory_index` 允许第二种行 `source_kind='answer'`；`memory_pending_index_references` 改为“两种行缺任何一种都算待索引”，所以以前索引过的情景会补上回答那一行。在独立测试库上升级、降级、再升级通过。
- `server/pdos_next/agent/memory/index.py`：每条情景写两行。`episode` 行是本人原话，不变；`answer` 行是回答摘要加未完成事项。没有模型自己写的回答时（被换成固定句子的、预算用完的、失败的）不收摘要。索引以本人身份、在行级权限下读运行，本人现在读不到的运行不会被收进去。
- `server/pdos_next/agent/memory/recall.py`：`memory.search` 两种行一起打分；结果卡片新增 `matched_in`（命中的是原话还是回答）和 `answer`（回答前 200 字的摘录，标“只是当时的记录，不是业务事实，不能作为依据引用”）。命中之后照旧逐条复核：出站类别不覆盖的、来源已撤权的，不返回也不提示存在。
- 会话列表搜索只查 `episode` 行。原因：回答的来源被撤权后，回答对本人是隐藏的，不能让人从列表搜索里按词把它搜出来。这也是分成两行而不是合成一行的原因。

和 P121 第 1 项的差别：

- 没有收“当时对象的标题”。范围对象的标题试过，同一范围里每条情景都带它，没有按稀有度加权，结果是只要问题里提到范围名，所有情景都被搜出来（已有测试抓到），所以去掉了。运行关注的具体对象（资料、产物）的标题还没有解析，记为余项。
- 情景向量没有改，仍只发送本人原话。把回答摘要发给嵌入服务是新的出站内容，需要另外决定。
- 工具定义和提示词没有改；变的只是工具返回的内容。
