# D268 守卫随会话变长变慢：剖析与修复（2026-11-08）

在隔离临时库 `pdos_test`（head `s0_0855`）上，用离线合成服务商，没有调用真实模型。
- 测量脚本：[d268-guard-profile.py](d268-guard-profile.py)；
- 数据：[d268-guard-pass.json](d268-guard-pass.json)。

## 结论

- 原因已确认。每次守卫都把当前运行和每个前序轮次的谱系各走一遍，同一个祖先的检索读取在一次守卫里被重复做证明校验、重复读整行，次数随轮次增长，守卫的 SQL 条数约是轮次的平方。
- 修复后，一次守卫里每个前序运行的封存读取只证明一次、整行只读一次。守卫 SQL 条数变成每轮固定约 9 条（线性），第 12 轮从 425 条降到 114 条；`check_conversation` 从 120 条降到 70 条。
- 权限口径不变：
  - 复用只在同一个数据库事务内；
  - 下一次守卫（包括同一次模型调用发出前的复核）照旧把全部历史按当前权限、撤回和扫描状态重新证明一遍。

## 1. 剖析

做法：会话里连续跑 N 轮（每轮检索一次、抽取一次），在下一轮冻结上下文后测 `adapter.guard` 和 `check_conversation`。

| 前序轮数 | 守卫 SQL（修前 → 修后） | 守卫耗时 ms | 会话检查 SQL | 会话检查耗时 ms |
|---:|---|---|---|---|
| 0 | 9 → 9 | 88 → 37 | 4 → 4 | 29 → 19 |
| 2 | 44 → 30 | 118 → 116 | 40 → 30 | 117 → 114 |
| 4 | 92 → 48 | 227 → 160 | 56 → 38 | 145 → 134 |
| 6 | 156 → 66 | 518 → 218 | 72 → 46 | 277 → 194 |
| 8 | 236 → 84 | 778 → 378 | 88 → 54 | 408 → 326 |
| 10 | 332 → 102 | 1165 → 508 | 104 → 62 | 468 → 306 |
| 12 | 425 → 114 | 1629 → 568 | 120 → 70 | 527 → 352 |

- 修前守卫每轮多出的 SQL 依次是 17、18、22、26、30……，每轮比上一轮再多 4 条。
- 耗时取 3 次中最快的一次。修后那一轮测量时，本机被其他会话占满（负载均值最高约 100），耗时只作参考，SQL 条数是准的。
- cProfile：剩下的时间约 97% 是等数据库返回，Python 计算可以忽略，所以 D257 的并发线程确实能把这部分重叠起来。

修前第 12 轮一次守卫的热点：
- `assistant_inheritance.registry` 每个前序轮次各调一次。每次都：
  - 走一遍该轮的完整谱系，对每个祖先跑 `search_issued(..., archive=True)`，逐条重做证明；
  - 再整行读取全部祖先，含很大的 `versions`。
- `assistant_ledger.carried()` 随后又整行读一遍这些轮次，这次连 `result` 也带上。
- `check_conversation` 里，`recheck()` 和 `_project()` → `saved()` 在同一个事务里各建一次谱系。

## 2. 修复

- `assistant_ledger.one_pass(session)`：一次守卫内的记忆，挂在本事务的 `session.info` 上，事务结束就丢弃，嵌套调用共用外层。
  - 每个前序运行的 `search_issued(..., archive=True)` 结果只证明一次，之后返回深拷贝。
  - 已经在本事务里按普通 RLS 读到的祖先行不再重读。`carried()` 读前序轮次时也复用这些行，原有的会话与请求人过滤照样逐条检查，没读过的照常查询。
- 启用范围只有两处：`assistant_ledger.carried()` 和 `work_state.check_frozen()`。其余调用方不变。

## 3. 测试

`server/tests/agent/enterprise_search/test_guard_pass_pg.py`，4 例：
- 4 轮会话里，一次守卫、一次会话检查中，每个封存调用都只证明一次；下一次守卫会把同一批调用全部重新证明。
- 守卫 SQL 每轮的增量保持不变。
- 两次守卫之间撤回资料，下一次守卫和会话检查都会拒绝。
- 记忆只在本事务内，嵌套共用外层，调用方改动返回值不影响记忆。

反证：把 3 个源文件换回修复前，前两例都失败。
- 4 轮时同一调用在一次守卫里被证明了 5 次；
- 守卫 SQL 依次是 9、26、44、66、92。

受影响范围回归（132 个文件）：1249 通过、19 失败。
- 15 个在不含本次改动的代码上逐条同样失败。
- 3 个是假会话没有 `info`，已改为没有 `info` 时不启用记忆，重跑通过。
- 1 个比较的是没有 `ORDER BY` 的查询结果摘要，重跑通过。

## 4. 没做的

- 剩下的线性项：
  - 每个前序轮次仍各跑一次谱系递归查询（约占第 12 轮守卫时间的 36%）、一次恢复根查询和一次会话绑定查询；
  - 每条证明 2 次 principals 查询。

  要再降，得改 `lineage()` 或证明函数本身，涉及按运行逐个核对的范围检查，这次没动。
- 真实回归没跑。第 24 轮的效果只是按上表外推：守卫 SQL 从约 1480 条降到约 220 条。真实数据里 `versions` 更大，整行重读减少的效果应更明显，但未实测。
