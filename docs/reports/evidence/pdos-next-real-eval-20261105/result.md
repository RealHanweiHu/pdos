## 4. 新发现

### 4.1 工具调用 id 被重复拼接，完整响应被记成未知（D254，11-07 已修）

- MiniMax 流式返回时，有时在同一个工具调用的每一块里都重复给出 id。`agent_client.py:338` 的拼接逻辑把它们连起来，结果 id 变成同一串重复 2–37 次。
- 超过 `ToolCall.id` 的 200 字符上限（`agent/kernel/types.py:45`）时校验失败，整条响应按 `PROVIDER_INVALID_RESPONSE unknown=True` 处理。
- 1177 次服务商返回里 5 次出现重复 id：
  - 3 次超限出错。服务商响应完整，JSON 合法、用量正常，却被记成未知。1 次在主循环，使 CTX-04 第 3 轮对账后失败；2 次在抽取子任务。
  - 2 次没超限，带着重复 id 照常往下走。
- 改法：id 以第一块为准，后续块给出相同 id 时忽略，给出不同 id 时才报错。

### 4.2 两个工具下发时没有参数定义（D255，11-07 已修）

- `evidence.extract` 下发的参数是空对象，说明是“何时调用尚未登记”。处理函数却要求 `row_schema`（含 `kind`、`version`），30 次调用全部 `VALIDATION_FAILED`。模型要么不带参数，要么按 JSON Schema 的习惯写 `type`。
- `skill.load` 也没有参数定义，7 次被拒，原因是“技能加载只接受名称”。
- D245 让这类错误退回模型、不再崩溃，但模型拿不到定义就改不对，每次都白白浪费一轮。
- 改法：从处理函数的参数模型生成工具定义；处理函数需要参数、定义却为空的工具，下发前检查拦住。

### 4.3 评测运行器缺口（D256，两处已修）

1. 已修：脚本的导入路径漏了 `server/tests`，CTX-04、CTX-11 和原生前置题的夹具导入失败。
2. 已修：父题停在问题处时没有输出，`bind_action_parents` 取值崩溃，整个原生题批次中断（`tools/xiaopai_real_rag_fixtures.py:439`）。改为空值处理后，子题按“父题缺引用”受阻。
3. 未修：运行超过 30 分钟观测上限后又停在问题处时，后续等待只认结束状态。API 也把“待对账”显示成 `waiting_input`，要结合错误码区分。
4. 环境：`caffeinate -i` 挡不住合盖休眠。长批次要接电源并用 `caffeinate -s`，或保持开盖。

### 4.4 单轮最长 31 分钟（D257，未修）

- 修复前，F=48000 的上下文轮次多数被截断，平均每轮 4.6 次模型调用；修复后能做完，平均 11.4 次，p95 运行时长因此从 11.3 分钟升到 24 分钟。
- 长尾集中在企业检索的隔离抽取 `assistant.extract`。以 CTX-01 第 25 轮为例：两次抽取分别耗时 11 分钟和 17 分钟，子调用一个接一个地串行执行，每个 1–2 分钟。
- 30 分钟的观测上限和 60 分钟的活动上限都可能被碰到。可以考虑子调用并行，或给单轮总时长设上限。
