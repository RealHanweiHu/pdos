# AI-native 项目规划闭环遗漏审计

日期：2026-09-09。触发：用户指出任务流程应在项目开始时确认，质疑 AI-native 主线是否遗漏。

**结论：存在产品入口、实现连接和验收覆盖三方面的遗漏。** 已有阶段、任务依赖、AI Finding 和局部测试计划建议，并未组成“输入项目目标→生成完整计划候选→评审确认→落实任务→变更更新”的产品闭环。此前静态指引及脚本模拟不能替代这一验收。

## 1. 已核实的事实

| 检查点 | 当前事实 | 依据 |
|---|---|---|
| 创建项目 | 创建项目、Workflow、Stage、Gate 和初始成员；没有同时建立正式项目任务计划 | [ProjectService.create](../../server/app/domain/projects.py:348) |
| 初始规划能力 | 当前 AI capability 注册表未提供项目初始计划生成能力；已有风险、知识、工程影响、质量、测试计划等能力 | [capability_contract](../../server/app/ai/capability_contract.py:47) |
| 建议应用 | 当前 Finding 应用适配器支持 risk、memory、test_plan；没有整项目计划的应用事务 | [Finding 适配器](../../server/app/domain/findings.py:957) |
| 时间与依赖 | 正式 Baseline/Forecast、依赖传播、关键路径、重基线和延期建议列于未完成的 V3-1～V3-6 | [活动清单](../../tasks/vnext-unified-todo.md) |
| 页面 | 四专业基线为人工编制的静态说明，明确尚未自动创建项目任务 | [四专业指引](../../web/src/components/projects/project-disciplinary-guide.tsx) |
| 模拟 | 脚本读取预设模板、按预定步骤创建与完成任务，未调用模型生成项目计划 | [模拟辅助脚本](../../scripts/simulations/disciplinary_tasks.py)、[模拟记录](2026-09-09-id-disciplinary-validation.md) |

`schedule_change_proposal` 等名称出现在 schema 允许值中，不等于相应业务服务、应用通道和用户入口已实现。局部 AI 测试项增改也不等于整个研发项目规划。

## 2. 遗漏的根因

1. **产品流程遗漏**：把需求/案例转项目与阶段实例化视为立项起点，缺少整体计划的编制、差异审阅、责任确认和正式启用入口。
2. **交付顺序脱节**：规划涉及 V0-6 模板和 V3 时间控制，却没有把它们与立项流程组成一条可用的纵向交付；随后又以静态文字逐项补 ID、分工和依赖。
3. **验收遗漏**：模拟证明的是预设脚本能操作系统，不是产品内 AI 能理解一个新项目、提出计划、处理缺项并在确认后落库。此前报告已说明模拟边界，但没有把“产品自身完成规划”列为主线验收。

这是产品工作流与能力接线缺失，当前没有证据表明换模型、增加 Agent 数量或改几句 prompt 能解决。通用流程模板应当保留，作为组织认可的规则；AI 在其上做项目适配和方案建议。

## 3. 应补齐的主线（执行合同待收口，非已实现）

**项目目标与输入 → AI 编制计划候选 → 系统检查 → 业务人员审阅 → 独立应用为正式计划 → 执行监测 → 变更提案与更新。**

| 环节 | 应有的产品行为 | 完成判据 |
|---|---|---|
| 项目输入 | 读取产品类型、需求版本、ID 来源/周期、团队、目标日期、客户条件及已有模板；只追问影响方案的缺项 | 不要求用户从空白手工拼全流程；缺信息明确为待定 |
| AI 计划候选 | 覆盖 ID、结构、硬件、嵌入式、验证与交付；给出任务、前置、交付、责任建议、里程碑、工期估算依据与不确定性 | 每个任务可追溯到模板/需求/项目条件；无依据的人员、工期或审批不得伪装成事实 |
| 系统检查 | 检查跨项目引用、人员范围、依赖环、遗漏输入及日期/日历约束；确定性计算依赖传播 | AI 不自行心算关键路径，不生成虚构可执行承诺 |
| 计划审阅 | 四专业及相关负责人核对输入/交接、负责人、ID 周期和目标；显示采用、修改、排除及理由 | 确认项目开始时的完整流程与初始计划，而非边执行边发现缺专业 |
| 应用与基线 | 按既有人工边界独立应用，形成正式任务、依赖和版本化计划；重试不重复创建，输入已变则要求重新核对 | 未批准的候选不派成正式任务；并发、幂等、过期候选与失败回滚可验证 |
| 执行与变更 | 基于真实进度、测试失败、ID 修改等更新预测；AI 解释受影响范围并起草应对方案 | 原计划、当前预测、对外承诺、实际日期分开；变更基线与承诺继续由人确认 |
| 项目结束 | 核对最终评审、任务/问题与责任移交，形成结项结论 | 不因点击 completed 或 AI 宣称完成而跳过结项条件 |

项目开始时确认整体流程、关键依赖、负责人、里程碑及首版计划；后续设计细节可逐步细化。已知不确定项必须带责任人与确认节点，不能为了看起来“计划完整”而编造精确日期。模板自动展开、日期计算和业务批准各有明确职责，不能全交给模型。

## 4. 修正后的验收案例

从产品内一个新项目开始，不预先用脚本创建任务：

1. 输入“全新 ID 的锂电自行车泵、无照明、有目标日期”，系统引用模板生成四专业及下游计划候选。
2. 缺 ID 确认人/周期或目标不可达时，展示缺项和影响，不编造已确认日期。
3. 用户修改 ID 周期或要求增加新功能，计划候选列出任务、依赖和验证范围差异。
4. 接受后仍可查看待应用状态；独立应用后生成具名任务和依赖，重复应用不重复创建。
5. 应用前需求/团队/模板变化，旧候选不能静默覆盖新状态；模板规则不能被输入文档中的指令改写。
6. ID 延期仅影响依赖可达的后续工作，能并行的预研不被一并推迟；预测更新保留基线与承诺。
7. 模型不可用时明确显示 AI 规划不可用，已有计划与业务执行仍可使用；不能把静态模板展开记为一次 AI 规划成功。

评测同时核对模型计划质量和实际落库/状态结果；用例先形成待人工审阅材料，不擅自写入冻结 golden 集。既有模拟作为任务与状态机回归资产继续保留，不能冒充本条产品验收。

## 5. 后续执行安排与边界

建议把上述闭环作为整体计划建设主线，关联 V0-6 与 V3-1～V3-6；先收口输入、候选、责任确认、版本/时间及应用合同，再实施生成—审阅—应用的纵向能力，最后验证变更循环。它需要合同与实施，不是再加一段页面说明就完成。

本次完成审计及待办校准，未实现新能力、改变已批准的阶段出口、冻结新对象/权限/迁移或提前标记 V3 通过。既有 SIM-GAP-01 提前结项、SIM-GAP-02 Quality TestRun 权限，以及任务模板实例化/ID 专属硬闸仍未修复；均应进入后续完整验收。现有生产和外发边界不变。
