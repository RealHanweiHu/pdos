# D14-02 重复上传行为验收

日期：2026-09-09。结论：4 个真实文件复传场景均已完成，已确认用例和结果证据覆盖保持不变，但当前系统没有按内容去重。重复上传同一份整机报告，每次会新增 1 个 Document、1 个导入批次和 8 条 Run 草稿；文件改名也会新增。行为已查明，不能据此声明防重复导入通过。

后续：用户已授权并完成 [DUP-01 本地修复与复验](2026-09-09-d14-02-import-deduplication-fix.md)。本文保留修复前的失败基线，以下“待修复”是当时状态。

## 范围与实际结果

用户针对“验证同一报告重复上传时的处理行为”回复“好的开始”。沿用已授权的 D14-02 原件及 8 项隔离确认范围；本次重复批次均保持草稿，没有追加采用重复测试结果。

| 场景 | API 响应 | 新增文件记录 / 批次 | 新增 Run 草稿 | 原正式结果与覆盖 |
|---|---|---|---:|---|
| 整机同名同内容，首批尚未确认 | 201 / parsed | 1 / 1 | 8，每项 run_number=2 | 不变，0/30 |
| 整机同名同内容，首批已确认 | 201 / parsed | 1 / 1 | 8，每项 run_number=2 | 不变，8/30 |
| 整机改名同内容，首批已确认 | 201 / parsed | 1 / 1 | 8，每项 run_number=3 | 不变，8/30 |
| 可靠性同名同内容，仍无有效记录 | 201 / parsed | 1 / 1 | 0 | 不变，8/30 |

首个场景在保存点内检查后回滚，再确认原有 8 条，因此第二个场景的编号仍为 2。随后改名复传才产生编号 3；这只是系统分配的记录序号，不代表实际又做了第二轮或第三轮测试。改名只改变请求中的文件名，原文件字节及桌面原件均未修改。

每次响应均返回全新的 Document ID 和批次 ID；整机新 Run ID 与旧集合不重叠，来源内容、测试日期、缺项/跳行原因和模板指纹均保持一致。新增文档摘要与原件一致，内存存储实际保存了独立副本，没有复用旧文件记录。

## 已验证的保护

- 逐次比较原有 Run、Document 和批次，全部字段不变；正式用例及计划覆盖快照也不变。
- 首批确认后始终只有 8 条已确认 Run，重复记录保持 draft；确认审计没有因上传而增加。
- 可靠性报告仍为 0 条有效 Run，缺日期等原因未被重传消除。
- 没有创建样机、Build 或 Issue；没有模型调用或 D14-04 结果写入。

本次复用了上一步已批准的原批次确认检查；同一批次重复确认仍为 409。它只能防止再次提交同一批次，不能防止相同文件先生成新批次。

## 待修复项 DUP-01

**同项目、同计划、相同文件内容会反复产生新的导入批次和测试草稿。** 实际风险是用户重试上传后出现多组待确认项；若另行确认这些新批次，会把同一历史来源重复记为测试记录。本次没有确认重复批次，因此不声称已经实测后续统计膨胀或再次确认后的行为。

后续建议按 tenant + project + plan + 文件 SHA-256 识别同内容上传，复用已有批次并明确提示其待确认/已确认状态，避免再次生成文件副本和 Run。改文件名不应改变此判断；不同计划或文件内容变化须分别处理。实现时还应覆盖并发重试、权限范围及既有重复数据，不能只做前端按钮禁用。本条是修复建议，不表示去重策略已经实现或冻结。

同模板但内容改变后的再导入、浏览器成员操作和完整 V0-7 历史导入范围仍需另验。各阶段 Exit 保持未关闭。
