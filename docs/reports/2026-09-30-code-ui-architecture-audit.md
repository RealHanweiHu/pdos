# PDOS 当前代码 UI 架构与人机交互评估

评估日期：2026-09-30。对象：当前共享工作区的未提交候选。读者：系统负责人及各建设线负责人。

**主要问题是体验承诺、上下文接线和运行恢复尚未形成一致的业务闭环。** 现有技术栈、服务端领域校验及受控 AI 写入方向可以继续使用；近期应优先修复对象上下文断点和请求恢复缺口，让产品经理主线真正能够从输入走到可核对的结果，再逐步治理公共代码的耦合。

本报告是评估与建议，没有修改业务实现、数据库、模型资格或唯一活动清单。工作区有同期建设，本次证据只支持所记录的候选范围。

**产品经理专项补充版本说明：** 用户追问产品经理闭环后，再次核对最新共享源码，初轮15份重点文件中9份已有变化。市场空间/产品线私人会话已接入小Pai，原请求导航保护与原run回链也已有增量。因此下文“未接入”等页面观察保留为初轮运行版本证据，不再直接代表最新源码；最新业务链结论见“产品经理闭环专项评估”。新增两份当前组件测试共20项通过，未将初轮类型/测试结果拼接为新版整链验收。新增证据见[最新源码与验证范围](evidence/code-ui-architecture-audit-20260930/pm-current-source-manifest.json)。

## 已有基础值得保留

| 方面 | 已看到的基础 | 应保持的方向 |
|---|---|---|
| UI | 统一主题、字体、橙色及组件基座，项目六入口和单一设置导航已经落实 | 沿现行视觉继续优化具体业务路径 |
| 权限 | HttpOnly 会话、同源转发、服务端身份和领域授权 | 页面范围只作提示，实际范围由服务端核对 |
| AI 可信性 | 来源摘要、运行回执、预算、租约、幂等及过期恢复已有实现 | UI 使用这些真值说明实际进度和结果 |
| 领域动作 | 产品工作等写入带版本和来源校验，业务事件与审计随事务提交 | 保留具名责任和确定性校验 |
| 容错 | 产品分析组件已保留原请求、支持查历史和停止，撤权会清理当前资料 | 将组件内保障扩展到跨页面持续运行 |
| 数据读取 | 项目列表批量读取工作流阶段，已有避免逐项目重复查询的处理 | 性能优化基于具体路径和数据规模开展 |

这些基础意味着可以持续重构当前系统。此次证据不足以支持更换技术栈或拆成微服务。

## 优先问题与调整建议

P1 表示直接影响核心使用目标、当前对象准确性或恢复可靠性；P2 表示需要在主线收口中处理的体验、验证和维护问题。这是本次建议顺序，不改变原 N/P/Q 状态。

### 小Pai的全系统入口尚无完整处理能力

**初轮运行候选的P1建设缺口；最新源码已补接入口，运行验收待补。** 初轮小Pai显示“你的个人 Agent”“已自动带入”，但非项目页面提交只在前端设置“处理尚未接入”的错误，没有持久会话或实际处理请求。页面可见文字被截取为最多2400字的预览，初轮代码没有把这份预览接到模型调用。最新源码已改为`ProductConversation`，支持个人暂存、市场空间及产品线的私人持久消息、附件和既有运行派发；不能继续据旧源码断言这些路径完全未实现。持续委托仍需按现行范围单独核对。

登录后桌面和窄屏均实看确认：在市场空间打开小Pai，顶部显示“已自动带入 产品工作”，主体提示“直接说出目标，不需要先选项目”，底部又显示“此页面的 AI 对话处理尚未接入”。本轮没有输入或发送消息，提交行为结论来自源码。

这不是新发现的回归，当前队列也已明确记录。它仍是最影响使用预期的缺口：产品经理在市场空间工作，而全局 Agent 的主要可用执行路径仍落在项目内。

证据：[小Pai呈现与提交](../../web/src/components/ai/xiaopai-provider.tsx:92)、[项目范围接口](../../server/app/api/xiaopai.py:17)。

建议先沿当前产品经理主线接通市场空间和产品线的私人持久对话、附件及受控能力调度。复用已有范围、身份和运行合同，不虚构 Project。完成前将“已自动带入”拆为“当前页面范围”和“本次实际读取的资料”，明确哪部分只是来源提示。

验收：市场空间中输入问题或文件后能生成真实回执，刷新可续问，答案带实际来源；未开放能力在提交前说明；私人消息进入项目共享委托时有明确范围提示。

### 工作项链接与小Pai对象识别不一致

**P1，纯函数已复现，并补充实际页面证据。** 阶段卡及工作项使用 `entity_id`，部分链接还有 `view=issues`。小Pai解析器只识别 `focus_kind/focus_id` 及 `task`、`issue`、`risk` 等参数，忽略 `entity_id`。当前问题链接和阶段链接均得到 `focus=null`，而旧问题参数和显式 typed focus 可以正确识别。

实际从A1项目总览打开“SN-001 流量不达标（19.4 L/min）”，问题详情正确展开；随后打开小Pai，界面仅显示项目名称及“已带入当前项目”，没有源码中识别具体对象时应出现的“当前工作对象”提示。没有实际发送模型请求，因此不声称已经观察到错误回答。

因此用户看到某条问题或任务时，Agent 可能只使用项目范围，不能可靠回答“这个问题为什么还没关”。

证据：[阶段卡链接](../../web/src/components/projects/project-stage-board.tsx:24)、[对象解析](../../web/src/components/ai/xiaopai-page-context.ts:19)、[复现结果](evidence/code-ui-architecture-audit-20260930/context-probes.json)。

建议让业务页与小Pai共用统一的对象定位合同。新链接携带明确类型和 ID，旧 `entity_id` 链接由服务端或已授权清单解析；仅有 ID 时不猜类型。具体对象读取仍再次鉴权和核对版本。

验收：从总览、阶段卡、问题列表、风险列表及旧回执打开同一对象，小Pai均显示并使用相同的真实对象；撤权或对象不存在时停止读取。

### AI原请求恢复信息会随组件重置

**P1，状态生命周期已确认，重复运行后果待整链验证。** `ProductAiRuns` 将原请求、请求号和待确认状态保存在组件的 ref/state 中。`ProductAiPreparation` 按范围重新挂载，工作区又按标签给它不同的 key。运行组件提供了 `onPendingChange`，但准备面没有把它传给外层导航锁或持续任务容器。

最新增量已为私人小Pai接入pending导航保护及持久消息恢复，改善了该入口的连续性；专业`ProductAiPreparation`中的`ProductAiRuns`仍未向父级转发pending回调，需分入口验收，不能将私人会话保障等同所有分析准备面均已闭合。

切换标签、范围或刷新会丢失组件内的原请求恢复信息；后端已保存运行仍可从历史读取，但尚未确认的输入不能完整依靠当前页面恢复。用户再次发起新请求可能产生另一次运行，当前证据没有证明一定重复写入业务对象。

证据：[原请求与待确认状态](../../web/src/components/product-work/product-ai-runs.tsx:41)、[按范围重置](../../web/src/components/product-work/product-ai-preparation.tsx:27)、[按标签重置](../../web/src/components/product-work/product-workspace.tsx:346)。React 文档也明确说明不同 key 会重置组件状态。[React 状态保留与重置](https://react.dev/learn/preserving-and-resetting-state)

建议把任务身份和原请求恢复移到按用户及授权范围隔离的持久请求记录或全局任务容器，页面只订阅读取。过渡期把已有 pending 回调接到导航守卫；长期允许离开页面后继续查任务，避免把全部后台运行都变成锁屏。

验收：提交后断网、切换标签、刷新和重启，均能找到原任务并先核对回执；继续同一请求时不产生新调用身份、额外计费或重复业务动作。

### 产品工作台仍然按内部模块组织操作

**P2，源码及实际页面确认。** 内部员工有 10 个横向标签，管理员有 11 个；“投入观察”“能力评测”等低频工作与日常业务并列。产品 AI 面仍要求填写问题、读取来源、选择依据、核对资料、读取分析开放状态，最后发起分析。“小Pai”同时出现在全局对话和多个专业准备面，用户需要判断哪一个入口能够做什么。

本次空间已有一条真实研究任务，但桌面首屏优先展示重复的空间摘要、责任调整、11个标签、刷新、AI准备和RFQ原件面板，研究任务排在后面。390像素窄屏中，即使AI准备折叠，任务标题也位于约1117像素的页面纵向位置，超出844像素高的首屏。窄屏全页没有横向溢出，标签在自身容器内横向滚动；问题主要是日常工作顺序和入口密度。

证据：[标签定义](../../web/src/components/product-work/product-workspace.tsx:37)、[手动来源准备](../../web/src/components/product-work/product-ai-preparation.tsx:74)、[手动读取后才可分析](../../web/src/components/product-work/product-ai-runs.tsx:147)。

建议先把当前任务、负责人、状态、待决问题和明确下一步放在首屏，将原件上传、来源管理和责任历史按任务展开；随后让主入口围绕“研究与证据、机会与验证、策略与定义、产品规划”组织，现有专业视图按对象和任务展开。导出跟随已发布定义，评测进入能力治理或专业检查入口。保留原 URL、专业能力和权限。

在当前对象页，系统自动准备有权限且与问题相关的来源，默认展示来源摘要、缺项及唯一下一步。用户可展开调整依据；权属不明、范围变化或需要具名确认时才新增步骤。专业准备面作为同一 Agent 的任务详情，避免再形成独立聊天逻辑。

验收：选择一条真实研究到定义任务，逐步记录点击、输入和主动操作时间；在保持原确认及发布边界的前提下减少手动准备步骤。

### 驾驶舱将阶段位置显示为百分比进度

**P1，实际页面与计算代码确认。** A1项目卡显示“阶段进度67%”及进度条。计算值是当前阶段序号除以阶段总数，没有使用任务完成、Gate通过、剩余工作或实际计划数据。最后阶段一开始便可能显示100%，不足以表达当前阶段完成度或项目完成度。

证据：[计算公式](../../web/src/components/dashboard/dashboard.tsx:203)、[百分比呈现](../../web/src/components/dashboard/dashboard.tsx:228)。现行[UI基线](../design/2026-08-09-ui-baseline.md:86)也已要求不以阶段位置推算完成百分比。

建议改为“当前EVT · 第4/6阶段”一类真实阶段位置；有可靠计划数据时，另列已完成任务/总任务及当前Gate状态。不同工作量的阶段不默认等权。验收覆盖进入最后阶段但仍有未完成任务、Gate未通过及项目未结项的场景。

### 产品资料读取实际失败，错误缺少可行动信息

**当前环境的P1流程阻断，P2错误体验缺口；具体故障原因待定位。** 市场空间主体及已有研究任务可正常显示，RFQ文件列表却自动显示“产品工作暂不可用，请重试”。展开AI准备并点击“读取可用来源”后，同样出现该错误，无法继续核对已有研究任务作为来源。两处失败分别留在局部区域，主体页面没有完全丢失，这是应保留的容错。

公共请求封装在响应没有预期的`detail.message`时使用相同兜底文案。界面无法区分“文件列表读取失败”“研究来源读取失败”“能力未开放”或“服务异常”，也没有关联排查编号。已检查同源转发的允许路径，源码包含这两个入口；当前证据不能据此断言运行服务已更新或数据库、存储、网络中哪一项出错。

证据：[请求错误封装](../../web/src/components/product-work/product-work-api.ts:11)、[文件列表读取](../../web/src/components/product-work/product-source-files.tsx:44)、[研究来源读取](../../web/src/components/product-work/product-ai-preparation.tsx:49)、[实际错误截图](evidence/code-ui-architecture-audit-20260930/12-research-source-error.jpg)。

建议先沿这两个实际失败请求核对当前服务版本、响应与关联日志，修复可读闭环；同时统一结构化错误合同，让页面显示失败操作、是否保留旧数据、可重试或需要管理员处理，并提供不含敏感内容的排查编号。保持错误可见，不把失败降级为“暂无资料”。验收要求同一空间可读取任务来源及原件列表，局部失败仍保留独立可用工作。

### 公共代码依赖集中在产品工作领域文件

**P2，架构维护风险已确认。** 统计中，298 个领域模块直接导入 `product_workspace.py`，其中有 505 个以下划线开头的私有符号导入。这些包含 `_plain`、`_role`、`_space`、`_line` 等公共或跨域职责。排程、物料覆盖和小Pai也依赖这个产品领域文件。它本身约 1302 行；数据库 schema 入口约 30636 行。

这些数字不表示运行一定有故障，但说明共享底座与某个业务领域混在一起。领域变更会扩大审阅范围，多条建设线更容易在共同文件上发生冲突。

证据：[结构与依赖统计](evidence/code-ui-architecture-audit-20260930/structure-metrics.json)、[排程跨域依赖](../../server/app/domain/schedule_forecasts.py:27)、[物料跨域依赖](../../server/app/domain/material_coverage.py:18)。

建议采用模块化单体：将序列化和摘要计算移到稳定公共模块；将身份、权限、范围和版本前置条件设为公共明确接口；产品、项目、计划、质量、物料各自保留领域服务。将通用异常与产品领域异常分开。按建设线逐步替换私有导入，保留兼容适配，集中验证行为等价。

schema 可按 namespace 拆分声明文件并保留一个聚合入口。文件拆分本身不新增迁移，不改变 schema、数据库权限或既有真实 head。

验收：跨域调用只依赖明确的公共接口；职责拆分后权限、来源漂移、事务回滚和幂等回归保持。维护指标是私有跨域依赖和共同变更范围减少，而不是文件数量减少。

### 工作区加载同时拉取大量领域资料

**P2，扩展性风险，未做本轮性能测量。** 市场空间主体通过一个 `Promise.all` 读取空间详情、证据和整个产品目录。空间详情一次返回研究任务和工作项，目录也读取产品节点和成员。空间列表、项目列表及多处主体数据没有分页。一个辅助读取失败时，主体数据也无法进入 ready 状态。

证据：[整体加载](../../web/src/components/product-work/product-workspace.tsx:310)、[空间列表与详情](../../server/app/domain/product_workspace.py:586)、[产品目录读取](../../server/app/domain/product_catalog.py:205)。

建议先读取空间摘要、当前标签和必要权限，证据及目录按使用加载；对长清单增加游标分页，对目录提供授权范围内的增量读取。采用局部错误区，区分“没有内容”和“读取失败”。权限撤销仍清理所有相关受保护资料。

验收：以真实或经批准的代表性数据量记录响应体、查询数、首个可操作时间及 p50/p95，沿原 UX10 门槛验证；辅助区失败不阻断仍可使用的独立操作。

### 长模型运行仍绑定部分HTTP请求

**P2，源码事实，负载影响待测。** 产品分析接口调用 `create` 后直接执行模型；同源转发为这类请求配置 300 秒等待。公共应用 worker 虽然已有队列，但产品分析尚未接入，而且多个既有队列在一个循环里顺序处理。

证据：[产品分析HTTP接口](../../server/app/api/product_research.py:555)、[同步执行](../../server/app/ai/product_work_runs.py:312)、[转发超时](../../web/src/app/api/product-work/[[...workPath]]/route.ts:53)、[应用worker](../../server/scripts/run_application_worker.py:48)。

建议复用现有持久运行、授权、预算和租约机制，让长任务先返回任务号，由 worker 执行；页面显示实际运行状态和结果入口。为各队列设置公平领取和有界并发，先测量再增加 worker。短的确定性领域动作保持同步。

验收：关闭页面不丢失已接受任务；取消和未知回执可核对；某个长模型任务不会无限拖延其他队列；全过程保留原身份、预算与当前来源校验。

### 影响产品经理连续工作的四个问题

**1. 单项能力派发尚不能承接常见的完整PM目标。** 最新小Pai已接私人产品会话，但派发仍按关键词匹配且要求恰好命中一种能力。我提取当前源码中的纯派发函数，复现“研究这个气泵市场，完成竞品分析、机会判断和产品定义”及“这些证据支持继续开发还是应该停止？”：两者均返回“多个目标请分轮办理”的指导，不形成分析请求。明确“制定研究规划”可以派发；在市场空间要求定义会提示先明确产品线，在产品线中可派发定义。

证据：[派发规则](../../server/app/domain/conversation_product_work.py:98)、[纯函数复现](evidence/code-ui-architecture-audit-20260930/pm-intent-probes.json)。这说明当前入口对单项任务有明确边界，常见决策问题与跨步骤目标的承接能力仍有限；不是实际模型回答质量的实测结论。

建议沿已有八项能力及领域服务，让同一目标形成可恢复的当前步骤、依据和待决事项；已授权的读取与分析连续执行，缺关键归属或资料时问一个具体问题，适用T1出一次核对，T2发布/批准继续由具名人办理。调度器保留明确能力映射、授权及停止条件，不让模型自由决定政策。

**2. 多区对象关系已有，但用户缺少一个连续的工作视图。** 产品研究、机会、实验、策略、定义和矩阵分别加载列表、选择来源和打开编辑。用户容易知道“有哪个模块”，却难以判断“这个产品目标当前证据到哪一步、为什么不能继续、谁需要处理”。从市场共同研究进入机会/定义还需要产品线和产品对象，当前提示散在AI准备及表单中。

建议用已有对象和引用组装一条PM主线视图：当前待决问题、事实/假设/未知、关联原资料、当前产物、下一步、负责人与阻塞。空间共同研究转为具体产品线时显式确认归属，保留原研究及快照；从当前产物直接进入已带入依据的下一步草稿。各专业页继续承担细节办理，业务真值仍归领域服务。

**3. 判定“形成文档”与“形成可执行承诺”的出口需要更清楚。** 代码已经区分分析回执、候选、发布定义、需求应用及商业批准，这是正确基础。UI应持续显示它们各自的状态，并让PM确认每条发布规格能定位来源、判据、验证负责人和下游需求/工程验证。英文item_key与阶段代码可由系统生成或从批准模板选择，PM主要核对业务含义和差异。

应保留：具名定义发布、当前轮次专业协审、需求复用差异确认、项目/G1正式批准。后续功能收敛不能把这些动作压成一个无区分的“全部完成”。

**4. 反馈功能存在，但持续学习需要从主线可发现。** 当前实测/服务/NCR反馈在定义详情中，需要人工选项目、原结果和定义字段，再选择采用/拒绝/补证，之后关联真实新修订逐项落实。这些守卫值得保留，但主入口应直接显示与当前产品目标相关的待回应反馈、采用后尚未落实的字段以及新版本发布状态。仅保存采用意见不代表规格已经改变，也不代表改动效果已验证。

### 收口方式与最小业务验收

以已有研究任务“连续运转流量衰减的用户感知阈值与竞品稳定性策略”为同一目标，核对“是否在DVT增加连续运转稳定性规格及修改判据”。不先扩充新模块，先贯通现有路径：

1. 在市场空间保存目标，读取真实来源并保留快照、未知和停止条件。
2. 形成同工况竞品与用户/JTBD依据，明确具体产品线。

## 建议实施顺序与完成标准

| 顺序 | 可交付闭环 | 主要归属 | 完成标准 |
|---|---|---|---|
| 第一 | 修复当前资料读取阻断及误导性状态，打通对象定位 | 产品资料读取与公共导航协调 | 文件列表与来源可读；阶段位置不冒充完成百分比；当前对象与链接一致 |
| 第二 | 小Pai使用正确对象、保存原请求并跨页面恢复 | 公共导航上下文与AI运行协调 | 新旧链接、对象切换、刷新、断网及撤权全部使用正确范围并可恢复 |
| 第三 | 市场空间输入真实资料到研究结果或定义草稿 | 当前产品经理主线及公共会话 | 自然语言或文件入口可用，资料有来源，任务有回执，刷新续接，适用T1一次确认 |
| 第四 | 产品工作台按任务收敛，局部错误与状态显示一致 | 产品UI及领域接口 | 核心任务在首屏、少手动准备，保留专业办理和原深链，键盘可用，真实员工主动时间下降 |

各闭环按现行清单原位登记能力、证据和余项；本报告不建立第二份活动清单。正在并行建设的领域应按既定文件归属接收修改，公共上下文、schema 和运行能力由协调会话整合。

## 必须保持的边界

T0 必须具备真实资格与当前授权；T1 保留适用对象的一次明确确认；T2 保留具名签核、批准、发布和外发边界。未迁移能力不因统一入口而跳过原 Finding 流程。页面文字、引用和模型参数不能充当服务端政策事实。

业务状态由确定性引擎和领域事务维护，Agent 提供整理、分析及受控执行。权限、来源版本、原请求身份、预算、租约和撤回守卫继续由公共运行控制与领域服务共同保证；不将这些责任交给提示词或 LangGraph 自行判断。

本轮完成了代码与结构评估、登录前后代表性页面及只读路径检查、上下文复现、键盘局部检查和定向静态与组件验证，没有修改业务实现或业务数据。登录态阻塞已解除。资料核对的后续步骤仍受当前读取失败阻断；恢复需先定位并修复这些实际失败请求。真实模型效果、上传及业务办理、读屏、数据库和联合候选验收尚未验证，需要对应真实材料、资格、授权及独立验证环境；本报告不宣称正式验收通过。
