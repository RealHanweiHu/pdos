# 备份与恢复

适用欠债总表 D211，验收场景 AT-47（v1.1 附录 B）和 v1.1 §11 第 4 段“备份覆盖业务 DB、对象版本、Workflow 持久库、密钥与映射；恢复演练核对配置→测试→决定→交接链，并确保事件重放不会重复外发；备份成功不等于恢复成功”。

写这页时没有做任何云上操作。本地工具和演练已完成；云上各项要等部署方案 D210 定了再填规格，执行前仍须对应授权（AGENTS.md“必须保留的批准与验收边界”）。标“〔你〕”的由你决定。

## 1. 目标（〔你〕待定）

| 项 | 建议起步值 | 说明 |
|---|---|---|
| RPO（最多丢多久的数据） | ≤ 24 小时 | 只靠每日备份时就是 24 小时。RDS 开了日志备份和按时间点恢复后，实际可以做到分钟级；对外承诺仍按你定的值。 |
| RTO（多久恢复服务） | ≤ 4 小时 | 本地演练里恢复全部存储用时约 30 秒；云上主要花在新建 RDS 实例和外发核对上（第 5 节第 4 步）。 |
| 备份保留天数 | 〔你〕，建议 ≥ 7 天 | OSS 历史版本的保留期不能短于它。 |

## 2. 备份范围

| 存储 | 内容 | 云上做法（待 D210） | 本地工具 |
|---|---|---|---|
| 业务库 | 全部业务事实、回执、事件外发表、钉钉投递记录、登录会话 | RDS 自动备份 + 日志备份（按时间点恢复）；每天另做一次逻辑备份存到单独的 OSS 桶，作为第二道 | `backup_restore.py backup` 的 `business.dump` |
| Temporal 持久库、可见性库 | 在途工作流的历史（等待中的小Pai运行、维护计时器、投递重试） | 按 D88 与业务库**同一 RDS 实例**分库，这样一次按时间点恢复就能把三者恢复到同一时刻 | 本地开发服务用 SQLite：`temporal.sqlite`（在线备份接口，服务不停）；用 PostgreSQL 时是 `temporal.dump`、`temporal_visibility.dump` |
| LangGraph 检查点库 | 小Pai执行图的检查点，保留 30 天（D58） | 同一实例分库 | `checkpoints.dump` |
| 运行时状态库 | `pdos-agent-runtime` 的作业、事件和检查点 | 同一实例分库，或随 D210 定 | `agent_runtime.dump` |
| OSS 原件 | 上传的原件，只增不改 | 开启版本控制；历史版本保留期 ≥ 备份保留天数；是否开跨地域复制〔你〕 | `objects.tar`，逐个文件记 sha256 |
| KMS 与凭据 | 模型 API Key、钉钉凭据、数据库口令 | 密钥本身不导出、不进备份。开启密钥删除保护；凭据放凭据管家并保留版本；另存一份“密钥 ID / 别名 / 用途”清单（不含值） | 本地没有 KMS，清单里记为 `included: false` |
| 部署配置 | 环境变量、租户模型配置、扫描档、专业资格与交接回执的签发方配置 | 跟发布目录一起管理（D212），不在数据库里 | 不在备份内；演练证明恢复后必须随部署一起恢复，见第 6 节 |

数据库角色：备份里有角色清单（`pg_dumpall --roles-only --no-role-passwords`，不含口令）。恢复时按清单重建角色，登录角色一律换新口令。

## 3. 一致性规则

1. **所有数据库恢复到同一时刻。** 这是把 Temporal 库、检查点库和业务库放在同一 RDS 实例（D88）的主要理由。
2. 做不到同一时刻时，**业务库的恢复点不能晚于 Temporal 库**。业务库较早时，备份点之后已投递的事件会再投一次，但事件对应的工作流 ID 是确定的（`pdos-security-queue:{租户}:{原件}` 等），Temporal 里已有同 ID 的运行，不会再跑第二次（演练情形 B）。反过来，Temporal 较早而业务库较晚时，业务库认为事件已投递，Temporal 里却没有对应工作流，这些工作就会悄悄丢失。
3. 外发以“结果未知时先核对、不重发”为准（AT-30）。恢复后任何“计划中 / 发送中 / 结果未知”的外发都先向对方核实，不由系统自动重发。

## 4. 本地工具

`tools/backup_restore.py`，从仓库根目录用 `server/.venv/bin/python` 执行。只认本 worktree `.local/` 下由 `local_environment.py`、`workflow_environment.py`、`agent_runtime_environment.py` 写的身份文件，操作前逐个核对容器 ID、标签和库内标记，不接受命令行传入的连接串，不打印任何凭据。

| 命令 | 作用 |
|---|---|
| `backup [--objects 目录] [--counts-only]` | 在同一个快照里统计每张表的行数和内容摘要，再用这个快照做 `pg_dump`；写 `.local/backups/<时间>-<标记>/` 和 `manifest.json`（每个文件的 sha256、迁移 head、角色清单） |
| `restore 备份目录` | 新建带新标记的容器（`pdos.next.restored-from` 标签指向原标记），重建角色并换新口令，恢复全部库、Temporal 历史和原件，然后自动核对 |
| `verify 备份目录 恢复目录` | 逐表比对行数和内容摘要、迁移 head、原件 sha256、Temporal 历史文件 |
| `audit-outbound 恢复目录` | 列出恢复库里在途的外发：未投递事件、钉钉投递与摘要（计划中 / 发送中 / 未知）、交接“发送结果未知”、未结束的工具调用和模型调用、未结束的小Pai运行。只给数量和 ID |
| `serve-temporal 恢复目录` | 在恢复出的历史文件上启动本地 Temporal 开发服务 |
| `destroy 恢复目录` | 核对标记后只删除这次恢复的容器和私有文件 |

恢复不会写入任何已有环境：新容器、新端口（避开受保护端口，含预览库 64387）、新标记。

## 5. 恢复步骤

云上命令要等 D210 定了实例和网络再补；顺序和判断依据不变。

1. **宣布与冻结。** 在钉钉支持群（D219）通知开始恢复。Web 切到维护页；停 Worker；钉钉通道保持关闭。记录发现时间。
2. **选恢复时间点 T。** 一般取故障前最后一个可信时刻；记下 T 和理由。
3. **恢复到新实例，不覆盖原实例。** RDS 按时间点 T 恢复出新实例（业务库、Temporal 库、检查点库、运行时状态库同在其中）。OSS 原件只增不改，一般不用回退；只把 T 之后被误删或被覆盖的对象恢复到 T 时的版本。KMS 不需要恢复，只确认要用的密钥处于启用状态。本地对应 `backup_restore.py restore`。
4. **启动 Worker 之前先核对外发**（本地对应 `audit-outbound`）：
   - 未投递事件：启动 Worker 后会各投递一次，不用处理；
   - 钉钉投递与摘要处于计划中、发送中、未知：逐条在钉钉侧按 `request_key` 查是否已送达；查不到的保持“结果未知”，走人工对账，不重发；
   - 交接“发送结果未知”：向对方系统核实，按对方回执原件经 `integration.receipt.record` 补录；系统本身从不发送交接包（`network_send=false`）；
   - 未结束的工具调用、模型调用、小Pai运行：由运行核对出口处理（[中断运行结果核对](pdos-next-run-reconciliation.md)），不重复推理，也不重复外部动作；
   - 清单和每条的处理结果写进恢复记录。
5. **恢复部署配置。** 和发布用同一份配置：签发方配置、租户模型配置、扫描档。没有恢复签发方配置时，页面上的来源与适用性会显示“需要重新核对”而不是“当前有效”（演练中实测如此），这不是数据损坏，但必须在开放使用前补齐。
6. **启动服务。** 先跑 [发布手册](release-and-rollback.md) 的工作流回放检查，通过后再启动 Worker；然后按发布手册做冒烟。
7. **补录与核对。** T 之后收到的外部回执按原件补录；按交接清单逐个打开，确认“配置→发布→决定→交接”链与 T 时一致。
8. **结束。** 通知恢复完成，记下实际 RPO（T 到故障的间隔）和 RTO（发现到恢复服务的时长），写进恢复记录。
