# PDOS 设计方向整合

日期：2026-09-28。来源：用户《PDOS 设计方向整合》文档（2026-09-28），§8 待决问题已于同日经系统负责人逐项裁决（见 §8 裁决记录）。本文件为该方向的仓库基线版本；与冻结合同冲突处以冻结合同为准，Q1 涉及的 §7 修订随实施同步登记。

## 1. 目的与基线原则

PDOS 只保留一套设计基线：**原合同（2026-09-10 完整设计合同 v1.1）是领域基线，V2 五份文档只作为体验层、入口和 AI 机制的来源**。本文件用于统一方向，不改变任何已冻结合同的效力；与冻结合同冲突处以冻结合同为准，需要修订的内容列入第 8 节（已裁决）。

一句话分工：**原合同管"对不对"，V2 与 Linear 理念管"顺不顺"，AI 管"谁来干"**。

五条基线原则：

1. **领域不删减**。原合同已想清楚的对象、状态机、确定性引擎和硬闸全部保留，包括齐套、资源、四时间、CCR/ECR/ECN、NCR/CAPA、会议与决定。
2. **内核不外露**。事务对象（候选包、计划候选、执行申请、签核记录）留在内核和审计视图，用户只看到业务含义。
3. **人只碰决定和例外**。AI 先完成，确定性引擎校验，人处理 T2 决定和异常；T2 硬闸清单不变。
4. **状态由工作推动**。实际发生的事件（报告上传、图纸发布、样品签收、ERP 回执）自动推进状态，不靠人手动更新。
5. **用真实证据扩展**。先在一个真实产品上走通一条纵向路径，拿到真实员工证据，再扩大范围。

GoodJob（CRM）与 PDOS 是两个独立系统，二者集成不在本文件范围，待 PDOS 完成后另行设计；本阶段仅在项目客户字段预留外部引用 ID。

## 4. 需要补充的对象

原合同覆盖了 IE、治具、SOP、试产的职责和交付，但多数只停在任务、资源或引用层面，§9.2 对象字典中没有对应实体。建议补充六个对象族，均归入现有 namespace，不新建 schema。

| 对象 | 解决的问题 | 最小字段与关系 | 建议归属 |
|---|---|---|---|
| 开发工艺路线（ProcessRoute / Operation） | NPI 期工艺还未进入 ERP；ECN 时无法列出受影响工序、SOP、治具 | 工序序号、关联 BOM 行、SOP 版本、治具、测试项、PFMEA 条目、控制计划条目；量产移交时作为 ERP 工艺来源 | project；对应 N5 与 PVT 移交 |
| 模具（Tooling） | 试模轮次、修模、签样只能靠任务拼凑，排期引擎无法计入 | 零件、供应商、模穴数、状态（开模 → T0 → T1 → … → 签样 → 量产）、每轮试模问题清单、修模记录、承认状态 | supplier；对应 N5-05、G26 |
| 治具与设备（Fixture / Equipment） | 设计变更时无法回答"哪些治具受影响" | 用途（组装/测试/检具）、适用工序与产品版本、状态（设计 → 制作 → 验收 → 在线）、数量需求、负责人 | project；对应 N5-05 |
| 试产批次与良率（Pilot Run） | 附录 PM2 保留"试制轮次/批次/真实良率"，但无对象 | 作为 Build 扩展：工艺路线版本、SOP 版本、治具清单、产线、投入/产出、各工序良率、首件结果；良率由确定性计算 | project；对应 N5-05 |
| 承认（Approval of Parts / Samples） | 客户承认、供应商零件承认、签样无统一承载 | 承认方（客户/内部/供应商）、对象（样机/零件/模具）、版本、结论、条件、证据；区分客户承认、内部工程发布、制造发布 | quality |
| ECN 断点与库存处置 | 现有 effectivity 仅一行描述，量产后变更易出错 | 断点方式（日期/批次/序列号）、在库与在制品处置（用完/返工/报废）、同步更新的 SOP 与治具、ERP 物料与 BOM 切换回执 | project；扩展现有 ECN |

另外，样机分配不新增对象，而是强化现有 Sample：DVT 起每台样机必须记录去向（可靠性测试、客户送样、认证送测、内部评审）和是否已被破坏性测试消耗，并纳入资源冲突计算。

## 5. AI-native 改造方案

默认模式从"人录入、AI 建议、人再确认"反转为"**AI 先完成、引擎校验、人处理例外和决定**"。头号指标是原合同 §23 的减负 = 原流程主动时间 − 新流程主动时间，辅以"完成一件业务需要人操作几次"。

### 5.1 确认次数：从双动作压到一次确认

- 尽可能多的能力从旧 Finding 双动作迁移到 DC-11 的 T1（预填一次确认）或 T0。
- 同一人、同一版本、无来源漂移时，"接受"与"应用"合并为"确认并应用"；版本变化才要求重新核对。
- 一个业务意图打一个包：例如测试失败时，Issue、关联规格与样机、通知责任人、复测任务合为一张卡片一次确认。
- T2 硬闸清单不变。

### 5.2 审批复用：G1 一次决定生成全部内核记录

决策人在 G1 页面看到完整证据包后点一次"批准"，内核在同一事务内生成 Case 批准、执行批准、计划应用回执和首版基线。依据是原合同 §7 已有的"同一已有批准可按政策引用复用"，本方案将其设为默认。

### 5.3 信息入口：AI 作为录入员

| 通道 | 做法 | 档位 |
|---|---|---|
| 钉钉转发 | 用户主动把供应商消息、群聊片段转给小Pai，AI 更新状态并重算排期；符合"不抓取全部聊天"边界 | T1 |
| 现场拍照与语音 | 拍不良品照片加一句描述，AI 起草 NCR/Issue 并关联当前批次与工序 | T1 |
| 文件投放 | 测试报告、试模报告、承认书、客户 RFQ 在任意位置拖入即解析，沿用 §12.2 导入合同 | 解析 T1，判定由引擎 |
| 会议转写 | 生成纪要、决定和行动项；内部分派可撤回 | 行动分派 T0，决定 T2 |

### 5.4 状态自动维护

- 项目 Agent 每天重建项目状态：变化、阻塞、待决定、距下一 Gate 的缺口。
- 周报自动起草（T0），项目经理只改结论句。
- Gate 准备度持续计算。PVT 前按"人机料法环测"（4M1E）每日检查：治具验收、SOP 版本、齐套率、培训完成度，缺项自动生成跟进任务。

### 5.5 AI 负责追踪推进

- 对内：临期或阻塞时自动提醒，并说明影响（如"该治具延期将使试产推迟 5 天"），复用 §11 提醒/SLA 引擎的合并、静默与日额度，T0。
- 对外：供应商和客户跟进由 AI 起草，发送仍为 T2。
- 升级：同一事项提醒两次无进展，转入项目经理"需关注"列表。

### 5.6 按角色落地

| 角色 | AI-native 做法 | 档位 |
|---|---|---|
| 项目经理 | 自动追踪提醒、每日状态重建、周报草稿、Gate 证据包持续准备 | 提醒/周报 T0，Gate T2 |
| 产品经理 | RFQ 与客户文件抽取需求并保留出处，规格书由结构化数据生成 | 需求 T1，定义发布 T2 |
| 结构工程师 | 试模报告转问题清单，修模进度转发即更新，改图列出受影响模具、治具、SOP | 问题清单 T1，影响只读 |
| 硬件工程师 | EDA 导出 BOM 自动比对，扫描 EOL、单一来源、长交期 | 比对 T0，替代料 T2 |
| 软件工程师 | 从 Git/Jira 同步版本发布，检查固件与 PCB 兼容 | T0 |
| DQE | 报告解析比对规格，失败起草 Issue，样机分配冲突预警 | 解析 T1，签核 T2 |
| SQE | 供应商回复转发即更新，由 NCR 生成 8D 初稿 | 状态 T1，承认 T2 |
| PIE / 制造 | PIE覆盖产品导入、工艺工程及工业工程：准备制造导入资料、由BOM与工艺路线起草SOP，ECN列出工序/参数/SOP/治具及工时产能影响，跟进试产准备；制造执行并接收 | SOP草稿T0须具备资格，发布T2；其他操作按既有逐能力资格，不因职责扩展自动获权 |
| 管理层 | 跨项目例外汇总，只推送待决定与重大风险 | 只读 |

2026-09-30职责补充：用户倾向采用PIE综合岗位，产品导入、工艺工程、工业工程的阶段交付均保留，详见[完整合同§6.4](2026-09-10-pdos-complete-design-contract.md#64-pie职责覆盖与协作)。原IE/PE/ME职责按项目映射，制造接收与品质独立验证继续分别办理；本补充不改变对象三批顺序或宣称已实现。

### 5.7 档位晋升机制

- 影子模式：新能力后台运行，结果不进员工待办，只与人工结果比对。
- T1 阶段：一次确认模式，统计接受率、修改率、拒绝率（含结构化拒绝原因）和下游错误。
- 晋升 T0：达到阈值后由治理人批准为可撤回直接写入；阈值按能力配置，不预填通用数值。
- 自动降级：出现下游错误或修改率上升，退回 T1。
- 晋升只适用于 T0/T1 之间；T2 事项任何情况下不由 AI 执行。

## 6. Linear 理念落地清单

借 Linear 的理念与机制，不借它的业务模型。总原则：**流程是护栏，不是表单**——治理全部保留在内核，只在真正不可逆的节点出现。目标比例：约 90% 日常操作一步完成或自动完成，T1 集中在"AI 替我做了，我看一眼"，T2 只出现在 Gate、冻结、ECN、对外承诺。

| Linear 理念 | 在 PDOS 中的做法 |
|---|---|
| 为干活的人设计 | 工程师日常操作要轻；只为报表存在的字段去掉，由系统从工作中推导 |
| 有主见的默认值 | 新品、OEM、派生三套模板开箱即用，带 20 节点依赖、DQE/SQE/IE 交付与 Gate 标准；自然语言配置作为少数情况的补充 |
| 速度即功能 | 低风险可撤回编辑乐观更新，后台校验落库；手机现场采集三步以内 |
| 状态由工作推动 | 报告解析 → 验证状态；PLM 发布 → 设计任务完成；样品签收 → 齐套重算；ERP 回执 → ECN 交接关闭；试模报告 → 模具进入下一轮 |
| Triage 待分拣区 | 钉钉转发、客户要求、供应商回复、AI 发现的问题、会议行动项先进待分拣区，负责人每天快速确认、合并、分派或丢弃；承接现有 Finding 与 Review Inbox |
| 自动滚动的节奏 | 小节奏为每周：议程由例外自动生成，未完成行动自动带入下周；大节奏为 Build：上一轮遗留问题自动进入下一轮准备清单 |
| 定期项目更新 | AI 起草更新与健康判断，项目经理修改结论句后发布 |
| AI 作为可指派的队友 | "起草 SOP""整理测试数据""比对 BOM""起草 8D 回复"可直接指派给小Pai，按档位交回 |
| 减少琐事 | 重复问题识别、停滞行动自动提醒或升级、结项遗留项转入产品层跟踪 |
| 客户需求挂到工作上 | 客户要求、反馈、承认挂到需求、样机与变更，随时看到"这个客户还在等什么" |

不照搬的部分：

| Linear 做法 | 不适合的原因 | PDOS 替代 |
|---|---|---|
| 尽量不设审批 | 开模、BOM 冻结、ECN 生效不可逆且代价高 | 保留 T2 硬闸，只在不可逆节点出现 |
| 只有最新版本 | 多版本并存，有库存与在制品 | 配置修订与版本并存 |
| 以团队速度衡量 | 瓶颈是外部等待 | 准备度、距量产时间、承诺达成率 |
| 一切皆 Issue | 样机、模具、测试、变更各有生命周期 | 多种对象，统一交互 |
| 两周 Sprint | 节奏由 Build 与外部交期决定 | 周节奏 + Build 节奏 |

## 7. 首条纵向路径与实施顺序

以 **D14-04（锂电自行车泵，29 项适用测试待测）** 为真实产品，先走通"样机 → 测试失败 → 复测"一条路径，目标是取得原合同 AT-12 要求的真实员工证据。原合同 65 项的完整度远超单人在合理周期内的交付能力，因此以纵向路径驱动，而不是按 N 包横向铺开。

### 7.1 纵向路径

1. 以 V2 方式创建 D14-04 项目，AI 项目设置给出简报与缺项。
2. 建立 EVT Build 与样机配置修订。
3. DQE 拖入测试报告（或现场拍照），AI 解析，引擎判定通过或失败。
4. 失败时一张卡片一次确认：Issue、关联规格与配置、责任人、复测任务。
5. 结构或硬件工程师整改，形成变更与新配置修订。
6. 复测建立新 Run，旧 Run 仍指向原配置。
7. 项目总览自动显示该问题对 DVT 日期的影响，周报自动起草。

### 7.2 首批四项能力

| 顺序 | 能力 | 选择理由 |
|---|---|---|
| 1 | 测试报告 → 验证结果 → 问题 | DQE 每天使用；已有 D14-02 回放基础（8/30 覆盖） |
| 2 | 会议转写 → 纪要与行动项 | 项目经理每周使用，见效最快 |
| 3 | 钉钉转发 → 状态更新 | 解决信息入口，覆盖供应、模具、客户沟通 |
| 4 | 项目状态重建与周报 | 管理层首次无需问人即可了解项目 |

### 7.3 验收与扩展

- 用原合同 §23 的主动时间口径，对比真实员工在新旧流程中的操作次数与耗时，含审核、纠错与学习成本。
- 四项能力全部先走影子模式，再按 5.7 晋升。
- 取得证据后，第二批扩展到齐套、资源预约与试产准备度（4M1E），并同步补入第 4 节对象。
