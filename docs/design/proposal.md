# AI-native 研发项目管理系统 · 产品设计提案 v0.3

> 2026-07-22。依据：[调研综合报告](../research/report.md)（11 agent 全网调研，Attio/Lightfield 结论已对源核验）。
> v0.2 = v0.1 经三视角对抗性审查（[审查记录](review-v0.1.md)）修订：收敛断言等级、修复分期依赖断裂、砍掉小团队不可承受的架构重量、把锋利点的燃料前置。
> **v0.3 = 用户定调「要 AI-native 不是 AI 赋能」后的路线修正**：恢复 CRV 原版拆除测试，AI 进入 M0 关键路径，废弃「零 LLM 骨架先行」的渐进式分期。
> 状态：决策清单已拍板，M0 计划见 [m0-plan.md](m0-plan.md)。

## 0. 定位与判据

**一句话定位**：研发项目的过程记录系统 + AI 装配层——协作痕迹（会议、评审、消息、审批、文档）进入系统成为原始事实，任务状态、gate 就绪度、风险清单是从事实派生的视图；AI 负责装配（状态汇报、评审就绪度、影响分析），人负责裁决（gate 决议、例外处理、红线签核）。

**路线声明（AI-native，2026-07-22 用户定调：不是 AI 赋能）**：采用 CRV 原版拆除测试——**关掉 AI，系统即失效**：不再有新状态产生，只剩一个只读档案。这是架构承诺，不是口号，落地为三条硬规则：
1. **人不录入数据，人审核数据**：系统不为对象建「填表」主界面；结构化状态默认由 AI 从事件流（CEHub 动作、会议转写、文档）派生，人的写入界面就是 For-review 审批与纠错（Lightfield：字段是派生视图，schema 只是给 AI 的索引）
2. **AI 在 M0 关键路径上**：第一行代码就是「事件→AI 派生→人裁决」的闭环，而不是先造无 AI 骨架再加 AI（后者正是 AI 赋能路线）
3. **AI-native ≠ 全自主**：For-review 队列、citation、红线人签不是对 AI-native 的妥协，而是它的组成部分（Lightfield 同款）。Height 死于静默自动改数据，不是死于 AI-first 数据流

接受的代价（明说）：AI 抽取质量从第一天决定系统可用性（golden-case 与 token 预算从 M0 开始）；无手工兜底路径——AI 管道故障时系统只读，修管道而不是退回手工。

**Gate 的目标方向**：Cooper 承认 stage-gate 在多数组织退化为文档官僚流程；调研在此之上的设计推论是——让 gate 审例外、审数据，而不是审更厚的材料（Cooper 自己的「AI-assisted gates」仍停留在「AI 起草更多文档」的框架层面，这恰是要避免的方向）。因此本产品的北极星指标是 **gate 决策周期（材料就绪→决议）与会议时长下降**，而非「材料生成速度」。

**验收五问**（改造自 Lightfield 五测试）：系统自动捕获了多少真实项目活动？能否跨库找模式？能否带证据解释「为什么 DVT 延了三周」？能否自然语言提问并得到带引用的回答？发现风险后能否自动起草跟催/变更影响清单/评审就绪度？

## 1. 设计原则（12 条）

| # | 原则 | 来源 |
|---|------|------|
| P1 | **双层数据**：append-only 原始事件层是出处与审计的载体；对象层是权威业务数据，AI 维护的派生字段全部可溯源到事件 | Lightfield / CRV（工程降级见 A1） |
| P2 | **身份与流程分离**：实体唯一存在；流程状态挂在流程实例上。同一交付物可同时在 Gate2 评审与受控发布两条管线里各自带状态 | Attio |
| P3 | **AI 挂在 schema 上**：AI 写入受类型约束的字段（select 只能落在选项内），不是自由文本；可单条重算、整列批量重算 | Attio AI attributes |
| P4 | **建议-审批，不静默写入**：AI 侦测的状态变化/新实体一律进 For-review 队列；**转正门槛**——AI 侦测的疑似任务/风险先入暂存态，有人认领或有后续活动才转正，防噪音实体灌库 | Lightfield（含其 AI 错录教训）/ LangChain；Height 反例 |
| P5 | **红线人签 + 双重痕迹**：gate 决议、基线变更、金样本确认永远人签、四眼；受审计交付物必须带「AI 生成 + 人签核」双重痕迹——把合规约束做成 For-review 留痕的卖点而非雷区 | 自家红线设计 / EU AI Act / 质量体系约束（待补研，见决策 5） |
| P6 | **Agent 是团队成员但不可担责**：assignee（人）与 delegate（agent）分离；agent 有独立身份、徽标、能力 scope；被叫停立即冻结 | Linear AIG |
| P7 | **无出处不落库**：AI 结论必须内联引用源事件；「AI 草稿 vs 人工修正」的 diff 留痕，既是治理信号也是校准语料 | shapeof.ai / MIT Sloan 状态失真研究 |
| P8 | **Opinionated 默认 + 资产库**：阶段/节点/checklist/交付物定义是可版本化资产；AI 从资产库选配而非凭空生成。不做 Jira 式自由工作流配置器 | Linear / 爪印工作室 FlowStack（飞书项目 ISV）/ 华为 IPDCenter / NPD 模板分档 |
| P9 | **确定性引擎干确定性的事**：依赖传播、影响分析图遍历、规则执行用算法；LLM 只做理解、抽取、起草、解释 | Motion / Lightfield |
| P10 | **权限单轨**：UI、agent、集成共用同一套带权限审计的 API；agent 继承委托人权限，无旁路 | Duro / Lightfield / Attio |
| P11 | **具名角色 agent 而非泛 copilot**：每个 agent 有名字、职责边界、权限清单 | Motion；Height 反例 |
| P12 | **模型可替换**：LLM provider 薄抽象（当前一个云端点即可）；全链路 trace 与 token 归因从第一天记；不为即将消失的模型局限造功能 | Attio Thread Agent / Granola（三形态部署见 A4 条件项） |

## 2. 产品概念：三层架构

```
┌─────────────────────────────────────────────────────┐
│  Agent 层   具名角色 agent + For-review 队列(主界面)        │
│            （M0:书记员/汇报员;M1:检查员;M2:分诊员;M3:哨兵）    │
├─────────────────────────────────────────────────────┤
│  对象层     领域对象(硬编码 schema) + 管线 + 字段所有权矩阵    │
├─────────────────────────────────────────────────────┤
│  事件层     append-only 出处/审计事件表:系统内动作、会议转写、  │
│            IM 事件、CEHub 动作、文档版本——带来源/时间/锚点    │
└─────────────────────────────────────────────────────┘
```

### 2.1 事件层

- **定性（v0.2 修订）**：出处与审计的载体，不承担对象层重建职责（见 A1）。每条事件带来源、时间戳、行为人、锚点（对象+版本+位置）。
- 采集面按接入成本排序：**系统内动作**（M0 起）→ **CEHub 事件连接器**（M0，第一个外部采集源——webhook/轮询同步任务、评论、gate 动作，让并行期的日常工作直接成为本系统的燃料）→ **会议转写稿**（M1，不自建 ASR：接飞书妙记导出或人工上传转写稿，转写稿文件是 M1 的明确输入边界）→ **共享盘/Excel 扫描导入**（M1 冷启动回填）→ **IM 开放平台事件**（M2，只做公司实际在用的那一家）→ **PLM/测试数据**（M2 起人工上传+AI 抽取，只读快照连接器视客户情况）。
- 冷启动回填是**有验收标准的工作项**（非顺带能力）：回填 N 个历史项目，决议/遗留问题抽取抽查合格率达标——这是 M3 组织记忆的进入条件（CoLab ingestion engine 先例）。

### 2.2 对象层

**首发对象（8 个，硬编码领域 schema，不做泛化元模型）**：

- `Project`、`Task`、`Person`
- `Deliverable`：不是附件堆——关键参数（如流量/扬程/噪音/成本目标/认证指标）做结构化字段，M2 起由检查员从上传文档中抽取（抽取即结构化，不靠人二次填表）
- `Review`：**双轨一等实体**——DCP 类（商业决策：GO/KILL/HOLD/REDIRECT，主体 IPMT）与 TR 类（技术评审：通过/有条件通过/不通过，主体技术专家）；支持前置依赖约束（如 ADCP←PVT 准出）；**支持异步评审形态**：低风险 TR 可「材料就位即线上分批签核、仅例外项召集会议」——AI 压缩材料准备时间后，评审排期与串行审批就是下一个瓶颈（Linear「流程倒挂」教训）
- `Issue/Risk`、`Change`（PCR/ECN：能触发状态机回退到指定 DCP 的一等对象）
- `PrototypeBatch`（样机批次：贯穿主键，串起试产痕迹）

**降级/预留**：`Supplier` 降为字段/轻量查找表；`CBB`、自定义对象机制移到 M3+（前置条件：已有多项目数据）；`Program`（项目集）仅预留 schema 不做功能（与 CEHub 项目集工作线呼应）。

**M3 语料从 M0 开始采集（不是可选项）**：Task/Review schema 从第一天包含——计划完成/实际完成双时间戳、延误原因（受限 select，AI 建议+人确认）、gate 有条件通过的条件项及其闭环状态。硬件单项目数据永远稀疏，这些字段就是未来组织记忆的全部燃料。

**字段所有权矩阵**（P4/P5 的初始配置，示例，完整版随 schema 定稿）：

| 字段 | 所有权 |
|------|--------|
| 任务状态（含 blocked）、gate 决议、金样本确认、基线 | **人工专属，AI 禁写**（任务状态语义铁律：预警是提示层，不改状态机） |
| 延误原因分类、intake 类别、交付物参数抽取 | AI 建议 → 人批准 |
| 摘要类字段、标签、检索索引 | AI 直写，可回滚 |

**三级闭环**：`Review` → `Action Item`（遗留问题）→ `Task` 全程关联（飞书项目 IPD 的主打卖点；其客户效果数字为厂商口径，未经独立验证——功能方向可信，量化收益存疑）。

**管线（Pipelines）**：「NPD 阶段门管线」「设计评审排期」「文档受控发布」各自独立，对象进入管线产生 entry，流程属性不污染本体。模板双轨：IPD 版（DCP/TR/准出/PCR/CBB 术语原生）与轻量版（对应模板分档轻量档）。

### 2.3 Agent 层

| Agent | 期 | 职责 | 验证等级（v0.2 标注） |
|-------|----|------|---------------------|
| **书记员** | **M0** | 会议转写稿/评论流 → 决议/遗留问题/任务提案，回链片段 | 通用域已验证；**制造业 NPD 域无先例**（领域词表/图纸引用/保密是已知难点）——M0 的头号自测风险项 |
| **汇报员** | **M0** | 从事件流起草项目状态叙事/周报（带 citation + diff 留痕） | 多厂商已验证（ClickUp StandUp、Asana smart status 等） |
| **检查员** | M1-M2 | M1:交付物文档→检查项状态提案+关键参数抽取；M2:**例外优先的 gate 就绪度视图**（v0.1 误放汇报员） | 单点有先例（CoLab AutoReview）；gate 就绪度组合无先例 |
| **分诊员** | M2 | intake 分类、查重（建议式；准确率达标后按类型开 auto-apply） | 已验证（Dart 查重、Linear Triage、Asana intake） |
| **哨兵** | M3 | 事件流巡检:逾期、参数变更传播、跨项目复发 | 单点有先例（Instrumental 跨阶段记忆）;进入条件见 M3 |

**统一约束**：
- 每个 agent 动作 = 一次有权限、有审计的 API 调用（P10）
- **M1 只建一种审批形态**：单一 For-review 队列（Approve / Edit 两键 + diff 视图 + citation）。三档策略引擎、autonomy slider、AgentSession 六态状态机推迟到出现第二档自治需求时再建（v0.1 超配）
- guidance 分层注入：组织级/项目级 markdown 指引（评审规则、命名规范、禁区）随委派打包进 agent 上下文（Linear 模式）
- 项目经理的高频入口是 Agent Inbox（待裁决收件箱）

## 3. 关键交互

1. **For-review 收件箱是主界面**：进系统第一眼是待裁决队列，不是看板或表单。对象详情页的定位是「查证据 + 纠错」——**系统不为对象提供填表主界面**，人工直改字段是例外操作（留审计），不是日常路径。
2. **Workbench 而非 chatbot**：AI 长在对象的原生动作里——交付物页「预审」按钮（record command：人召唤 AI）、评审页「就绪度视图」。聊天只是入口之一。
3. **上下文自动注入**（Attio interests 机制）：助手自动知道用户开着哪个评审页/任务，回答无需粘贴上下文。
4. **Diff 式审核 + citation 一键跳转**：验证必须快于生成；每条 AI 结论点开直达源片段。
5. **报表是派生层的免费产物**：项目驾驶舱（阶段分布、gate 通过率、缺陷收敛/DI 值、逾期交付物）从对象层自动派生，M1 与周报同期交付最小版——买家（老板/PMO）用报表做判断；报表弱是 Attio 最持久的差评 | 配 SQL 直查逃生舱（A6）。
6. **AI 入口可按模块静默**（ClickUp 反例）；agent 带徽标（AIG）。
7. **动态检查单**：gate 检查项按项目类型/风险等级从资产库选配，不是 55 项全量铺开。
8. 速度目标务实化：常规 CRUD 快、列表不卡即可；命令面板/乐观更新/虚拟化是后续 polish。Declarative UI（回复渲染可点卡片）为增强项。

## 4. 架构决策

| # | 决策（v0.2 修订） | 理由 |
|---|------|------|
| A1 | **append-only 出处/审计事件表 + 常规关系表作为对象层权威**。不做事件溯源重建。「schema 变更回填」通过对存量原始工件（转写稿/文档/Excel）重跑 LLM 抽取实现，不靠事件重放 | 保住 P1/P7 的全部产品价值，去掉 90% 工程复杂度；2-5 人团队可维护 |
| A2 | 单一 API：UI/agent/集成同源，权限与审计在 API 层 | Duro 铁律 |
| A3 | 第一天只做两件事：全链路 trace/日志（prompt、输出、token 归因）+ 人工修正 diff 结构化落库。eval = golden-case 目录 + 跑分脚本（pytest 级），样例从 M0 真实修正中累积 | v0.1「第一天建 eval 框架」是伪需求——第一天无标注数据；修正 diff 就是 eval 集长出来的地方。v0.3 注：AI 在 M0 关键路径上，此纪律相应从 M0 第一周开始 |
| A4 | LLM provider 薄抽象 + 当前一个云端点。三形态部署（客户云/纯本地）标注为**商品化决策触发后**的条件项 | 军工离线对自用场景无意义；抽象接口保留可能性即可 |
| A5 | 连接器次序：CEHub + 转写稿上传（M0）→ 妙记导出自动化（M1）→ 公司在用的那一家 IM（M2）→ PLM 只读快照（按客户实施，商品化后）。对外 MCP server 为商品化条件项 | 采集面现实排序；书记员在 M0 需要转写稿输入（上传即可，自动化拉取后置）；PLM 连接器是服务成本 |
| A6 | 依赖传播/影响分析用确定性图遍历模块，独立于 LLM；报表配 SQL 直查逃生舱 | P9；Motion/Attio 验证 |
| A7 | 技术栈沿用现有（Next.js + FastAPI + PG）——A1 降级后无需为事件溯源换栈 | 团队熟悉度本身是速度 |
| A8 | 商品化形态下必须承诺 SLA 与事件层持久化保证；AI 计费并入席位价或实时用量面板，不做 credit 迷宫 | Attio 无 SLA 差评 / 三大平台 credit 集体踩坑（均为条件项） |

## 5. 差异化定位

**两个不同验证等级的断言（v0.2 拆分）**：
- **Gate 评审就绪度/材料装配**——本轮全网扫描（中外）未发现任何厂商实现或宣称（扫描口径，非穷尽证明）。这是最锋利的点。
- **状态自动生成**——通用域已被广泛实现（ClickUp/Asana/Motion/飞书 AI 助手），NPD 执行层无原生产品化；客户自建案例（雅迪「IPD 智能项目助手」）反证需求真实。我们做的是已验证用例的**领域化**，不是发明。

**M2 旗舰交付物的正确形态**：不是「更快拼出更厚的材料包」，而是**例外优先的 gate 就绪度视图**——默认展示缺项、风险、有条件通过的遗留项、与模板基线的偏差；完整材料包是按需展开的附属物。验收指标：gate 会议时长/材料页数下降（rnd-domain 警告：AI 若用来更快生产 gate 文档，只会加速官僚化）。

**缝隙选择与防守（v0.2 新增）**：调研给出中国市场三条缝隙——①AI PMO 原生产品化；②服务不用/不能用飞书体系的客户；③项目层与交付物内容/试产数据的深水区连接。**主打缝隙③、以①为表现层**：这是飞书项目（做底座不做场景）与流程审批引擎玩家（Sopheon 20 年未下沉）都进不来的地带。防守逻辑：若飞书把 AI PMO 原生化（大概率快于我们走完 M0→M2），我们的壁垒在领域数据模型（双轨评审/PCR 回退/交付物参数化）+ 组织记忆语料（评审意见、延误原因、条件项闭环）——这些沉在客户数据里，不可被平台功能复制；采集集成随时可换宿主。

**窗口期对照**：执行层空窗的窗口期**估计** 12-24 个月（依据 Teamcenter BOM agent 已能监督下多步执行、PLM 大厂正向上爬；属推测非承诺）。这要求 M0+M1 合计不超过一个季度量级——达不到就继续砍范围，优先级：事件层+汇报员+书记员 > 一切。

**护城河的准确表述**：飞书项目有协同无领域模型；华为 IPDCenter 有 IPD 领域模型但无协同与 AI——「领域模型+协同+AI 装配」三者兼备的产品不存在，这才是护城河所在。现有资产直接转化：325 份交付物模板 = 检查员检查项语料（M0 结构化工作项）；CEHub 流程实践 = procedural 记忆种子；金样本纪律 = For-review 留痕治理框架。

## 6. MVP 分期（v0.3 重排：AI 从 M0 进入关键路径）

> 前置门槛：决策清单 0-3 拍板。v0.2 曾把 M0 设计为「零 LLM 骨架」——那是 AI 赋能路线，已按用户定调废弃。

**M0 · 派生闭环**（AI-native 的最小完整循环，目标:数周而非数月）
- **燃料**：事件表 + CEHub 事件连接器（拖尾 activity_logs + comments，镜像 users/projects/tasks）+ 会议转写稿上传入口
- **派生**：书记员雏形（转写稿/评论流 → 决议/遗留问题/任务提案）+ 汇报员雏形（事件流 → 项目状态叙事草稿），全部带 citation
- **裁决**：For-review 收件箱（Approve/Edit + diff + 引用跳转）——这是系统主界面，不是辅助功能
- **schema**：8 个领域对象（含 M3 语料字段）+ 检查项资产库导入（manifest 687 条）——对象没有填表主界面，字段由 AI 提案填充、人纠错
- **纪律**：LLM provider 薄抽象 + 全链路 trace/token 归因 + 人工修正 diff 落库（A3）从第一天
- 砍掉（v0.1 超配）：泛化元模型、自定义对象、命令面板级 polish、三档策略引擎
- **拆除测试验收**：关掉 AI 服务 → 系统不再产生任何新状态，只读

**M1 · 派生面扩大 + 最小驾驶舱**
- 检查员 v1：交付物文档上传 → 检查项状态提案（对照资产库）+ 关键参数抽取
- 带引用的工作区问答
- **PCR/ECN 创建时确定性影响清单**（纯图遍历零幻觉——制造业专属差异化；变更单本身也由 AI 从评审/会议中侦测起草，人确认立单）
- 驾驶舱：从派生层自动出（阶段分布、gate 通过率、逾期）
- 冷启动回填 v1：历史项目的 Excel/评审文档摄取，含验收标准（N 个历史项目、抽查合格率）

**M2 · 锋利点**
- 检查员 v2：**例外优先的 gate 就绪度视图**（默认展示缺项/风险/条件项/偏差，完整材料包按需展开）
- **装配输入契约**（启动条件，未就位则降级）：检查项状态←M1 检查员提案+人裁决；交付物关键参数←M1 抽取；测试数据←人工上传测试报告+AI 抽取（PLM 同步不是前置依赖）
- 分诊员：intake 分类与查重
- IM 事件采集（公司在用的那一家）

**M3 · 组织记忆**（进入条件：回填 ≥N 个完结项目且抽取质量验收通过）
- 哨兵：跨项目复发预警、参数变更传播提醒
- episodic 检索（「上次类似项目卡在哪」）+ 影响分析叠加 LLM（成本量级估计、历史类似变更召回）
- 自然语言规则（编译执行）；策略引擎/自治分档（若出现第二档需求）；PLM 只读快照

## 7. 工程风险与运维（v0.2 新增）

1. **IM 采集合规**：企微会话存档是付费接口且需员工逐人同意；飞书机器人需入群、历史消息拉取受限。选定 IM 后需逐条核对接口权限/费用/合规前提，并解决内部隐私治理（见决策 6）。
2. **会议采集**：不自建录音硬件与 ASR；M1 以转写稿文件为输入边界。中文领域词（扬程/气蚀/流量曲线…）的 ASR 与抽取质量是书记员的自测项，golden-case 从第一场真实评审会开始积累。
3. **运维负载**：语义索引+LLM 队列对 2-5 人团队的 on-call 成本要预算；目标可用性与降级策略明确为——AI 管道故障时系统退化为纯手工工具（即 §0 的退化态）。Attio 无 SLA 宕机丢数据是前车之鉴（商品化后必须 SLA，A8）。
4. **Token 成本**：回填与整列重算是烧钱大户。M1 上线前对汇报员/书记员/问答做每月 token 预算估算；trace 归因（A3）从第一天记账。
5. **采集即监控的组织接受度**：全量采集可能引发被监控感与规避行为（关键沟通迁出系统），掏空 Capture 分母。试点期把「工程师是否改变沟通行为」与 review fatigue 并列为观测项（见决策 6）。
