# PDOS · 完整目标架构 v1.1

日期：2026-10-08（v1.0：2026-10-02）  
定位：全新 AI-native 产品开发与 NPI 操作系统。  
性质：目标设计和实施依据，不是现有系统的增量改造、迁移方案或完成声明。

## 1. 核心架构决定

**产品/工程开发与制造导入两条主线，在每轮实物活动汇合；一套领域事实与证据内核，服务人员操作、确定性流程和唯一的 AI 执行者小Pai。**

系统贯通：品类研究/客户输入→立项提案→G0立项→产品定义→工程与制造策划→计划/资源→Build/样件→测试→问题/变更→试产→放行/移交→爬坡与产品反馈。

产品定义、配置、承诺、测试、制造能力和专业决定都是一等对象。任务、聊天、看板与报告是工作方式，不替代这些对象。

**品类是顶层对象和权限范围根**（v1.1）：品类 = 市场空间 = 产品线，存放该品类所有型号共用的知识、规格字典和成员权限；型号、立项提案、客户变体都挂在品类下，在品类内逐级收窄受众。

**只有一个 Agent：小Pai**（v1.1）：通过注册工具、MCP 连接器和渐进加载的技能包完成对话、页面动作、事件和定时工作；不设领域 Agent。Temporal 管理持久任务、等待、取消和恢复，LangGraph 管理小Pai 的推理循环和检查点，领域服务拥有业务事实与批准。

本架构从真实业务和理想体验推导；不以旧PDOS代码、表结构、目录、技术栈、合同编号、现有完成状态为约束。保留真实事实和必要责任边界，并不意味着沿用旧架构。

## 3. 名词控制

- 品类（Category）：市场空间 = 产品线 = 品类，三者是同一个对象。存放共用知识、规格字典、成员权限；汽车充气与自行车充气是两个品类。权限范围根。
- 型号（Product）：品类下持续演进的产品身份（界面称"型号"），不等于Project。族、系列只是可选标签。
- 平台（Platform）：独立于产品树的可复用技术底座，与型号多对多，记录兼容范围和版本。
- 立项提案（Proposal）：立项前唯一的交付物，一案一页，挂在品类下；含叙述、关键规格、方案对比、待决问题、风险和决策记录。
- 规格字典 / 参数版本（ParameterVersion）：品类内不可改的参数定义（键、名称、单位、方向、测试条件、方法、判据）；修订产生新版本。
- 规格条目（SpecItem）：提案与型号定义共用的结构，引用参数版本，记录值/上下限、单位、工况、验证方法、来源、条目状态和负责人。
- G0 / G1：业务关卡。G0 = 具名立项评审，G1 = 计划基线。与建设阶段 S0–S5 不同。
- Project：有真实目标、负责人和交付边界的开发活动；由 G0 批准后建立。
- Build：一次有目的、配置、实物、验证范围及处置的活动；不是任意任务分组。
- NPI：从早期制造可行性到工艺准备、试产、制造放行和爬坡的连续工作。
- 小Pai：系统唯一的 AI 执行者。对话、页面按钮、事件和定时都由它承担。
- WorkRequest：委派给系统的结果型工作；不强迫每次问答创建一条。
- 技能包（Skill）：由工具、数据语义、使用原则三要素组成的版本化配置，渐进加载；附带治理元数据（输入/输出、上下文、证据与失败政策、预算、评测、负责人）。
- AutomationRule（自动化规则）：有触发、技能包、授权工具、目标、停止条件和资源上限的持续工作义务。v1.0 中的 Loop 统一改称 AutomationRule。
- MCP 连接器：经管理员准入、按技能包或自动化规则逐项授权的外部系统工具来源。
- ConfirmationBatch：T1 候选的确认批次（v1.0 称 ProposalBatch，为避免与立项提案混淆而改名）。
- T0/T1/T2：受控自动写入 / 一次实质确认 / 具名专业或业务决定。只读是READ，不与T0混同。
- S0–S5：新工程的建设阶段编号（v1.0 称 G0–G5）。

## 4. 使用原则

产品与业务语义优先于框架便利；所有页面和AI入口共用同一领域命令。机器可读契约与正文冲突时，不允许编码Agent静默选择，需要修改成一致版本。

本包默认用于独立新工程。没有授权删除旧代码、覆盖数据库、向客户发送信息、将业务材料送到外部模型或部署生产。本文件也不宣称任何模型、规则、生产工艺已经通过真实资格验证。

文中数字、操作目录和验收用例是设计，不是工厂现有测量结果。官方资料核验日期为2026-10-02（v1.1 补充来源核验于 2026-10-08）；竞品营销效果不作为收益承诺。

**设计变更纪律（v1.1）**：本稿冻结后，设计变更只能通过用户确认的决策记录。切片施工合同、波次合同只能细化本稿，不能把规则加严或扩大范围（例如把"最小必要来源读集"改成"完整闭包每步重证"、把请求大小上限改成业务上限、自加时间窗）。确需加严时，先提决策记录。

# 01 · 产品、生命周期与总体架构

## 1. 系统要完成的工作

系统不是帮助员工“把事情记录得更多”，而是减少重复输入、资料查找、跨部门追问、状态维护和无意义确认，并使真正需要专业判断的工作具有正确资料。

面向消费电子的自主品牌、OEM、ODM、平台派生、降本、质量改进、客户变更、制造转移和认证相关开发。完整目标包含产品管理、研发协同、项目管理、NPI和开发期质量，而非仅提供一个项目驾驶舱。

### 六个始终可回答的问题

我们为什么做；明确要做什么；实际做出了什么；验证了什么且适用于哪里；是否能在目标场地稳定制造；谁需要对下一步作出决定。

## 2. 全生命周期

| 工作域 | 输入 | 业务结果 | AI应承担的工作 |
|---|---|---|---|
| 品类研究与立项 | 客户需求、竞品、渠道、评论与退货、质量反馈 | 品类知识、证据、立项提案（叙述、关键规格、方案对比、待决问题、风险、决策记录）、G0 决定 | 公开研究、同口径对比、价格带与痛点、方案起草、规格骨架、缺项与冲突维护（研究方法以技能包执行，v1.1） |
| 产品定义 | G0 固定的立项版定义、约束、平台资料 | 版本化型号定义（规格条目引用参数版本）、验收要求与范围；规格冻结 | 抽取、匹配、差距分析、定义编排、专业缺项提示 |
| 投入与项目启动 | G0 决定与触发物（提案、客户需求或父型号）、可行性、成本/供应假设 | 真实项目、职责、目标、计划候选；待决问题转为任务或风险 | 生成类型适配的工作包、依赖、所需专业和验证 |
| 工程与制造策划 | 产品要求、接口、风险 | 工程配置与制造准备方案 | 跨专业一致性、影响、资料接续和缺项管理 |
| 实物与验证 | 配置、物料、工装、规程、样件 | Build、TestRun、原始数据、明确结果 | 交接、解析、关联、异常分流、复验资料准备 |
| 变更与迭代 | 失败、客户修改、供应变化 | 新版本、受影响范围、实施与验证 | 双线影响、方案整理、回归验证候选和跟进 |
| 试产与制造放行 | 产品和制造基线、人员/线体、验证证据 | 试产结果、整改、范围化放行和移交 | 准备度、良率口径检查、发布包与遗留追踪 |
| 爬坡与产品维护 | 现场结果、客户反馈、成本差异 | 改进、知识候选、生命周期决定 | 复发识别、跨产品适用性、改进和经验回流 |

## 3. 产品研发和NPI并行

产品主线：需求→结构/硬件/固件/接口→工程配置→验证→工程发布。

制造主线：制造可行性→工艺/供应策划→模具/治具/设备→试模/试装→试产→制造放行→爬坡。

Build同时引用两条主线的适用配置，并产出实物和证据。项目阶段与Build不是一一对应；多个Build可并行，范围明确，资源和样件不能重复占用。纯研究和非实物分析不强制建立Build。

NPI从产品定义就参与。制造风险越早识别越有用，但不要求概念阶段拥有已发布的全部SOP和量产参数；成熟度要求按活动目的和不可逆投入逐步提高。

## 4. 三个入口与轻重路径（v1.1 改写）

三个入口都落到同一种立项提案上；立项前只回答四个问题：值不值得做、做成什么样、走哪条路、还有什么不确定。唯一业务关卡是具名 G0 立项评审（§03.14）。

| 入口 | 输入 | AI（小Pai）先做 | 人做 |
|---|---|---|---|
| 客户需求（含 ODM、OEM） | RFQ、客户规格书、图纸、邮件、客户设计包 | 逐条抽取需求并标出原文位置；与现有型号、平台比出差距；起草立项版定义；列出待问客户和专家的问题 | 确认理解、选路线、决定是否立项 |
| 自主新品 | 想法或细分，加链接、导出数据 | 公开研究：竞品同口径对比、价格带、评论痛点；起草 2–3 个定位方案和立项版定义 | 选方案、做关键取舍 |
| 派生迭代（产生新型号或新变体） | 一个现有型号，加上改动说明 | 以原型号已发布定义为基线，起草规格、BOM、认证、模具差异 | 确认改动范围和影响 |

- 研究期间不建项目；不同方案可以放弃，不留下虚假的研发项目。
- 只有真实开发工作才建项目：G0 批准后由触发物（提案、客户需求或父型号）建项目。标准品匹配不建项目。
- OEM 不重做客户已经决定的市场策略，但要把客户设计包转成可受控的内部输入和适用版本。
- 客户商业沟通和报价留在 CRM（GoodJob），PDOS 不另建销售漏斗；不需要开发的标准品询价不进 PDOS。
- 客户资料只挂在对应提案或变体上，权限收窄到相关人员；沉淀到品类必须经人工去标识（§02.3a）。

### 同一型号的修改和持续工程

同一型号在项目内的修改走 ChangeRequest，不重新立项。涉及独立投入、跨项目资源或显著范围改变时，创建真实项目或受控项目工作包，条件由版本化项目类型政策决定。派生出新型号或新变体时，走上表的"派生迭代"入口。

| 产品经理 | 品类、立项提案、我的工作 | 用户价值、要求取舍、立项提案与产品定义、产品路线 |
| 项目负责人 | 项目现在、计划、交接 | 依赖、承诺、资源、跨方推进与项目取舍 |
| 技术/结构/硬件/固件 | 工程工作包、配置、问题 | 专业设计、接口、变更内容和技术验证范围 |
| 工程/模具/自动化/治具 | 制造准备、试模与设备工作 | 工装/设备/模具技术状态与改进 |
| 生产 | Build执行、试产、交接 | 实际过程、产出、现场异常和制造接收 |
| 品质/测试 | 待接收、测试、验证与质量问题 | 方法、数据、判定、独立验证与质量处置 |
| 采购/供应 | 承诺、齐套、替代与异常 | 外部供应事实、采购协调、交期和适用资格 |
| NPI协调职责 | 制造准备、试产和放行 | 制造导入协调和跨专业接续，不替代品质签核 |
| 管理层 | 组合、决定、产品与资源 | 投入、优先级、重大承诺和适用批准 |

一个人可兼任多个职责，权限不因岗位名称自动扩大。没有独立工艺部门时必须明确工艺职责承接人；不能省略工艺工作，也不能虚构一个已就位的PIE/PE。技术发起试模、工程负责模具/工装、生产实际执行、品质验证的工作边界保留。

## 6. 前台信息架构

全局：**我的工作｜项目｜组合与资源｜知识**（确认稿 P15）。品类与立项提案不是平级主干，改为按品类产品管理权限显示的"产品管理"分组；对有该权限的人仍是常驻入口，对其他岗位不出现，立项结果只以项目属性里的"触发物"呈现。默认落地屏仍是"我的工作"。小Pai常驻（右侧对话，可放大）且对所有岗位开放，从哪一屏打开就带那一屏的范围与相应技能包；能读能写什么由本人权限与当前范围决定（§06.5）。管理设置和运行治理在二级入口。

品类（v1.1）：品类列表 → 品类页 → 提案页或型号页。
- 品类页：直接显示共享知识（用户与场景、竞品库、用户声音、法规认证）、规格字典、型号列表和品类矩阵视图；"立项提案"入口打开当前品类的小Pai对话，已有提案在辅助弹窗中查找。
- 提案页：一案一页，主位是叙述和关键规格；证据、竞品对比、用户声音、方案对比、待决问题、决策记录都是同一文档的视图；右侧是小Pai；只有一个"提交 G0 立项评审"关卡。
- 型号页：定义版本、配置/变体、平台关联、项目与反馈。
- 不再设独立的研究、机会、实验、策略页面；对应方法由小Pai 以技能包执行，结果写进提案或以视图呈现。

项目：现在、工作与计划、Builds、工程与制造准备、问题与变更、评审与交接、资料。

专业跨项目队列是上述事实的保存视图，不再建设另一套事实数据库。例如品质队列聚合VerificationRequest和Handoff，不复制为“品质任务表”。

## 7. 三种体验，共用一个业务内核

**对话委派**：自然语言+文件+页面上下文，形成可恢复工作。

**就地办理**：当前对象里阅读、修改、确认、接收和决定，结果直接回到对象。

**主动执行**：事件或日程触发，完成后静默记录，只有需要动作的例外进入注意队列。

三种入口调用相同命令、权限与验收。对话不能绕过页面权限，页面也不应因为未使用AI而额外多一套流程。

## 8. 整体结构

```text
体验：用户工作空间 + 小Pai + 对象内协作 + 移动轻办理
                        ↓
工作：目标型委派、业务工作包、承诺、交接、决定、注意队列
                        ↓
领域：品类/提案/型号/工程配置/项目/Build/测试/NPI/品质/供应/发布
                        ↕
证据：原始资料、版本、关系、来源、适用性、权限与撤回
                        ↕
智能：小Pai（唯一 Agent）：上下文 → 计划 → 技能包/工具/MCP → 领域命令 → 结果复查
                        ↕
平台：持久工作流、身份、数据库、模型、存储、检索和连接
```

体验、工作、领域、证据、智能、平台是逻辑分层，不意味着六个微服务。正式状态由领域模块拥有，其他层使用投影和命令。

## 9. 产品体验的非目标

不是通用聊天软件、无限自定义数据库、任意拖拽流程搭建器，也不要求员工维护全部内部状态。不是替代CAD/EDA、实验室、ERP/MES作业，但必须完整管理开发期配置、制造准备、验证和移交。

范围边界不是“少做业务”；它防止同一库存交易、图纸或生产记录在两个系统产生互相冲突的权威版本。

## 10. 总体成效

关注同类工作主动操作时间、重复录入、有效结果交付、试模到验证等待、问题复验周转、变更漏项、试产成熟度和放行证据。AI调用次数、文字长度、页面数量和待办增长均不代表成功。

## 2. Category / Product（型号）/ Platform / Variant / Project（v1.1 改写）

**Category（品类）是顶层对象和权限范围根。** 品类 = 市场空间 = 产品线，一份身份、一套成员权限和生命周期。不同使用场景、测试工况或规格字典的产品分属不同品类，例如汽车充气与自行车充气。品类内不再设"产品线"层级。

**Product（型号）**是品类下的产品身份与长期演进记录，直接挂在品类下；族、系列只是可选标签。每个型号声明目标细分（可多个）和目标价，供品类矩阵视图计算。存量型号可以从 Excel 或规格书导入关键规格，标"导入，未复核"。

**Platform（平台）**是跨型号、跨品类复用的技术底座，不是产品树中的层级。平台与型号多对多（PlatformProductLink），记录兼容范围和版本。

**Variant（变体）**从型号派生，是明确的客户、地区或配置变体，包含差异范围而非无限复制产品。客户变体只对相关人员可见。

**范围与受众**：成员与授权（Grant）挂在品类上；型号、立项提案、客户变体、原件和研究快照都带 category_id，能挂在型号上的同时带 product_id。可见性在品类内逐级收窄，至少分为品类、私有（负责人与具名评审人）、指定受众三档。路由以品类为前缀（§08.6）。

**Project** 是开发活动，由 G0 批准后用触发物（提案、客户需求或父型号）建立，通过 ProjectProductLink 关联一个或多个明确型号/变体；每个关联绑定 G0 固定的立项版定义（型号定义 v1）和工作范围。禁止仅依靠同时填写product_id与project_id却不定义其语义。

仅研究、客户标准品匹配或一次问答无需项目。不存在虚拟项目/虚假负责人/假定客户批准。

## 3. 定义与规格

DefinitionRevision最小字段：稳定ID、category/product/variant范围、revision、status、用途、使用场景、要求、可测规格（SpecItem）、成本/市场约束、验收准则、排除范围、未知项、来源、父版本、来源提案版本（G0 生成 v1 时记录）、创建/发布身份和时间。

**SpecItem（规格条目，v1.1）是立项提案与型号定义共用的结构**：引用品类规格字典的参数版本（参数 ID + 版本），记录值类型、目标值或上下限、单位、允差、测试工况、判定/验证方法、适用变体、来源、条目状态（AI起草 / 已确认 / 待专家 / 未知）和负责人。键、名称、单位、测试条件来自字典；不同版本、单位或工况不当作同口径比较。原有自由键仅作兼容，逐步人工映射到字典。成本、售价、币种、数量假设、估算时点分别保存；缺值不填零。

**定义演进**：G0 批准时，由领域命令把提案中的立项版定义固定为型号定义 v1（记录来源提案版本）；项目内沿定义版本化继续迭代，完整规格与专业协审在项目内完成，规格冻结为 T2。专业协审按产品类型选择适用专业，可以标"不适用"并写理由，作者不能审自己。

PRD、Spec表格、PDF和对比视图都由这些结构化数据生成。客户原件保持不可变，翻译和AI抽取是派生结果，不替换原文。

研究观察、AI推断、已接受需求、已发布规格不是同一成熟度。设计不得只用一个confidence字段表达所有差别。

## 3a. 品类知识、规格字典与立项提案（v1.1 新增）

### 品类知识

品类存放该品类所有型号共用的知识，研究做一次、多个型号复用：
- **用户与场景**：细分、JTBD、购买标准、地区与渠道；
- **竞品库**：区分实测、宣传、推断、未知；报价注明口径（币种、日期、零售或促销、是否含税运）；
- **用户声音**：评论、退货原因，由 AI 归类并显示样本量；
- **法规认证**：按销售地区列出；
- **品类测试模板**：按规格字典生成同参数、同版本的测试项骨架；
- **品类矩阵**：计算视图（细分 × 价格带上的我方型号与竞品分布），不另存。

CategoryKnowledge 只追加、不改写；每条记录来源（`human` / `ai_draft` / `imported`）、状态和引用。纠正或撤回通过追加替代或撤回记录完成，保留历史。AI 草稿必须标为 `ai_draft`，不能记成人工来源。

### 规格字典

ParameterVersion 是品类内不可改的参数版本：稳定参数 ID、版本、键、名称、单位、方向（越大/越小越好）、标准测试条件、方法和通过判据。修订产生新版本，旧版本保留；旧条目由人工映射到新版本。缺项和不可比的条件保持"未知"，不补造测试标准或指标。

竞品指标、提案与定义条目、品类测试模板都引用同一参数版本，规格对标、定位图、品类矩阵因此可以自动生成。

### 立项提案

Proposal 是品类下独立版本化的文档，可以引用同品类型号或变体作为基线；创建提案不自动创建型号。内容：
- **叙述**：值不值得做（证据摘要：客户或市场信号、竞品与价格带、主要风险）；
- **立项版定义**：目标客户、市场、渠道；核心功能（含明确不做的）；10–20 条关键规格（SpecItem）；目标售价、成本、数量；认证与销售地区；上市窗口；
- **方案对比**：至少 2 个方案（可以包括"沿用现款"或"不做"），写明大致成本和周期；少于 2 个须写理由；
- **待决问题**（OpenQuestion）：每条有负责人和期限，G0 后转为项目任务或风险；
- **风险**与**决策记录**。

提案修订只追加；每条规格保留来源和条目状态。小Pai 以条目级命令编辑提案（T0 草稿，署 AI 名、可按运行撤回、不覆盖人工值），人可直接编辑。提案在 G0 提交时固定当版内容；品类背景以快照引用（逐条记录"对象 ID + 版本"），品类资料的后续修改不阻断在审提案。

### 客户资料边界

RFQ、客户规格书、客户特殊要求只挂在对应提案或变体上，权限收窄到负责人和具名评审人。**提案默认私有**；从对话创建的提案一律私有，改为品类共享必须由人显式选择。任何引用私有原件的提案都按私有提案限制读取，不进入共享的品类对标与矩阵。

要沉淀到品类，必须由人确认并去掉客户身份（例如"多个欧美客户要求 ≤75 dB"）。共享摘要不携带客户原文、文件名或原件链接；去标识的人和时间记入 PromotionProof，原提案回链只保留在私有证明里。

## 4. 派生与复用

派生采用固定父版本+显式覆盖：记录父定义/配置、覆盖路径、原因、来源与适用范围。父版更新时做旧父/新父/当前子版三方差异，不自动覆盖子项目。

**派生边界（v1.1）**：派生出新型号或新变体时走立项提案（派生迭代入口），以原型号已发布定义为基线列出差异，G0 批准后生成新型号或变体的定义 v1；同一型号在项目内的修改走 ChangeRequest。三方差异只保留一套实现。

**派生入口统一到 G0（确认稿 P23）**：可被定义 v1、项目或平台关联引用的变体身份只由 `proposal.g0.decide` 产生，并带该 G0 决定。`product.variant.derive` 只产生提案准备用的派生草稿：草稿变体不带 G0 决定，任何下游对象不得引用它，也不因此获得定义版本或项目范围。

允许复用的对象包括要求、平台模块、BOM子装配、测试规程、制造工序和知识；是否可复用由版本/适用性决定。跨客户共享还需要权限。

子项目成果回写平台通过独立的采用/发布动作。设计成功不代表平台已经接受；客户定制要求也不应无意成为全平台规则。

## 5. BOM与工程引用

研发BOM记录part、数量、单位、可选/替代关系、适用变体、版本和设计引用。内部研发编号、外部ERP料号、客户料号分别记录并有映射版本。

每条关键外部引用包含system、external_id、revision、as_of、content_hash或可验证源信息。只有“最新文件链接”不足以证明某轮Build采用的版本。

Part是物料/组件身份；Lot是实际批次；SampleUnit是实际单件样机；三者不能混同。关键件追溯粒度由风险与客户要求决定，不强迫每个非关键小零件序列化。

## 6. 两种配置与五个视角

工程配置：定义、BOM、机械/电子版本、固件制品、关键件和批准偏差。

制造配置：工艺路线、工序参数、模具/治具/设备、SOP、检验控制、包装标识、场地/产线和必要岗位资格。

五个视角：As-designed、As-planned、As-built、As-tested、As-delivered。它们是配置快照的用途和实际关联，不是五份会自动同步的最新版。

每轮Build固定计划配置；每个样件/批次记录实际配置和差异；TestRun固定实际测试对象、规程和条件；交付客户样件固定实际交付配置。

关键变化发生在测试中途时，按测试规程允许的分段记录或中止并新建Run，不静默改变原Run所代表的整体配置。无明确分段规则时选择新Run。

## 7. Build / Lot / Sample / TestRun

Build最少包含目的、类型、项目与产品范围、计划数量、时间、计划配置、验证目标、责任、前后轮关系和处置要求。

一个Build可有多批实际配置明确的BuildLot；混合配置必须拆分或逐件明确，不允许平均掉差异。

SampleUnit保存实际配置、来源批次/工序/模穴、保管/位置、去向、预约、破坏性消耗和可用性。样件资产记录仅为开发追溯，不扩展为完整仓储交易系统。

TestRun保存样件和配置、规程、设备/校准引用、执行者、环境、实际起止、读数、附件、异常、确定性判定与专业结论。

measurement、computed_result、professional_conclusion、ai_hypothesis必须区分。AI可以组织解释，不能填造实测值或冒充专业结论。

## 8. 工序与制造对象

ProcessRevision拥有有序Operation；Operation关联BOM行、关键特性、参数、SOP/检验版本、工具设备、过程风险与控制措施。

Tooling与ToolTrial记录模具/模穴及试模轮次；Fixture/Equipment记录适用版本、用途、验收/校准和资源可用性；PilotRun是Build的制造扩展，不是孤立试产报告。

制造基线发布固定工艺、工具、作业/检验指引、反应计划、包装及人员/线体要求。实际执行另记录实际工艺与偏差。

## 9. 五种事实性质与四种可用性

Claim性质：observed、extracted、computed、inferred、decided。

数据可用性：known、unknown、conflicted、not_applicable。not_applicable需要依据；缺失不自动变不适用。来源是否过期/撤回是另一个维度。

EvidenceReference指向原文件版本及页/段/单元格/图片区域，或确定性领域记录版本。哈希用于内容身份，不证明内容真实性；仍要有来源、作者/系统和核验语义。

事实发生时间、系统接收时间、业务有效时间分别记录。延迟收到的报告不可篡改真实执行时间。

## 10. 证据适用性

ApplicabilityAssessment绑定：证据/测试版本、目标配置与用途、差异、采用规则、适用条件、判断人/引擎、有效期和撤回原因。

旧测试结果能否用于新电机、新固件、新工艺或新产线必须经过适用性评估。语义相似仅产生候选线索；不能自动成为“已覆盖”。

源记录失效或撤回后，关联投影和待执行工作需要失效传播。已发生的历史决定保留，但它对当前新操作是否仍适用应重新判断。

## 11. 工作对象与注意队列

Task是实际工作；Decision是决定；VerificationRequest是验证请求；Handoff是责任接续。不要为了统一看板将其全部压成Task。

AttentionItem是这些对象的只读聚合/排序投影，存原因、来源、负责人和有效期，不产生第二份待办真值。完成领域工作后注意项自动更新。

WorkRequest表示用户委派给AI/系统的多步目标。结果标准放在outcome_spec中；不额外创造一个无人维护的Outcome模块。

ConfirmationBatch（v1.0 称 ProposalBatch）用于T1候选，包含可独立选择的组、组内原子性、依赖、版本、证据和期限。它不是所有AI输出的强制载体，也不是立项提案。

## 12. 身份、责任、执行与决定

human_owner、writer_principal、requester/trigger、approver、verifier、receiver是不同字段。

AI可以是writer，不能因此成为测试执行者或专业批准人。任务被分派不等于负责人接受承诺；一人兼岗不自动豁免必要独立验证。

人员休假、离职、委托应有作用域和生效期；允许合法移交并记录原因，不用通用管理员身份补造业务责任。

## 13. 数据所有权与外部系统

PDOS拥有开发定义、研发计划/配置、验证和NPI准备、决定与移交状态。ERP拥有库存/采购/正式核算和实际物料生效；MES拥有生产执行；CAD/EDA/Git拥有专业原始制品；CRM拥有销售管道。

已有PLM/QMS等权威对象时，通过绑定策略选择原生管理或外部引用，同一对象同一阶段不允许双方无规则双写。未连接系统可用真实人工导入；未知字段明确标出，不能把未连接当成已完成。

## 14. 核心不变量

I01：业务字段有唯一权威所有者。
I02：每个项目产品范围绑定 G0 固定的立项版定义（型号定义 v1）及其后续有效版本（v1.1 修订）。
I03：发布/冻结内容不可静默修改。
I04：计划配置与实际配置不得互相覆盖。
I05：TestRun必须绑定真实测试范围。
I06：原始测量与AI解释分开。
I07：复用证据必须适用于目标配置和用途。
I08：预测、基线、承诺、实际分开。
I09：制造、工程、客户与外部接收分开。
I10：AI使用受控命令而非任意表写入。
I11：T0成功不自动产生人工待办。
I12：T1只确认真实载荷和目标版本。
I13：T2不授予AI决定权。
I14：共享输出不能突破来源/目标受众权限。
I15：业务、审计、Outbox在同一事务提交。
I16：重复意图不产生重复有效副作用。
I17：删除/撤回不能抹去受控历史或下游消费事实。
I18：外部结果未知不等于失败可重发，也不等于成功。
I19：缺失、冲突、不适用和失败不能混为一类。
I20：软件测试通过不代表制造或模型真实资格通过。
I21：品类是权限范围根；所有品类内对象的读写都在品类成员权限内，再按对象受众收窄（v1.1）。
I22：客户私有资料不进入共享品类知识、对标和矩阵；沉淀到品类必须经人工去标识并留证明（v1.1）。
I23：AI 写入署 AI 名、记录运行，可按运行撤回；AI 草稿不能记成人工来源（v1.1）。
I24（v1.1；P26 修订，2026-10-18）：出站不以服务商签约登记为前置；每次出站的服务商与数据类别在服务器端按当前 Run 绑定判定并记入运行回执；租户登记了当前有效服务商数据协议的，按"服务商 × 数据类别"作限制执行，未登记不阻断。

# 03 · 工作、状态、时间与决定

## 1. 三套状态各有所有者

领域记录状态表示实际业务；持久工作流状态表示系统在等待什么/何时继续；Agent步骤状态表示一次智能执行到了哪里。三者以稳定ID关联，不互相覆盖。

不能把LangGraph的interrupt当成已批准的工程决定，也不能把Workflow completed当成Build测试通过。

## 2. 项目生命周期与阶段政策

项目生命状态建议：draft、active、on_hold、completed、cancelled、archived。阶段采用独立StageInstance，模板可配置Concept/Planning/Design/EVT/DVT/PVT/MP等，不硬编码所有项目走完全相同路径。

模板规定进入条件、交付成熟度、责任、验证/评审与允许例外；不是按日历自动推进的检查表。OEM、派生和小改有不同路径，但同类专业决定的语义一致。

阶段推进只引用真实成果和适用决定。一个Build失败不必把整个项目状态重置，多个Build并行也不强迫项目同时处于多个矛盾状态。

## 3. 核心状态契约

| 对象 | 主状态 | 重要边界 |
|---|---|---|
| Proposal（v1.1） | draft→in_review→approved / returned / rejected / withdrawn | 提交 G0 时固定当版；returned 可修订后重提；approved 触发型号定义 v1 与项目建立 |
| ProposalDecision（G0，v1.1） | 一次性具名决定：approved / returned / rejected | 不可改写；撤回以追加撤回记录完成并说明对已建项目的处理 |
| DefinitionRevision | draft→in_review→released→superseded/withdrawn | 发布固定版本；撤销不删历史；规格冻结为 T2 |
| WorkRequest | accepted→running→waiting_input/decision/external→completed | completed需outcome_spec满足或明确部分结果处置 |
| Task | proposed→assigned→accepted→in_progress→submitted→completed | 分派、承诺、完成验收分开；简单任务可按模板合并展示 |
| Build | draft→preparing→authorized→executing→evaluating→closed | authorized只覆盖本轮批准用途，不是量产放行 |
| VerificationRequest | draft→offered→accepted→scheduled→executing→reported→disposed | 接收/承诺时间/实际开测分别记录 |
| TestRun | planned→running→results_pending→reviewed→disposed | pass/fail/invalid为结果维度，不混入执行状态 |
| Handoff | preparing→offered→accepted→in_progress→returned→closed | 可partial_return；接收拒绝保留缺项理由 |
| Issue | open→triaged→actioning→awaiting_verification→closed | 高风险关闭按独立验证政策 |
| ChangeRequest/Order | draft→analysis→review→approved→implementing→verifying→closed | 批准、实施、生效、有效性分开 |
| Review | preparing→ready→in_review→decided→superseded | 人工决定绑定固定ReviewPackage |
| ReleasePackage | draft→assembled→reviewed→released→superseded/withdrawn | 新内容形成新版本 |
| ExternalHandoff | prepared→authorized→sent→acknowledged→reconciled | delivery_unknown和rejected独立处理 |
| AutomationRule | draft→active→paused→retired | 版本化规则；暂停停止新运行 |
| Run | queued→running→waiting→succeeded/partial/failed/cancelled | succeeded不能替代业务验收 |

所有状态迁移还受目标版本、来源有效性、对象权限和用途约束。界面可简化显示，但后台不能伪装已经发生的步骤。

## 4. 结果型工作契约

WorkRequest至少包含goal、subject_scope、outcome_spec、due_window、accountable_owner、authorization、budget、inputs、source_version和stop_condition。

outcome_spec列出必须产生的对象、有效性条件和可接受的部分结果。例如“形成品质可接收试模包”需要样件/配置/要求齐套，不是生成一段摘要。

正常问答不产生长期工作对象。连续跨步骤、有等待或需要复查的委派才形成WorkRequest。UI统一工作卡，内部步骤不膨胀成用户待办。

## 5. 时间真值

Baseline：批准的计划版本。
Forecast：依据当前输入计算的预计时间，可自动更新。
Commitment：明确由某主体对某接收者作出的承诺及其范围。
Actual：真实事件发生时间与来源。

四者分开版本化。计划预测改变不自动改变承诺；用户页面必须看见差异。所有时间存UTC与原始时区/日历引用，按工厂/人员/供应方工作日历显示和计算。

估时保存范围、剩余量、来源和可信程度。信息不足时输出未知/区间；不得为画甘特图而虚构精确工时。

## 6. 承诺与外部等待

ExternalWait包括等待对象、请求内容、发起/有效送达、对方承诺、下次检查、是否阻塞、对应里程碑/Build、最新回复与关闭条件。

升级算法以有效送达、工作日历、承诺及下一检查点为主，提醒次数仅用于节流。无送达证据不能认定对方已开始承担响应时钟。

责任转交先建立接收请求，接受后改变责任；不允许自动改负责人后宣称旧负责人已卸责。紧急代理按显式授权和时间范围处理。

## 7. 准备度是一组规则而不是AI分数

每条规则：id、version、scope、applicable_if、predicate、required_evidence、freshness、severity、responsible_role、waivable、allowed_purpose。

维度至少分产品/验证、制造、交付适用性。常见结果：满足、不满足、未知、冲突、不适用、有效例外。

聚合优先级：

1. 未被有效允许覆盖的硬阻塞→BLOCKED；仍展示同时存在的未知。
2. 无硬阻塞但有必需未知/冲突/过期→UNKNOWN。
3. 必需条件存在有效限定例外，其余满足→READY_WITH_CONDITIONS。
4. 全部适用必需条件满足→READY。

风险预警和完成比例是其他投影。高分不能抵消硬阻塞。

**项目健康度（确认稿 P17）**：健康度是上述规则结果的投影，由硬阻塞、必需未知、承诺超期、临近冻结点未决按固定优先级映射为四档（正常 / 有风险 / 有阻塞 / 待批准），与门禁聚合同源，可下钻到产生它的规则。它没有人工可改字段，模型不参与计算；不得以健康度抵消硬阻塞，也不得作为门禁或放行依据。算不全的档位留空，不退回人工填写。

## 8. 未知与受控探索

早期试验可以在限定用途下允许未知，但要创建明确的试验范围、风险控制和可执行限制。这是“允许为解决未知而做试验”，不是把未知标成已通过。

非可豁免条件不能通过通用例外绕过。制造放行/客户交付的规则与内部探索试验的规则不同，审批必须绑定用途。

## 9. 冻结点与不可逆投入

FreezePoint不仅是阶段末Gate，还包括ID/结构冻结、开模授权、长交期采购承诺、认证样机冻结、客户承诺和制造发布。

每个冻结点明确：冻结什么、适用版本、用途/数量/金额或范围、批准主体、依据、变更策略及下游消费。

系统可自动准备冻结包和识别未解决项，但不能把“任务完成”当成投入授权。已跨冻结点的变化自动进入影响评估，不静默重写冻结内容。

## 10. 决定、确认与批准

READ无写权。T0是受控自动写；T1是一次实质确认；T2是专业/业务决定。

T1确认绑定候选载荷、独立原子组、当前目标版本和最小必要来源读集。可以选择独立组；组内依赖项不可随意拆开。版本变化只重新呈现真正受影响差异，不全流程重来。

T2由有权人员发起领域命令；后台服务可执行已批准发送/发布的确定性步骤，AI不因此得到签核身份。

已批准的高风险决定需要独立复核时保留真实人员独立性，不为统一UX把多方专业责任合成一次按钮。

## 11. 四种放行及接收

工程发布回答“设计可用于什么”；制造放行回答“哪个场地/产线可以在什么范围制造”；客户承认回答“客户接受了哪个版本及条件”；市场/认证适用性回答“相关要求和证据适用于哪个交付范围”。

ERP/MES接收与实际生效是外部执行事实，独立于上述决定。

每个决定保存subject_config、release_scope、purpose、limits、evidence_digest、policy_version、signers和expiry。原件改变形成新候选；不覆盖历史签核。

## 12. 失效和撤回

来源撤回或配置改变后，系统重新判断相关决定当前是否适用；对新的受约束动作阻止不适用执行。历史确实发生的批准仍可查，不改写过去。

**签发人资格在签署时固定（v1.1）**：决定或确认按签署当时的资格成立。签发人之后资格被撤销，只把相关对象标为"待复核"，并拦截基于它发起的新受约束动作；不实时传播到所有下游，也不在每次读取时重核签发人资格。

运行撤回使用补偿记录。人工后续编辑、下游引用、正式发布消费或不可逆外部结果不能强制级联撤销，需列明未撤回项和处理理由。

取消运行持久化cancel_epoch；后续命令在开始和提交前检查。已经发出的外部动作需对账，不能因为UI显示取消就假装外界动作没发生。

## 13. 模板体系

分别版本化项目类型、阶段、工作包、验证、制造准备、评审、自动化及UI保存视图。模板复用相同业务对象，不能派生另一套隐形状态机。

模板更新对在途工作生成差异，不自动覆盖实例。允许配置是否适用、角色映射、阈值和顺序；不允许模板脚本绕过授权、原始数据和正式历史约束。

## 14. G0 立项评审（v1.1 新增）

G0 是立项前唯一的业务关卡，属于 T2 具名决定。

- **提交**：提案负责人提交，选择一名具名评审人。评审人必须有该品类的产品管理权限，**非试点时不能是提案负责人本人；当前有效试点允许负责人本人具名评审**（2026-10-22 确认稿 P27；领域层和数据库共同检查，界面按当前试点事实列候选人）。提交时固定当版方案、取舍、待决问题和风险。
- **评审内容**：值不值得做、做成什么样、走哪条路、还有什么不确定。未知项可以带入项目，但评审人必须为每条记录处理安排（负责人与期限）。
- **决定**：approved / returned / rejected，附理由。决定不可改写；需要撤回时追加撤回记录，并说明对已建项目的处理。
- **批准的结果**（同一领域事务内，或经 Outbox 驱动的后续命令）：
  1. 固定立项版定义为型号定义 v1（新型号或变体时先建立型号/变体身份）；
  2. 用触发物（提案、客户需求或父型号）建立项目，绑定型号定义 v1；
  3. 把待决问题转为项目任务或风险，保留负责人和期限。
- **G0 不产生**：规格冻结、专业签名、BOM 批准、客户承诺。这些在项目内的概念与计划阶段完成：细化完整规格 → 按产品类型做适用的专业协审（可标"不适用"，作者不得自审）→ 规格冻结（T2）→ 定义转需求 → G1 计划基线。

# 04 · 专业工程与NPI完整契约

## 1. 专业工程不是附件目录

| 专业 | 管理的开发事实 | 与其他域的接口 |
|---|---|---|
| ID/CMF | 设计简报、方案、外观反馈、色材工艺、样板与版本 | 结构边界、表面工艺、包装及客户承认 |
| 结构/机械 | 图纸/模型引用、材料、尺寸/公差、接口、装配和模具要求 | 电子布置、散热、工艺、检验与可靠性 |
| 硬件/PCBA | 原理图/PCB/关键器件引用、电源/电池接口、保护与验证 | 结构/热、固件版本、测试工装与供应 |
| 固件/嵌入式 | 制品与源码版本引用、功能/参数、兼容性、刷写与回退 | PCB、显示/传感器、测试版本与生产配置 |
| 品质/认证 | 验证矩阵、方法、设备、原始结果、适用条件和批准 | 产品定义、样件、变更及交付范围 |
| 工艺/NPI | 工艺路线、参数、SOP、工装设备、防错和试产证据 | 设计/BOM、供应、人员与制造接收 |

系统不编辑CAD/EDA源设计，不直接控制设备；管理准确版本、输入输出、接口、验证和责任。

## 2. InterfaceContract

接口可能是机械尺寸、供电/电流、热边界、通信协议、连接器、固件兼容、测试方法或制造定位。

记录参与模块/专业、约束、单位、版本、负责人、确认状态、验证方式和受影响项。变更通过关系传播，不依赖每次让AI从所有文件重新猜测。

例如充气泵电机替代可能影响电源保护、驱动参数、温升、结构定位、噪声、治具和测试规程；系统先显示显式依赖和规则推导，再列AI待核实线索，不能混成确定结论。

## 3. 制造基线

ManufacturingBaseline固定以下适用对象：ProcessRevision、Operations、Tooling/Fixture/Equipment版本、关键参数、WorkInstructions、Inspection/ControlPlan、过程风险、人员资格、包装/标识和产线范围。

它与EngineeringConfiguration联结但独立版本化。同样产品配置在不同产线或工艺下制造，需要判断过程证据是否仍适用。

## 4. 制造工序

Operation最少包含顺序/前后置、输入输出、关联BOM项、资源、关键特性、参数和允差、检验/测试、反应计划、SOP版本、过程风险、节拍/采样来源和责任。

需要表达并行、返工和检验分支时采用受控流程图；不强迫全部线性。工序步骤不能自由执行脚本修改业务状态或生产设备参数。

DFM、DFMEA/PFMEA、控制计划、8D等方法按产品风险/客户要求选用，不自动给所有消费电子项目增加不适用的行业表单。

## 5. 模具与试模

Tooling包含零件、版本、供方、模穴、进度、限制、验收和生命周期；ToolTrial记录本轮目的、试次、模具状态、材料、实际参数、样件/模穴、问题、整改和承认。

技术可发起试模；工程组织模具/设备/治具条件；生产执行和记录实际参数；品质准备方法并验证；技术/工程按归属整改。NPI/项目协调人追踪交接而不是代签。

**术语消歧**：试模T0/T1是试次，AI写入T0/T1是自主级别。数据分别使用`trial_round`和`write_tier`；界面自主级别显示“自动/一次确认/具名决定”，避免混淆。

## 6. 试模前的品质准备

试模发起时同步形成VerificationRequest：图纸/特征、判据、样件数量/模穴、材料、规程、设备、预期时点与返回形式。

品质可提前确认方法可用性和暂定时段。暂定预约不同于已接受实际交样；正式资源占用按资料/样件准备和约束政策确定。

资料不齐不必阻塞所有并行准备；仅阻断受其影响的验证。允许先做明确适用的部分试验，覆盖范围显式记录。

## 7. 试模后交接

必须分别记录：request_created、sample_ready、documents_complete、offered、accepted、promised_start、actual_start、preliminary_result、final_result和disposed。

生产记录实物就绪，资料owner补齐资料，品质正式接收并承诺窗口，设备和人员影响排程。AI检查差异、整理交接包、提示阻塞与跟进，不代替任一真实事件。

品质可以退回缺项或接收部分明确样件；系统记录原因及下一责任人，不让双方在聊天中反复追问。返回部分结果时明确测试项/模穴/样件覆盖与未完成项。

## 8. 工装、设备和测试资源

Fixture/Equipment保存用途、适用产品/工序/版本、验收、校准/维护、数量、能力和时段。实体是否存在与是否适合本轮验证是两件事。

Reservation校验设备、人员资格、工装和样件可用性。破坏性测试消耗实际样件，不能重复使用“测试任务还在列表”作为实物可用证明。

外购电池Pack等模块可按外购组件管理其配置/批次/供方证据，不要求虚构内部电芯设计BOM。需要下钻时通过有来源的供方资料。

## 9. 试产

PilotRun引用Build、实际产品配置、制造基线、产线、人员、物料、工装设备、实际参数、首件结果、投入/产出、返工/报废、异常与处置。

首次通过率与最终合格率分开，分母和统计范围固定。相容批次才可汇总；百分比不直接简单平均。批次状态需要核对合格、报废、待判、返工中等互斥口径，避免重复计数。

节拍、工时、产能和过程统计保存采样范围及条件。不充分样本只呈事实和不确定性，不自动宣布长期过程能力达标。

AI可组织缺陷分布和可能关联、生成整改候选、追踪复验；不能补填缺失产出或把某一次高良率当作制造成熟证据。

## 10. 供应、齐套和成本

MaterialDemand由Build配置/数量产生；供应事实分需求、供方承诺、在途/库存快照、实际可用与质量限制。供方承诺到货不等于已齐套。

AlternateQualification绑定可替代范围和验证，不允许模型因参数相近直接替料。长交期投入前明确配置、费用/数量、取消影响和批准范围。

CostEstimate记录BOM、工艺、报价、币种、时点、数量和损耗假设。确定性引擎计算，AI解释敏感项与降本路径；估算不替代ERP正式成本和财务批准。

## 11. 三种成熟度与用途范围

产品验证成熟度、制造成熟度、交付适用性独立显示。每轮活动按目的选择规则：探索试验、工程样机、客户样品、认证样品、试产、制造放行。

早期允许在受控范围内解决未知；不能为了“让流程通过”降低最终交付规则。关键治具未验收、方法无效或必需证据过期时，不用其他项目高分抵消。

## 12. 客户样品和承认

CustomerSampleDelivery绑定实际样件与配置、资料版本、用途、数量、收件方、外发授权和回执。客户反馈先作为来源事实，再区分意见、变更要求、条件承认和正式承认。

客户承认、内部工程发布和制造放行各自办理；客户接受外观不意味着性能/法规/制造全部通过。系统必须显示承认覆盖了什么，没有覆盖什么。

## 13. 变更：同时穿透产品和制造

显式路径示例：Spec→Part/BOM→EngineeringConfiguration→Build/Sample/Test。

制造路径：Part/Interface→Operation→Tooling/Fixture→SOP/ControlPlan→PilotRun→ManufacturingRelease。

影响结果包括证据适用性、在途Build、客户样件、供应承诺、库存/在制品处置、生产切换和培训。AI推测与显式依赖分栏，避免把猜测变为已批准变更范围。

## 14. 放行包与移交

发布包固定定义、双配置、验证结果、遗留/例外、适用数量/批次/产线/地区和批准。工程与制造专业分别作决定，接收方确认接收范围。

ERP/MES移交包括编号映射、BOM/工艺版本、文件manifest、内容摘要、外部ID、发送意图与接收/生效回执。

发送成功、对方接收、实际生效分别记录。结果未知先对账；接口超时不盲目重发。若外部暂未连接，允许受控人工交接证据，不伪装实时集成。

## 15. 量产爬坡与生命周期反馈

量产执行仍在作业系统。PDOS关注已承诺的爬坡目标、过程偏差、质量复发、供应/成本偏差、客户问题和变更生效。

Field反馈必须关联已知产品/批次/配置与来源；无法定位则保持未知并组织调查。经验先成为候选，经适用性和审核后发布规则，不自动污染全部平台知识。

停产或平台替代应考虑在售变体、售后、备件、未完成承诺和外部主数据状态；不能只把Product改成archived就认为全部义务已结束。

# 05 · 页面与AI交互契约

## 1. 用户不管理内部架构

前台展示工作、版本、结果、等待和决定，不展示消息总线、候选事务、Agent调用拓扑或数据库命名。复杂业务对象在需要时展开，不变成几十个一级菜单。

“统一入口”不是所有人都必须聊天；工程师可直接提交版本，品质可直接接收样件，产品经理可边对话边编辑定义。

## 2. 统一工作卡

每张卡回答：发生了什么、关联哪一版、为什么与我有关、现在谁负责、下一步是什么、证据在哪里、AI实际做了什么。

卡片数据来自权威对象/投影。主动作只显示当前真实可执行的动作；无权限、来源过期、版本冲突和必需缺项要显示具体原因，而不是一个永远可点的“继续”。

AI成功写入静默更新卡片和活动记录。需要人补缺项或决定时才增加注意项。重复提醒聚合到同一个事项，不产生多个新任务。

## 4. 个人小Pai

入口包含自然语言、文件、当前页面上下文和历史工作。系统显示当前目标范围，但不强迫用户每次手工选择项目。右下角入口打开侧边对话，可放大为整页；同一会话在跨页、刷新和关闭面板后可继续。

范围可推导时直接使用并展示；若同名对象会导致错误写入，只询问影响该动作的最小选择，其他只读工作继续。

个人对话默认私人。共享对象中的产出需按明确受众保存，不能把整段私人讨论一起发布到项目。用户可把经确认内容发布为项目记录。

**会话管理（确认稿 P20）**：会话是用户可管理的持久对象，提供列表、搜索、切换、重命名、置顶与归档；**不提供删除**——归档可恢复，归档与重命名都不影响 Run、ActionReceipt 与已写入的业务记录（I17、§06.10）。自动化规则的运行历史可与会话同栏分组呈现，但触发、授权与预算规则不与会话混同（§06.4）。

**立项前对话（v1.1）**：
- "新建品类"打开个人小Pai对话；在品类页点"立项提案"，打开该品类的小Pai对话。
- 只追问会改变方向的问题，边问边研究。例如"充气泵"先区分汽车、自行车还是桨板，不自动混成一个品类；地区、价格等未明确项作为显式假设，不强迫先填齐表单。
- **Grill me**：按依赖顺序澄清，每次最多三个关键问题（由输出 schema 约束）；推荐答案不预先选中；问题用弹窗回答，答案和后续研究留在同一对话。对话恢复不自动重开历史弹窗，隐藏的小Pai不弹窗。
- 用途明确后使用受控公开研究（§06.6），显示实际进度、引用、失败和覆盖缺口。
- 小Pai 先生成可检查的品类或提案候选。品类候选含边界、用户、场景、地区、研究问题、字典骨架和公开研究摘要；提案候选继承当前品类资料与参数版本，补本案需求和目标。AI 值和专业条件保持"AI起草 / 未知"，不能自行升级为"已确认"。
- 候选保存按 T1 由发起人一次确认；品类还须明确确认共享内容已去除客户身份；保存后跳转到对象页。在试点租户中，草稿类写入可按 T0 执行（§06.12）。

**过程可见**：生成时显示可展开的过程面板：公开的处理思路摘要、实际搜索关键词与来源读取、覆盖情况和耗时；完成后收起，随回复保存。不展示模型内部推理原文。

## 5. 三种输入路径

拖文件：先显示上传/解析状态与原件，识别可能对象，再以可操作候选呈现。

说情况：例如“供应商说周五才能到样”，先创建有来源的外部承诺候选或在预授权内登记，区分声称与实到。

委派结果：例如“准备本轮试模验证包”，创建WorkRequest并持续执行，结果放回Handoff/Verification，而非仅输出清单。

## 6. 一次确认的粒度

批次中独立组可分别选择；有前后依赖的组明确整体确认。必须看见原值、新值、影响、来源与未确定项。

前端按钮“只接受这一条”必须真的只作用于该原子组。后端只有整包事务时，前端应明确整包，不伪装逐条。

确认时发生版本冲突，只重新呈现真实变化，不因无关摘要更新重审全部资料。

## 7. 多人协作与私有草稿

编辑草稿使用乐观版本/并发检查。多人实时编辑可在文档草稿引入协同编辑机制，但正式字段与发布状态不能仅靠协作文档合并。

个人草稿、团队候选、正式记录和已发布基线分层。AI在人的草稿里工作不自动影响正式定义；用户编辑字段可局部锁定AI维护。

## 8. 图表与专业视图

可用视图包括需求-验证覆盖矩阵、产品/竞品规格对比、配置差异、依赖/资源时间轴、Build前后差异、失效分布、制造准备矩阵和变更影响列表。

每个数值可钻取口径与来源。缺数据显示unknown，不用虚假示例数据补满生产页面。图谱用于表达关系，不替代实际主操作。

**立项视图（v1.1）**，按优先级：
- 第一批：定位图（价格 × 关键性能）、规格对标、功能配置、定义成熟度；
- 第二批：需求 × 平台差距矩阵、用户声音热力图、方案对比、目标成本桥图；
- 第三批：品类矩阵（细分 × 价格带）、竞品价格与评分时间线。

所有立项视图遵守同一组规则：实测、宣传、推断、未知分开显示，未知不画点，只写数量和原因；测试条件、币种、日期不同就分组或提示，不硬比；每个点都能点开原始来源；样本量可见，样本少要标出；我方现款和目标用强调色，竞品统一用灰色。视图只读计算工具和证据的结果，不另存为事实。

## 9. 移动与弱网

移动优先覆盖交样/接收、拍照上传、现场情况、结果确认、例外和查看资料。复杂BOM与多版本比较可保留桌面优势，不强迫全部重型编辑在手机完成。

弱网允许本地保存未提交资料并清楚标记，恢复后同一幂等意图上传。放行、签核、跨人承诺等正式动作必须在线校验；离线缓存不宣称成功。

相机/音频输入需要来源和时间，转写是候选不是原始事实。二维码可作为精确对象定位入口，但不扩展为完整仓储/借还系统。

## 10. 错误与恢复

必须有空态、加载、运行中、局部完成、等输入、等决定、等外部、权限失效、来源过期、版本冲突、失败、取消、撤回受限和外部结果未知。

用户刷新或重新登录后看见同一个工作，不重新创建。错误提示必须说明哪些已经发生、哪些尚未发生、下一步可采取什么动作。

## 11. 体验质量检查

系统不要求用户重复录入已可靠提取的数据；不把一次工作拆成多处不可关联页面；不把AI成功转成人工审批负担；不隐藏实际写入；不以“AI已完成”替代专业结论。

所有主要操作支持键盘和清晰焦点，颜色不是唯一状态信号。中英内容原文和译文分别保留，单位/编号不随语言变化。

## 12. 界面契约补遗（确认稿 P22）

以下条文来自 [2026-10-17 界面决定三分法与契约补遗](2026-10-17-pdos-v1.1-ui-contract-addendum.md)的 B 类，用户 2026-10-17 确认采用。它们只细化本章既有规则，不新增领域对象、命令或自主档位。括号内为补遗编号与被细化的小节。

### 12.1 项目列表与视图（细化 §05.8）

- **同源三读法**（B2）：列表、看板、时间轴共用同一组项目事实与同一套口径，视图只读计算结果、不另存为事实。切换视图不产生任何写命令；同一项目在三个视图里的阶段、门禁日期与健康度取值一致。
- **看板不可拖拽换列**（B3）：卡片无拖拽把手、无 drop 目标；阶段推进只能通过满足出口条件并留具名决定完成。在看板上试图改阶段时，给出的是"去阶段与门禁查看出口条件"，不是一个可点的推进按钮。
- **组合层只暴露冲突**（B4）：组合时间轴用于发现跨项目资源撞车，不提供改期、改承诺、改资源分配的直接动作；点击冲突跳到对应项目的计划候选比较。
- **阶段进度是位置不是比例**（B6）：列表里的阶段迷你进度条表示离散阶段位置（已过/当前/未到），组件输入是阶段序号而非百分比；界面任何位置不出现以百分比表达的"阶段完成度"。
- **四时间固定分四条**（B9）：基线/预测/承诺/实际在时间轴上固定分四条呈现，不得合成一条或以单条加标记代替；承诺与冻结点各有独立图元；预测滑期时承诺仍显示为成立并标超期。数据缺失显示未知行而不省略该行。**数据上不合并**——对不同接收者的承诺永远是不同记录；**显示上允许折叠**——可折为一行并标出接收者数量，展开后逐行可见，折叠不改变记录。
- **估时"未知"是合法值**（B10）：工作包估时可保持"未知"并写出原因，不以 0、区间中点或默认工时填充；汇总时未知项单独计数并在汇总旁显示，不并入数值合计。

### 12.2 阶段与门禁（细化 §05.3、§03.2）

- **阶段条按模板渲染**（B5）：项目的阶段条与看板列由该项目类型的 StageInstance 模板决定，段数、名称与顺序来自模板，不得硬编码。OEM、派生与小改项目按各自模板显示，不出现空的占位段。
- **窄屏堆叠不合并**（B7）：窄屏下双线影响、门禁两栏与三种成熟度可纵向堆叠，堆叠只改布局，**不得合并为一个综合结论或综合分**；三种成熟度在窄屏下仍是三个独立结论块。具体堆叠宽度由 [UI 基线](2026-08-09-ui-baseline.md)规定，不写进本契约。
- **下一阶段进入条件前置可见**（B8）：当前阶段的门禁视图同时显示下一阶段的进入条件，用于提前发现缺口；前置显示的条件须标明属于下一阶段、当前不构成本阶段阻塞，不因前置显示而阻断当前阶段。

### 12.3 项目工作区（细化 §05.3）

- **合并面板不减内容**（B11）："现在"可把阻塞/待接收/待决定合并为一张"需要办理"并沿用动作类型读法，但同一屏仍必须能看到"下一 Build"与"关键承诺"；合并只改面板数量，不减少内容项。
- **引用已漂移**（B12）：被引用对象已有更新版本而本轮 Build/验证仍按旧版执行时，显示"引用已漂移"并同时写出两个版本。漂移与"来源过期""来源已撤回"是三种不同状态；**漂移是提示不是阻塞**，是否阻断由 §03.7 规则判定，界面不得因漂移自动阻断已授权的 Build，提示必须指出"本轮按哪一版执行"。

### 12.4 小Pai 会话（细化 §05.4、§06）

- **范围与已加载技能可见**（B13）：会话顶部显示当前范围（可改）与"已加载技能"，并写明未加载的技能不授予其写工具。改范围只改范围、不授予权限；范围变更后重算可用技能与工具；越出本人有效范围的范围值不可选。**技能列表是服务器下发的事实，不是前端枚举。**
- **携带什么显式告知**（B14）：输入区显式列出本次发送携带的范围、对象与技能，与实际 ContextSnapshot 一致，列出的条目能在运行详情里逐条对上；`@` 选中的对象进入显式范围并记入 ContextSnapshot，不只是文本提及。
- **转后台继续同一 Run**（B15）：运行中可停止或转后台继续；转后台不中断同一 Run，工作 ID 与幂等意图不变，关闭面板后仍可在会话列表与 AI 工作详情里找回，后台完成后结果回到同一会话线程，不新建会话。
- **重跑是新运行**（B16）：消息级动作提供复制/重跑/运行详情。重跑建立新 Run 与新幂等键，不复用原回执；原回执保持不变；对已写入对象的重跑须先给出"将产生新候选"，不静默覆盖（I16）。
- **撤回受限必须列出未撤回项**（B17）：按运行撤回的入口在写入回执与会话层均可达；撤回受限时按条列出已撤回/未撤回与具体理由（人工已修改、已被正式决定消费、下游已引用），未撤回项给出负责人可执行的下一步，不只是失败提示。
- **档位用词与过程面板**（B18）：界面提到自主档位时只用"自动 / 一次确认 / 具名决定"三个词，全界面不出现 T0/T1/T2 作为档位词（试模试次 T0/T1/T2 不受影响，§04.5）；代码不得把 `write_tier` 枚举值直接渲染给用户。过程面板显示耗时、写入条数与待确认候选数，**不显示 token 用量**。

### 12.5 全局入口（细化 §05.2、§01.7）

- **命令面板与快速创建不扩权**（B19）：⌘K 命令面板只调用已注册的领域命令，档位与权限与页面入口完全一致；T2 不在面板内直接执行，面板只能定位到对象或打开其正式入口。无权限命令不出现在检索结果里（而非出现后报错）；编号精确检索只做定位，不附带执行。快速创建清单按角色收窄。

# 06 · 小Pai：单 Agent 运行、工具、技能包、Context 与 Memory（v1.1 改写）

## 1. 运行体系

**系统只有一个 Agent：小Pai。** 对话、页面按钮、领域事件、定时和持续委托，都由同一个运行时、同一张 Agent 图执行；每次执行是一个 Run。小Pai 通过注册工具、MCP 连接器和渐进加载的技能包完成各类工作。

- 不设领域 Agent，不默认构造 Agent 群聊，不通过投票形成正式结论。原"六领域 Agent + PMI"的业务能力语义保留为技能包和工具的需求来源，不再作为运行单元或能力管线。
- 只拆两类子任务：可并行的广度只读研究；读取不可信外部内容的隔离子任务（不给写工具，只交回结构化结果）。
- 运行主线：意图→范围/授权→结果标准→上下文→计划→技能包/工具/MCP→输出验证→政策→领域命令→结果核对→等待/继续→效果复查。
- 用户面只有小Pai；后台工作的结果也署名小Pai，并标明触发来源和所用技能包。

## 2. 执行结构：Temporal 外层 + LangGraph Agent 图

```text
入口（对话 / 页面 / 事件 / 定时）→ 领域 API：鉴权、范围绑定、幂等键，写 Run
  → Temporal workflow（持久任务、等待、取消、重试；历史只存引用）
      → Activity（心跳、超时）：运行 LangGraph Agent 图（PostgresSaver 检查点，独立库）
      → 等待 signal：人回答问题、T1 确认、专家答复、G0 结果（领域事务提交后经 Outbox 发出）
  → 领域命令：唯一写入口，业务事实 + ActionReceipt + Audit + Outbox 同事务
```

Agent 图的节点：

1. `prepare_context`：按技能包声明组装上下文（§7）。
2. `model`：原生工具调用；输出要么是工具调用，要么是最终结构化结果。
3. `route`：工具调用 → `tools`；需要人输入 → interrupt（Activity 返回 needs_input，workflow 等 signal 后在同一 thread 用 `Command(resume=…)` 继续）；最终结果 → `verify`。
4. `tools`：只读工具可并行；写工具串行，带幂等键。
5. `verify`：schema 校验、引用逐字核对、数值交确定性引擎复算、档位与范围复核。
6. `finalize`：写结果与回执。轮次和工具次数有上限；上限用尽时强制收尾，保留已完成部分，不整段丢弃。

每个会话对应一个 LangGraph thread；同一会话的证据池跨轮复用，只存快照引用和定位，不存原文副本。LangGraph 的 interrupt 和 workflow 完成都不代表业务批准（§03.1）。

迁移期内，已有能力入口可以整体作为一个节点运行；新能力一律按上述 Agent 图接入。

## 3. 技能包

### 3.1 三要素

| 要素 | 内容 |
|---|---|
| 工具 | 该技能可以调用的工具（§6），带各自档位 |
| 数据语义 | 相关对象、字段、状态的含义：单位与测试工况、参数版本，"实测、宣传、推断、未知"的区别，什么能算证据 |
| 使用原则 | 什么时候用、方法步骤、边界与禁止事项、失败时怎么处理 |

**治理元数据**：key、version、purpose、input_schema、output_schema、context_requirements、allowed_operations、evidence_policy、failure_policy、budget、model_capability_requirements、evaluation_suite、owner。

### 3.2 存放

- 技能包是版本化配置文件，随代码发布；**不写进数据库 CHECK 约束或触发器**，改提示词或使用原则不需要迁移。
- 数据库只存 TenantSkillEnablement："租户 × 技能包"的启用状态与资格（§12）。
- 运行记录保存所用技能包、模型和工具的完整版本组合。

### 3.3 渐进披露

1. **目录**：固定系统提示只放技能目录（名称加一句话说明），保持前缀稳定。
2. **按上下文预载**：服务器根据当前页面、对象、会话范围或触发事件，在第一轮附上相关技能的完整内容。
3. **运行中自加载**：小Pai 用 `skill.load(name)` 加载其他技能，内容作为消息追加；服务器校验当前用户和范围能否使用，加载记录写入回执。

工具定义整体保持稳定以命中提示缓存；技能加载决定"允许调用哪些工具、按什么原则调用"，未加载对应技能时服务器拒绝写工具调用。工具数量大到影响选择准确度时，引入按需检索工具，不在运行中改写工具列表。

### 3.4 来源与首批技能

技能先在对话中做对，再保存为个人技能，稳定后共享给团队，并持续优化。产品线首批技能：`public_research`、`category_framing`、`proposal_drafting`、`rfq_extraction`、`competitor_comparison`、`price_band`、`review_pain_clustering`、`jtbd`、`option_comparison`、`opportunity_scoring`、`derivative_diff`、`gap_check`。v1.0 中的研究、机会、实验、策略等方法，都以技能包形式提供；数值类结果（市场规模、机会评分、成本）交给计算工具复算。

## 4. 自动化规则（AutomationRule）

AutomationRule 绑定 trigger、scope、conditions、技能包、授权的 MCP 工具、goal/stop_condition、owner、budget、cooldown、max_runs 与用途。v1.0 中的 Loop 统一改称 AutomationRule。

- 触发类型：domain_event、schedule、relative_milestone、manual。持续义务由 Temporal 维护，模型只在需要理解的步骤调用。
- 规则版本化：草稿、发布、回滚；每条规则有运行历史，可以在历史上继续追问或追加动作。
- 权限逐项开关：可访问的品类范围、是否联网、可用的 MCP 工具、是否允许由外部来源（邮件、IM 建立的对象）触发（默认关闭）、是否允许写触发对象以外的对象（默认只写触发对象）。
- 触发事件去重、来源变化合并、因果链、级联深度和总预算均须受控。自己更新摘要不能无限触发自己；同一测试失败不重复建多个Issue。
- 正常成功进活动，例外聚合进原对象注意项。达到目标、范围失效、取消或过期后停止，不能永久检查已关闭Build。

## 5. 分级执行

READ：无业务写权。
T0：独立AI身份在明确授权内自动进行可逆、无签核/外发语义的操作。
T1：一次实质确认，固定载荷、来源、版本和组内事务范围。
T2：具名业务/专业决定；AI只能准备，不取得该命令执行身份。

例：自动建立来源明确的Issue、关联证据、维护AI专属字段、在提案中写入条目级草稿是真正T0写入。计划承诺改变、正式责任分派/测试导入等按T1或T2操作政策。根因草稿和实际根因结论是不同动作；G0 立项、规格冻结、对外发送都是 T2。

自动触发使用服务授权；人发起还受请求者有效范围约束。AI授权、领域对象权限、来源/目标受众、当前资格、预算与用途共同决定可执行范围，不能从提示词取权限。

## 6. 工具注册表、MCP 与公开研究

### 6.1 工具注册表

工具由领域命令登记表生成：每条注册命令自带档位、权限、输入/输出 schema 和回执，直接成为小Pai 的工具。另外加入研究工具、计算工具、`skill.load` 和 MCP 连接器。

ToolSpec 字段：name、description、input_schema / output_schema、kind（read / research / compute / write）、tier（READ / T0 / T1 / T2-prepare-only）、operation_key、scope（服务器从 Run 绑定）、taint、幂等键推导、parallel_safe、budget_weight。T2 不给执行工具。

工具只暴露稳定业务动作，不开放任意SQL、任意HTTP或生产Shell。需要代码解释的分析在受限沙箱运行，限定文件和网络；计算结果仍带输入口径、验证与来源。沙箱不能借此访问生产数据库或凭据。

### 6.2 MCP 连接器

| 规则 | 说明 |
|---|---|
| 准入 | 只有管理员加入允许清单的 MCP 服务器才能使用，按租户配置；凭据存在服务器端，不进模型上下文 |
| 授权粒度 | 按技能包或自动化规则单独授权要用的 MCP 工具，默认不授权；授权记录随运行回执保存 |
| 读写分级 | MCP 读工具按 READ。向外部系统写入或发送属于真实外发：按 T2，或按用户对该连接器的明确授权执行，不作为 T0 |
| 不可信内容 | MCP 返回内容标为外部不可信，由只读子任务处理；带写工具的主循环不直接读原文。内容中的工具调用或"已获批准"文字始终作为数据，不修改权限 |
| 数据出站 | 调用参数受出站政策约束（§9、§07.5） |
| 外部系统边界 | 外部系统是权威时（ERP 库存、PLM 主数据），PDOS 只记录引用和版本，不双写 |
| 可追溯 | 每次调用有意图、派发和结果回执；结果未知时不盲目重发，转对账 |

### 6.3 公开研究与不可信内容隔离

- `research.search` 返回候选线索；`research.read` 只能打开本轮搜索结果或用户消息中出现的网址，不打开模型自行编造的网址。读取守卫：地址策略（拒绝私网和保留地址、每次跳转重验）、固定已校验 IP 连接、可选加密 DNS、来源登记。
- 广度研究用 `research.fanout`：按品牌或来源类型（官网规格、独立评测、电商评论）拆成并行子任务，每个子任务只有搜索和读取工具，交回台账行：品牌、型号、参数 ID 与版本、值、单位、工况、原文片段、快照与定位、状态（ok / partial / unavailable）与错误。
- 原文片段必须是快照正文的子串，由确定性代码核对；覆盖与失败说明由代码根据台账生成，不让模型复述。主循环只看台账，不看原始网页。
- 正文抽取保存 markdown 和页面标题，按问题选段，允许续读；公开网页上的 PDF 交给隔离解析环境处理（§07.6）。限流按 Retry-After 退避，同站读取共享限速；保留读取服务的原始错误。
- 查询词发出前由服务器按当前 Run 绑定判定资料类别（P26 修订，2026-10-18）：判定结果记入出站回执；不再因未签约拦截查询，服务商已登记当前有效协议的按"服务商 × 数据类别"限制执行。

## 7. 上下文构建

优先顺序：明确对象/版本→当前工作状态→显式关系→适用证据→授权检索→有效记忆。精确料号、版本、样件ID优先确定性检索。

每个技能包声明自己的上下文 schema，按技能包投影后才发给模型；开发和测试环境中字段被投影删除即报错，生产环境记录删除原因并在运行详情中可见。ContextSnapshot记录必要读集与来源权限，不把全部项目文本塞入提示。写入前只对受影响的最小关键读集再验（§08.11），避免无关消息变化导致过度过期，也避免依据陈旧规格继续写。

固定系统提示和工具定义不插入动态内容；动态状态由代码预聚合后追加在末尾。对未知、来源冲突和证据失效采用显式状态。检索未找到不等于业务上不存在。

## 8. Memory

五层：个人偏好、当前工作短记忆、项目事实摘要、产品/平台经验、企业正式规则。每条记忆有来源、版本、作用域、有效期/条件、敏感度和撤回标记。

长对话按任务保存可恢复摘要：目标、约束、精确对象/版本、已完成与未完成动作、来源和原始记录定位；不以"最近若干条原话"充当记忆。

项目/产品事实应从领域查询重建，摘要只是缓存；正式规则经审核发布。私人对话不因被Agent读过而自动共享。

检索前过滤，输出和写入前再次检查来源与目标受众。共享Agent可调用权不等于拥有其所有来源访问权。向量库、缓存、汇总和过去生成摘要都纳入权限撤回传播。

经验晋升：运行/实物结果→候选→适用性验证→发布规则。自动反馈学习不能修改安全边界、工程阈值、批准政策或评测金标准。

## 9. 模型网关

按能力需求、资料敏感度、出站许可、质量资格、可用性、延迟和预算选模型。没有依据时采用一个已验证的默认模型，而非自动把敏感任务转发给任意备用模型。

- 使用原生工具调用和 JSON schema 结构化输出；消息只往后追加，保持前缀稳定以利用提示缓存；流式输出 SSE。
- 结构化校验失败时，把上次输出和校验错误回传给模型再试；供应商 429/5xx 按退避重试。
- 原生工具调用和 schema 遵从度是模型资格的评测项。不达标的模型可以在适配器内部降级为 JSON 文本模式，但对外显示能力限制，不伪装成相同能力。
- **出站检查与回执（v1.1；P26 修订，2026-10-18）**：出站不再以服务商签约登记为前置。服务器端按当前 Run 绑定的数据类别判定每次出站，服务商、类别与依据记入运行回执；模型传来的参数不作为依据。租户登记了当前有效 ProviderDataAgreement 的，按"服务商 × 数据类别"作限制执行（类别超出许可即拦截）；未登记、已停用或已过期不阻断。当前阶段服务商为 MiniMax；多服务商租户自助配置（OpenAI 兼容与 Anthropic 原生）为后续方向。

替换模型必须保留质量证据与版本。模型不可用时领域操作和确定性引擎仍可用，AI显示失能。不能用旧缓存回答"刚刚完成"新的工作。

## 10. 运行与行动回执

Run保存目标、技能包/模型/工具版本、范围、触发、预算、状态、结果和错误。

ActionReceipt保存命令、执行身份、请求来源、对象/版本、依据、真实副作用、审计和撤回方式。工具返回成功字符串不是完成证明；必须查询/收到实际命令回执。

业务写入与回执/Outbox同事务。跨多个独立动作允许partial，但用户看到具体已完成与未完成；对不能拆开的业务组必须原子。

## 11. 取消、恢复与补偿

长时间等待保存在 Temporal workflow，不持续占用模型。Worker重启后恢复相同工作ID和业务幂等意图。

- **取消**：用户停止即取消 workflow；Activity 在心跳时检查取消状态；清理步骤按预留上限做估算结算并释放预算名额。用户取消与供应商错误分开记录，不产生永久占用的未知用量。领域持久 cancel_epoch 在命令开始和提交前检查。
- **恢复**：已保存的完整结果可以恢复并重新验证；结果不确定的动作进入对账，**对账必须有出口**：按 run 读业务回执，有回执补记完成，没有则记失败并允许以新请求号重发；提供管理员入口和超时自动对账。
- 已提交或结果未知的外部副作用先对账。单条/整Run撤回产生补偿回执；人工已修改、正式决定已消费或下游引用的对象不能强制覆盖，必须报告限制与待处理项。

## 12. 资格与评估

开发→离线评估→（可选）影子比对→T1真实试用→限定T0→持续监测。资格绑定具体技能包/操作/模型版本/场景，不是某个模型全局获得所有写权。

**试点资格（v1.1）**：草稿类技能包的 T0 资格，可以用户本人对 10–20 个自有或合成案例的审阅记录为依据；资格按"租户 × 技能包 × 模型版本"记录，技能包或模型变更后重新审阅；只在试点租户开启。T2 不变。

评估按维度打分：覆盖度、引用有效（片段可核）、单位与工况正确、保留未知、无越权、篇幅；不要求整份输出逐字等于参考答案。真实样本、独立测试集、出处、错误严重度、误建/漏建、修改/撤回、越权和净减负都要记录。模型自报置信度不能单独作为放行条件。产品线评测集取自自家真实或合成案例，真实模型定期运行。

T0持续抽检，关键错误触发暂停或降级；普通成功不要求逐条复核。不是为每次写入增加一个审核人，而是在能力质量和例外处置上管理风险。

## 13. 效果复查

Run完成后依据outcome_spec判断业务结果；需要等待接收/验证/外部回执的工作继续跟进，而不是仅验证“创建了一条任务”。

系统区分AI动作完成、人员工作完成、实际结果已验证。复查发现没有推进时，更新原工作状态和必要例外，不不断新建提醒。

## 14. 人类可理解性

公开展示读取了哪些依据、调用了什么动作、修改了哪些记录、失败在哪里、还有哪些限制。对话中以可展开的过程面板展示处理思路摘要、实际搜索与读取、覆盖情况和耗时。只展示行动解释和证据，不输出内部模型私有推理过程。

用户可反馈错误对象、错误数值、缺来源、无价值、操作过多或不应自动执行；反馈与具体技能包/运行版本关联，不能仅给一个无定位的星级评分。

# 07 · 技术、安全、存储与运维

## 1. 推荐拓扑

模块化业务内核＋独立持久工作流＋AI/解析/连接Worker。领域模块按02分工，初期不要求每个模块独立部署。

```text
Web / 移动Web / 授权钉钉轻入口
            ↓
React+TypeScript界面 / Next.js同源BFF
            ↓
FastAPI领域命令与查询
  ├─ PostgreSQL业务事实、版本、审计、Outbox
  ├─ 私有版本化对象存储
  └─ 读取投影 / 全文与向量检索
            ↓
Outbox → Temporal持久工作流
           ├─ AI Worker → 模型网关
           ├─ 解析/分析Worker → 隔离处理
           └─ Connector Worker → ERP/MES/CRM/钉钉等
```

这些技术是新目标下的建议，不由旧栈决定。Python适合统一领域和AI能力类型；TypeScript适合前端；同语言不是共享数据库写权限的理由。

## 2. 技术决策

领域API使用FastAPI/Pydantic，关系访问SQLAlchemy，迁移Alembic。数据库PostgreSQL，私有S3兼容存储，初始检索全文+pgvector。UI采用单一可访问组件系统，可用shadcn/ui。

Temporal拥有长期等待、定时、取消、重试和恢复；LangGraph 承载小Pai 的 Agent 图（推理循环、工具调用、中断与检查点）。Temporal的Activity会重试，业务副作用仍须自行幂等；LangGraph持久化不替代业务真值。[S08/S09]

依赖选择（v1.1）：HTTP 客户端统一为 httpx；中文分词用 jieba；Office 解析（python-docx、python-pptx）和 PDF 解析只装在隔离解析环境中，不进入 API 进程。

Redis仅用于缓存、节流与实时辅助，不作为唯一工作状态。不要无条件加入Kafka、Neo4j、Kubernetes、多套向量库和微服务网格；有测量支持的容量/隔离需求时再拆。

## 3. 四类状态存储

领域数据库：正式状态与事实。
Temporal持久库：执行位置、定时器与等待，独立数据库/凭据。
AI检查点：一次运行的中间结果和恢复信息（LangGraph 检查点，以及只存引用和事件流的运行作业库），独立数据库，不拥有批准。
查询投影：可重建的页面、检索与统计，显示as_of/watermark。领域对象的"当前状态"（Current）落库并由失效事件维护，不在每次读取时实时重算上游链（§08.11）。

长人工等待在Workflow挂起。人通过领域API作决定，事务提交后Outbox发信号；Workflow读取正式结果继续，不在两个引擎分别批准。

模型和外部网络调用放Activity/非确定性步骤，不能放在需要确定性重放的流程控制代码里。

## 4. 数据库设计

强类型字段保存状态、时间、数量、单位、币种、负责人和版本；JSON用于明确可扩展的参数/输出，不用EAV替代核心事实。

重要关系有外键、租户一致性、唯一约束和版本。通用对象引用可供日志/关系图使用，但必须校验对象存在、类型和scope；不能随意填字符串ID。

命令校验expected_revision；冲突不自动覆盖。被冻结记录只追加纠正/替代/撤销记录。计量用明确单位和精度，成本用十进制定点，不用二进制浮点作为正式金额真值。

## 5. 数据安全

应用层角色+对象关系+操作属性检查；数据库RLS作为纵深防御。PG表所有者、超级用户和BYPASSRLS角色的特殊行为意味着仅配置policy不足以证明隔离。[S10]

应用连接非超级用户/表所有者；迁移凭据独立。事务级绑定tenant/actor并在连接池复位。AIWorker只通过受控命令服务，不持有任意业务表写凭据。

来源权限、字段敏感度、私有对话、客户边界、模型出站许可、目标受众共同检查。管理权限不自动等于任意向外发资料的权限。

**范围根与受众（v1.1）**：授权以品类为范围根（Grant 挂在品类上），对象再按受众收窄（品类、私有、指定受众）。RLS 策略同样以 category_id 为第一键，私有提案与客户变体按负责人、具名评审人和指定受众过滤。

**服务商数据协议（v1.1；P26 改为可选治理工具，2026-10-18）**：ProviderDataAgreement 记录服务商、签约日期、允许的数据类别（客户原件、客户名、内部资料等）、留存和训练条款、到期日、登记人。登记是可选的租户治理手段：登记了当前有效协议的服务商（模型、搜索、读取服务）按"服务商 × 数据类别"限制出站，类别超出许可即拦截；未登记、已停用或已过期不再阻断出站，每次出站的服务商与类别仍记入运行回执。协议登记与变更属于管理员具名操作。

MCP 连接器凭据由服务器保管，不进入模型上下文、日志或回执；连接器只能访问其配置和授权范围内的数据。

凭据在密钥管理服务，日志脱敏。调试输出不得包含模型密钥、完整客户私有原件和任意连接串。

## 6. 文档与图像处理

原件版本化保存；记录上传主体、时间、来源和内容摘要。扫描、病毒/恶意文件检查、文件类型、尺寸和解压额度校验；解析在隔离Worker。

优先原生文本、表格和结构化字段；确有需要才OCR/视觉识别。OCR值和图形读取保留区域/不确定性，可查看原件核对。解析不执行嵌入脚本/宏。

CAD/Git等内容优先使用授权版本引用。需要预览可生成受控衍生件，不把预览当工程源文件。

支持的原件类型（v1.1）：文本、Markdown、PDF、XLSX、DOCX、PPTX、邮件；定位类型包括行、页、段、表格行段和单元格。公开网页上的 PDF（规格书、说明书）由研究读取后交给隔离解析环境处理（下载、安全检查、解析），不在读取层直接解析。

## 7. 检索与证据

混合检索：精确ID和条件→全文/向量召回→重排→源版本和引用验证。

索引保存tenant/scope/ACL、来源版本、有效期、撤回状态和重建水位。不能先召回所有客户资料再只在页面上隐藏。

关系图初期用关系表实现，显式依赖、规则推导和AI怀疑分开。向量相似性不能决定测试覆盖、零件等价或权限。

公开研究（v1.1）：实时搜索服务按顺序回退（例如 Tavily → Firecrawl → SearXNG），读取结果保存为 PublicWebSnapshot（网址、标题、摘要、采集时间、可信度、品类范围），经命令回执登记。第一个闭环不建本地全文索引和爬虫订阅；需要时以 Temporal 定时任务另行建设。

## 8. 确定性引擎

准备度、验证覆盖/证据适用性、齐套、计划/容量、成本、生效/例外均由可测试规则计算。LLM解释和提出候选，不独占这些结果。

资源不仅是人，还包括设备、模具、治具、线体、样件、技能、材料和日历。未知估时不填假值；冲突可产生情景比较和待决事项。

高级约束求解在数据足够时引入；它计算给定假设下的方案，不保证真实交期。预测不覆盖承诺。

## 9. 集成与权威绑定

Connector管理身份映射、来源字段所有权、外部ID、版本、inbox去重、outbox意图、限流和回执。并非简单定时复制数据。

ERP库存/采购/BOM生效、MES执行、CRM客户/商机、钉钉身份通知、PLM/CAD/Git版本各自有边界。未连接采用明确人工引用/导入，不伪造实时状态。

网络超时后的结果未知应查询外部ID/回执，不默认重试写入。外部无幂等或查询能力时进入人工对账路径。

## 10. 可观测性

关联request_id、work_request_id、run_id、command_id、event_id和delivery_id；v1.1 起，Temporal workflow ID、LangGraph thread、模型调用、工具意图与派发共用同一个 trace ID，排查一次失败不需要跨多张表人工拼接。失败的模型调用保存脱敏后的提示与回复，便于复原。业务界面显示结果和原因；技术界面显示延迟、错误、费用、重试、队列积压、投影落后与源版本。

关注自动化风暴、误建单、长期等待、来源失效、取消后动作、补偿失败、外发未知、权限拒绝和资格降级。

业务完成指标以实际有效结果计算，不以模型token或重试次数充数。

## 11. 容量与恢复目标

性能、RPO/RTO和可用性数字是上线前需要按实际并发、附件量、Build与调用规模确认的运行合同，不在没有数据时宣称已达到。

应分别测短事务延迟、查询p95、首次工作回执、长工作等待、解析吞吐、模型费用和投影延迟。长任务立即返回稳定工作ID，不阻塞HTTP等待完成。

**性能验收线（v1.1；分档见确认稿决策 P3）**：标准本地夹具下，读取与保存草稿 p95 ≤1 秒；预览、T1 确认、提交 p95 ≤2 秒；开测提交、影响分析等重计算的同步部分 p95 ≤3 秒，超出部分改为后台工作并立即返回工作 ID。写入每个切片的验收；每个切片记录计时与 SQL 次数，作为回归基线。本地结果不代表生产容量承诺。

备份覆盖业务DB、对象版本、Workflow持久库/恢复方案、密钥与映射。恢复演练核对配置→测试→决定→交接链并确保事件重放不会重复外发。备份成功不等于恢复成功。

## 12. 环境隔离

开发、临时测试、存续联验和生产有独立身份/目标标记与凭据。破坏性测试必须检查实际实例、数据库唯一标记、角色和本轮允许清单，不只检查数据库名字是否含test。

测试工具不得回退环境变量中的其他库。跨租户、并发、幂等、RLS与恢复在真实隔离DB验证，纯mock不能代替。

## 13. 模块扩展

当AI、媒体或外部同步负载增大，先独立扩Worker；当明确模块需要独立事务/团队/隔离时再拆服务。领域边界先于部署边界。

模板和Skill是受版本控制的配置，不允许任意脚本拥有生产权限。项目模板升级对在途实例显式应用差异。

# 08 · 命令、事件、API与一致性

## 1. 单一领域命令入口

页面、聊天、自动化和集成都通过相同领域命令完成业务操作。每条命令有固定操作名、对象类型、输入Schema、权限、前置条件、事务、事件和回执。

contracts/operations.json是关键动作目录，不是暴露任意SQL/HTTP的工具。常规CRUD可按相同原则补齐，但所有涉及自主级别、正式状态和外部动作的命令必须显式注册。

## 2. 请求与可信上下文

客户端可提交command_id、idempotency_key、operation、subject_ref、expected_revision、source_read_set和payload。

tenant、actor、requester、run、grant、current_scope、model_egress_policy和cancel_epoch由服务器认证/运行上下文绑定；模型提供同名字段不成为授权。

contracts/action-request.schema.json验证共同信封。每个操作仍须自己的payload与领域验证器，不能以共同Schema通过宣称全部业务正确。

## 3. 命令事务

1. 读取当前身份、授权、运行取消标记和领域状态。
2. 校验目标版本、关键来源读集、人工锁定、资格和操作用途。
3. 在一个事务内写领域事实、ActionReceipt、Audit和Outbox。
4. 提交后返回真实结果ID/版本及实际状态。
5. 异步更新投影、Workflow和外部通知。

事务中不等待LLM/ERP网络调用。对外发送先持久化授权意图，Worker执行后写回真实回执。

服务端依据来源事件、目标、操作及业务版本生成/校验稳定意图指纹；不能依赖模型每次自行填写不同key绕过去重。客户端请求key只作为受控映射的一部分。

同幂等键+相同载荷直接返回原回执，只核对请求者当前的读权限，不重跑全量校验，也不因时间窗过期而失败（v1.1）；同键不同载荷返回冲突。跨重试使用稳定业务意图键，不每次重新生成。相同输入不是永远同一意图，合法新一轮工作必须有明确新业务版本/来源；失败的请求可以用新请求号重发。

命令的校验范围和时机见 §11 一致性与性能规则。

## 4. T1与T2原子性

T1候选分独立原子组；组内保证业务完整性，依赖组必须同时满足。返回每组结果和失败，不用总的“成功”隐藏部分失败。

T2决定绑定审阅内容摘要、范围、版本、证据和政策。人确认后发生实质变化则不执行旧决定，展示真实变化；无关消息变化不重开全部审批。

高风险动作不能因为已有某次同类批准就永久预授权；批准适用范围和有效性必须匹配。

## 5. 事件

EventEnvelope：event_id、schema_version、tenant、type、subject_id、subject_revision、occurred_at、recorded_at、actor、correlation、causation、payload_ref。

领域事实与Outbox同事务，至少一次投递，消费者Inbox去重。同一对象按版本处理，落后事件不回退状态；发现缺口补读/对账。

不承诺分布式外部世界恰好一次。对于无法幂等的远端副作用，使用持久意图和结果未知对账。

事件载荷尽量引用受控数据，不把客户私有正文广播给所有消费者。schema_version演进和消费者兼容测试必需。

## 6. API分组

## 7. 错误契约

FORBIDDEN_SCOPE：当前范围不可操作。
SOURCE_UNAVAILABLE/SOURCE_STALE：来源不可用或关键版本失效。
VERSION_CONFLICT：目标改变。
MISSING_REQUIRED_EVIDENCE：用途所需证据缺失。
CONFIRMATION_REQUIRED：需T1载荷确认。
NAMED_DECISION_REQUIRED：需T2决定。
QUALIFICATION_REQUIRED：能力尚无对应自动执行资格。
DUPLICATE_INTENT_CONFLICT：幂等键与载荷冲突。
EXTERNAL_OUTCOME_UNKNOWN：远端副作用未能确定。
UNDO_BLOCKED_BY_DEPENDENCY：已被下游或人工编辑消费。
CANCELLED_RUN：运行已取消。

实现时使用统一大写标识`SOURCE_STALE`；正文大小写描述不作为另一个错误类型。

**错误码收敛（v1.1）**：错误码总数约 15 类：上述 11 类，加上 `VALIDATION_FAILED`（输入或领域校验不通过）、`NOT_FOUND`（对象不存在或无权得知其存在）、`RATE_LIMITED`（限流）、`INTERNAL_ERROR`（内部错误，不暴露细节）。具体原因放进 `detail` 字段（例如 `{"reason": "parameter_version_mismatch", "field": "...", ...}`），前端和小Pai 只按类别处理。不为单个场景新增顶层错误码；确需新增时走决策记录。

## 8. 外部授权

收取/解析文件、读取CRM来源、发送客户资料、接收ERP回执是不同权限。允许读取不代表允许出站。

连接器接收到的“客户批准”消息先保存来源声称，只有满足身份、范围和证据政策才建立Acceptance。AI不得通过解析邮件直接充当客户签名。

## 9. 读模型一致性

页面投影带as_of/watermark；命令成功后读取回执或权威对象，不能展示旧缓存造成“改完又恢复”。

准备度展示可缓存，但实际放行在事务前重新读取关键规则/来源。向量索引和图谱缓存不能成为正式决定唯一输入。

## 10. 关键完整序列

### 试模交接

技术请求→领域VerificationRequest→事件→AI整理包→T0 Handoff草稿→必要T1发起交接→品质具名接收→承诺排程→生产/品质真实结果→AI归并问题→整改/复验。

### 测试失败

真实结果提交/确认导入→TestRun事件→幂等失败建单→精确配置上下文→影响/根因候选→工程决定→新配置→新Run→独立验证/处置。

### 外部移交

固定发布包→具名授权→DeliveryIntent事务→Worker发送→远端回执/回读→接收/实际生效对账→更新Handoff，不把HTTP状态码当业务完成。

### 立项（v1.1）

小Pai 对话澄清方向→公开研究（子任务台账、片段核对）→品类或提案候选→T1 一次确认保存（试点租户草稿可 T0）→提案条目级编辑→负责人提交 G0（非试点评审人不得为本人，试点允许本人具名评审（P27））→具名决定→同事务或经 Outbox：型号定义 v1、项目、待决问题转任务/风险。

## 11. 一致性与性能规则（v1.1 新增）

以下规则是 §03.10"最小必要来源读集"和 §3"关键来源读集"的具体化。切片合同不得加严。

1. **Current 落库**：每个对象的当前状态存入数据库，由失效事件维护。读取只比较 id、版本、来源摘要和水位；完整重证只在 T2 决定或放行提交前做一次。
2. **最小读集**：来源读集为"直接来源 + 上游摘要或水位比较"，不在每次读取时重读整个上游闭包。
3. **请求内一次校验**：校验、预览、应用三步共享同一份绑定事务和水位的证明；T1 确认只绑定载荷、版本和水位，不重算整个视图摘要。
4. **签发人资格签署时固定**：见 §03.12。
5. **幂等直接返回**：见 §3。
6. **时间窗收窄**：有效期只用于 T1 确认，约束"能否基于它发起新决定"；提交时比较版本或水位。不取全链最早期限，不设"不可延长"；长计算改为异步工作，返回工作 ID。
7. **上限分离**：数量上限只用于请求大小和分页，不作为业务规则；不存在"来源最多 N 条"这类业务硬上限，完整集合通过分页读取。
8. **快照读取**：在快照隔离或依赖锁保护下只读一次，不用"读两遍比较"判断并发变化。
9. **扇出收窄**：共享资产（工装、设备、平台等）变更时，只通知实际引用它的型号或对象，不扇出到全租户。

实现要求：批量读取（`IN (...)`），同一事务内同一对象只加锁一次，同一请求内授权只查一次，ORM 身份映射保持有效，同类守卫只实现一次。测试使用可注入的时钟，不真实等待时间窗。每个切片记录交互命令计时与 SQL 次数，交互命令 p95 达到秒级（§07.11）。

# 09 · 验收与新工程建设

## 1. 什么才算交付

每条路径必须真实贯通入口、AI/人工操作、领域结果、异常、权限、回执和后续接续。页面截图、编译通过、模型回答流畅或单一API返回成功，都不能单独证明业务闭环完成。

contracts/acceptance.json提供关键正向/负向场景与关联操作。目录覆盖是设计覆盖，不是这些测试已经运行。

## 2. 六条黄金业务路径

v1.1：第一个闭环只验收路径 A（品类研究到立项）；B–F 在后续建设阶段（S2 起）按需纳入，届时按 v1.1 的规则修订原有切片合同。

### A 品类研究到立项（v1.1 改写，第一个闭环）

小Pai 对话澄清→品类（共享知识、规格字典）→公开研究（子任务台账、片段核对）→立项提案（客户需求、自主新品或派生迭代入口）→G0 立项评审→建项目（绑定型号定义 v1，待决问题转任务/风险）。

必须证明：
- 未建项目也可做研究；标准品匹配不制造虚拟项目；客户未知参数不补造；
- 品类为范围根：非成员不可见，私有提案只有负责人和具名评审人可见；客户私有资料不进入共享品类知识、对标和矩阵；
- 提案规格条目引用参数版本；不同工况或单位不当作同口径比较；
- 一次确认（或试点 T0）产生真实记录与来源；AI 草稿署名、可按运行撤回、不覆盖人工值；
- 非试点 G0 评审人不能是提案负责人，试点允许本人具名评审（P27）；批准后生成型号定义 v1 和项目；
- 引用片段全部可在快照正文中核对；未签约服务商不接收客户资料；
- 交互命令 p95 达到秒级。

### B OEM与制造可行性

客户设计包→资料冲突/接口→内部导入定义→供应/工艺/验证准备→样品方案。

必须证明：不强迫重复市场策略；客户设计版本、内部可制造性结论与正式制造放行分开。

### C 试模到品质返回

技术发起→试模前验证策划→生产实际产出→资料/样件交接→品质接收与排程→部分/最终结果→问题整改。

必须证明：每个时钟和责任正确；不AI代替接收；部分结果不伪装整体通过。

### D 失败到变更和复验

精确样件/配置测试→失败建单去重→双线影响→工程变更→新配置/新Run→适用独立验证。

必须证明：旧测试不被覆盖，错误复用被阻止，工艺/治具/SOP影响没有消失。

### E 试产到放行和外部移交

制造基线/资源/物料→准备度→试产实绩→整改→固定发布包→分别决定→外部接收/生效对账。

必须证明：高分不抵消硬阻塞，口径明确，客户承认不是制造放行，发送成功不是外部生效。

### F 爬坡反馈与复用

真实现场/客户反馈→配置定位→遏制/改进→变更/复验→适用经验→发布规则。

必须证明：无法定位保持未知，私有客户材料不泄漏，AI总结不直接成为企业标准。

## 3. 必须覆盖的可靠性路径

多用户并发、T1期间版本改变、源权限撤销、来源失效、重复事件、同幂等键不同载荷、模型超时、Worker重启、取消并发、撤回遇下游消费、外部发送结果未知、备份恢复与事件重放。

这些场景要用真实隔离数据库/事务与可观察结果验证。模拟模型可验证编排，但真实模型能力和权限负向必须单独评价。

## 4. AI评价

评价对象匹配、字段/单位正确、来源引用、无越权、无虚构事实、无重复、恢复能力、修正成本和工作结果。根据动作风险分层，严重错误不被平均成功率掩盖。

离线调试集、独立评测集和真实试用分开。晋升T0绑定具体技能包/模型/工具/操作/用途；不采用模型自报置信度作为唯一阈值。评测按维度打分，不要求逐字等于参考答案；试点租户的资格依据见 §06.12。

验证样本量与未覆盖范围必须说明。本组样本没有越权不代表未来绝对安全。数据缺失时不能宣称已具备真实资格。

## 5. 业务指标

减负：同类工作主动操作时间、重复录入、切换页面、必要确认数。
推进：输入到可用结果、交接等待、问题复验周转、准备缺口提前发现。
质量：误建/漏建、错误写入、重复动作、来源完整、撤回和补偿。
NPI：首次通过/最终合格口径、返工报废、爬坡问题、制造放行缺项、外部对账周期。

用可比任务和真实基线评估，不拿AI生成次数当价值，不预先承诺节省百分比。

## 6. 建设顺序

完整目标一次定义，工程按纵向可用路径交付，不按“全部后端→全部UI→再接AI→最后补NPI”。

建设阶段编号改为 S0–S5（v1.1），与业务关卡 G0（立项评审）、G1（计划基线）区分。

| 阶段 | 交付结果 |
|---|---|
| S0 可信执行骨架与整体重构 | 身份/范围、原件/版本、命令/回执、Outbox、WorkRequest、可恢复AI、最小真实写入与撤回（已有）；**v1.1 整体重构**：品类范围根迁移、§08.11 一致性与性能规则、错误码收敛、术语改名，覆盖已有全部代码（含暂停中的交样到制造部分）及相关切片合同 |
| S1 品类研究到立项 + 小Pai 内核（第一个闭环） | 品类、规格字典、公开研究、立项提案、G0、建项目；真实模型接入、Agent 图、由命令登记表生成的工具注册表、第一批技能包、MCP 准入、服务商数据协议登记 |
| S2 实物与专业交接 | 配置→Build/试模→样件→品质接收/测试→结果 |
| S3 问题与迭代 | 失败→变更双线影响→新配置复验 |
| S4 制造交付 | 制造基线→试产→整改→放行→外部接收/生效 |
| S5 持续运营 | 组合资源、AutomationRule、会议/周报、知识、爬坡与产品反馈 |

S0～S5是新工程交付建议，不是旧项目任务编号。顺序（v1.1 确认；确认稿决策 P4 调整）：S1 中的小Pai 内核在 S0 的 B3 完成后开始，与 S0 的 B4–B6 并行；S1 的第一个闭环（品类研究到立项）在 S0 全部完成后开始；S2–S4 已有代码保留，在 S1 之后恢复施工，恢复时按 v1.1 规则修订原有切片合同。NPI和主动AI的数据契约不能以“以后加模块”取消。

## 7. 每个切片的DoR/DoD

开始前明确用户结果、领域对象/命令、状态/权限、AI行为、读写来源、事务/幂等、失败路径、对应验收ID。

结束时：实际UI可办理、真实记录/回执正确、相关权限/并发/异常验证、必要移动路径、源/模型版本和限制明确。缺真实外部条件只暂停依赖验证，不虚报完成，也不停止独立可做部分。

# 10 · Codex新工程执行入口

## 任务性质

从本包目标架构建设独立的新系统，不做旧PDOS迁移或兼容改造，不以现有表/目录/能力注册和旧任务编号裁剪目标。

**v1.1 背景**：主线工程是 `pdos-next/`。原工程（`server/` + `web/`）已于 2026-10-08 停用归档（标签 `original-final-2026-10-08`），数据不迁移；原工程的 N/P/Q 义务与 Q0–Q6 人工出口随之归档，所需业务范围由本稿验收场景承接。原工程中的纯运行框架、协议与算法可以复制后按新接口改写（复用清单见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) §5），业务模块、资格和批准不继承。

本包是设计与关键契约，不是已实现代码。`tools/validate_contracts.py`只检查文档包结构和交叉引用，不代表业务测试、安全评估或生产资格通过。

## 读取顺序

00→01→02→03→04→05→06→07→08→09，再读contracts。遇到真实冲突需统一修正对应契约，不允许只改前端制造假成功。决策背景见设计确认稿。

## 第一条可用路径（v1.1）

1. **S0 整体重构**：在已有 pdos-next 代码上完成品类范围根迁移、§08.11 一致性与性能规则、错误码收敛、术语改名；已有业务路径回归通过，已知慢路径（开测提交、影响分析、发布）交互命令 p95 达到秒级，保留重构前后计时对比。
2. **S1 第一个闭环**：品类 → 公开研究 → 立项提案 → G0 → 建项目，加上小Pai 内核（真实模型、Agent 图、工具注册表、第一批技能包、MCP 准入、服务商数据协议登记）。验收按 §09.2 路径 A。

禁止先建立所有空页面、无数据的驾驶舱和只有Prompt的能力管线；不设领域 Agent。

## 实施纪律

- 领域规则一处实现，页面/AI/连接器共用。
- READ无写权；T0自动写、T1一次确认、T2具名决定，不改名混淆。
- 产品定义/工程配置/制造配置/Build/Sample/TestRun不能压缩为任务与附件。
- AI有独立身份，使用类型化命令，不直接任意写表。
- 权限、来源、版本、cancel_epoch、幂等、审计、Outbox在服务端校验。
- 单条接受、整批确认、部分成功和撤回必须真实对应后台事务。
- 交接、承诺、验证与发布有真实责任，AI不伪装人员已办理。
- 工程发布、制造放行、客户承认和外部生效分别记录。
- 所有新payload实现其专用Schema及领域验证；共同信封通过不是完整语义验证。
- 只有一个 Agent（小Pai）；能力以工具和技能包提供，技能包是配置文件，改提示词不写迁移；不把版本号写进数据库约束或触发器。
- 品类是范围根；客户私有资料不进入共享品类；出站只到已登记签约的服务商。
- 遵守 §08.11 一致性与性能规则和 §08.7 错误码收敛；切片合同不得加严本稿规则，确需加严先提决策记录。
- 未授权不删除旧代码、覆盖旧库、推送、部署生产、外发业务资料或将敏感内容送外部模型。

## 建议启动Prompt

> 以本目录（v1.1）为目标架构，在 `pdos-next/` 继续建设，不按旧PDOS做兼容。先读设计确认稿和本稿 §00–§09，理解品类范围根、单 Agent 小Pai、领域不变量 I01–I24 和 §08.11 一致性规则。第一步完成 S0 整体重构并以计时对比验收；第二步实现 S1"品类 → 公开研究 → 立项提案 → G0 → 建项目"加小Pai 内核。每个切片必须有用户入口、真实领域结果、回执、异常、权限、计时和对应验收证据。不要重启旧仓库审计，不用静态页面或聊天长文冒充业务功能。缺少外部授权只暂停依赖部分；代码/合成测试和真实模型/工厂验收分开报告。

## 输出
