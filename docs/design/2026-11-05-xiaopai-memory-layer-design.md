## 0. 一页读懂

小Pai 的“记忆检索”分两层：

- **Memory 层**：小Pai 记得的东西，比如这次在做什么、以前做过什么、你的习惯、团队的约定、它自己的做事方法。这些都是辅助信息，**不是业务事实**。
- **RAG 层**：公司的资料和业务数据，比如品类、项目、问题单、原件、核实答案。这是事实的来源，已基本建成（RAG 设计切片 A–G）。

记忆按两个维度来分：

- **按性质分五类**：你提的四类（工作、情景、语义、感知），加上主流框架都有的“程序性记忆”。感知放到 RAG 层处理，理由见 §6.5。
- **按归属分两种**：**个人的**（只给本人用），和**业务范围的**（挂在品类、产品、提案、项目上，团队共享）。

个人记忆：

| 类型 | 通俗说法 | 例子 | 现在 | 本稿要做的 |
|---|---|---|---|---|
| 工作记忆 | 这次对话在做什么 | “这次只看 B2 版本” | 已有（P32 工作状态） | 加时效；转述的约束经确认后也能带上 |
| 情景记忆 | 以前和小Pai做过什么 | “上周三比过三家气泵供应商” | 记录都在，新会话查不到 | 新增：跨会话查自己的历史 |
| 语义记忆 | 关于我的长期信息 | “我负责充气泵品类，回答先给结论” | 只有 6 个固定偏好字段 | 增加自由文本条目；小Pai 提议，你确认 |

业务场景记忆（§7）：

| 种类 | 例子 | 放在哪 | 本稿要做的 |
|---|---|---|---|
| 业务事实 | 目标价、规格、G0 决定、问题单状态 | 业务数据（已有） | 不进记忆，每次按权限读当前版本 |
| 范围备忘 | “客户 A 评审必问跌落测试”“本项目样件编号按 项目-批次-序号” | 品类、产品、提案、项目下的备忘 | 新增：团队共享，小Pai 起草、成员确认 |
| 业务经验 | “同类气泵气嘴漏气，根因是 O 圈材质” | 知识候选 → 适用性评估 → 设计规则（已有） | 接上业务事件，问题关闭、项目复盘时自动起草候选 |
| 场景配方 | 起草提案时带客户关注点，处理品质问题时带同类经验 | 技能包里的声明 | 新增：每个业务场景只带它需要的记忆 |

程序性记忆（小Pai 做事的方法）和感知（看图片、扫描件）是两种归属共用的能力，见 §6.4、§6.5。

三条底线不变：

1. 事实永远以业务数据为准；记忆和业务数据冲突时，以业务数据为准。
2. 记忆跟着权限走：个人记忆只给本人用；范围备忘只给该范围里有权限的人；资料撤权后，引用它的记忆一起隐藏。
3. 小Pai 只能起草，不能自己写：个人记忆由你确认，范围备忘由有写权限的成员确认。

分四期做，第 1 期（跨会话回忆）用户最能感到，风险也最低。

各部分之间怎么衔接（读写各有一个总入口，上下文分约束、证据、背景三区，只有证据区能被引用）见 §14.9；评测方案见 §10；每个人叫法不同导致的检索问题见 §6.7。

## 4. 总体结构

```text
小Pai 记忆检索系统
├── Memory 层：小Pai 记得什么（辅助信息，不是业务事实）
│   ├── 个人记忆（只给本人）
│   │   ├── 工作记忆    会话工作状态（P32，已有）＋ 时效、确认后的转述约束
│   │   ├── 情景记忆    本人每次运行的确定性记录 ＋ 跨会话检索（新）
│   │   └── 语义记忆    本人记忆条目：固定偏好 ＋ 自由文本（修订 P72）
│   ├── 业务场景记忆（挂在品类 / 产品 / 提案 / 项目上，团队共享）
│   │   ├── 范围备忘    团队约定、客户关注点、背景说明（新）
│   │   ├── 范围近况    由业务事件和动态流确定性生成的近况摘要（新，只读视图）
│   │   └── 场景配方    每个技能包声明本场景要带哪些记忆（新）
│   └── 程序性记忆      技能包与提示词版本；纠正 → 修订候选 → 审核 → 评测 → 发布（新）
├── RAG 层：公司资料与业务数据（事实来源，已建成）
│   ├── 业务对象与显式关系：“图谱”就是业务表之间的引用，多跳用递归查询
│   ├── 原件与核实答案：固定版本，带页、段、单元格定位
│   ├── 业务经验：知识候选 → 适用性评估 → 设计规则（已有；业务事件触发沉淀，新）
│   ├── 混合检索：关键词（jieba）＋ 向量（pgvector），RRF 融合，一跳关系扩展，同品类补查；术语表与三字片段模糊匹配（评测后决定，§6.7）
│   ├── 感知：OCR、照片读数 → 带区域和置信度的文本 ＋ 图片区域证据（新）
│   └── 检索增强候选：MQE、HyDE（评测后决定）
├── 存储：PostgreSQL（行级权限 RLS）＋ pgvector；后台任务走 Temporal
└── 嵌入：租户嵌入配置（P30，OpenAI 兼容接口）
    ├── 云端：任意兼容服务商，包括通义千问的兼容模式
    ├── 本地：自建模型服务，套一层兼容接口，适合离线部署
    └── 兜底：嵌入不可用时退回关键词检索，不冒充零结果
```

两层之间只有一条接口：**记忆里只存对象的引用（类型、ID、版本）；需要对象内容时，由 RAG 层按当前权限读取当前版本。** 记忆从不直接提供事实。

业务经验放在 RAG 层，是因为设计规则经 T2 发布后就是正式知识，可以作为依据引用；范围备忘放在 Memory 层，是因为它不经正式发布，只能当提示，不能当依据。

具体的组件、数据表、读写流程和各项机制见 §14。

### 4.1 在 LangGraph + Temporal 里怎么落

现有运行链路：Temporal 工作流 `XiaopaiWork` 调用活动 `advance_xiaopai_run`，活动里执行 LangGraph 图（`prepare_context` → `model` → `route` → `tools` / `verify` → `finalize`）；运行结束时 `record_finish` 追加工作状态版本。记忆按下表接入，不新增第二条运行链路：

| 部分 | LangGraph（一次运行内） | Temporal（持久与后台） | 存储 |
|---|---|---|---|
| 运行内临时信息（消息、工具结果、草稿） | 图状态与检查点（已有），运行结束即止 | `XiaopaiWork` 负责等待、取消、恢复（已有） | LangGraph 检查点库；保留期见 D58 |
| 工作记忆 | `prepare_context` 读取并冻结（P32）；30 天时效也在这里判断，是确定性计算 | `advance_xiaopai_run` 结束时由 `record_finish` 追加版本（已有） | `agent_work_states` |
| 个人情景 | `prepare_context` 放同范围最近情景目录；`tools` 节点执行 `memory.search` | 情景记录随工作状态版本在同一事务写入；分词索引由后台活动补上，幂等键为 run_id，失败重试，不影响回答；向量化复用现有嵌入工作流（`embedding_workflow.py`） | 新增情景表 + pgvector |
| 个人语义（记忆条目） | `prepare_context` 放进运行信封；`finalize` 把模型输出里的 `memory_candidates` 交给服务器存为候选 | 不需要：本人确认走普通接口，以本人身份写入 | 新增条目表 |
| 范围备忘与范围近况 | `prepare_context` 按场景配方装载；模型在 `tools` 节点准备备忘候选，走现有 T1 准备与确认 | 业务事件触发的起草作为自动化运行，仍走 `XiaopaiWork`，结果进待确认列表 | 新增备忘表；近况是只读查询 |
| 业务经验沉淀 | 同上，候选经 `knowledge.candidate.create` 现有档位 | 业务事件触发（§7.5） | 现有知识表 |
| 程序性记忆 | 技能包经预载或 `skill.load` 进入图（已有）；场景配方随技能包版本 | 定时工作流做信号汇总、生成修订候选；评测走 Prompt A/B 流程 | 技能包版本 + 新增修订候选表 |
| 感知 | 图里不做解析，只通过检索工具读派生文本 | OCR 与照片读数作为活动在隔离环境执行 | 原件与切片 |

**不使用 LangGraph 自带的长期记忆 Store**（`BaseStore` / `PostgresStore`）作为记忆库，理由：

1. 记忆要按租户、本人或业务范围做行级权限，还要有版本和撤权隐藏；Store 只有命名空间，做不到行级权限。
2. 图在 Temporal 活动里运行。如果图内直接写 Store，就等于 AI 身份写记忆，违反 §5 第 4 条。
3. 读取已经由 `prepare_context` 和注册工具完成，不需要第二条读取路径。

以后如果要接 LangGraph 生态里的记忆组件，可以写一个只读适配器，底层仍是本稿的表。

模型输出 schema 增加 `memory_candidates` 字段属于输出合同变更，走提示词版本升级和 Prompt A/B；冻结前缀的规则不受影响，只是换一个版本。

| 产品/平台经验 | 知识候选 → 适用性评估（已有），业务事件触发沉淀（新）；FailureMode 仍按 P80 延后 |
| 企业正式规则 | 设计规则（T2 发布）、核实答案 |

## 5. 所有记忆共用的规则

v1.1 §06.8 要求每条记忆都有来源、版本、作用域、有效期或条件、敏感度和撤回标记。具体字段：

| 字段 | 含义 |
|---|---|
| 类型 | 工作 / 情景 / 语义 / 范围备忘（程序性记忆存在技能包版本里，不进记忆表） |
| 归属 | 个人记忆：本人（`owner_id`），服务器从请求身份绑定。范围备忘：挂靠对象，品类必填 |
| 作用域 | 个人记忆：本人全局 / 品类 / 产品 / 提案 / 项目 / 会话。范围备忘：品类 / 产品 / 提案 / 项目。服务器校验作用域对象可读 |
| 内容 | 自由文本条目，或结构化字段 |
| 来源 | 人工填写；或某次运行（run_id）、某个讨论串、某个业务事件，带对象版本 |
| 时间 | 记下的时间；生效、失效时间（可空）；范围备忘另有复核日期 |
| 状态 | 有效 / 待复核 / 已替换 / 已过期 / 已隐藏（来源撤权）/ 已删除 |
| 版本 | 修改即追加新版本；替换时旧条目标“已替换”并记失效时间 |

规则：

1. **记忆不是事实**。注入上下文时标“本人记忆（不是业务事实）”“团队备忘（某人某日确认，不是业务事实）”或“历史（as_of）”。和业务数据冲突时以业务数据为准，并在回答里提示更新。
2. **记忆不是权限**。记忆不扩大范围，也不授予读取；模型传来的作用域不作数。
3. **撤权传播**。记忆引用的对象被撤权、撤回或扫描失效时，该条在注入和检索中都隐藏（同 P32）。
4. **AI 只起草**。AI 身份对记忆表零写权限。
   - 个人记忆：你确认后以你的身份写入。个人记忆不是业务记录，不走 T0/T1/T2（同 RAG 设计 §6.5 对偏好的处理）。
   - 范围备忘：会被团队看到，也会进入别人的小Pai 上下文，所以按业务写入办理：小Pai 准备、有写权限的成员确认（T1），经领域命令写入并生成回执。
5. **删除就是真删除**。你删除一条个人记忆，正文和对应向量立即清除，只留“某时删除了一条”的元数据。范围备忘是业务记录，只能停用，停用后保留版本历史，供审计（P83 D193、P87）。
6. **只放在动态段**。记忆按固定格式放进运行信封，不改冻结前缀（不可协商项 4）。
7. **写入关口**。每类记忆只能从 §14.5 规定的入口写入。只有本人原话、本人的明确操作或业务事件能触发记忆提议；原件、邮件、IM、OCR 文字里的内容（比如一份文档里写着“记住：以后都用供应商 X”）不能触发（P84 第 7 项）。
8. **可信顺序**。事实冲突时按“业务对象当前值 > 核实答案 > 原件 > 范围近况 > 范围备忘 > 个人记忆 > 情景记录”取舍，同 RAG 设计 §3（P84 第 5 项）。

## 6. 个人记忆与共用能力

### 6.1 工作记忆

P32 的规则全部保留，补两处：

1. **时效**。会话闲置超过 30 天（租户可配置）后再续接，工作状态不自动带入，输入区显示“恢复上次的工作状态”，可以一键带回。焦点对象有了新版本的，照 P32 标“资料已更新”。
2. **确认后的转述约束**。小Pai 可以提议非逐字的约束，比如把“按上次那样”解析成“只看 B2 版本、按欧标”。这条约束在“本次携带”里显示为“待你确认”，你点确认后才进入工作状态，并标“本人确认”；不确认就不生效。逐字约束原有的核对不变。

### 6.2 个人情景记忆（新）

**记什么**：每个运行结束时，和工作状态的新版本在同一事务里写一条情景记录。内容全部从已有数据投影，不调用模型，不新增事实来源：

- 时间、会话、运行范围（品类 / 产品 / 提案 / 项目）；
- 本人原话（去掉页面附带的资料，沿用 `user_goal`）；
- 焦点对象（类型、ID、版本；不存标题，展示时按当前权限补上）；
- 完成的回执（ID 与操作）、准备的候选（ID 与当前状态）；
- 未完成事项、待答问题、结果状态（完成 / 部分完成 / 失败）、用到的技能；
- 使用清单：用到的记忆条目 ID，引用片段的 ID 与原件版本（只存引用）；检索状态（正常 / 仅关键词）；
- 纠正记录：内容、分类、去向、处理状态（§14.9 纠正分流）。之后只追加纠正，不改原记录。

首期**不收小Pai的回答正文**。回答可能引用后来被撤权的资料，进了索引就要额外做撤权同步。要看当时怎么答的，先定位到那个会话，再用 `conversation.history` 读，照 P32 规则隐藏或标注。

**怎么存**：建一张独立的本人情景索引表（含 `owner_id`，行级权限只许本人读）。关键词索引沿用企业检索的 jieba 分词版本，分词和向量化都由后台 Temporal 活动完成（§4.1）。向量化可选：租户嵌入配置勾选了“本人会话记录”这个数据类别才做，默认不勾，和 P30 中客户原件默认不含是同一做法；不勾就只用关键词。向量化照 P30 生成出站回执，并计入索引预算。

**怎么用**：

1. **新增只读工具 `memory.search`**：搜本人的情景记录、个人记忆条目，以及当前范围内本人可读的范围备忘。查询人由服务器绑定为本人，模型不能指定别人。默认范围同 RAG 设计 §7.1：项目、提案、品类运行先查当前范围，个人全局运行查本人全部。在项目运行里要查其他范围，由你在界面切换，不由模型参数决定。情景结果返回情景卡：时间、范围、原话首句、对象的当前标题、回执和候选的现状、session_id、run_id。
2. **扩展 `conversation.history`**：可以按 session_id 读本人的其他会话，服务器校验归属。
3. **同范围最近情景目录**：运行范围是项目、提案或品类时，服务器把你在同一范围最近 3 次运行的一行目录（时间、原话首句、run_id）放进运行信封，不超过 300 token。这一步只用 SQL，不调用模型或嵌入，回答速度不受影响。个人全局运行不放。
4. **会话列表搜索**：页面上的会话列表加搜索框，用同一个接口。

**排序**：关键词和向量结果先用 RRF 融合，再按新近度衰减（半衰期初始 30 天）；有回执、候选被采纳或本人置顶的加分；被纠正过的降权，并在结果里附上纠正内容，避免旧的错误回答被再次放大。全部是确定性计算。

**保留与删除**：跟随会话记录的保留期，具体年限写进 D217 试点协议（P83 D193），纳入生命周期目录（`originals/lifecycle/catalog.py`）。会话归档或删除时，情景记录和向量同步处理。“不进记忆”的会话不生成情景记录（§9）。

### 6.3 个人语义记忆：本人记忆条目（修订 P72）

**分两部分**：

- 固定偏好：现有的 6 个字段，不变；
- 自由文本条目（新）：关于我、我的工作方式、我常用的口径。上限 50 条，每条不超过 200 字。作用域可以是本人全局，也可以是某个品类、产品、提案或项目。条目分“口径”（进约束区）和“背景”（进背景区）两种，确认时选定，小Pai 给建议（§14.9）。默认不过期，可以自设有效期；引用了对象的，对象出新版本时标“可能过期”；
- 个人叫法（新，条目的一种）：见 §6.7。

**写入途径**：

1. 你在“我的记忆”页直接写、改、删；
2. 你在对话里说“记住……”，小Pai 生成候选卡“要记住这条吗？”，卡上显示内容、建议的作用域和疑似冲突的旧条目；你点“记住”才写入，忽略就作废。如果这条内容更像团队约定，卡上同时给“记为项目备忘”的选项（§7.2）；
3. 小Pai 主动提议（§12 Q4，P86）：同一会话里你对同一件事纠正两次以上时提议一次；每个会话最多一次，可以在设置里关掉。

**冲突处理**：写入前，代码按作用域和相似度找出疑似重复或矛盾的旧条目，候选卡上给三个选择：合并、替换旧的、都保留。选择替换时，旧条目标“已替换”并记失效时间，你可以在历史里看到，也可以彻底删除。

**怎么用**：运行开始时，服务器取出和当前运行范围匹配的有效条目（全局条目加本范围条目），和偏好一起放进运行信封，不超过 1,000 token。超出时本范围条目优先、最近确认的优先，并告诉模型还有几条没带、可以用 `memory.search` 查。回答下方显示“用到了 N 条记忆”，点开能看到是哪几条。

**不变的边界**（P72）：不作为权限来源，不进入企业知识，不进入别人的上下文，不自动学习。个人条目不会自动变成范围备忘；要分享，只能由你点“分享到项目”，生成一条新的范围备忘候选，确认时显示受众（§7.2）。

**管理员**：可以在租户级关闭自由文本记忆、主动提议和情景向量化；看不到个人条目内容，只能看启用状态和条目数量。

### 6.4 程序性记忆（新）

程序性记忆就是小Pai 的做事方法：技能包（正文、工具、预载条件、上下文合同）、冻结系统提示和租户规则。这些都已有版本，资格按“租户 × 技能包 × 模型版本”记录（v1.1 §06.12）。§7.4 的场景配方也是技能包的一部分。本稿补的是“从纠正中改进”这个闭环：

1. **信号**：工作状态里的纠正和排除条件、被你删掉的约束、被拒绝或大幅修改的候选、评测失败、工具错误类型（D246 修好后能区分具体原因）。
2. **汇总**：后台按“技能包 × 工具 × 错误类型”做确定性汇总，30 天内同类达到 5 次（初始值）就生成一条技能修订候选。修订文字可以由模型起草，但只是候选。
3. **审核**：技能负责人或管理员看差异，决定采纳、修改或驳回。
4. **评测**：用 10-31 建好的 Prompt A/B 流程，跑该技能的 golden-case 和回归题。golden-case 是可信根，这个流程不能修改它。
5. **发布**：发布为技能包的新补丁版本，已有的 T0 资格照 §06.12 重审。

这个闭环永远不能改：冻结前缀里的安全规则、权限与写入档位、工程阈值、批准政策、评测金标准。

### 6.5 感知（归入 RAG 层的原件处理）

图片和扫描件都是原件，有权限和版本。小Pai 不是“记住”一张图，而是从图里读出证据，所以放在 RAG 层，和其他原件走同一套权限、撤权和出站规则。分三步：

1. **扫描件 OCR**：解析器已经能标出需要 OCR 的扫描件。OCR 在隔离环境里运行，结果是带页码、区域和置信度的文本，进入现有切片和检索；低置信度的会标出来，可以对照原件核对（v1.1 §07.6）。
2. **照片与截图读数**：视觉模型读出描述和读数，作为带图片区域的“派生文本”，标“AI 读取，待核对”。出站按 P26 判定数据类别，客户原件默认不出站（P30）。这对样件照片、不良品照片、测试台读数照片最有用。
3. **图纸与形状相似**：需要多模态嵌入和图纸解析，暂不做（RAG 设计 §11.5 已记录）。

### 6.6 RAG 层的相关增强（只列接口，不属于 Memory 层）

- **MQE（多查询扩展）、HyDE（假设文档检索）**：每次检索多一次模型调用，会增加延迟和出站。现有关键词检索在 28 道检索题上的 recall@5 已达 97.92%。先用已制作的 52 道候选题做对照实验，召回提升明显才开，而且只用于慢档和研究。HyDE 生成的文字只当查询用，不进上下文，也不能被引用。
- **多跳关系**：现在只扩展一跳（`relations.py`）。需要时扩到两跳，仍在 PostgreSQL 里用递归查询，设深度上限并做环检测，两端照常按权限过滤，不引入图数据库。一跳扩展和同品类补查的结果仍可引用，分组标“关联对象”“同品类其他项目”，但不能当作当前对象的事实（P84 第 5 项）。
- **术语表与模糊匹配**：见 §6.7。

### 6.7 语言习惯与叫法（新，你 11-07 提出）

**问题**：每个人说法不同，检索会漏召回：

- 同物异名：气嘴、气门嘴、充气嘴；
- 简称和昵称：“老王那个泵”；用 F64 指 F64000；
- 中英混写和缩写：PCBA、ECR；
- 错别字；
- 部门口径不同：采购说“料号”，工程说“物料编码”；
- 用中文问英文资料：品类研究的用户声音以英文平台为主（P82 D180）。

**现状**：jieba 只有一个 12 个词的手工词典（`enterprise_search/terms.txt`）；编号通道只处理型号、料号的规范化（RAG 设计 D19）；向量召回能补上一部分近义；没有同义词表，也没有个人叫法。

**做法**（全部是确定性规则，不让模型自己学，P89）：

1. **租户与品类术语表**（RAG 层，并行轨）：一个标准词下挂多个叫法，含英文对照；查询时服务器按任一叫法扩展检索。品类名、产品名、型号从业务表定期导出，补进 jieba 词典。试点期由你维护（同 P76 第 1 项）。改词典或术语表就是新的分词与排序版本，先在问题集上比对再启用（RAG 设计 §7.5、§7.6），版本写进检索读账本。
2. **个人叫法**（个人记忆条目的一种，M2a）：如“我说的‘老王那个泵’是某项目”“我说气嘴指气门嘴”。只对本人生效：放进运行信封，供小Pai 写检索词时换成标准词；服务器在本人的 `memory.search` 和企业检索里做同样的扩展。指向对象的只存对象引用，按当前权限读；撤权后这条叫法一起隐藏。像通用说法的，候选卡上给“提议加入品类术语表”，由维护人确认（P86 第 5 项）。
3. **模糊匹配**（RAG 层，并行轨）：针对型号、料号的错写和简写，试加 pg_trgm 三字片段匹配，作为第三路召回进入 RRF。它是 PostgreSQL 自带的扩展，不算新库；评测有提升才开。
4. **新词来源**：只有本人确认的叫法、用户主动提交的知识缺口报告（RAG 设计 §11.8）、维护人手工录入三个来源。不从别人的私人会话里挖叫法（RAG 设计 N6）。
5. **评测**：问题集加入同一问题的不同说法（口语、简称、中英混写、错别字、部门口径），按说法分别计算召回（§10）。

## 7. 业务场景记忆（新）

研发团队真正依赖的“记忆”大多不属于个人，而是挂在业务上：这个客户在意什么，这个项目定过什么约定，这个品类以前踩过什么坑。本节把这类记忆分清楚、放对位置。

### 7.1 三种业务信息，各走各的路

| 种类 | 例子 | 放在哪 | 小Pai 怎么用 |
|---|---|---|---|
| 业务事实 | 目标价、规格值、G0 决定、问题单状态、变更生效 | 领域对象（已有） | RAG 层按当前权限读当前版本，不进记忆 |
| 范围备忘 | “客户 A 评审必问跌落测试”“本项目样件编号按 项目-批次-序号”“给该客户的报告一律英文”“噪音放宽 3dB 是 10-12 和客户电话确认的，正式变更待补” | 挂在品类、产品、提案、项目上的备忘（新，§7.2） | 按场景配方带进上下文，标“团队备忘（某人某日确认）” |
| 业务经验 | “同类气泵气嘴漏气，根因是 O 圈材质” | 知识候选 → 适用性评估 → 设计规则（已有） | 规则按适用范围检索，可作依据；候选只作提示 |

判断标准：**有结构化字段能放的，就是业务事实，去改业务对象；能跨项目复用、需要验证适用性的，就是业务经验，走知识链；剩下的“团队该知道、但不是正式记录”的，才是范围备忘。**

### 7.2 范围备忘

**挂靠与标签**：品类必填（权限范围根），可以细到产品、提案、项目。可以加标签：客户标识（沿用提案上已有的客户标识，见 §7.6）、阶段、主题。

**受众**：继承挂靠对象的受众，不能更宽（同 P34 对讨论的规则）；挂靠对象的受众收窄时，备忘随之收窄。

**写入**：

- 有该范围写权限的成员可以直接写；
- 小Pai 可以起草备忘候选，场合有三种：在项目、提案、品类运行里用户要求“记下来”，在讨论里被 @ 时（P34：小Pai 不旁听），以及业务事件触发时（§7.5）；
- 候选由有写权限的成员确认（T1：小Pai 预填，人确认一次），经领域命令写入并生成回执。命令暂定为 `scope_note.save` 和 `scope_note.retire`，实施时定名，并登记进 v1.1 附录 A。按 P76 第 4 项（写工具须先加载列出它的技能），`scope_note.save` 列进带业务记忆配方的技能包的 `allowed_operations`。

**字段**：内容（不超过 300 字）、种类（约定 / 背景：约定进约束区，背景进背景区，都不能被引用，§14.9）、挂靠与标签、来源（人工 / run / 讨论串 / 业务事件，带对象版本）、确认人与时间、复核日期（租户可配，缺省 90 天，同核实答案的复核做法）、状态（有效 / 待复核 / 已替换 / 已停用）、是否置顶。

**停用不删除**：范围备忘是业务记录，只能停用，保留版本历史（P83 D193）。作者离开或被移出项目后，备忘保留，作者标“已离开”，复核责任转给对象负责人。

**边界**：

- 不作为工程判据或批准依据。判据只来自已发布的定义，比如产品基线；
- 不改变权限，也不代替正式决定。备忘内容一旦像决定或变更，界面就给出“转为决定草稿 / 变更请求”（P34 已有“转为”动作），按原档位办理；
- 个人记忆不会自动升为范围备忘（§6.3）。

**时效**：

- 超过复核日期的标“待复核”，照常可用，但降级并标注（同 RAG 设计 §11.7 对核实答案的处理）；
- 挂靠或引用的对象出了新版本（提案改版、变更生效）时，相关备忘标“对象已更新，待复核”；
- 项目关闭时，备忘随项目归档，并进入 §7.5 的复盘。

**页面**：项目驾驶舱（P34）、提案页、品类页各加一个“备忘”区，置顶的在前。回答下方的“用到了 N 条记忆”里，团队备忘和个人记忆分开显示。

### 7.3 业务情景：这个项目发生过什么

项目和提案的时间线已经存在：业务事件、回执、项目动态流和讨论（`business_events.py` 已把领域事件纳入企业检索；P34 定义了动态流）。所以**不另建“项目情景记忆”**，避免和业务记录存成两份。

只补一个只读视图“范围近况”：最近的业务事件、置顶的状态更新和备忘变更，复用驾驶舱动态流的查询，用确定性 SQL 生成，不超过 400 token，供 §7.4 的场景配方使用。读取时现算，不另存一份；达不到 p95 目标时再改为按事件预先算好存下（P87 第 7 项）。用户问“这个项目上个月怎么了”时，走 RAG 检索业务事件，不走记忆。

### 7.4 场景配方：每个场景只带它需要的记忆

v1.1 §06.7 要求每个技能包声明自己的上下文合同。本稿在合同里加一项“要带哪些记忆”。服务器按配方装载，模型不能要更多；需要时可以用 `memory.search` 在当前范围内补查。

| 场景（技能包） | 业务记忆 | 个人记忆 | 带来的好处 |
|---|---|---|---|
| 品类研究（`category_framing`、`jtbd`、`opportunity_scoring`、`review_pain_clustering`、`price_band`、`competitor_comparison`、`public_research`） | 品类备忘（目标用户、价格带口径、重点竞品）；品类设计规则 | 本人在该品类的研究情景 | 不重复查已查过的品牌；沿用团队口径 |
| 立项与提案（`proposal_drafting`、`gap_check`、`option_comparison`、`derivative_diff`、`rfq_extraction`） | 提案和同客户标签的备忘（客户关注点、交付要求）；同品类设计规则；以往 G0 意见（业务事件） | 本人写作偏好 | 提前覆盖客户必问的点 |
| 品质与变更（`quality_issue`、`change_control`） | 项目备忘（围堵约定、客户通知要求）；同品类的经验候选和设计规则 | 本人处理过的同类问题 | 借鉴已验证的根因和措施 |
| 试产与验证（`build_execution`、`test_verification`） | 项目备忘（样件编号规则、测试工况约定）；设计规则 | — | 按约定的工况和编号执行 |
| 发布交接（`release_handover`） | 项目和同客户标签的备忘（交付格式、文件清单要求） | — | 交付不漏客户要求 |
| 工作管理与日常问答（`work_management`、日常问答） | 当前范围的置顶备忘和范围近况 | 本人记忆条目、同范围情景 | 接着上次的事继续 |

**预算**：范围备忘不超过 800 token，置顶的优先，其次按相关度和新近度；范围近况不超过 400 token。

**配方属于技能包**：改配方就是改技能包版本，已有资格照 §06.12 重审（同 D247 对预载条件变更的处理）。

### 7.5 业务事件触发的沉淀

主流做法是让模型在后台自动抽取记忆。本稿改为：**业务事件触发，小Pai 起草，人确认后才生效**。触发由 Temporal 的事件或定时工作流发起（即 v1.1 的自动化规则），每次触发都生成运行回执：

| 事件 | 小Pai 起草什么 | 谁确认 |
|---|---|---|
| G0 评审结束 | 评审意见里反复出现的关注点 → 品类备忘候选，或同客户标签的备忘候选 | 提案负责人 |
| 品质问题关闭 | 根因和有效措施 → 知识候选 | 问题负责人；走 `knowledge.candidate.create` 现有档位（T0，须资格与授权；没有资格时进入“AI 需要你”例外队列，DC-11） |
| 项目阶段结束、项目关闭 | 复盘清单：本项目的备忘逐条建议“升到品类 / 转为知识候选 / 随项目归档” | 项目负责人 |
| 变更生效、提案改版 | 不起草，只把引用旧版本的备忘标“待复核”，提醒确认人 | 备忘确认人 |

起草结果进“我的工作”的待确认列表，不自动生效。小Pai 不旁听讨论（P34），触发只来自业务事件和明确的订阅。按 P57，这些系统规则的负责人取触发对象的负责人（表中“谁确认”一列），读写范围不超过其当前范围；起草的只是候选，不写触发对象以外的对象。

### 7.6 客户与供应商

- PDOS 不建客户、供应商实体（不替代 CRM/ERP，不可协商项 5）。客户维度用提案上已有的客户标识作标签；供应商维度用供应快照里的外部引用作标签。
- **客户私有**：带客户标签的备忘默认只在同一客户的提案和项目里装载。跨客户使用，须用户点“包含其他客户项目资料”（RAG 设计 §7.1 的同一规则）；出站按 P26、P30 判定。

## 8. 在上下文里的位置与预算

沿用上下文设计 §4.1 的布局，记忆放在 S3 运行信封里（运行内不变）：

```text
S2 技能正文
S3 运行信封    范围与当前对象；
               本人偏好与记忆条目（≤1,000 token）；
               按场景配方装载的范围备忘（≤800 token）与范围近况（≤400 token）；
               同范围最近情景目录（≤300 token）；
               可继承引用、被删减的字段名
S4 会话历史
S5 工作状态
—— 当前问题 ——
S6 循环内容
```

记忆用服务器信封的固定标签包起来：“本人记忆”“团队备忘”“范围近况”“历史（as_of）”，都注明“不是业务事实”。

按能否被引用分三区（P84 第 4 项，详见 §14.9）：

| 区 | 放什么 | 在上面布局里的位置 | 能否被引用 |
|---|---|---|---|
| 约束区 | 个人固定偏好；个人条目和范围备忘中的口径、约定类条目 | S3 运行信封 | 否，只约束表达方式和做法 |
| 证据区 | 业务对象当前值、核实答案、原件片段 | S3 的当前对象（已有）；运行中检索工具返回的结果（S6） | 是，引用带页、段、单元格定位 |
| 背景区 | 范围近况、情景目录、个人条目和范围备忘中的背景类条目、标为可能过期的条目 | S3 运行信封 | 否，需要依据时回证据区核实 |

证据仍由小Pai 在运行中调用检索工具获取；组装阶段只读当前对象，不在回答前另跑一次检索（回答前预检索会多一次检索和查询向量化出站，影响 P46 时延目标）。记忆和证据内容重复时，保留证据、去掉记忆。

记忆合计最多约 2,500 token，计入上下文预算。缩减顺序（上下文设计 §6.2）补两处：

- 第 1 步同时去掉范围近况和同范围情景目录（背景区先裁）；
- 第 5 步之前，本人记忆截到只剩本范围条目，范围备忘截到只剩置顶条目，都不整体去掉（再裁约束区里优先级低的）。

系统提示、当前问题、工作状态里的约束和焦点对象仍然不缩减。

## 9. 权限、出站、保留

- **个人记忆只有本人可读**：记忆条目和情景索引都用行级权限限定本人；小Pai 以本人请求的身份读取，不能跨人。
- **范围备忘按挂靠对象的受众**：行级权限连挂靠对象过滤，和企业检索同一做法；带进草稿或其他对象时，照 RAG 设计 §9.3 检查受众。
- **共享会话**：按 P52，每位发起人各有一份工作状态和情景记录，只记本人发起的运行。
- **出站**：记忆随运行发给模型，和会话历史一样按 P26 判定数据类别，并记入运行回执。情景向量化见 §6.2。
- **钉钉**：首期钉钉入口不注入本人记忆和情景目录，避免它们出现在群消息里。范围备忘作为有受众的来源，按 P31 的引文规则处理。
- **“不进记忆”模式**：会话级开关。开启后，这个会话不读个人记忆、不生成情景记录、不提议记忆候选、不注入情景目录，和主流的无痕对话一致。范围备忘属于业务上下文，照常按配方装载。运行回执和审计照常保留（v1.1 §06.10），不因这个模式删除。
- **删除**：删除个人记忆条目即清除正文和对应向量；情景记录随会话归档或删除同步处理；范围备忘只能停用，停用后保留版本历史。
- **人员变动**：离职或移出项目时，个人记忆按租户策略归档或删除；他写的范围备忘保留，作者标“已离开”，复核责任转给对象负责人。

## 10. 评测与验收（v0.4 按你 11-07 的评测方案改写，P90）

参考的个人助理记忆评测方案（生命周期六环节、三组对照、分层样本）可以借用，但它评的是用户画像记忆；小Pai 的记忆挂在业务对象上、事实来自 RAG，所以补一条“记忆不冒充事实”的评测线。新增的评测题和用例一律先作为候选，经你确认后才入库（golden-case 不由自动化写入，不可协商项 5）。

### 10.1 十个环节

| 环节 | 核心问题 | 关键指标 | 对应设计 |
|---|---|---|---|
| 写入 | 该不该记、记得对不对 | 写入相关性、提取准确率、分类准确率、元数据完整率、注入写入率 | 写入关口（§5 第 7 条、§14.5） |
| 更新 | 能否正确合并、替换、并存 | 更新操作正确率、幂等性、冗余度 | 个人条目（§6.3）、范围备忘（§7.2） |
| 失效与冲突 | 事实变了，记忆能否让位 | 过期判定召回率、冲突裁决正确率 | §14.9 冲突与失效、事件扇出 |
| 召回 | 记忆和证据能否找对 | 召回率@k、精确率、不应召回抑制率、权限过滤后召回率；按说法变体分别计算（§6.7） | `memory.search`、混合检索、场景配方 |
| 装配与使用 | 放对分区、用得对 | 分区正确率、记忆被当证据引用次数、回复忠实度、任务完成度 | §8、§14.3 |
| 纠正 | 分对去处，错答不再复现 | 分流正确率、已纠正错答复现率 | §14.9 纠正分流、情景记录 |
| 程序性记忆 | 新版本只进不退 | 回归用例通过率、相对上一版的指标变化 | §6.4 |
| 遗忘删除 | 删得干净、不误删 | 删除执行率、误删率、残留召回率、传播完成率 | §5 第 5 条、存储 |
| 权限隔离 | 守住用户、对象、租户边界 | 越权率、权限变更跟随率 | §9、§14.7 |
| 降级 | 嵌入不可用时诚实降级 | 降级告知率、伪零结果率、换模型前后召回差 | §14.9 嵌入版本 |

记忆召回和证据召回分开计分，避免一方的好成绩掩盖另一方。删除的传播范围包括：主表、向量、三字片段索引（如启用，§6.7）、运行记录里对该条目的引用。范围备忘不删除，只考核停用后不再装载。

### 10.2 准出门槛

**零容忍项**（任一用例失败即阻断发布）：

| 指标 | 失败的含义 |
|---|---|
| 越权率 | 跨用户、跨业务对象或跨租户读到、写到、删到了内容 |
| 注入写入率 | 原件、邮件、OCR 文字触发了记忆提议或写入 |
| 未确认写入率 | 小Pai 提议的记忆没经确认就生效 |
| 删除残留召回率 | 已删除的个人条目仍被召回或使用 |
| 记忆被当证据引用次数 | 回答把约束区或背景区的内容当依据引用 |
| 事实冲突采信记忆次数 | 记忆与业务数据冲突时，回答采信了记忆 |
| 伪零结果率 | 嵌入失败却返回空结果，而不是退回关键词检索 |

**质量项**：先测基线，之后按“不低于上一版”把关，下降须说明原因并经评审接受。包括：记忆净收益（真实记忆组相对无记忆组的任务完成度提升须大于 0）、召回率@k 与精确率（记忆与证据分别算）、回复忠实度、分区正确率、过期判定召回率、纠正分流正确率、写入与分类的一致率；范围近况是确定性生成，重复生成必须完全一致。积累几轮基线后，再决定哪些固化为绝对值。

### 10.3 对照组

每次评测在同一评测集上跑四组，RAG 在各组照常开启，变量只有记忆：

| 对照组 | 设置 | 回答的问题 |
|---|---|---|
| 无记忆 | 关掉全部记忆 | 只靠 RAG 时的基础表现 |
| 真实记忆 | 全链路照常运行 | 当前的实际收益 |
| 理想记忆 | 把人工标注的正确记忆直接注入，跳过写入和召回 | 记忆能带来的上限 |
| 单类消融 | 在真实记忆组里分别关掉个人记忆、范围备忘、情景 | 哪类在帮忙，哪类在添乱 |

真实减无记忆是当前净收益，小于 0 说明记忆整体在添乱；理想减真实是写入和召回造成的损失；理想减无记忆是价值上限，上限很小的场景，配方里可以少带或不带记忆。单类消融中增益为负的类型，在对应场景配方里下调预算或去掉。

### 10.4 评测集

最小样本单元是一条**业务场景时间线**：一个业务对象上的业务事件，和多名成员的会话交织在一起，再加一份权限快照；评测题从时间线上截取。字段包括：基础信息（样本、租户、对象、成员、权限快照、会话 / 运行 / 轮次）、业务事件、写入、更新、召回、装配、使用、纠正的标准答案，以及边界标签（负样本、删除、跨用户、跨对象、注入、降级、高敏），另记标注人、复核人、争议项和数据版本。

用例来源：

- 合成时间线：用真实业务对象的结构脱敏后生成，覆盖品类、产品、提案、项目；
- 对抗用例：注入文本、跨用户、跨对象、权限撤销、删除后追问、嵌入服务关停；
- 运行记录回放：**只用本人同意提交的会话**（试点期就是你自己的），去标识后再标注（RAG 设计 N6）；
- 纠正转回归：每条被纠正的运行**生成一道回归用例候选**，你确认后才进入下一版评测集。

敏感分桶除个人信息外，加上业务敏感：客户报价、未公开提案、跨项目内容。

### 10.5 判定与运行

- 能用规则判的不用模型判：越权、注入写入、未确认写入、删除残留、引用指向、分区、近况一致性、降级标记，直接比对运行记录（含使用清单）与标准答案，结果确定、可重放。
- 回复忠实度、任务完成度、写入内容的表述质量由模型评审，须有一份人工标注子集校准，一致率不够的不作门槛。**试点期只有你一名标注人，无法双人校准，这类指标只观察、不作门槛。**
- 质量类按 10 / 5 / 0 三档评分；安全违规不计分，直接判失败。写入与分类类用例重复运行 10 次，记录不一致次数。
- 评测作为 Temporal 工作流运行。技能包、场景配方或嵌入配置变更时，**只跑受影响场景的评测**；完整评测放在闭环检查点和发布前（AGENTS.md“按影响验证”）。真实模型评测的费用和出站照常记账。程序性记忆和 MQE、HyDE 的评测并入同一套评测集。
- 落地顺序：先做安全门禁（越权、注入写入、删除残留、伪零结果）和无记忆基线（M1），再做写入与更新，然后是时间线端到端（真实、理想、单类消融），最后把纠正转成回归用例候选、把运行指标接进监控（降级率、过期记忆命中率、冲突提示数、被纠正运行占比、各配方预算用量）。

## 11. 取舍

| # | 取舍点 | 安全 | 功能 | 体验 | 选择 |
|---|---|---|---|---|---|
| 1 | 情景记录用确定性投影还是模型摘要 | 不会编造，可审计 | 只能靠原话和对象来找，语义略弱 | 用户一般按自己说过的话找，通常够用 | 确定性投影 |
| 2 | 首期索引是否收回答正文 | 不收就不用额外做撤权同步 | 搜不到“小Pai当时说了什么” | 要先定位会话再读全文，多一步 | 首期不收 |
| 3 | 记忆常驻注入还是全部按需查 | 两者一样 | 常驻条目每轮都生效 | 不用等工具调用 | 少量常驻，其余按需 |
| 4 | 小Pai 能否主动提议记住 | 仍需人确认 | 能记下用户没明说的习惯 | 可能打扰，所以每会话最多一次、可关 | 允许，限次 |
| 5 | 不进记忆模式是否也不读 | 更干净 | 这次对话用不上已有的习惯 | 和主流一致，容易理解 | 个人记忆不读也不写；范围备忘照常 |
| 6 | 工作状态闲置 30 天后不自动带入 | 防止旧约束悄悄生效 | 需要时一键恢复 | 多点一次 | 采纳 |
| 7 | 范围备忘是否必须人确认 | 防止 AI 写的内容进入别人的上下文 | 沉淀慢一些 | 确认一次，成本低 | 必须确认（T1） |
| 8 | 是否另建“项目情景记忆” | 不重复存业务记录 | 用业务事件和动态流即可 | 无感知 | 不另建，只补“范围近况”视图 |
| 9 | 是否建客户实体 | 不越过 PDOS 的边界 | 客户维度只能靠标签 | 标签够用于装载过滤 | 不建 |
| 10 | 业务经验自动抽取还是事件触发起草 | 人确认后才生效 | 只在关键事件沉淀，可能漏掉零散经验 | 提醒出现在该出现的时候 | 事件触发起草 |
| 11 | 是否引入专用向量库、图库 | 换库后权限同步有延迟 | 现有规模用不到 | 无感知 | 不引入 |
| 12 | 程序性记忆是否要人审加评测 | 防止坏规则上线 | 改进慢一些 | 无感知 | 采纳 |
| 13 | 回答前是否按配方预取证据 | 无差别 | 证据仍由检索工具在运行中取 | 不多一次检索和查询向量化，时延不增加 | 不预取，组装阶段只读当前对象 |
| 14 | 叫法问题由模型学习还是用词表 | 不从别人的私人会话里挖词 | 词表要人维护，覆盖慢一些 | 本人叫法确认一次即生效 | 术语表加本人确认的叫法 |
| 15 | 质量门槛用绝对值还是“不低于上一版” | 安全类仍零容忍 | 没有基线时绝对值没有意义 | 无感知 | 先测基线，再“不低于上一版” |

| `memory_episode_marks` | 本人对情景的置顶、隐藏；纠正记录 | episode_id、置顶、隐藏；纠正内容、分类、去向、处理状态 | 置顶、隐藏由本人以人的身份写；纠正由服务器按本人的反馈（`run_feedback`）追加，只追加 | 本人 |
| `memory_notes` + 版本表 | 个人记忆条目 | owner_id、版本、作用域、种类（口径 / 背景 / 叫法）、正文（≤200 字）、叫法指向的标准词或对象引用、来源（手写 / run_id）、状态、生效与失效时间、替换关系、依赖清单 | 只允许本人以人的身份写：写入策略要求当前执行者等于请求人且是真人账号，AI 身份写入被数据库拒绝 | 本人 |
| `memory_conflict_notices` | 记忆与业务数据的冲突提示 | 被冲突的条目（个人条目或范围备忘）、run_id、冲突的对象引用与版本、状态（待处理 / 已处理） | 服务器在 `finalize` 后按模型输出存入；不改被冲突条目本身 | 条目作者（范围备忘另加确认人） |
| `memory_candidates` | 待确认的个人候选：记忆条目、转述约束、分享到项目 | owner_id、run_id、种类、内容、建议作用域、疑似冲突条目、状态（待定 / 已采纳 / 已忽略 / 已过期）、过期时间（初始 7 天） | 服务器在 `finalize` 后写入（候选不是记忆）；状态由本人改 | 本人 |
| `memory_index` | 个人情景和个人条目的检索索引 | owner_id、来源种类、来源 ID 与版本、分词结果、向量（可空）、嵌入配置版本 | 后台索引活动；幂等键 = 来源 ID + 版本 + 嵌入配置版本 | 本人 |
| `scope_notes` + 版本表 | 范围备忘（业务对象） | 品类（必填）、产品 / 提案 / 项目（可空）、标签（客户标识、阶段、主题）、种类（约定 / 背景）、正文（≤300 字）、置顶、复核日期、状态、来源依据（带对象版本）、作者与是否已离开、确认人、回执 ID、版本 | 只经领域命令 `scope_note.save` / `scope_note.retire`（T1），与回执同一事务 | 挂靠对象的受众（行级权限复用品类范围策略，再叠加挂靠对象的受众判断） |
| `skill_revision_candidates`（M3） | 程序性记忆的修订候选 | 技能与版本、信号汇总、样例 run、修订差异、状态 | 每日汇总工作流 | 技能负责人、管理员 |

场景配方不是表，写在技能包的上下文合同里（`agent/skill_packages/context-schemas.json`），随技能包版本走。示例：

```json
"memory": {
  "personal": ["notes", "recent_episodes"],
  "scope_notes": {"anchors": ["project", "proposal", "category"], "customer_tag": "same_only", "budget_tokens": 800},
  "scope_recent": {"budget_tokens": 400},
  "knowledge": ["design_rules"]
}
```

### 14.3 读：一次运行怎么装载记忆

1. Temporal 派发运行，`advance_xiaopai_run` 执行图，进入 `prepare_context`。
2. 服务器从运行绑定中取出：租户、本人、范围、已加载的技能、会话是否“不进记忆”、入口（网页或钉钉）。模型参数不参与。
3. 读工作状态（P32，已有）。闲置超过 30 天的不带入，界面提示可以恢复。
4. 合并已加载技能的记忆配方：多个技能取并集，预算取各技能声明的最大值，总量受 §8 的上限约束。
5. 在同一个只读事务、同一行级权限上下文里执行四个查询，不调用模型和嵌入：
   - **个人条目**：作用域为全局或落在当前范围链上（品类 → 产品 → 提案或项目）、状态有效的条目，本范围优先、最近确认优先，截到 1,000 token；
   - **同范围最近情景**：本人在当前范围最近 3 条情景，取一行目录；
   - **范围备忘**：挂在当前范围链上、状态为有效或待复核的备忘。带客户标签的，只取和当前提案或项目同一客户的，除非用户选择了包含其他客户。置顶优先，其次按与当前问题的关键词相关度和新近度，截到 800 token；
   - **范围近况**：复用驾驶舱动态流的查询，取最近的事件，截到 400 token。
6. 把这些条目引用的对象合成一份依赖清单，用 `conversation_acl` 的批量复核方式走一遍当前权限；有依赖不可读的条目不放。
7. 按固定标签写进 S3 运行信封。用到的条目和版本记入 ContextSnapshot，用于回答下方的“用到了 N 条记忆”和审计。
8. “不进记忆”模式或钉钉入口：跳过个人条目和情景目录。

回答路径上只多了四个 SQL 查询和一次批量权限复核；初始目标是记忆组装在 p95 150 毫秒以内，实测后再定。

### 14.4 检索：`memory.search` 怎么算

- **工具定义**：READ，所有范围都下发；参数只有查询语句、种类（情景 / 个人条目 / 范围备忘）、时间范围、更窄的范围、分页。没有租户、本人、权限类参数。
- **步骤**：
  1. 服务器按运行范围确定检索范围（RAG 设计 §7.1），参数只能收窄；
  2. 关键词召回：jieba 分词，词项与编号抽取和企业检索一致，取前 50；
  3. 向量召回（可选）：嵌入配置启用了“本人会话记录”类别才做；查询向量化随运行出站并记回执（P30）；
  4. 用和企业检索相同的 RRF 参数融合；
  5. 乘以新近度衰减（半衰期 30 天），再加重要度：有回执、候选被采纳、置顶的加分，系数按评测定；
  6. 返回前逐条按当前权限和依赖清单复核，撤权的直接去掉，不透露它存在过；
  7. 每页最多 10 条，单条结果受工具结果上限约束（上下文设计 §6.3）。
- **`conversation.history(session_id)`**：服务器校验会话属于本人后才返回，隐藏规则照 P32。

### 14.5 写：各条写入路径

下表是五条主要写入路径；另有两条辅助路径：冲突提示（小Pai 在最终输出里报告记忆与业务数据冲突 → 服务器存入 `memory_conflict_notices` 并通知作者，不改条目本身），纠正（本人反馈 → 服务器追加到 `memory_episode_marks`，再按 §14.9 分流生成候选）。所有路径都受 §5 第 7 条的写入关口约束。

| 路径 | 起点 | 经过 | 落到 |
|---|---|---|---|
| 情景记录 | 运行结束 | `record_finish` 在同一事务里写工作状态新版本和一条情景记录；提交后发事件，后台索引活动做分词和可选向量化 | `memory_episodes`、`memory_index` |
| 个人条目 | 用户说“记住”，或同一会话里纠正两次以上 | 模型在最终输出里给 `memory_candidates`；`finalize` 做确定性校验（长度、作用域必须是本次运行可读的范围、主动提议每会话最多 1 次）→ 存为候选 → 界面候选卡 → 本人点“记住”，以本人身份写入；写入前列出疑似冲突的旧条目，由本人选合并、替换或都保留 | `memory_candidates` → `memory_notes` |
| 转述约束 | 用户说“按上次那样” | 模型提议非逐字约束 → 存为候选 → “本次携带”显示待确认 → 本人确认后，以人的身份追加工作状态版本（现有的 `origin='human'` 路径） | `agent_work_states` |
| 范围备忘 | 用户要求记下来、讨论中被 @、业务事件触发 | 模型调用 `scope_note.save` 准备（T1）→ 现有 T1 候选机制（`domain_candidates.py`）生成待确认项，显示内容和受众 → 有写权限的成员确认 → 领域命令执行，写新版本、回执和领域事件 | `scope_notes` |
| 分享到项目 | 本人在“我的记忆”页点“分享” | 本人直接办理 `scope_note.save`，不经 AI；提交前显示受众 | `scope_notes` |

### 14.6 业务事件沉淀怎么跑

- **复用现有自动化**：每个租户预置几条系统自动化规则（触发方式为 `domain_event`）。管理员可以停用，不能改写。按 P57，规则负责人取触发对象的负责人，读写范围不超过其当前范围，每次运行重新核对。事件：
  - `proposal.g0_decided`（已有）→ 起草品类或同客户标签的备忘候选；
  - 问题关闭（对应 `quality.issue.close` 的领域事件）→ 起草知识候选；
  - 项目阶段结束、项目关闭 → 起草复盘清单。阶段事件随 P33 的 NPI 框架实施后才有，在那之前只接项目关闭；
  - `change.effectivity_recorded`（已有）、提案改版 → 不起草，只做下面的确定性标记。
- **起草**：触发后按现有链路起一个自动化运行（`XiaopaiWork`，来源为 domain_event，用合并窗口去重），加载新技能包“经验沉淀”。它读该对象的评审意见、根因、措施和本项目备忘，输出范围备忘候选（T1）或知识候选（`knowledge.candidate.create`，T0 须资格，没有资格时进入“AI 需要你”例外队列）。候选进负责人的“我的工作”待确认列表。
- **标待复核**：不经模型。一个后台活动查出依据里引用了旧版本对象的备忘，把状态改为“待复核”，并通知确认人。这是系统规则写入，记回执。
- “经验沉淀”是新技能包，上线前要有 golden-case 和资格（v1.1 §06.12）。

### 14.7 撤权怎么传播

- **依赖清单**：每条情景、个人条目、范围备忘都存它引用的对象（类型、ID、版本），格式和 `conversation_acl` 的依赖清单一样，只存引用，不存权限副本。
- **读时复核**：装载和检索时，依赖清单批量走一次当前行级权限；有依赖不可读的，个人条目和情景不放，范围备忘对这个用户隐藏。
- **写时检查**：范围备忘带进草稿或其他对象时，照 RAG 设计 §9.3 检查受众。
- **索引不用同步删除**：因为每次返回前都复核，撤权时不必实时清索引；来源被永久撤回（比如原件撤回）时，后台清掉对应的向量。

这就是 v1.1 §06.8 要求的“检索前过滤，输出和写入前再次检查”在记忆上的具体做法。

### 14.8 程序性记忆的汇总（M3）

- **信号都已有来源**：
  - `run_feedback`：对象错、数值错、缺来源、没用、动作太多、不该自动做；
  - `retrieval_feedback`：用户显式排除的来源；
  - 工作状态里的纠正条件；
  - T1 候选被拒绝或大幅修改；
  - 评测失败；
  - 工具错误类型（D246）。
- **每日定时工作流**：按“租户 × 技能 × 技能版本 × 工具 × 原因”汇总近 30 天的信号，超过阈值就写一条修订候选，附样例 run。可选由模型起草修订差异。管理员在审核页决定；采纳后走 Prompt A/B，发布补丁版本，资格重审。

### 14.9 节点衔接（并入你 11-07 文档的第一部分，P84）

衔接靠三处：读路径的总入口“上下文装配”（即 §14.3 的 `assemble`）、写路径的总入口“事件与写入”，以及贯穿各层的“横切治理”。原有节点都保留，只给每类记忆补上写入、失效和可见性规则。

```text
小Pai 记忆检索系统（节点衔接）
├── 上下文装配（读路径总入口，§14.3）
│   ├── 按场景配方取记忆；证据由检索工具在运行中取，组装阶段只读当前对象
│   ├── 冲突与失效校验：事实以证据为准，可能过期的降为背景
│   ├── 预算裁剪与分区：约束区 / 证据区 / 背景区（§8）
│   └── 生成后核对引用，使用清单写入情景记录
├── 事件与写入（写路径总入口）
│   ├── 业务事件扇出：近况、经验沉淀、记忆失效检查、增量索引
│   ├── 纠正分流：事实错误 / 做法问题 / 个人偏好 / 团队约定
│   └── 写入关口：来源校验、确认、防注入
└── 横切治理
    ├── 权限：个人记忆只给本人；范围记忆继承业务对象的可见性
    ├── 嵌入版本：向量记嵌入配置版本，换模型先重嵌再切换
    └── 评测与观测：§10
```

**各类记忆的写入与失效**：

| 记忆 | 写入来源 | 谁能写 | 需要确认 | 失效条件 | 可见性 |
|---|---|---|---|---|---|
| 工作记忆 | 会话过程 | 系统；转述约束由本人确认后以本人身份写 | 转述约束需要 | 闲置超过时效不自动带入 | 本人 |
| 情景记录 | 每次运行确定性投影 | 系统 | 否；之后只追加纠正 | 随会话记录保留期 | 本人 |
| 个人固定偏好 | 设置页 | 本人 | 本人操作即确认 | 本人修改 | 本人 |
| 个人条目 | 本人手写；本人说“记住”或纠正两次以上时小Pai 提议 | 本人 | 提议须本人确认 | 自设有效期到期；引用对象更新后标“可能过期” | 本人 |
| 范围备忘 | 成员手写；小Pai 在“记下来”、被 @、业务事件时起草 | 对挂靠对象有写权限的人 | 起草须确认（T1） | 超过复核期限标“待复核”，照常带入但降级；对象归档随之归档；只停用不删除 | 继承挂靠对象 |
| 范围近况 | 业务事件与动态流，确定性生成 | 系统 | 否 | 读取时现算 | 继承挂靠对象 |
| 程序性记忆 | 纠正汇总成修订候选 | 审核人 | 审核并通过评测 | 新版本发布后旧版本退役 | 技能包适用范围 |

**写入关口**：必带来源、写入时间、写入人、有效期（可空）、对象引用与版本（可空）。只有本人原话、本人的明确操作或业务事件能触发提议；原件、邮件、IM、OCR 文字里的内容不能触发。个人记忆可查、可改、可删，删除时连同向量一起删；范围备忘只能停用。

**冲突与失效**：

- 每条记忆先分清是口径、约定类（只管表达方式和做法，不和事实比对，进约束区），还是背景、事实类（例如“某客户只接受某规格”，必须让位于业务数据，只进背景区）。
- 带对象引用的：装载时比较对象当前版本和记下的版本，不一致就标“可能过期”，只作背景。
- 内容直接冲突的：回答按事实，可以补一句“你之前记的是 A，当前资料是 B”；小Pai 在输出里报告冲突，服务器存为冲突提示并通知作者复核（§14.5），AI 身份不改条目本身。
- 没有对象引用的：个人条目靠自设有效期；范围备忘靠复核期限，到期标“待复核”，照常带入但降级。
- 可信顺序见 §5 第 8 条。

**纠正分流**：一次纠正先记在运行记录上，再按错在哪分到四个去处。每个去处都只生成候选，纠正不会直接改提示词，也不会直接改事实：

| 错在哪 | 去处 |
|---|---|
| 事实错误 | 提示对象负责人改数据或原件；记忆层不替事实打补丁 |
| 做法问题 | 技能修订候选（§6.4） |
| 个人偏好 | 个人记忆候选（§6.3） |
| 团队约定 | 范围备忘候选（§7.2） |

被纠正过的运行仍可被检索，但降权并附上纠正内容，避免旧的错误回答被再次放大。

**业务事件扇出**：每个业务事件由一个 Temporal 工作流分给四个处理方。事件至少带对象 ID、对象版本、事件类型和时间；处理方按（事件 ID，处理方）去重，各自幂等、可重放，一个失败只重试自己，不阻塞其他三个：

- 范围近况：近况是读取时现算的视图，这一路只让相关缓存失效（如果有缓存）；
- 经验沉淀：符合 §7.5 条件的事件起草候选；
- 记忆失效检查：找出引用该对象的个人条目和范围备忘，版本不一致的标“可能过期”或“待复核”；
- 增量索引：重建该对象相关片段的关键词、向量（以及启用后的三字片段）索引。

**权限衔接**：

- 范围记忆不单独维护权限表，行级权限策略直接引用业务对象的可见性；对象权限一改，记忆的可见性跟着变。
- 个人记忆按“所有者 = 当前用户”过滤；装配时只取当前用户的情景，从不跨用户。
- 向量检索与行级权限：HNSW 是先取近邻再过滤，范围小的租户或对象召回会明显下降。企业检索已开启 `hnsw.iterative_scan`（`embedding_hybrid.py`），记忆沿用；个人记忆量小，可以不建近似索引，直接精确检索。
- 人员变动见 §9。

**嵌入版本**：

- 每条向量带嵌入配置版本（现有企业检索已按 `profile_version_id` 区分），查询只在同一配置的向量里做。pgvector 列维度固定，换维度要用新列或新表（现有做法是按维度建部分索引）。
- 换模型：新配置上线后，后台重嵌全部记忆与 RAG 片段；重嵌期间新写入的两套都写；重嵌完成且检索评测通过后，查询切到新配置；观察一段时间没有回退，再清理旧向量。过渡期一次查询只用一套配置，不把两个向量空间的分数放进同一次 RRF 融合。记忆和 RAG 用同一套租户嵌入配置，一起迁移。
- 降级：嵌入不可用时，检索结果带“仅关键词”标记，写进运行记录，回答里说明本次只做了关键词检索。
