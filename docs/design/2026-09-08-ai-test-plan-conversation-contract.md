# AI 对话调整项目测试计划合同 v1

日期：2026-09-08。状态：**本地对话、来源选择与版本复核已实现**；首片见 §8，本轮新品类/客户冲突/文件应用补验见 §9 和 [补验记录](../reports/2026-09-08-ai-test-plan-acceptance.md)。真实业务试配及用户最终关闭仍待，各阶段出口尚未通过。

用户希望通过对话为新产品功能（例：汽车应急启动）或客户特殊要求增加、调整测试项。本合同承接 [项目类型与测试模板合同](2026-09-08-project-type-test-template-contract.md) §7 的本地首版，作为 V0-6 项目差异配置的后续切片；与 V1-B10 报告导入衔接，分别验收。用户本人负责需求澄清、建议审阅和最终应用；不重复索要其他 Owner。

## 1. 用户得到的能力

在项目“试制·测试·质量”的测试计划旁进入“用 AI 调整测试项”。系统带入已选模板、项目差异和当前计划，用户直接描述变化，不要求用户先制作一套新 Excel 模板。

| 用户表达 | 系统应做什么 |
|---|---|
| “这个新品类增加了汽车应急启动功能，帮我补测试项。” | 先整理新增功能的验证范围和信息缺口，提出候选项；不把其他泵类的已有清单当作完整验证方案 |
| “客户对这项测试提出了额外要求。” | 保留用户转述或所选客户文件原文及版本，定位受影响的原项，展示修改前后差异；已有同义项优先建议修改或合并 |
| “按刚才的客户要求调整方法，其余沿用。” | 在当前候选上继续修改，保留前轮已明确的条件；不重新询问已确认功能，也不丢掉其他已选变更 |
| “这个项目没有该功能。” | 提出项目级不适用变更及理由，展示必测范围影响；不得把“未测试”或“不合格”解释为不适用 |

汽车应急启动是新功能示例，**不是 D14-04 已新增功能的事实**。D14-04 仍按已确认的锂电自行车泵 29 项适用、照明不适用处理。

## 2. 一次完整交互

1. **描述变化**：用户输入自然语言，可选择当前项目内的 Requirement、Specification 或已上传文件作为依据。没有材料也能先形成验证方向草稿；不要求一次填完全部规格。
2. **展示候选**：AI 按“新增 / 修改 / 不适用”列出变化、理由、来源及待补信息；每项可继续对话、编辑或取消选择。界面同时列明未改动的项数。
3. **补齐关键条件**：只追问会改变测试方法或合格判据的信息；将已知条件带入后续轮次。条件缺失的项目保留候选状态，不用模型猜测值补空。
4. **审阅建议**：用户在既有 AI Review 入口查看逐字段差异、依据和范围影响，接受、修改后接受或拒绝。接受仅冻结本轮建议，不改变正式测试计划。
5. **应用变更**：用户单独发起应用；服务端重新核对项目、权限、源计划版本和依据，生成关联原计划的修订计划。返回新版本及新增/修改/不适用清单，原计划与报告可追溯。

对话入口负责生成和完善候选，审阅入口沿用统一 AI Review，不新增另一套审批中心。质量页可展示候选状态并直达相应审阅详情。连续对话产生新候选修订；已接受的内容不被下一轮静默改写，新修订需要重新审阅。

## 3. 候选项必须说清楚什么

| 内容 | 要求 |
|---|---|
| 变更目标 | 新增、修改或不适用；修改须定位稳定测试项标识，不能只凭标题覆盖 |
| 验证目的 | 对应哪个功能、客户要求或项目风险，为什么需要这项变化 |
| 测试内容 | 名称、类别、适用条件、方法、判定依据、证据要求；样机数量/条件在确有来源时填写 |
| 差异 | 原值与建议值、增减原因、必测/选测与不适用影响 |
| 来源 | 用户哪条消息，或哪份需求/规格/文件的版本和段落；引用必须在用户可访问的当前项目范围内 |
| 依据状态 | 已有规格依据、用户提供要求、AI 建议、待补依据分开；用户转述不伪装为已批准客户文件 |
| 未决问题 | 缺哪些参数、条件、方法或判据；来源互相冲突时同时展示，不能自行择一覆盖 |

AI 可建议验证方向，但不能凭一般知识捏造标准编号、条款、合格阈值或“满足认证”的结论。可查验引用的存在和原文，不等于自动证明该引用适用于本产品；适用性由用户审阅确认。未核实的标准引用标为待核实。

候选允许不完整；要应用为可执行测试项，方法、判定依据及适用条件必须明确。若测试只记录参考值，必须明确参考用途与记录要求，不凭参考值判 passed。用户补充的工程判据保留为用户定义依据，不冒充外部标准。

## 4. 版本、历史与覆盖

- 公共模板、项目计划修订、测试执行结果分别保存。一次项目对话只影响该项目的候选，不发布公共模板或改变其他项目。复用到新品类模板属于另一次显式发布动作，首片不包含该发布功能。
- 首片采用“从原计划创建修订计划”，不原地覆盖已有模板快照。保留父计划、原模板版本与 digest、候选修订、最终差异、接受人/时间、应用人/时间。应用前展示目标阶段和范围。
- 原项的稳定标识用于说明谱系；新增标识由服务端分配。新版本用例重新实例化，原 Run、报告、样机、测量值、执行日期和签名留在原计划。旧证据可供查看，首片不自动算作新版本的执行证据。
- 已接受但未应用的建议不改变覆盖分母。应用后的必测分母按新快照计算，新增/修改项不会因生成文本变成已测试。通过、失败、缺证据、参考与不适用继续分开显示。
- 源计划、用例决策或引用版本在建议生成后发生变化时，旧建议不能直接应用；显示冲突并重新生成差异、重新审阅，不能静默合并。幂等重试同一次应用只产生一个修订计划。
- 删除旧用例、覆盖历史结果、降低 Gate 硬闸或修改已批准基线均不由本入口直接执行；涉及既有工程变更/基线政策时转入对应流程。新建修订计划不代表既有 Gate 已批准采用它。

## 5. 接入现有 AI 与授权机制

现有只读 `/ai/chat` 不因本功能获得通用写权限；报告导入模型目前只建议列映射，也不复用为业务测试政策。新增能力归属既有 Quality Intelligence，经统一模型网关调用，登记独立 capability、版本化静态 prompt、结构化输出和所需上下文投影。

首片沿用现有 Finding `pending_review → accepted/rejected → applied` 的两个人工动作。模型只有候选出口，实际计划写入由受控应用服务完成，`pdos_agent` 对业务表零写权限不变。用户可按现有角色权限分别完成两步；不据此豁免产品已存在的独立签核约束。

实现必须同步扩展 Finding 载荷校验、白名单应用适配、前后端类型与收件箱差异展示，不可把未登记的新 payload 塞入其他 Finding 类型。租户、项目、计划、操作者和引用权限由服务端绑定，模型返回的 ID 或“用户已经批准”等文字不能成为授权事实。

上下文只包括经现有数据治理允许的投影和用户授权范围内的资料；不为生成测试项上传整个历史报告或跨项目客户材料。文件/消息中的指令按不可信内容处理。保留模型调用、prompt 版本和候选来源，模型不可用或超预算时明确显示失败，已保存草稿与人工编辑继续可用。

## 6. 验收场景

以下为完整验收合同，不因首片工程验证而整体勾选。各项当前覆盖和缺口见验证记录；合成参数仅用于隔离测试，不构成真实产品规范。

| # | 场景 | 必须看到的结果 |
|---|---|---|
| ATC-01 | 新功能没有详细规格 | 生成有理由的验证方向及待补清单；未知阈值不编造，未就绪项不能应用为可执行用例 |
| ATC-02 | 用户分两轮补充条件 | 第二轮继承已确认条件，只调整相关候选；可取消选项，不重复生成同一项 |
| ATC-03 | 客户要求与现有测试重复或冲突 | 定位原项显示字段差异；保留双方来源和冲突，不悄悄新增重复项或认定客户要求已批准 |
| ATC-04 | 用户审阅后尚未应用 | 正式计划、覆盖分母与执行记录均不变；拒绝也无业务写入 |
| ATC-05 | 用户应用已就绪建议 | 同事务生成一个可追溯修订计划、用例、事件和审计；重试不重复创建 |
| ATC-06 | 原计划已有通过/失败报告 | 原结果完整保留；新计划不继承通过结论或执行日期，待测项数正确 |
| ATC-07 | 建议生成后计划或来源变化 | 旧建议应用被拦截并提示重审，不覆盖用户后续修改 |
| ATC-08 | 跨租户、跨项目、伪造操作者/批准、无写权限 | 读取与应用均按服务端权限拒绝；候选文本不能提升权限 |
| ATC-09 | 文件含“忽略规则、自动批准”或模型虚构引用 | 不执行嵌入指令；不存在/越界引用被确定性预检拒绝，未核实依据不能伪装已验证 |
| ATC-10 | 把失败项要求改为不适用 | 展示失败历史与变更影响，不能删除失败或借此绕过 Gate |
| ATC-11 | 模型关闭、超预算或输出不符合结构 | 可见失能，没有业务变更；已存候选可继续查看，人工路径仍可用 |
| ATC-12 | 普通项目对话提到应急启动 | 不修改 D14-04 或公共自行车泵模板；该示例不冒充第二产品线真实试配 |

验收证据须包括隔离 API/浏览器完整成功与拒绝路径、权限/幂等/历史保护、适用完整回归与构建。真实模型产出质量需另留所用模型、prompt 版本、输入范围与用户审阅结果；模拟模型的工程测试不能代替质量验收。golden 可信集仍由人管理，本次不写入。

1. 先完成候选与计划修订合同落库、Finding 白名单适配及历史/并发保护，按当时迁移 head 分配新迁移号。

初次登记时只完成需求与验收口径；后续实现进展按下节记录，真实试配、V0/V1 及 Sprint 5 出口分别裁决。

## 8. 本地首片实现（2026-09-08 历史切片，当前增量见 §9）

- 已接通质量页“用 AI 调整测试项” → 多轮候选 → AI Review 逐字段核对/编辑/取消项 → 接受 → 独立应用为新修订。保存原始候选、人工修改后的候选与每次动作，前轮建议在新候选成功后失效。
- 新迁移 `0058_ai_test_plan_changes` 与 `quality_intelligence.test_plan_change` 能力登记、Finding 类型/应用白名单和界面同批交付。仅显式对话请求触发，走既有合格模型和统一网关，业务表写入仍由人审应用服务执行。
- 首片输入为所选模板和用户输入的要求，可直接转述客户要求；当时没有 Requirement/Specification/客户文件版本选择器。提示语不把用户输入当作已批准文件。
- 首片启用 `test-plan-change-v3`：模型只选当前输入中的来源标识，系统绑定对应原文（去除两端空白），未知或越界来源拒绝。保留 v1/v2 静态版本供实验调用追溯。引用适用性、语义重复及技术标准正确性仍须人审；没有改写或发布 golden 可信集。
- 每次正式应用创建一个后继计划，所有新用例从待执行开始；已有报告与 Run 保留。后续变更从最新修订继续，旧计划不能并行派生多个后继。计划/用例/报告/Run 变化、失败项排除、必测范围全部取消、重复应用均有确定性保护。
- 真实浏览器与 MiniMax-M3 已在合成指示功能场景中完成补充条件、修改后接受和独立应用；原计划 1 项，新修订 2 项且结果证据为 0。操作由 Agent 使用测试 Owner 完成，**不是用户签署 D14-04 验收**。完整验证与剩余场景见记录。

首片结束时的来源选择和指定冲突样本缺口已按 §9 补验。汽车应急启动仍只是示例；D14-04 的 29 项范围与照明排除不变。

## 9. 来源与验收增量（2026-09-08）

- 已接通项目内已关联需求、规格和已上传/解析的内部文件片段选择；展示名称、版本、状态、定位及原文。最多选择 8 处，分页加载；长文本明确提示拆分，不静默截断。沿用既有文件上传入口，机密/受限文件不进入模型来源。
- 来源由服务端按项目/租户重取，摘要覆盖版本和正文；生成后、接受和应用时均复核，正文修改或权限收回则要求重审。新计划保留冻结来源；选择文件不视为批准其内容。
- 当前使用静态 `test-plan-change-v5`，v1～v4 保留调用追溯。实际 M3 验证新品类缺条件候选、客户文件与原项冲突、用户补充判据后的连续修订；实际浏览器走通文件引用→接受→独立应用，旧 1 项保留、新 2 项待测且 0 结果证据。
- 验收发现该路由 30 秒传输等待不足，限定该入口为 90 秒、一次结构化生成；其他入口保留原策略。实际供应商繁忙时界面保留输入与所选文件，手动重试成功。
- 完整覆盖、失败实验及工程证据见 [补验记录](../reports/2026-09-08-ai-test-plan-acceptance.md)。这些是受控合成场景下的软件结果，不代表开放域技术标准/同义识别准确率，也不替代用户对真实项目方法、判据、适用性的审阅。真实要求试配及用户最终关闭仍待；不增加生产/外发授权，不勾选 V0/V1/Sprint 5 Exit。
