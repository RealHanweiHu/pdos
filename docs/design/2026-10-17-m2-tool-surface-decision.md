# M2 工具面收敛：A/B/C 实际代价与可决策取舍

**状态：待你决策，2026-10-17。只写文档，未改代码，未改 v1.1 冻结条款。**
本稿细化[M2 工具下发方案](2026-10-08-m2-skill-tool-delivery-proposal.md)，补三项它当时没有的事实：**今天实测的载荷**、**供应商端已经可用的原生机制**、**实际配置的模型路线**。活动状态仍以[唯一清单](../../tasks/ai-native-integrated-todo.md#current-queue)为准。

## 0 结论

**推荐 C 作为两协议通用底座，在合格的 Anthropic 路线上升级为 B；不采用 A，除非你坚持"跨技能组前缀绝对稳定"这一条。不采用 tool search。**

理由一句话：A 用**确定的损失**（永久放弃业务参数的原生 schema 约束，并重建唯一的写入证明路径）去买**跨组缓存前缀稳定**这一收益，而该收益在本项目实际默认配置的 OpenAI 兼容路线上**从未被测量**——该分支连缓存断点都没有设置。B 在合格模型上同时拿到缓存稳定、原生 schema 和更小的可见面，代价只是协议与模型可用性。

## 1 先纠正三个已过期的前提

今天用项目自己的 `default_registry()` 与 `SkillCatalog()` 离线重算（未连数据库、未读凭据、未调模型），结果与 10-08 方案稿已显著不同：

| 指标 | 2026-10-08 方案稿 | 2026-10-17 实测 | 变化 |
|---|---:|---:|---|
| 主循环工具数 | 106 | **115** | +9 |
| 主循环定义字节 | 167,596 | **227,803** | **+35.9%（9 天）** |
| 12 技能并集 | 32 个 / 6,255 B（3.7%） | **33 个 / 54,007 B（23.7%）** | 字节 **×8.6** |
| 不属任何技能的工具 | 74 | **82** | +8 |

**第一个纠正**：方案稿"并集只占全量 3.7%"已失效。它自己预告了原因（"部分 M3 工具目前也只有占位 schema，领域合同补齐后应重测"）——M3 把占位 schema 填成真实领域合同，并集字节涨了 8.6 倍。**不要再用 3.7% 或"降低 96.3%"做决策依据。**

**第二个纠正**：真正的收益不在"并集"，在**单组**。一次运行通常只预载 1 个技能、偶尔自加载第 2 个：

| 技能组 | 主循环工具 | 定义字节 | 占全量 |
|---|---:|---:|---:|
| category_framing | 7 | 6,717 | 2.9% |
| public_research | 11 | 9,458 | 4.2% |
| proposal_drafting（最大） | 16 | 19,489 | 8.6% |
| 12 技能并集 | 33 | 54,007 | 23.7% |

典型单技能运行的可见面是全量的 **3%–9%**；双技能约 **6%–15%**。这是分组真实能买到的东西。

**第三个纠正**：82 个未归组工具按档位分布为 **T1 50 个、T2-prepare-only 16 个、T0 13 个、READ 3 个**。即模型每轮看到的绝大多数工具，是它在当前技能下**根本不被授权调用**的实质写入与具名决定命令。隔离子任务侧已经没有问题（research 2 个 / 662 B、extract 1 个 / 665 B、mcp 1 个 / 410 B）。

增长曲线本身是独立论据：9 天 +36%，而工具由领域命令登记表自动生成（v1.1 §06.6.1），S3–S5 的制造、供应、质量、组合尚未接入。**这不是一次性优化，是需要一个随领域增长不失效的机制。**

## 2 这是两个问题，缓存只解决第一个

方案稿把两件事合成一个"载荷与选择问题"。它们的解法不同：

**P1 每轮重发 227,803 字节的费用与时延。** 这个问题**基本由缓存解决，前提是前缀稳定**。按已核对的 Anthropic 定价，Opus 5.5 的缓存读是输入价的 0.05×（$0.20 / $4.00 每 MTok），写是 1.25×（5 分钟 TTL）；渲染顺序为 `tools → system → messages`，而**现有适配器把唯一的 `cache_control` 放在 system 文本块上，恰好把 tools+system 一并缓存**（[agent_client.py:111](../../pdos-next/server/pdos_next/providers/agent_client.py:111)）；`registry.definitions()` 也已按名称排序，没有静默失效源。也就是说：在 Anthropic 路线上这件事今天已经做对了，P1 在命中缓存时的边际成本只有标价的 5%。

**P2 模型可见面 115 个工具（其中 82 个当前无权调用）带来的选择准确度与上下文占用。** **缓存完全不解决 P2**：缓存只降低重复传输的计价，不会把无关工具从模型视野里拿走。方案稿自己写了这一点（"即使缓存命中，全量工具仍需传输并占用模型可见上下文"）。

所以取舍的正确问法不是"哪个方案最省钱"，而是：**在不破坏 P1 已经做对的部分、不破坏写入证明的前提下，用什么机制解决 P2。**

## 3 四个方案的实际代价

供应商侧事实已核对（渲染顺序、失效层级、原生追加机制、tool search 约束）。**关键事实：顶层 `tools` 数组的任何增删改序，会同时让 tools、system、messages 三层缓存全部失效——这是唯一和模型切换并列的"全量重建"操作。** 下表的"组切换"指运行中 `skill.load` 导致可见工具集变化。

| | A 固定窄入口 + `arguments_json` | B 原生 `defer_loading` + `tool_addition` | C 按技能组固定 tools | D tool search |
|---|---|---|---|---|
| 解决 P2（可见面） | 是 | **是** | 是 | 是 |
| 顶层 `tools` 是否恒定 | 是（4 个入口） | **是（仍是全量 115，只带 defer 标记）** | 组内恒定 | 是 |
| 组切换是否重建缓存 | 不重建 | **不重建**（追加块走 `messages[]`） | **重建一次** | 不重建 |
| 业务参数是否保留原生 schema | **否** | **是** | **是** | 是 |
| 未来能否启用 `strict: true` | **永久不能** | 能 | 能 | 能 |
| 协议可用性 | 两协议 | **仅 Anthropic 原生** | **两协议** | 仅 Anthropic 原生 |
| 模型可用性 | 不限 | Opus 5/5.5/4.8、Fable/Mythos 5/5.1、Sonnet 5.5；**不含 Sonnet 5**；Foundry 不可用 | 不限 | 需支持 tool search 的模型 |
| 谁决定可见工具 | 服务器 | **服务器** | 服务器 | **模型自主检索** |
| `tool_definitions_digest` 改动量 | **大（见 §4.4）** | **小**（顶层仍全量，只多 defer 标记与披露集合） | 中（摘要改为"组定义"，组是已记录技能绑定的确定函数） | 大 |
| 模型回复里是否仍是真实工具名与原生参数 | **否，需重新解析重建** | **是，证明第 4 类事实零改动** | 是 | 是 |

**D 直接排除**，不是性能原因：tool search 是**模型自主发现**工具，而 v1.1 的冻结前提是服务器按当前用户、范围、技能启用与资格决定可调用范围（§06.3.3、§06.5）。供应商文档对二者的分工写得很直接——tool search 用于 *discovery*，原生追加用于 *control*，"你的应用决定工具集变了并显式说明"。PDOS 要的是后者。另外 tool search 要求至少一个工具不得 deferred，否则请求直接 400。

**B 的机制**（这是 10-08 方案稿低估的部分，它当时写"依赖具体 API、模型和协议能力，当前适配器尚未接入"——机制现已明确可用）：所有 115 个工具照旧在首轮声明于 `tools[]`，非当前技能的那些带 `"defer_loading": true`；**deferred 工具对请求是已知的，但不进入模型上下文，直到服务器发出 `tool_addition` 把它浮出**。追加与撤回都是 `{"role": "system"}` 消息里的内容块（`tool_addition` / `tool_removal` + `tool_reference`），走 `messages[]` 末尾追加，不改顶层 `tools`，因此缓存前缀完整存活。beta 头 `mid-conversation-tool-changes-2026-07-01`。

B 与 v1.1 的契合度高于 A 和 C：
- **前缀冻结（AGENTS.md 不可协商项 4）**：顶层 `tools` 与 system 字节恒定，动态状态按 §06.7 追加到末尾——这正是该条要求的形状。
- **渐进披露（§06.3.3）**：`skill.load` → 服务器校验租户启用与范围 → 服务器发 `tool_addition` 浮出该技能的工具。服务器仍是唯一决定者，与"未加载对应技能时服务器拒绝写工具调用"同构，且现在**模型连看都看不到**，而不只是被事后拒绝。
- **撤权**：`tool_removal` 给了权限撤销一个协议级落点，当前只能靠执行前拒绝。
- **附带修正一处注入面**：B 的追加块必须走 `role: "system"` 消息，而该通道是**不可伪造的 operator 通道**（供应商文档明确：用户/工具内容里的文字可被任何能写入用户可见输入的东西伪造）。当前实现把技能正文和服务器上下文都作为 `{"role": "user"}` 消息注入（[graph.py:196](../../pdos-next/server/pdos_next/agent_kernel/graph.py:196)）——在一个以"外部内容是数据不是指令"为前提的系统里，操作者指令和用户输入同处一个不可区分的通道，是值得单独修的。接 B 顺带解决。

**B 的两个硬约束，必须一起定**：
1. **协议**：仅 Anthropic 原生。而 `.env.example` 的默认是 `PDOS_LLM_MODEL=MiniMax-M3` 走 `openai-compatible`。B 对默认路线不可用。
2. **模型**：`.env.example` 的 anthropic 预设写的是 `claude-sonnet-5`——**恰好是 Claude 系里唯一两个机制（会话中系统消息、会话中工具变更）都不支持的那个型号**。采用 B 必须同时把该预设改为 Opus 5.5 或 Sonnet 5.5。
3. 另有一条运维语义：**改一个工具的定义要跨两次请求**（先 `tool_removal`，下次请求带新定义），需与现有 `VERSION_CONFLICT` 与恢复规则对齐。

**C 被方案稿低估。** 方案稿判它"无法承诺跨组完整前缀稳定"而降级为备选。按实测重算这个代价：运行开始时由预载技能确定该运行的 tools 列表并固定；预算是 12 轮模型调用，12 轮共享同一前缀；只有运行中 `skill.load` 导致组变化时重建一次，一次运行现实上最多 1–2 次。换来的是：两协议都能用、业务参数保留原生 schema、`strict` 保持可选、摘要改动有界。**用偶发一次缓存重建，换"永不放弃原生 schema"，是比 A 划算得多的交易。**

## 4 放弃原生 schema 约束的风险（A 专项）

你专门问了这一条。先把现状说准，避免高估也避免低估。

**4.0 现状基线**：今天每个工具发的是 `{name, description, parameters}`（[registry.py:82](../../pdos-next/server/pdos_next/agent_kernel/registry.py:82)），**没有任何工具设置 `strict: true`**；`strict` 只用在输出 schema 的 `response_format` 上（[agent_client.py:70](../../pdos-next/server/pdos_next/providers/agent_client.py:70)）。所以现在并不存在"供应商侧保证"，只有**供应商侧尽力约束 + 服务器校验**。这也正是 §09 把 schema 遵从度写成**评测项**而不是保证的原因。

据此，A 的风险要精确表述为下面五条：

**4.1 失去的不是已有的保证，是获得保证的可能性。** `strict: true`（配 `additionalProperties: false` + `required`）能让供应商保证 `tool_use.input` 完全符合 schema。A 之后，供应商看到的只有 `{tool: string, arguments_json: string}` 这层信封；业务参数是一个不透明字符串，**`strict` 对它永久失效**。同时连今天的尽力约束也一起失去。这是一条单向门。

**4.2 新增一类今天不存在的失败模式：字符串内 JSON。** 供应商文档明确要求工具参数必须用 `json.loads()` 解析、绝不做原始字符串匹配，并提示近期模型在工具参数里的 JSON 转义（Unicode、正斜杠）会不一致。把一个 JSON 对象再包进字符串，等于让模型做双层转义。方案稿自己要求严格解析（拒重复键、非有限数字、非对象）——这是一整类新的拒绝面，且**供应商侧帮不上忙**。每次这类失败都要消耗一轮模型调用去纠正，而预算只有 12 轮。

**4.3 它会拆掉 T0 资格阶梯所依赖的测量。** §09 写明"原生工具调用和 schema 遵从度是模型资格的评测项"，§06.12 的 T0 阶梯要以此为证据。A 之后所有工具调用都走同一个信封，**按操作测量 schema 遵从度这件事本身不再可能**——你会在正式启用资格阶梯之前，先把该阶梯要用的度量拆掉。这是 A 最被低估的代价：它不是性能问题，是**资格证据链**问题。

**4.4 它要求重建唯一的写入安全边界上的证明路径。** [execution.py:277](../../pdos-next/server/pdos_next/agent_kernel/execution.py:277) 断言 `digest(registry.definitions()) == model.tool_definitions_digest`，并逐项核对模型回复里的 `name`/`arguments` 等于实际领域工具调用。A 之后模型回复是窄入口，必须按固定解析规则从入口参数**重新推导目标工具**，才能接回 `WriteSource(skill, model_call_id, response_index)` 与幂等键。方案稿 §6 已经点明"只筛选 tools、只放宽摘要比较或改写模型回复名称，都会破坏既有证明"。对比之下 **B 的第 4 类事实（实际调用来源）零改动**，因为回复里仍是真实工具名和原生参数。把新解析代码放在全系统唯一的写入边界上，是风险最不该增加的位置。

**4.5 它买的收益在实际配置的路线上未经测量。** A 的全部正当性是"跨组前缀稳定以命中缓存"。但本项目默认路线是 MiniMax over OpenAI 兼容，而该分支**没有设置任何缓存断点**（`cache_control` 只在 Anthropic 分支），第三方 OpenAI 兼容服务的缓存行为方案稿自己也要求"按实际服务商与模型验证"，至今未测；MiniMax codec 还会往 `tools` 里追加一个 `finish_tool`。**在未证实该路线存在可利用缓存之前，A 是用 4.1–4.4 的确定损失，换一个未验证的收益。**

## 5 推荐路径与顺序

**第一步（无论最终选 B 还是 C，都要做，且只做一次）**：按 `allowed_operations` 从唯一注册表生成技能工具组；把"每次模型调用的披露集合"（技能绑定、工具名/版本/schema 摘要、披露消息摘要）作为服务器事实记入运行、调用与检查点。保留方案稿 §6 的"同一回复里先 `skill.load` 再调用新技能工具 → 拒绝，要求下一轮"这条规则。A/B/C 共用这一层，先落地它不锁定任何路线。

**第二步**：落 **C**，两协议通用。组由预载技能在运行开始时确定并固定；运行中 `skill.load` 触发一次重建，记录重建次数作为可测指标。此时已经拿到 P2 的主要收益（可见面降到全量 3%–15%），且没有放弃任何东西。

**第三步**：在 Anthropic 原生且模型支持的路线上升级为 **B**，连组切换都不再重建，并顺带把技能正文与服务器上下文从 `role: "user"` 迁到 `role: "system"` operator 通道。前提是把 anthropic 预设从 `claude-sonnet-5` 换成 Opus 5.5 / Sonnet 5.5，并接 `mid-conversation-tool-changes-2026-07-01`。按 §09"不达标的模型可以在适配器内部降级，但对外显示能力限制，不伪装成相同能力"，C 与 B 的差别就登记为该路线的能力限制。

**A 只在一种情况下需要**：你要求在 OpenAI 兼容路线上也达到跨组前缀绝对稳定。那么先补 §4.5 的前置测量（证明该路线真有可利用缓存），再按 4.1–4.4 逐条接受代价，并把"业务参数无供应商侧约束"登记为该路线的能力限制。

## 6 需要你定的三件事

1. **是否接受 C 作为底座**（偶发一次缓存重建，换保留原生 schema）。
2. **是否开 Anthropic 原生路线并把预设模型换成 Opus 5.5 / Sonnet 5.5**，以便升级到 B。不换型号，B 不可用。
3. **A 是否保留为 OpenAI 兼容路线的退路**；若保留，是否先做 §4.5 的缓存前置测量再决定。

## 7 本稿未验证的边界

- 全部字节数为离线实测；**token 数未计**——需在获得模型调用授权后用 `count_tokens` 按实际型号测，不在此估算。
- 真实时延、费用、误选率与参数错误率的对照未做，需真实模型授权；本稿不授予模型调用、出站或 T0 资格。

- 供应商侧机制与可用型号按 2026-10-17 已核对的官方能力口径；采用前按当时文档复核 beta 头与型号清单。
- 本稿只给候选取舍，**不修改 v1.1 §06.3.3 或任何冻结条款**；确定路线后按 AGENTS.md 先形成你的决策记录，再同步架构文字与 AT-58 判据。
