## 0. 本次交付与批准边界

用户已批准执行本计划。先做 B0，再按 B1–B8 推进，M2 按 §4.1 在 B3 后并行。批次是实现与受影响验证的边界，不新增逐批人工审批；权限、事务和缺陷修复立即验证，完整构建、整链和恢复集中到检查点。

覆盖 `pdos-next/` 已有后端、必要的前端/BFF/契约接线、测试夹具，包含暂停中的交样、测试、CAPA、变更、制造代码。S2–S4 的新业务能力继续冻结；不在 M1 补工装验收、正式制造放行等尚未完成的能力。小Pai 新内核、公开研究、立项提案、规格字典与 G0 新闭环由 M2/M3 建设；M1 只提供所需的品类范围根和共同执行基础。

原工程 `server/`、`web/` 及其备份不改、不导入数据，也不再为它做兼容（V7）。共用运行时包 `packages/pdos-agent-runtime` 去掉 realm `pdos`，只保留 pdos-next。git push、生产操作、真实外发及账号操作不在本计划的实施授权中。

沿用 shadcn/ui + Tailwind v4 + Geist 与[双主题 UI 基线](2026-08-09-ui-baseline.md)。golden-case 只作只读可信根。AI 经领域命令写入、固定提示前缀、服务器绑定运行范围和 Temporal→LangGraph 的执行边界保持。

## 3. 统一实施规则

| v1.1 规则 | 落地方式 | 必须保留的保障 |
|---|---|---|
| Current 落库 | 复用各域已有 Current；缺少的当前摘要由事实所有者维护，事实/Current/水位/Outbox 同事务 | 异步失效事件未消费时，权威水位仍能发现旧摘要；UNKNOWN 不变成已通过 |
| 直接来源 + 上游摘要 | 批量读取直接来源和对应 Current/水位；完整重证只在 T2/放行提交前一次 | 来源权限、不可变字节、安全状态、适用范围继续核对 |
| 请求内一次证明 | 共享 tenant/actor/category/subject、版本、来源摘要、水位、用途、事务绑定的请求内证明 | 不跨 Session/事务复用；人工确认跨请求只保存载荷/版本/水位绑定，提交时比较权威值 |
| 签署时固定资格 | Decision 固定签署身份和当时资格，撤销事件追加待复核状态 | 历史决定不被改写；新的受约束动作检查当前适用状态 |
| 幂等快速返回 | 在昂贵领域计算前查原意图/回执，同载荷只核当前读权限 | 同键不同载荷冲突；受众收窄后不能读出旧私有回执 |
| 时间窗收窄 | 删除材料捕获/全闭包的最早期限传递；T1 确认保留有效期，其他提交比较版本/水位 | 登录、授权、服务商协议、校准等本身的有效性仍按安全/业务事实判断 |
| 上限分离 | 删除"来源最多 20 条"等业务上限及对应 CHECK；集合完整性用服务端完整读取/分页 | HTTP 字节大小、分页、解析资源限制仍存在；不可静默截断来源 |
| 一次快照读取 | 对相关命令明确选择 PostgreSQL 快照隔离或依赖锁，批量读取一次 | 并发新增/撤回由单调水位、约束和必要锁保护；序列化失败走有界事务重试 |
| 精确扇出 | 依实际引用关系写失效事件/更新受影响水位 | 新增引用与资产变化的竞态要验证，未授权范围不收到私有载荷 |

实现时避免把全品类 `FOR UPDATE` 变成所有命令的串行瓶颈：公共范围/成员保护与实际对象写锁分开；多对象锁顺序固定且去重。每个新请求重新建立授权证明，运行中的下一条命令能感知撤权；"请求内一次授权"不等于整个 Run 永久授权。

删除业务集合硬上限不等于取消运行预算、资源隔离、去重/冷却或外部权限；这些按各自的运行政策保持。

同一批同时更新该模块的范围字段、Current 消费、错误类别、术语和相关测试；不做一次全仓库文本替换后再逐个修补。

## 5. 新 schema 与迁移链重置（决策 P1）

pdos-next 没有真实数据，原工程数据不迁，合成环境已删除。因此**不保留旧 schema 的升级路径，也不建任何兼容层**。

### 5.1 做法

1. **归档旧链**：`server/migrations/versions/next_0001`–`next_0032` 移入归档目录（例如 `server/migrations/archive/`），不再参与升级；git 历史保留。
2. **建立新链**：新修订号使用新前缀（例如 `s0_0001_baseline`），不复用旧编号。基线迁移按重构后的 ORM 从空库建立全部表、约束、索引、RLS 策略和触发器；之后各批的结构变化按新链单调追加。
3. **结构要求**：
   - Category、成员/Grant 与受众表示；Product 及从属对象带 `category_id`（tenant + category 复合外键），能挂在型号上的同时带 `product_id`；品类级对象（如研究快照）允许 `product_id` 为空。
   - 一开始就设好应有的 NOT NULL、复合外键和唯一约束，不需要"先放宽、回填、再收紧"。
   - RLS 以 tenant + category 为第一键，受众（私有、指定受众）在对象层过滤；范围上下文只能由认证与权威对象关系绑定，查询不能只凭客户端提供的 category_id。
   - 索引按 B0 的查询形状建立（tenant/category/对象 ID、成员、Current 版本/水位、反向引用），不无依据地全表加索引。
   - 删除业务数量和计算窗口类 CHECK；身份、版本、金额等业务约束保留；不把模型、技能包或工具版本写成数据库约束。
4. **不做**：不回填旧数据；不建旧 URL 兼容入口、旧事件版本解析、旧 Run 或旧回执兼容；不做"带旧数据升级"和"不可逆降级拒绝"演练。
5. **夹具与工具**：`pdos-next/tools/` 的环境建立脚本和测试夹具改为直接按新链建库；合成业务案例按真实品类语义建模（例如"汽车充气泵"品类下多个型号）。
6. **一次性**：新链建立后恢复 AGENTS.md 不可协商项 3 的单调规则；出现真实用户数据后，任何 schema 变更都必须走正常迁移。

### 5.2 回滚

- 各批回滚以 git 为准：代码与新链迁移成套回退，测试库直接按回退后的新链重建。
- B8 只做新链的空库 upgrade/downgrade/upgrade 往返，以及在新数据上的备份恢复与事件重放检查；恢复验证只在本轮隔离环境进行。

## 6. 错误码、术语与重复实现

### 6.1 错误契约

顶层错误使用 v1.1 §08.7 的显式标识：`FORBIDDEN_SCOPE`、`SOURCE_UNAVAILABLE`、`SOURCE_STALE`、`VERSION_CONFLICT`、`MISSING_REQUIRED_EVIDENCE`、`CONFIRMATION_REQUIRED`、`NAMED_DECISION_REQUIRED`、`QUALIFICATION_REQUIRED`、`DUPLICATE_INTENT_CONFLICT`、`EXTERNAL_OUTCOME_UNKNOWN`、`UNDO_BLOCKED_BY_DEPENDENCY`、`CANCELLED_RUN`、`VALIDATION_FAILED`、`NOT_FOUND`、`RATE_LIMITED`、`INTERNAL_ERROR`。共 16 个标识（原文把两个 SOURCE 标识写在一行），与"约 15 类"相符。

- 公共输出为 `{code, message, detail, recovery?}`；具体原因存 `detail.reason`，必要时携带字段/对象版本/水位等脱敏定位信息。前端和小Pai 只按顶层类别决定恢复方式。
- 各批逐项登记 `旧 code/HTTP 状态 → 新 code/detail.reason/HTTP 状态`；不用一张兜底表把未知异常都转为"冲突"。未登录用 HTTP 401，范围拒绝用 403。
- 不泄漏"不存在"与"无权查看"的差异；内部错误不把 SQL、堆栈或原件写给用户，诊断留在内部日志。
- 没有历史数据需要兼容；B7 检查 API、BFF、组件、Worker、运行回执都不再依赖旧顶层码。

### 6.2 术语与三方差异

| 名称 | 选择 |
|---|---|
| Product | 代码类名、表名和 `product_id` 保留，界面与现行文档称"型号"；新增 category 根，不做无意义的大面积改名 |
| ProposalBatch | 改为 ConfirmationBatch，复用现有 Confirmation 存储的语义；不与立项提案混同 |
| Loop | 只用 AutomationRule；M1 不新建自动化体系，只清理现行引用 |
| G0–G5 建设阶段 | 现行施工文档和注释改为 S0–S5；业务关卡 G0/G1 保留 |
| 三方差异 | `domain/products/variants.py` 为唯一权威实现；先对照 `engines/derivation` 的有效用例补足能力并移植测试，再删除后者 |
| 第 14–18 波施工合同 | 整体标为"已被 v1.1 取代"，附条款对照表（V6），不逐份改写；旧证据和已发生的失败保留 |

3. 保存/预览/确认/开测/影响分析同步部分和覆盖发布路径完成真实结果与回执，并达到 §2.3 分档目标；长任务返回稳定工作 ID，并能查到真实终态；前后计时、SQL 次数和失败率可核对。
4. 同键同载荷在确认过期、来源变化、资格变化后重放仍返回原回执，只要求当前读权限；同键不同载荷冲突；当前无读权限时不泄漏历史私有结果。

### 7.3 失败与收尾

某批权限、事务或结果回归失败时，暂停该批的依赖消费者，按原因修复并定向复核；继续已授权且独立的工作，不绕过守卫。性能未达标时按 SQL 热点、锁等待、重复证明或确需异步分别处理，不延长 TTL 来制造通过。

每批只在唯一清单原位更新一段"可用能力、证据、剩余缺口"；原始输出放证据目录。收尾集中停止本轮临时服务、清理本轮 fixture，保留可追溯的测量材料。不操作其他项目环境或历史备份。
