## 2. 待确认清单（按影响面排序，越前面越早定、越省返工）

每项给出选项、推荐和不定的后果。"现状"列出审计看到的事实。

### C1 授权与范围的"根"

- **现状**：
  - pdos-next 的授权、可见性和路由都以 Product 为根：`/v1/products/{id}`；Grant 按产品授权；可见性只有 private 和 product 两档（`models.py:117`）；原件必须带 product_id（`models.py:94`）。
  - models.py 里有 68 处 product_id。
  - 品类、尚无产品身份的私有提案、客户变体的受众，都挂不上去。
- **选项**：
  1. 品类为范围根；型号、提案、客户变体挂在品类下，并逐级收窄受众。**推荐。**
  2. 保留 Product 为根，品类另外授权。
  3. 以租户为根，逐个对象设 ACL。
- **不定的后果**：每加一种对象都要补一次权限；立项前研究的快照没有地方挂；越晚改越贵。
- **结果（用户 2026-10-08）：选 1，品类为范围根。** v1.1 据此修改：
  - 成员与授权（Grant）挂在品类上；
  - 型号、立项提案、客户变体、原件和研究快照都带 category_id；能挂在型号上的，同时带 product_id；
  - 可见性在品类内逐级收窄，至少分为品类、私有（负责人与具名评审人）、指定受众三档；
  - 路由以品类为前缀；
  - 现有 `product_id` 为根的表和路由要迁移，迁移方案在 v1.1 施工计划中给出。

### C2 立项提案、产品定义、规格之间的关系

- **现状**：目标架构的 DefinitionRevision/Spec 用自由参数；立项提案在 pdos-next 中不存在；原工程里提案和定义是两套，互不引用。
- **选项**：
  1. 提案独立版本化。提案条目和定义共用同一个"规格条目"结构，并引用字典的参数版本。G0 批准时，把立项版定义固定为型号定义 v1，项目内继续迭代到规格冻结（T2）。**推荐。**
  2. 提案就是定义的早期状态，同一个对象。
  3. 提案和定义各一套，再做映射。
- **不定的后果**：G1 会建出两套模型，"定义转需求"要多一层映射。
- **结果（用户 2026-10-08）：选 1。** v1.1 据此修改：
  - 新增共用的"规格条目"结构：参数版本引用、目标值或上下限、单位、工况、验证方法、来源、条目状态（AI起草、已确认、待专家、未知）、负责人；
  - 立项提案和型号定义（DefinitionRevision）都用这个结构；
  - G0 批准后由领域命令生成型号定义 v1，记录来源提案的版本；
  - 项目内迭代沿用现有的定义版本化，规格冻结为 T2；
  - 目标架构第 256–260 行的 Spec 条目改写为引用参数版本。

### C3 研究类对象的去留

- **现状**：目标架构把 Research、Opportunity、Experiment、策略列为一等对象，产品下有 7 个子页面（第 120、177、232、663–668 行）。K2 和 10/05 评审 B1 认为这是"方法论被做成强制关卡"。
- **选项**：
  1. 删掉机会、实验、策略这三类对象。保留证据库、品类知识、提案和决策记录；JTBD、机会评分等方法改为技能包，结果以视图或提案段落呈现。**推荐。**
  2. 保留为不带状态机的轻记录。
  3. 照原架构做。
- **不定的后果**：重流程会复活，并按 pdos-next"每个对象都要状态机 + Current 指针"的写法实现，以后再推倒的代价很大。
- **结果（用户 2026-10-08）：选 1。** 机会、实验、策略等研究方法全部做成技能包，结果作为提案的一部分，或以可视化方式呈现。v1.1 据此修改：
  - 删除 Opportunity、Experiment、策略这几类对象及对应页面；
  - 保留的对象：证据库、品类知识、立项提案、决策记录；
  - JTBD、同口径竞品对比、价格带、评论痛点、机会评分、方案对比、实验设计等方法写成技能包；产出写进提案的段落或方案对比，或者作为由证据、提案派生的图表视图，不另存状态机；
  - 数值类结果（市场规模、机会评分、成本）由计算工具复算，图表只读这些结果；
  - 目标架构第 120、161、177、232、663–668 行据此改写；产品导航改为"品类 → 提案 / 型号"。

### C5 一致性与性能规则（冻结前必须改的设计规则）

- **现状**：
  - 分钟级耗时**主要由设计规则造成**，不只是实现问题：单条 SQL 约 1.8 毫秒，慢在次数（一个案例 58.5 万次）。
  - 目标架构原文只要求"最小必要来源读集"（第 481 行）和"关键来源读集"（第 1020 行），并允许准备度走缓存（第 1093 行）。是波次合同把它升级成了"完整闭包、每次读取、每个阶段、所有 IO 之后都重核"。
- **推荐把以下 9 条写进 v1.1**：
  1. Current 状态落库，配合失效事件。读取时只比较 id、版本、来源摘要和水位；完整重证只在 T2 或放行提交前做一次。
  2. 来源读集改为"直接来源 + 上游摘要或水位比较"，不再每次重读整个闭包。
  3. 同一请求内只校验一次：校验、预览、应用三步共享同一份证明；确认只绑定版本和水位。
  4. 签发人资格在签署时固定。之后撤销只产生"待复核"，只拦截新的受约束动作，不实时传到所有下游。
  5. 幂等重放直接返回原回执，只核对当前的读权限（与目标架构第 1027 行一致）。
  6. 时间窗只约束"能否基于它发起新决定"。提交时比较水位；长计算改为异步工作；不再取全链最早期限、也不再"不能延长"。
  7. 请求大小上限和业务规则分开。取消"来源最多 20 条"这条业务硬上限：它原本只是请求信封的大小限制（`contracts.py:22`）。
  8. 改用快照隔离或依赖锁之后只读一次，去掉"读两遍比较 ABA"的规则。
  9. 共享资产写入时，只扇出到实际引用它的产品，不再扇出到全租户。
- **验收线**：交互命令 p95 达到秒级，写进 v1.1。
- **选项**：
  1. 新代码立即遵守，旧代码在动到时再改。**推荐。**
  2. 立即整体重构。
  3. 维持现状。
- **不定的后果**：G1 照现有写法实现，同样会是分钟级。
- **结果（用户 2026-10-08）：选 2，立即整体重构。** 已有代码全部按上述 9 条规则改一遍；用户已知悉工作量大，且会推迟第一个闭环。执行安排：
  - 先冻结 v1.1，再开始重构。重构与 C1 范围根迁移、C6 形式化收敛（若同样选立即）、C10 术语改名合并为同一轮，避免同一批代码改两遍；
  - 重构范围包括已暂停的 G2–G4 代码，以及相关波次合同的条款修订（第 14–18 波）；
  - 验收：已有业务路径按原测试回归通过；开测提交、影响分析、发布案例这些实测过的慢路径，交互命令 p95 达到秒级；保留重构前后的计时对比；
  - 重构完成后，再开始 C4 的第一个闭环。

### C6 收敛过度形式化

- **现状**：
  - 字面错误码 323 种，加上原因码共 487 种，而目标架构只定义了 11 类（第 1069–1079 行）。
  - "20"这个数字写死在 84 处 Pydantic 和 44 处 SQL CHECK 中。
  - 有 17 个自加的 `MAX_` 常量。
  - 有 42 处时间窗；测试里要真实等待 216 秒。
- **推荐**：
  - 错误码收敛到约 15 类，具体原因放进 detail 字段；
  - 上限只保留在请求大小和分页上；
  - 时间窗只保留 T1 确认的有效期；
  - 新代码立即遵守，旧代码动到时收敛。
- **结果（用户 2026-10-08）：选 1，立即收敛，并入 C5 的整体重构。** v1.1 据此规定：

  - 时间窗只保留 T1 确认的有效期，其余改为提交时比较版本或水位；

## 4. 性能与形式化：根因（审计摘要）

| 热点 | 规模 | 主要原因 |
|---|---|---|
| 测试资源深读 `_load` | 60 次调用产生 48,147 次 SQL，88 秒 | 每次读取都重查权限、Current 和时效；同一次调用里父级加锁跑两遍 |
| 样件检视 | 33 次调用产生 20,953 次 SQL，38 秒 | 每次都重核签发人资格、重算准备度 |
| `source_for` 逐条锁 Product 和原件 | 约 15.8 万次，266 秒 | 按"完整并集"规则逐条重读 |
| ORM 主键读取 | 约 16.7 万次 | 强制刷新 ORM 缓存（populate_existing）；同一套来源守卫写了 4 份 |
| 影响分析 | 单次 198 秒 | 一个阶段内全图遍历约 7 遍、完整捕获两遍，加上预览和执行共 5 次深读 |

**结论**：N+1 等实现问题只是放大器；只优化实现大约能降一个数量级，但工作量仍按"节点 × 阶段 × 链深"相乘增长，回不到秒级。必须按 C5 修改设计规则。这些规则大多来自第 14–18 波的合同，比目标架构原文更严。

### P9 新增 `evidence.claim.withdraw`（用户 2026-10-08，按推荐）

问题：`proposal.share` 被某条私有上下文 Claim 的身份检查挡住，或某条 Claim 登记有误时，原来只能用 `ai.run.revert` 撤回整次运行，会连带撤掉同一运行里正确的条目与关联。

结论：新增单条撤回命令 `evidence.claim.withdraw`，T1（人一次确认，小Pai 可预填候选）。
- 执行者：私有 Claim 为所在提案负责人，品类可读 Claim 为品类写者。
- 只追加撤回记录，原 Claim 保留为 withdrawn；该 Claim 的证据关联失效；引用它的提案条目与品类知识标记"来源已撤回"，条目值不变，由负责人决定是否修订。
- 已被签署的 G0 决定或封存定义消费的 Claim 不能撤回（UNDO_BLOCKED_BY_DEPENDENCY）；在审提案引用的 Claim 撤回后，按原件撤回同样处理：批准时得 SOURCE_STALE，退回重提。
- 事件 `claim.withdrawn`；落实位置：M3 合同 §3.1、§3.6–§3.8、§4、§5.4、§10、AT-50，技能包草稿 README §3 与 proposal_drafting，v1.1 附录 A。契约目录 `pdos-next/contracts/*.json` 由主会话同步（不在本次修改内）。

### P23 派生入口统一到 G0（用户 2026-10-17，按推荐）

- 起因：v1.1 §02.4 要求"派生出新型号或新变体时走立项提案…G0 批准后生成定义 v1"，而附录 A 同时把 `product.variant.derive` 列为 T1 一次确认的独立命令，代码里它也确实能直接建出 `product_variants` 行。入口两套、合同自相矛盾。
- 采纳：可被定义 v1、项目或平台关联**引用**的变体身份只由 `proposal.g0.decide` 产生并带该 G0 决定；`product.variant.derive` 保留为提案准备用的派生草稿入口（三方差异计算与显式覆盖沿用同一套实现，§02.4）。已并入 v1.1 §02.4 与附录 A 该行。
- 现状核对（2026-10-17）：`create_project` 只在 G0 物化路径被调用，`DefinitionRevision.variant_id` 只在 `bind_g0_definition` 写入，`product_variants` 全行受 `status='draft'` 约束，因此草稿变体拿不到定义 v1 也进不了项目范围。唯一仍能引用草稿变体的下游是 `platform.link.create`，**已按本条加守卫**：目标变体 `g0_decision_id IS NULL` 时 preview 与提交都返回 `FORBIDDEN_SCOPE` / `variant_without_g0_decision`，不写任何平台关联行。
- 测试侧：`tests/g0_fixture.py` 新增 `create_g0_variant`（派生提案 → G0 批准 → 真实变体身份）、`add_category_human`（同租户第三个真人，使具名评审人不必是 `setup.peer`）与 `published_parent`（复用派生测试里那套唯一的 owner-only 合成发布 fixture）。原平台关联测试改为用 G0 产生的私有变体，并新增草稿变体被拒的负向测试。
- 顺带暴露的事实：`product.definition.publish`（规格冻结，T2）仍 `not_implemented`，且 `protect_fixed_definition` 不允许把已存定义改成 `published`，所以**派生提案在真实命令链上还拿不到可引用的发布父版**——派生入口要端到端走通，先要实现规格冻结。这正是 `product.variant.derive` 一直被当作实际派生路径的原因。
- 剩余缺口：派生草稿仍落在独立的 `product_variants` 行上而不是提案内，把它收进提案连同前端"型号派生与父版重核"页的入口改写一起做；在那之前该页仍可用，但它产生的草稿不能被平台关联引用。
- 判据：草稿变体（`g0_decision_id IS NULL`）不能被平台关联、定义或项目引用；G0 批准产生的变体带决定 ID；AI 无技能包声明该操作，不能自行派生。

### P26 服务商数据协议改为可选治理工具；当前模型服务商为 MiniMax；多服务商自助配置为后续方向（用户 2026-10-18）

- 起因：v1.1 §06.9/§06.6.3/§07.5、I24 与 AT-57 把"服务商数据协议登记"设为出站前置——未签约服务商只接收合成或公开资料，查询词命中客户标识也拦截。用户 2026-10-18 明确："不需要这个数据协议。目前阶段使用 Minimax。后续允许用户调用其他 API 包括 chatgpt、qwen 等。"当前试点租户只有自有/合成资料，协议前置只构成真实模型接线的额外阻塞，没有对应保护对象。
- 采纳：
  1. **出站不再以 ProviderDataAgreement 登记为前置。** 每次出站的服务商与数据类别仍由服务器按当前 Run 绑定判定并记入运行回执（`egress_checked`）；模型传来的参数不作为依据。
  2. **ProviderDataAgreement 保留为可选治理工具**：登记了当前有效协议的，按"服务商 × 数据类别"作限制执行（类别超出许可即拦截）；未登记、已停用或已过期的协议不阻断出站。协议登记/续版/停用仍是管理员具名 T2（`provider.agreement.register`）。
  3. 查询词私有标识拦截（`private_query_blocked`）随前置一并取消；研究查询的资料类别判定（公开/内部/客户原件）保留，作为出站回执的分类记录。
  4. 当前阶段模型服务商为 MiniMax（国内 M3）。真实接线的剩余恢复条件是**凭据（KMS 引用）与价格/计费材料**；"数据协议"从恢复条件中移除。
  5. 后续方向：模型服务商配置改为租户自助（OpenAI 兼容与 Anthropic 原生协议，如 MiniMax、ChatGPT、Qwen），凭据进 KMS 不落文件。该自助配置界面是独立建设项，不属本条施工范围。
- 代码对齐（2026-10-18）：`policy.egress` 改为"无当前有效协议不拦截、已登记当前有效协议按类别限制"；随前置取消移除 `text` 私有标识拦截参数；模型网关、MCP、研究读取等出站调用点同步。v1.1 §06.6.3/§06.9/§07.5、I24、AT-57 与附录 A 该行已按本条修订。
- 判据：未登记协议时出站放行且回执 `agreement_id` 为空；已登记当前有效协议但资料类别超出许可时返回 FORBIDDEN_SCOPE；登记覆盖类别后放行且回执带协议 ID/版本；协议登记仍须管理员具名 T2 与回执原子；撤销/过期协议不再拦截，只留历史。
