# PDOS v1.1 · 界面决定三分法与契约补遗（三类均已确认；B、C 类已并入 v1.1）

**性质**：草稿。本稿把 [2026-10-13 UI 重设计稿](2026-10-13-pdos-v1.1-ui-mockup.html)（v3 → v3.1 → v4 → v4.1 → 项目列表两轮 → 小Pai 两轮 → 项目工作区两轮，2026-10-13 至 10-16）累积的界面决定，对照[完整目标架构 v1.1](2026-10-08-pdos-complete-target-architecture-v1.1.md) §05 逐条判定，供用户逐条确认。

**在用户确认前，本稿不构成设计合同**：v1.1 §05 仍是唯一生效的页面契约；设计稿与[唯一清单](../../tasks/ai-native-integrated-todo.md#current-queue)里的逐轮记录仍只是设计素材。确认后，§2（B 类）并入 v1.1 §05，§3（C 类）逐条写入[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) §8 决策记录并同步 v1.1 对应位置，本稿再登记进[设计文档索引](README.md)。

**目的**：实施阶段（S1 及以后的前台建设）不必重新争论这些界面问题，也不靠"各自发挥"填 §05 没写的空白。

## 0. 三分法与用词

| 类 | 判定 | 处置 |
|---|---|---|
| **A 类** | v1.1（§05 或被 §05 引用的章节）**已经写明**，设计稿只是把它画出来 | 不补契约。实施时直接按 v1.1 对应节；本稿只登记"界面决定 ↔ 依据"的对应关系，防止实施时当成新发明再讨论一遍 |
| **B 类** | §05 **没写**，但只是把 v1.1 既有规则在界面上具体化：不新增领域对象、不新增命令、不改档位、不扩大可见范围、不加严既有规则 | 进**契约补遗**（§2）。用户确认后作为 v1.1 §05 的补充条文 |
| **C 类** | 实际**改变了 §05/§01.6 的规则，或扩大了范围**（新增领域对象、新增能力、改既有页面分区、改全局信息架构） | **单独作为决策记录条目请用户确认**（§3），一律标"待确认"并写清选项。不混进 B 类，也不在实施中顺手做掉 |

**约束 vs 仅演示素材**：本稿只有 §1–§3 的条目是（或将成为）约束。设计稿里的演示数据、具体文案措辞、示例编号、颜色与图元形状选择属于**仅演示素材**，见 §4，实施时可自由替换，不得被当成契约引用。

**AGENTS.md 不可协商项 7 的边界**：B 类按定义不得加严 v1.1 规则或扩大范围；本稿若有条目实际触碰该边界，一律移入 C 类。C 类未经用户确认不得实施。

## 2. B 类：契约补遗 — **19 条已于 2026-10-17 确认并并入 v1.1 §05（P22）**

> **决定**：整体采用。B1 为 §05.3 新增三行，B2–B19 并入新增的 v1.1 §05.12；其中 **B7 删去 1080px 断点**（归 UI 基线）、**B9 改为"数据不合并、显示可折叠"**。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P22。下文为确认前的原稿，B7、B9 已就地标注修订。

每条写成：**规则** / **依据** / **判据**。

### B1 §05.3 页面契约表补三行

- **规则**：§05.3 的页面表增加三行——**项目列表**（核心内容：在办项目的阶段位置、健康度、负责、下一门禁的承诺与预测、临近冻结点、最新具名状态更新；主动作：打开项目 / 切换读法；结果：不产生业务事实）、**阶段与门禁**（核心内容：当前阶段出口条件判定、三种成熟度、下一阶段进入条件、冻结点、阶段历史；主动作：补缺项或发起阶段评审；结果：Review/Decision 真实记录）、**小Pai 会话管理**（核心内容：会话列表与状态、范围、已加载技能、后台委托；主动作：新建/切换会话；结果：不产生业务事实）。
- **依据**：§01.6 已把"项目"和"小Pai 常驻"写进全局信息架构，§03.2 已有 StageInstance 与阶段政策，但 §05.3 表里没有对应行，实施时无契约可依。
- **判据**：三行只描述已有事实的读法与已有命令的入口，不引入新领域对象、新命令；三行均可实现为上下文标签或保存视图，不要求新增一级导航（§05.3 末段）。

### B2 项目列表三视图是同一批事实的三种读法

- **规则**：列表 / 看板 / 时间轴共用同一组项目事实与同一套口径，视图只读计算结果，不另存为事实；分组按钮与底部说明只在列表视图出现。
- **依据**：§05.8 末段"视图只读计算工具和证据的结果，不另存为事实"。
- **判据**：切换视图不产生任何写命令；同一项目在三个视图里的阶段、门禁日期、健康度取值一致，不各算一套。

### B3 看板卡片不可拖拽换列

- **规则**：看板按 NPI 阶段分列，卡片不能拖拽换列；阶段推进只能通过满足出口条件并留具名决定完成。
- **依据**：§03.2 第 3 段"阶段推进只引用真实成果和适用决定"；§05.2"主动作只显示当前真实可执行的动作"。
- **判据**：卡片无拖拽把手、无 drop 目标；试图在看板上改阶段时给出的是"去阶段与门禁查看出口条件"，不是一个可点的推进按钮。

### B4 组合层时间轴只暴露冲突，取舍回项目内

- **规则**：组合层时间轴显示跨项目的阶段区间、门禁与冻结点，用于发现资源撞车；具体取舍仍回到项目内的计划候选决定。
- **依据**：§05.3（组合与资源行：主动作"比较取舍方案"，结果"方案和需决定的影响"）、§03.5 四时间分开。
- **判据**：时间轴上不提供改期、改承诺、改资源分配的直接动作；点击冲突跳到对应项目的计划候选比较。

### B5 阶段条按模板渲染，不硬编码六段

- **规则**：项目工作区的 NPI 阶段条与看板列由该项目类型的 StageInstance 模板决定，段数、名称与顺序来自模板；设计稿里的"概念 / 计划 G1 / EVT / DVT / PVT 试产 / MP 量产"是一个模板的取值，不是产品常量。
- **依据**：§03.2"模板可配置 Concept/Planning/Design/EVT/DVT/PVT/MP 等，不硬编码所有项目走完全相同路径"；OEM、派生、小改路径不同。
- **判据**：阶段条组件以模板为输入，段数可变；OEM 或派生项目打开时阶段条按其模板显示，不出现空的 EVT/DVT 占位段。

### B6 阶段迷你进度条是阶段位置，不是完成百分比

- **规则**：项目列表里的六段迷你进度条表示离散阶段位置（已过 / 当前 / 未到），不表示完成度百分比，也不由任何分数驱动。
- **依据**：§03.7 末段"风险预警和完成比例是其他投影"，高分不抵消硬阻塞。
- **判据**：组件输入是阶段序号而非百分比；界面任何位置不出现以百分比表达的"阶段完成度"。

### B7 门禁两栏与三种成熟度窄屏堆叠但不得合并

- **规则**（2026-10-17 确认时修订）：窄屏下双线影响、门禁两栏与三种成熟度可改为纵向堆叠；**堆叠只改布局，不得合并为一个综合结论或综合分**。具体堆叠宽度由 [UI 基线](2026-08-09-ui-baseline.md)规定，不写进页面契约——断点变化不应触发设计合同变更。
- **依据**：§04.11 独立显示；§05.9 复杂比较可保留桌面优势，但不得降级为假结论。
- **判据**：窄屏下三种成熟度仍是三个独立结论块，各自带自己的规则结果与缺项。

### B8 下一阶段进入条件前置可见

- **规则**：当前阶段的门禁视图同时显示下一阶段（如 PVT）的进入条件，用于提前发现缺口。
- **依据**：§03.2"模板规定进入条件"；§09.5 推进指标"准备缺口提前发现"。
- **判据**：前置显示的进入条件标明属于下一阶段、当前不构成本阶段阻塞；不因前置显示而阻断当前阶段。

### B9 工作与计划时间轴四时间固定分四条

- **规则**：基线 / 预测 / 承诺 / 实际在时间轴上固定分四条呈现，不得合成一条或以单条加标记代替；承诺与冻结点各有独立图元；预测与承诺必须同屏对照（预测滑期时承诺仍显示为成立并标超期）。
- **依据**：§03.5"四者分开版本化……用户页面必须看见差异"、I08。
- **判据**（2026-10-17 确认时修订）：四条数据缺失时显示未知行而不是省略该行；**数据上不合并**——对不同接收者的承诺永远是不同记录，不得画成一条；**显示上允许折叠**——默认可折为一行并标出接收者数量（如"3 个接收者"），展开后逐行可见。折叠只是呈现，不改变记录。

### B10 估时"未知"是合法显示值

- **规则**：工作包估时可保持"未知"并写出原因（如"未知，缺台架"），不以 0、区间中点或默认工时填充。
- **依据**：§03.5 末段、§05.8"缺数据显示 unknown，不用虚假示例数据补满生产页面"。
- **判据**：汇总工时时未知项单独计数并在汇总旁显示，不并入数值合计。

### B11 「需要办理」合并面板沿用动作类型读法，但不得丢 §05.3 既有内容

- **规则**：项目工作区"现在"把阻塞 / 待接收 / 待决定合并为一张"需要办理"，用与我的工作相同的动作类型读法；同一屏仍必须能看到 §05.3 要求的"下一 Build"与"关键承诺"。
- **依据**：§05.3（项目现在行：核心内容为下一 Build、关键承诺、决定和交接）、§05.11"不把一次工作拆成多处不可关联页面"。
- **判据**：合并后"下一 Build"与"关键承诺"仍在"现在"屏可见；合并只改面板数量，不减少内容项。

### B12 资料新增「引用已漂移」显示状态

- **规则**：当被引用对象已有更新版本、而本轮 Build/验证仍按旧版执行时，显示"引用已漂移"并同时写出两个版本；漂移与"来源过期""来源已撤回"是三种不同状态。
- **依据**：§05.10 必须有"来源过期"等状态；§02.10 证据适用性；§03.12 失效与撤回。
- **判据**：漂移是提示不是阻塞——是否阻断由 §03.7 的规则判定，界面不得因漂移自动阻断已授权的 Build；漂移提示必须指出"本轮按哪一版执行"。

### B13 小Pai 顶部显示当前范围与已加载技能

- **规则**：会话顶部显示当前范围（可改）与"已加载技能"chips，并写明未加载的技能不授予其写工具；改范围只改范围，不授予权限，范围变更后重算可用技能与工具。
- **依据**：§05.4"系统显示当前目标范围"、§06.3.3 末段"未加载对应技能时服务器拒绝写工具调用"、§06.5 末段。
- **判据**：改范围后技能 chips 与建议动作重算；越出本人有效范围的范围值不可选；技能 chips 是服务器下发的事实，不是前端枚举。

### B14 「本次发送携带什么」显式告知

- **规则**：输入区显式列出本次发送携带的范围、对象与技能，与实际 ContextSnapshot 一致。
- **依据**：§06.7 ContextSnapshot、§06.14 人类可理解性。
- **判据**：列出的条目能在运行详情里逐条对上；`@` 选中的对象进入显式范围并记入 ContextSnapshot，不只是文本提及。

### B15 运行中卡片可"转后台继续"

- **规则**：运行中卡片提供停止与"转后台继续"；转后台不中断同一 Run，工作 ID 与幂等意图不变，关闭面板后仍可在会话列表与 AI 工作详情里找回。
- **依据**：§06.11"长时间等待保存在 Temporal workflow"、§05.4"同一会话在跨页、刷新和关闭面板后可继续"、§05.10"用户刷新或重新登录后看见同一个工作，不重新创建"。
- **判据**：转后台前后 Run ID 相同；后台完成后结果回到同一会话线程，不新建一条会话。

### B16 消息级「重跑」是新运行

- **规则**：消息级动作提供复制 / 重跑 / 运行详情；重跑建立新 Run 与新幂等键，不复用原回执，不因重跑产生重复有效副作用。
- **依据**：I16"重复意图不产生重复有效副作用"、§06.10。
- **判据**：重跑后原回执保持不变，新运行有自己的回执；对已写入对象的重跑须先给出"将产生新候选"而非静默覆盖。

### B17 撤回受限必须列出未撤回项

- **规则**：按运行撤回的入口在写入回执卡片与会话右上角；撤回受限时必须列出未撤回项与具体理由（人工已修改、已被正式决定消费、下游已引用）。
- **依据**：§06.11 末段"必须报告限制与待处理项"、§05.10"撤回受限"状态、I17。
- **判据**：撤回结果页按条列出已撤回 / 未撤回；未撤回项给出负责人可执行的下一步，不只是一句失败提示。

### B18 自主档位界面用词固定为三词；过程面板不显示 token

- **规则**：界面提到自主档位时只用"自动 / 一次确认 / 具名决定"三个词，全界面不出现 T0/T1/T2 作为档位词（试模试次不受影响）；过程面板显示耗时、写入条数与待确认候选数，不显示 token 入/出。
- **依据**：§04.5 术语消歧（三词由 v1.1 规定）；§06.14 过程面板列耗时而未列 token；§09.5"不拿 AI 生成次数当价值"。
- **判据**：当前设计稿只出现"一次确认"，另两词尚未在界面出现——实施时三词齐备且用词不混；代码里不得把 `write_tier` 的枚举值直接渲染给用户。

### B19 ⌘K 命令面板与快速创建不扩权

- **规则**：⌘K 命令面板只调用已注册的领域命令，档位与权限与页面入口完全一致；T2 不在面板内直接执行，面板只能定位到对象或打开其正式入口。快速创建清单按角色收窄（立项提案仅产品经理可见）。
- **依据**：§06.6.1"工具由领域命令登记表生成，各自带档位"、§01.7 末段"对话不能绕过页面权限，页面也不应因为未使用 AI 而额外多一套流程"、§05.11 键盘可达。
- **判据**：面板里每条命令的档位与权限来自同一登记表；无权限命令不出现在检索结果里（而不是出现后报错）；编号精确检索只做定位，不附带执行。

## 3. C 类：改变 §05/§01.6 规则或扩大范围——**六条已于 2026-10-17 确认（P15–P20）**

### C1 全局信息架构改为项目优先 + 「产品管理 · 仅产品经理」分组 · **已确认（P15，用户 2026-10-17）**

> **决定**：(a) 改 §01.6 为项目优先 + 产品管理分组；明确不采纳 (c)，默认落地屏仍是"我的工作"。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P15。以下选项与分析为确认前的原稿，保留备查。

- **用户已明确的方向**：2026-10-16"立项提案和品类开发是产品经理专属，产品还是要以项目管理为核心"。
- **v1.1 现状**：§01.6 第 1 行把全局信息架构定为五个平级主干"**我的工作｜品类｜项目｜组合与资源｜知识**"。
- **设计稿要的**：侧栏主干改为 我的工作 → 项目（直接列出在办项目及阶段）→ 组合与资源 → 知识；品类与立项提案移出主干，进入按角色收窄的"产品管理 · 仅产品经理"分组；顶栏标签顺序同步改为项目列表/项目工作区在前。
- **为什么必须单独确认**：角色可见性本身是 A4（I21 已定），但"品类不再是五个平级主干之一"改的是 §01.6 枚举的全局信息架构文本，属于 v1.1 冻结后的设计变更。
- **选项**：
  - **(a)** 改 §01.6：全局主干为"我的工作｜项目｜组合与资源｜知识"，品类与立项提案为按品类产品管理权限显示的分组（对产品经理仍是常驻入口）。
  - **(b)** 不改 §01.6 文本：五个主干保留，仅对无品类产品管理权限的用户隐藏"品类"主干（等价于按权限裁剪同一套 IA）。
  - **(c)** 改 §01.6 并进一步把"项目"确立为默认落地屏（登录后落到项目列表而非我的工作）。
- **不定的后果**：S1 建侧栏时在 (a)(b) 之间各自发挥；两种实现对"产品经理之外的人第一眼看到什么"结论不同。

### C2 「以项目成员视角预览」开关 · **已确认（P16，用户 2026-10-17）**

> **决定**：(b) 只留在设计稿作验证装置，不进产品。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P16。以下选项与分析为确认前的原稿，保留备查。

- **v1.1 现状**：无角色预览能力；§05 无相关条文。
- **设计稿要的**：一个开关，切换后"产品管理"分组与两个 PM 标签整体消失并落到项目列表，用于验证"对非产品经理这就是一个项目管理系统"。
- **为什么必须单独确认**：这是新增能力。若做成真正的角色模拟（按他人权限读数据），涉及越权读取与审计（I14、§06.8 权限撤回传播）；若只做前台导航隐藏，则它是开发期校验工具而非产品功能。
- **选项**：
  - **(a)** 作为产品功能保留，但严格限定为**前台导航隐藏**：不改任何数据读取、不改写命令档位、不写入任何记录；界面显著标注"预览中"。
  - **(b)** 只保留在设计稿与开发期，不进产品。
  - **(c)** 做成真正的角色模拟（按目标角色的有效范围读数据），须同时定义审计记录、禁止在模拟态下执行任何写命令、以及谁有权使用。
- **不定的后果**：(a) 与 (c) 的实现代价与风险差一个数量级；不定会出现"看起来是预览、实际按自己权限读数据"的误导界面。

### C3 项目「健康度」 · **已确认（P17，用户 2026-10-17）**

> **决定**：(a) 纯规则投影，无人工字段、AI 不参与；算不全的留空不退回人工。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P17。以下选项与分析为确认前的原稿，保留备查。

- **v1.1 现状**：无"健康度"概念。§03.7 明确"准备度是一组规则而不是 AI 分数"，并把风险预警与完成比例降为"其他投影"。
- **设计稿要的**：项目列表与项目工作区属性头显示健康度（色点 + 词：正常 / 有风险 / 有阻塞 / 待批准），有风险或有阻塞时给一句定位原因。
- **为什么必须单独确认**：健康度是新引入的派生判断，必须先定口径与所有者，否则极易演变成一个 AI 或系统打的综合分，与 §03.7 冲突。
- **选项**：
  - **(a)** 纯规则投影：由既有规则结果（硬阻塞、必需未知、承诺超期、临近冻结点未决）按固定优先级映射为四档，与门禁聚合同源，界面可下钻到具体规则；无人工可改字段，AI 不参与。
  - **(b)** 具名人工判断：由项目负责人在状态更新里具名设定，界面显示"谁在何时判为此档"；系统只做提示不自动改。
  - **(c)** 两者并存：规则投影为默认值，负责人可具名覆盖并写理由，两值同时可见。
- **硬边界（任一选项都适用）**：不得由模型给出健康度；不得以健康度抵消硬阻塞；不得把健康度当作门禁或放行依据（§03.7、I19）。
- **不定的后果**：实施时很可能落成"一个看着像分数、来源说不清"的字段，正是 §03.7 要防的东西。

### C4 具名「项目状态更新」对象 · **已确认（P18，用户 2026-10-17）**

> **决定**：(a) 新增轻量 ProjectStatusUpdate，只追加具名、不改领域状态、不构成承诺或批准。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P18。以下选项与分析为确认前的原稿，保留备查。

- **v1.1 现状**：§05.3 项目现在的主动作是"处理阻塞"；无 StatusUpdate 类对象。AI 成功写入进活动记录（§05.2）。
- **设计稿要的**：项目列表"最新状态更新"列（具名摘要 + 时间 + 下一步）、项目工作区主动作改为"写状态更新"、右栏"项目动态"把小Pai 静默记录与具名状态更新合成一条流并带写入口。
- **为什么必须单独确认**：这是新增领域对象与新增命令（扩大范围），且项目列表、工作区属性头、项目动态三处都依赖它；没有它，设计稿里"显示状态更新却无处可写"的问题会原样回到实施。
- **选项**：
  - **(a)** 新增轻量 `ProjectStatusUpdate`：只追加、具名、含摘要与下一步，**不改任何领域状态、不构成承诺、不构成批准**；AI 可起草（一次确认），不得自动发布。
  - **(b)** 不新增对象：用现有活动记录 / 注意项投影呈现"最新动态"，项目列表那一列改为显示最近一条领域事件，不提供自由文本写入。
  - **(c)** 推迟到 S3 及以后，S1 只做读（列显示最近领域事件），"写状态更新"入口暂不建。
- **若选 (a) 的硬边界**：状态更新里的日期不得写入 Baseline/Forecast/Commitment/Actual 任何一条（§03.5、I08）；"下一步"不自动建 Task。
- **不定的后果**：三处界面悬空，或实施时自行发明一个会被当成承诺来源的自由文本字段。

### C5 我的工作四分诊取代 §05.3 的「阻塞 / 承诺」分区 · **已确认（P19，用户 2026-10-17）**

> **决定**：(b) 四分诊之外补第五组"我作出的承诺"，阻塞作为状态标记。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P19。以下选项与分析为确认前的原稿，保留备查。

- **v1.1 现状**：§05.3 我的工作的核心内容是"**决定、阻塞、承诺、外部等待和已完成活动**"。
- **设计稿要的**："等我办理"按动作类型分诊为**要我决定 / 要我接收 / 要我验证 / 等外部回复**，各带自己的时钟与对手方；Task 只留在"我的任务"；另有通知流。
- **判定**：按对象类型分诊符合 §02.11（A6），这部分是细化；但分诊后 §05.3 明列的"**阻塞**"与"**我作出的承诺**"在我的工作屏没有自己的入口（阻塞改到项目工作区的"需要办理"，承诺只在项目内与时间轴出现），"已完成活动"落到通知流。这是对 §05.3 该行内容的重新分区，不是单纯细化。
- **选项**：
  - **(a)** 改 §05.3 该行为"决定、接收、验证、外部等待、我的任务与已完成活动"，并明确：阻塞不是独立分区而是各类事项上的状态标记；我作出的承诺在"我的任务"内按承诺排序呈现。
  - **(b)** 保留 §05.3 原分区，在四分诊之外补第五组"我作出的承诺（对谁、何时到期）"，阻塞仍作为标记。
  - **(c)** 保留 §05.3 原分区，补"我作出的承诺"与"阻塞我的"两组（回到六组）。
- **不定的后果**：承诺人在"我的工作"里看不到自己对别人作的承诺，只能在项目里找；§03.6 的升级算法在界面上没有归属屏。

### C6 小Pai 多会话的会话生命周期 · **已确认（P20，用户 2026-10-17）**

> **决定**：(b) 有归档无删除，保留重命名与置顶；"后台委托"仅为同栏分组。见[设计确认稿](2026-10-08-pdos-next-design-confirmation.md) P20。以下选项与分析为确认前的原稿，保留备查。

- **用户已明确的方向**：2026-10-16"可以有不同的会话，就像 claude、chatgpt 一样"。
- **v1.1 现状**：§05.4 只写"**同一会话**在跨页、刷新和关闭面板后可继续"，没有会话的命名、置顶、归档、删除，也没有会话列表。
- **设计稿要的**：会话管理器——新建、搜索、置顶 / 今天 / 过去 7 天 / 后台委托分组、每条悬停可重命名 / 置顶 / 归档 / 删除；四个会话可真实切换，线程、标题、范围、已加载技能、建议动作随会话变；"后台委托"列的是 AutomationRule。
- **为什么必须单独确认**：会话从"一个可继续的上下文"变成**用户可管理生命周期的持久对象**（新增对象 + 新增删除动作），且删除语义直接撞 I17"删除/撤回不能抹去受控历史或下游消费事实"。
- **选项**：
  - **(a)** 新增 `Conversation` 对象（标题、范围、置顶、归档、删除标记），**删除只删对话显示，不动 Run、ActionReceipt 与已写入的业务记录**，界面必须明说这一点（设计稿已这样写）；归档可恢复。
  - **(b)** 只做会话列表、搜索与切换，不提供删除（只归档），避免"删除"一词的歧义。
  - **(c)** 不新增对象：会话按 WorkRequest / Run 分组呈现，标题由系统生成，用户不可重命名。
- **附带确认项**："后台委托"分组把 AutomationRule（§06.4）与人发起会话列在同一栏——确认这只是同栏分组呈现，两者的触发、授权与预算规则不混同。
- **不定的后果**：实施时可能做成可真删的对话记录，连带丢掉运行与回执的可追溯性（I17、§06.10）。
