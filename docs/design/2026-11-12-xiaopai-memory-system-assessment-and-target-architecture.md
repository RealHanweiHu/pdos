总体判断：**个人侧的写入边界和隔离做得扎实，团队侧和学习闭环还没有开始，记忆的业务收益没有被测量过。**

### 1.2 最关键的三个问题

1. **记忆条目缺少统一的状态契约。**
   - 证据：`memory_note_versions` 只有 `status`（有效 / 已替换）和 `valid_until` 两个字段（[models.py:196](../../server/pdos_next/agent/memory/models.py)）；种类只有口径、背景、叫法。
   - 影响：“这个问题似乎是供应商造成的”这类未核实的归因，要么记不下来，要么记成和已确认事项同等的“背景”。等范围备忘上线、内容开始进入别人的上下文，这个问题会放大。
   - 推荐：每条记忆把来源权威性、可信状态、业务确认状态、生命周期、三种时间分开记（§5.7）。
   - 验证：§8 的 T03、T05、T14、T20。
2. **最有业务价值的两类跨会话内容召回路径弱：未完成的任务、此前决策的依据。**
   - 证据：情景索引只收本人原话（[index.py](../../server/pdos_next/agent/memory/index.py) 只对 `episode.goal` 分词）；情景卡不带未完成事项和结论（[recall.py:291](../../server/pdos_next/agent/memory/recall.py) 的 `card`）；常驻目录每条只有原话前 40 个字。
   - 影响：新会话要接着干，模型得先搜到那次运行，再调 `conversation.history` 读当时的回答，两跳，而且用户的说法和当时不一样就搜不到。项目上别人做的决定，个人情景里完全没有。
   - 推荐：常驻一份“未完成工作目录”；情景索引加入回答摘要和当时对象的标题（仍按来源撤权隐藏）；决策背景作为团队记忆的一个种类，挂在正式决定或对象版本上（§5.2）。
   - 验证：§8 的 T01、T02，以及与“原始历史检索”基线的对比。
3. **没有证据表明记忆让小Pai做得更好。**
   - 证据：[11-05 真实模型回归](../reports/evidence/pdos-next-real-eval-20261105/result.md)只测 RAG 和上下文；[记忆门禁评分器](../../tools/xiaopai_memory_gates.py)是离线规则评分，只有评分器自己的单元测试记录，没有找到用真实运行观测跑出的结果。
   - 影响：现在调的所有参数（半衰期 30 天、置顶加 0.25、被纠正乘 0.5、常驻 1,000 token）都没有依据。
   - 推荐：先建四组基线再扩建（§8、§9）。

### 1.3 推荐的目标架构

**以领域事实源为核心的分层记忆：业务事实永远现读；记忆是一本带来源、带时间、带状态的“主张账本”；索引、向量、近况、简报都是可以随时重建的派生物；全部放在和业务数据同一个 PostgreSQL 里。**

选择依据（不含成本因素）：

- 小Pai 的事实都有明确主人（规格、决定、冻结状态都在业务对象里）。记忆系统最容易犯的错是造出第二份事实，所以架构的第一原则是让记忆在结构上无法充当事实。
- 权限以品类为根、按对象受众收窄，而且随时会变。记忆和业务数据在同一个库里，才能在一次查询里同时过滤权限和有效性，撤权当场生效。换成独立的图库或记忆平台，权限要复制过去，撤权就有延迟。
- 研发业务需要“当时有效的是什么”。这需要时间模型，而不需要图数据库；图谱方案里真正有用的是双时态和“失效不删除”，这两点可以直接放进账本。
- 图数据库、专用记忆平台、独立记忆 Agent 都不需要，理由和会让我改变判断的证据见 §4.4。

## 2. 参考原则与适用性

### 2.1 先澄清术语

几份资料对“记忆”的范围划得不一样，直接套用会混：

| 资料 | 它说的“记忆”包含什么 | 不包含什么 |
|---|---|---|
| Anthropic《The components of agent memory》（2026-11-06） | 从交互和任务经验里得来、跨会话保留、存成以后能读的上下文 | 明确排除：模型权重变化、单次对话内的上下文学习、上下文压缩 |
| LangGraph Memory overview | 短期记忆（线程内的状态，由检查点保存）和长期记忆（跨线程，按命名空间存） | — |
| CoALA | 工作记忆（当前决策周期的活跃信息）加三种长期记忆 | — |
| Letta Memory & dreaming | 一个由 Agent 自己维护、用 git 管理的记忆文件目录 | 对话历史检索是另一套 |

冲突点：LangGraph 把线程状态算作短期记忆，Anthropic 把上下文内的信息和压缩都排除在记忆之外。

本稿在 PDOS 里固定用下面六个词，后文不再混用：

| 词 | 定义 | 是不是记忆 |
|---|---|---|
| 执行状态 | 一次运行执行到哪了：图状态、Temporal 历史、子任务检查点 | 不是，是恢复机制 |
| 会话记录 | 每轮用户原话、小Pai回答、工具调用账本 | 是记忆的原始材料 |
| 工作状态 | 服务器维护的当前任务状态：目标、约束、焦点对象、未完成事项 | 是（工作记忆） |
| 长期记忆 | 跨会话保留的条目：个人条目、团队备忘、经验候选 | 是 |
| 企业知识 | 原件、核实答案、已发布的设计规则 | 不是记忆，是知识检索的对象 |
| 领域事实 | 业务对象及其版本、回执、事件 | 不是记忆，是事实来源 |

### 2.2 各资料说了什么、怎么用

每行分三栏：原文明确提出的、我针对小Pai的推导、还需要实验的假设。

| 资料 | 原文明确提出 | 对小Pai的推导 | 待验证假设 |

| LangGraph | 程序性记忆通常是 Agent 改自己的提示词（反思） | 不采用自动生效：见 CoALA 一行 | — |
| Letta | 记忆是 Agent 自己的 git 仓库；根目录文件每轮进系统提示，子目录按需读；dreaming 由后台子 Agent 在步数或压缩时触发；每次改动都提交，有版本历史；可选“应用前由 Agent 复核”，但不问用户 | 借用两点：常驻和按需分层；每次后台改动都有版本、可回滚。不借用：Agent 自主改写记忆且不经人 | — |
| CoALA | 四类记忆的定义；写入程序性记忆比写情景和语义记忆“风险高得多”；修改和删除记忆（遗忘）研究不足 | 程序性记忆只经人审和评测发布；遗忘要单独设计，不能当成普通删除 | — |
| Mem0 | 每个候选事实由模型在新增、更新、删除、不操作四种里选一种；LOCOMO 上全量上下文的准确率（72.90%）高于所有记忆系统，记忆系统的优势在延迟和成本 | 借用“四种操作”这个结构，但由规则找出疑似重复、由人决定；“全量上下文更准”提醒我们：记忆不是为了更准，是为了在有限上下文里够用 | — |
| Zep / Graphiti | 边上有四个时间戳（何时成立、何时失效、何时记下、何时作废）；矛盾时旧边标失效，不删除；论文自述弱模型用不好时间信息 | 采用双时态和“失效不删除”，放在条目上而不是图的边上 | 小Pai 的默认模型能否用好有效期标注，要测（§10） |

### 3.2 做得好的地方

这些在目标架构里原样保留：

- 写入边界落在数据库权限上，不靠提示词：AI 身份向记忆表插入会被行级权限拒绝。
- 约束必须对上用户原话，页面资料不能触发记忆。这两条用代码核对，是防注入的有效做法。
- 每次返回前按当前权限复核，所以索引滞后或没清干净也不会泄露。
- 运行内冻结、调用前复核、撤权即停。
- 记忆只进运行信封，不动冻结前缀。

### 4.3 三条关键流程

**读：一次运行怎么取记忆**

```text
① 识别任务与实体   运行绑定的范围、@ 选中的对象、编号通道识别的型号和料号、本人叫法换成标准词
② 定权限与范围     服务器从运行绑定取租户、本人、品类、受众；模型参数只能收窄
③ 选来源           当前事实 → 领域读取；某个时点的事实 → 按版本或 as_of 读领域历史
                   为什么这么定 → 正式决定 + 决策背景 + 情景；团队怎么做 → 范围约定 + 规则
                   文档里怎么写 → 企业检索
④ 查               结构化条件先过滤（范围、适用条件、有效期）→ 关键词 + 编号精确 + 向量 → 一跳关系
⑤ 校验             生命周期有效；在查询时点有效；引用的对象版本没变（变了标“可能过期”）
⑥ 处理冲突         按固定可信顺序取舍；有争议的条目两边都给并标明
⑦ 重排去重         融合排序；同一根来源的多条只算一次；与证据重复的记忆去掉
⑧ 装配             分区、限额、记使用清单
⑨ 回答或执行       写入前对关键读集再验一次
```

**写：一句话怎么变成记忆**

```text
输入（本人原话 / 本人操作 / 业务事件）
   │
   ▼
关口一：能不能记      来源可信吗？目标范围可写吗？不进记忆开着吗？被本人要求遗忘过吗？
   │ 不能 → 不提炼（记原因）
   ▼
关口二：值不值得记    能从业务系统现读的不记；一次性的留在工作状态；猜测标为观察
   │ 不值 → 仅工作状态 / 仅证据引用
   ▼
关口三：做什么操作    新建候选 / 补证据 / 合并 / 修订 / 标冲突 / 替代 / 撤回
   │
   ▼
确认（个人：本人一次确认；范围：成员 T1；已有资格的观察类：T0）
   │
   ▼
同一事务：条目新版本 + 证据链接 + 回执（范围）+ 事件
   │
   ▼
后台：索引、向量、失效检查、简报重建（都以来源水位核对）
```

**纠正：用户说“不对”之后**

```text
纠正 → 记在这次运行上（只追加）
     → 本会话：写进工作状态，下一轮即生效
     → 分流（只产生候选，不直接改任何东西）
         事实错了   → 提示对象负责人改业务数据；有权限时起草变更候选
         做法不对   → 技能修订候选
         个人习惯   → 个人条目候选
         团队约定   → 范围条目候选
     → 被纠正的运行：检索降权并附纠正内容
     → 可选：生成一道回归用例候选（你确认后入库）
```

### 4.4 方案比较

比较四种真正可行的方案。评分只看业务正确性，不看改动大小。

| 维度 | A 结构化分层（v0.4 原样） | B 时态知识图谱混合 | C 文件 / Wiki 记忆 | **D 推荐：领域为核心 + 主张账本 + 可重建派生** |
|---|---|---|---|---|
| 做法 | 个人条目、范围备忘、情景，各一套表，状态较少 | 模型从对话和文档里抽实体和关系，存进图库，边带双时态 | Agent 自己维护一组 markdown 页面，后台整理 | 条目统一契约（来源、适用、时间、三种状态）；简报作为派生物 |
| 事实一致性 | 好：记忆不存事实 | 风险大：图里会出现第二份“规格是多少” | 风险大：页面里的事实会过期 | 好：结构上只存引用 |
| 时态表达 | 弱：只有失效时间 | 强 | 弱：靠版本历史 | 强：双时态在条目上 |
| 复杂关系查询 | 一跳，够用 | 强 | 靠页面链接 | 一到两跳递归查询；实体图就是业务表的引用关系 |
| 筛选质量 | 好：人确认 | 取决于模型抽取，无确认 | 取决于模型 | 好：硬规则管能不能，人或资格管生效 |
| 检索效果 | 关键词加向量 | 多路召回加图遍历 | 多文档归纳强（Anthropic 数据） | 关键词加向量加结构化过滤；归纳类用简报补（待消融） |
| 上下文可控性 | 好 | 一般：返回的子图大小难控 | 一般：页面会变长 | 好：分区限额 |
| 权限隔离 | 好：同库行级权限 | 差：权限要同步到图库，撤权有延迟 | 差：页面级，无法按受众拆分 | 好：同库行级权限，读时复核 |
| 并发更新 | 好 | 实体消解在并发下易重复 | 靠 git 合并，自然语言冲突难解 | 好：按主张键加锁和版本号 |
| 纠错与遗忘 | 删除干净；没有抑制机制 | 难：一个事实散在多条边和摘要里 | 难：内容揉在段落里 | 好：条目级删除加抑制指纹加派生物登记 |
| 故障恢复 | 好 | 图库是又一个要备份、要恢复的状态 | 好（git） | 好：派生物全部可重建 |
| 业务表现 | 未测 | 未测 | 未测 | 未测；D 相对 A 的增益由 §8.4 消融逐项证明 |

**明确推荐 D。**

- **为什么最适合**：小Pai 的特点是事实有主人、权限会变、需要回溯时点、团队共享需要治理。D 是唯一在这四点上都不让步的方案。A 的方向是对的，但状态模型不够（C4）、召回路径弱（C2）、没有学习闭环的工程契约。B 和 C 的强项（关系遍历、多文档归纳）可以用派生物的形式拿到，而它们的弱项（第二份事实、权限同步延迟、难遗忘）是这个业务不能接受的。
- **必须通过它解决的问题**：假设与事实分开；补录的旧信息不覆盖新信息；同名产品、不同 Build 不串；撤权和遗忘传播到所有派生物；后台整理不漂移。
- **组件处置**：

  | 处置 | 组件 |
  |---|---|
  | 保留 | 工作状态、情景投影触发器、读时复核、写入关口的原话核对、个人条目的写权限与真删除、知识候选到规则的链路、企业检索 |
  | 替换 | 个人条目的版本表结构 → 统一条目契约（加状态和时间字段）；情景索引（只收原话）→ 加回答摘要与对象标题；写死的排序系数 → 评测校准 |
  | 合并 | 设计里的“范围备忘”和“冲突提示”并入范围条目（冲突是条目之间的关系，不单独建表）；“范围近况”和“范围简报”统一登记为派生物 |
  | 删除 | 无。没有发现应该删掉的现有组件 |

- **图数据库：不需要。** 实体和关系已经在业务表里，带版本、带权限。再让模型抽一张图，就是第二份事实。多跳用递归查询。
- **专用记忆平台（Mem0、Zep、Letta）：不需要。** 它们让模型决定新增、更新、删除，和“讨论不等于确认”的业务语义冲突；数据放到平台里，行级权限和撤权当场生效都做不到。
- **独立记忆 Agent：不需要。** 只有一个 Agent 的约定下，后台整理就是小Pai 加载“经验沉淀”“记忆整理”技能包跑的自动化运行，用同一套工具权限、回执和评测。多一个 Agent 身份只会多一套要治理的权限。
- **取舍**：
  - 抽取覆盖率低于自动抽取的平台，零散的经验会漏。
  - 人确认带来打扰。
  - 范围简报有维护算力成本，还可能没用。
- **什么证据会让我改变推荐**：
  - 关系类问题（三跳以上，例如“用了这个模具的所有 Build 里出过的所有问题对应的所有变更”）用递归查询达不到秒级 p95，或召回明显不够 → 重新评估图存储，但只作为派生索引，不作为事实源。
  - 消融显示范围简报在归纳类任务上没有增益 → 去掉 D3，只留确定性的近况。
  - 评测显示人确认率长期很低（提议大多被忽略）而自动观察的错误率也很低 → 扩大 T0 自动生效的范围。
  - 理想记忆组相对无记忆组的提升很小 → 说明这个业务里记忆价值有限，收缩而不是扩建。

## 5. 记忆模型与治理规则

### 5.1 五个维度

一条信息要同时回答五个互不相干的问题。把它们混在一个“类型”字段里，是多数记忆系统出错的原因。

| 维度 | 问的是什么 | 取值 |
|---|---|---|
| 表示层次 | 这是原始记录，还是提炼出来的，还是派生的？ | R0 原始记录 / 条目（M1–M5）/ 派生表示（D）/ 上下文包 |
| 内容类型 | 它服务什么任务？ | 工作（现在在做什么）/ 情景（发生过什么）/ 语义（知道什么）/ 程序（怎么做） |
| 作用范围 | 谁能看到、对什么生效？ | 会话 / 任务 / 个人 / 项目或提案 / 产品 / 品类 / 租户 |
| 时间 | 什么时候的事、什么时候记的、什么时候有效？ | 发生时间 / 记录时间 / 生效起止 |
| 状态 | 有多可信、业务上确认到哪一步、还有效吗？ | 可信状态 / 业务确认状态 / 生命周期（三个独立字段，§5.7） |

各层在五个维度上的位置：

| 层 | 表示层次 | 内容类型 | 作用范围 | 时间 | 状态 |
|---|---|---|---|---|---|
| R0 原始记录 | 原始 | 情景的材料 | 跟随会话或对象 | 发生时间即记录时间 | 不适用（只有保留期和撤权隐藏） |
| M1 工作状态 | 条目 | 工作 | 会话、任务 | 每版有记录时间；闲置 30 天不自动带入 | 约束分“原话”“本人确认”两种 |
| M2 情景账本 | 确定性投影 | 情景 | 个人；团队（业务事件） | 发生时间 | 不可改，只能追加纠正和隐藏 |
| M3 主张账本 | 条目 | 语义 | 个人；品类、产品、提案、项目 | 三种时间齐全 | 三种状态齐全 |
| M4 经验 | 条目 | 语义（向程序过渡） | 品类、产品；发布后按规则可见范围 | 生效起止 | 候选 → 已评估 → 已发布 → 需复核 |
| M5 程序 | 版本化文件 | 程序 | 租户、技能包适用范围 | 版本 | 草稿 → 评测通过 → 已发布 → 退役 |
| D 派生表示 | 派生 | 任意 | 继承来源 | 来源水位 | 当前 / 已过期待重建 |

### 5.2 各层定义

每层按同样十项写。

**M1 工作状态**

- 目的：让当前任务不因窗口滑动、换会话而丢目标和约束。
- 输入：用户原话、服务器看到的对象与回执、模型输出里的未完成事项。
- 输出：进上下文末尾的工作状态段；“本次携带”界面。
- 权威来源：用户原话（约束）、领域回执（已完成）。
- 数据结构：每个会话一份、只追加版本的 JSON；新增“任务接续包”（见下）。
- 读取：运行开始时装载并冻结。
- 写入权限：服务器；约束须对上原话或经本人确认。
- 更新触发：每次运行收尾；本人在“本次携带”里增删。
- 失效：闲置 30 天不自动带入；本人删除；任务完成。
- 案例：“这次只看 B2 版本”在第 15 轮仍然生效。
- 相对现状的两处新增：
  - **未完成工作目录**：本人在当前范围里尚未完成的任务（未完成事项、待答问题、待确认候选的当前状态），常驻注入，≤300 token。纯 SQL，从各会话最新的工作状态取。
  - **任务笔记**：小Pai 在长任务里记下的阶段性结论（如“已排除供应商 C，报价超目标价 12%”），每条必须引用本次运行的某条工具结果或引文编号，由服务器核对引用存在；标“小Pai 的工作笔记，不是事实”；只在本任务内带入，任务结束即归档。这一项改变了“AI 不自己写记忆”的现行约定，见[附录 A](#appendix-a) 第 2 条。

**M2 情景账本**

- 目的：回答“以前做过什么、当时怎么定的”。
- 输入：工作状态版本、运行结果、回执、业务事件。
- 输出：情景卡；同范围目录；按会话读回原文。
- 权威来源：R0 原始记录。情景本身不是事实。
- 数据结构：个人情景一运行一行，只存引用和原话；团队情景不另建表，就是业务事件和项目动态流。
- 读取：`memory.search` 按需；最近几条目录常驻。
- 写入权限：只有数据库投影；任何身份不能直接写。
- 更新触发：运行收尾；业务事件提交。
- 失效：随会话记录保留期；来源撤权时隐藏；本人隐藏；会话删除时同步删除。
- 案例：“上周三比过三家气泵供应商”，新会话里能找到并读回当时的结论。
- 相对现状的新增：索引加入回答摘要、当时对象的标题、回执操作名；情景卡带未完成事项。回答摘要标“小Pai 当时的回答”，沿用现有的依赖清单做撤权隐藏。这一项改变了 P85“首期不收回答正文”，见附录 A 第 1 条。

**M3a 个人条目**

- 目的：记住本人明确交代的长期信息。
- 输入：本人手写；本人在对话里的明确交代（小Pai 起草、本人确认）。
- 输出：约束区（偏好、口径、叫法）和背景区。
- 权威来源：本人。
- 数据结构：条目加只追加的版本，字段见 §5.7。
- 读取：范围匹配的常驻（≤1,000 token），其余按需查。
- 写入权限：只有本人以真人身份；AI 身份被数据库拒绝。
- 更新触发：本人确认、修改、替换、删除。
- 失效：自设有效期到期；引用对象出新版本时标“可能过期”；本人删除（真清除，并留抑制指纹）。
- 案例：“以后给我表格形式的周报”。
- 不变的边界：不做隐式画像（N12）；不进别人的上下文；不是权限来源。

**M3b 范围条目**

- 目的：团队该知道、但没有结构化字段可放的信息。
- 输入：成员手写；成员要求“记下来”；讨论里被 @；业务事件触发的起草。
- 输出：约束区（约定）和背景区（关注点、决策背景、观察）。
- 权威来源：确认人。条目不是事实，不能当判据。
- 数据结构：条目加版本加证据链接加关系；必须挂品类，可细到产品、提案、项目；带结构化适用条件。
- 读取：按场景配方装载（≤800 token），其余按需查。
- 写入权限：只经领域命令；默认 T1（成员确认一次）；“观察”类和“补充证据”在取得资格后可 T0。
- 更新触发：成员操作；业务事件（对象改版 → 标待复核）。
- 失效：复核到期标待复核并降级；被替代；撤回；停用。不删除。
- 四个种类及其区别：

  | 种类 | 例子 | 进哪个区 | 默认档位 |
  |---|---|---|---|
  | 约定 | “本项目样件编号按 项目-批次-序号” | 约束区 | T1 |
  | 关注点 | “客户 A 评审必问跌落测试” | 背景区 | T1 |
  | 决策背景 | “选方案 B 是因为模具周期短 3 周；方案 A 成本低但要换供应商” | 背景区；必须挂一个正式决定或对象版本，没有就标“未形成正式决定” | T1 |
  | 观察 | “这批气嘴漏气似乎和供应商换料有关”（未核实） | 背景区，带“未核实”标注 | T1；有资格后 T0 |

**M4 经验**

- 目的：让一个项目学到的东西，在适用的地方被下一个项目用上。
- 输入：有结果的业务记录（问题关闭、复验通过、试产复盘）。
- 输出：已发布规则可作为依据引用；候选只作线索。
- 权威来源：发布后的设计规则是正式知识（进 K 层）。
- 数据结构：现有的知识候选、适用性评估、设计规则三张表。
- 读取：企业检索按适用范围查。
- 写入权限：候选 T0（须资格）；规则发布 T2（具名）。
- 更新触发：业务事件；复核到期。
- 失效：来源撤回或对象改版 → 需复核；有效期到期。
- 案例：“同类气泵气嘴漏气，根因是 O 圈材质”，限定在该气嘴结构和工况。

**M5 程序**

- 目的：小Pai 做事的方法。
- 输入：纠正和失败的汇总；人工编写。
- 输出：技能包、提示词、场景配方的新版本。
- 权威来源：发布人；评测结果。
- 数据结构：版本化文件加修订候选表。
- 读取：预载或 `skill.load`。
- 写入权限：只经审核加评测发布；自动反馈不能改安全规则、权限档位、工程阈值、批准政策、评测金标准。
- 更新触发：信号达到阈值生成候选。
- 失效：新版本发布后旧版退役；资格重审。
- 案例：纠正汇总显示“对比报告总漏单位换算”→ 修订对比技能 → A/B 通过 → 发布。

**D 派生表示**

- 目的：让检索快、让上下文省。
- 输入：R0、M1–M5、F、K。
- 输出：索引命中、近况、简报。
- 权威来源：没有。永远指回来源。
- 数据结构：每个派生物在登记表里有一行：种类、对象、来源水位、构建版本、状态。
- 读取：检索时用；简报按需读。
- 写入权限：只有后台构建任务。
- 更新触发：来源事件；水位落后。
- 失效：来源版本变化、撤权、删除 → 立即标过期，重建或清除。
- 案例：项目范围简报里“已知风险”一节，每句话后面跟着它依据的问题单版本或范围条目编号。

### 5.3 七个划界问题

1. **什么留在工作状态，什么值得跨会话保留？**
   留在工作状态：本次任务的目标、约束、焦点对象、进度、临时计划、未核实的猜测。跨会话保留：本人明确要求长期生效的；团队确认的约定和关注点；有结果支撑的经验；以及“做过什么”的情景索引（自动，不需要判断价值）。
2. **什么直接查业务对象，什么可以用可重建的摘要？**
   凡是有主人的字段（规格、状态、负责人、日期、决定、冻结）一律现读。摘要只用于“概览”和“归纳”，每句带引用，回答具体数值前必须回到来源。
3. **什么属于企业知识检索，什么属于记忆？**
   文档、核实答案、已发布规则里写着的 → 企业知识。从交互和任务结果里来、还没有（或不需要）正式发布的 → 记忆。一条经验一旦发布成规则，就从记忆进入企业知识。
4. **什么经验能跨项目用，什么必须限定？**
   默认都限定：每条经验带适用条件（品类、型号、版本范围、客户、Build、工况）。跨项目使用需要三个条件同时满足：读者对来源范围有权限或它已发布；不是客户私有；适用条件匹配或经过适用性评估。不满足第三条时只能作为“线索，未评估适用性”出现。
5. **程序记忆怎么和技能、流程、系统策略衔接？**
   三者是同一层的三种载体，优先级固定：系统策略（冻结前缀）> 受控流程（领域命令和档位）> 技能包 > 场景配方。学习只能产生技能包和配方的修订候选，前两者只能由人改。
6. **什么常驻，什么按需，什么只留索引？**
   常驻：固定偏好、本范围的个人口径和叫法、范围约定、未完成工作目录、近况。按需：背景类条目、情景详情、简报、经验候选。只留索引和引用：会话原文、回答正文、原件。
7. **哪些是逻辑职责，哪些要独立存储？**
   见 §4.2 末尾：只有个人条目和范围条目需要分表；不需要独立服务。

### 5.4 此前五层划分的评估

“个人偏好、当前工作、项目事实摘要、产品/平台经验、企业正式规则”这个划分，按归属排了一条线，优点是容易理解。问题有三个：没有情景记忆和程序记忆的位置；把“项目事实摘要”当成一层会诱导出第二份事实；没有状态维度。

| 此前的层 | 调整 | 落在本稿哪里 |
|---|---|---|
| 个人偏好 | 保留，扩为“本人明确交代的长期信息” | M3a |
| 当前工作 | 拆开：现在在做的是工作状态，做过的是情景 | M1、M2 |
| 项目事实摘要 | 取消这一层。事实现读；软信息进范围条目；概览用派生物 | F 现读；M3b；D2、D3 |
| 产品 / 平台经验 | 保留，强调适用条件 | M4 |
| 企业正式规则 | 保留，但归到企业知识，不算记忆 | K；做法类规则进 M5 |

### 5.5 事实权威关系

冲突时按下面的顺序取舍，沿用已确认的顺序并补上条目内部的排序：

```text
业务对象当前值 ＞ 核实答案 ＞ 原件 ＞ 范围近况 ＞ 范围条目 ＞ 个人条目 ＞ 情景记录
                                              └ 条目内部：已关联正式记录 ＞ 本人或成员确认 ＞ 有人这样说 ＞ 推断
```

- 记忆永远不进证据区，不能被引用为依据。
- 记忆与业务数据冲突时，回答按业务数据，并提示“你之前记的是 A，当前资料是 B”。
- 标了“有争议”的条目不会因为排序被悄悄丢掉：两边都给出，并说明争议。

### 5.6 筛选与写入

#### 5.6.1 三个独立判断

1. **能不能记**：硬条件，全部通过才往下走。相关性再高、模型再有把握，也不能抵消任何一条。
2. **值不值得长期记**：决定去向（不记、只留工作状态、成为候选）。
3. **做什么操作**：新建、补证据、合并、修订、标冲突、替代、撤回。

原始记录的保留和长期记忆的提炼是两件事：原始记录按保留期自动留着，不需要判断价值；提炼才需要过这三关。

#### 5.6.2 决策表

**关口一：能不能记（确定性规则）**

| 检查项 | 规则 | 不通过时 |
|---|---|---|
| 触发来源 | 只有本人原话（页面资料分界线之前）、本人的明确操作、业务事件可以触发 | 不提炼 |
| 内容来源 | 条目文字不得出自页面资料、原件、邮件、IM、OCR、工具结果、小Pai 自己的回答 | 不提炼 |
| 用户设置 | 会话开着“不进记忆”；管理员关闭；钉钉入口 | 不提炼，不提议 |
| 目标范围 | 必须是本次运行的范围或全局，当前可读；团队范围还要有写权限 | 不提炼 |
| 遗忘抑制 | 命中本人的遗忘指纹（§6.4），且触发片段是遗忘之前的旧话，或这是小Pai 的主动提议 | 不提炼，不再提议。本人在遗忘之后重新明确交代的不受限，确认后解除该指纹 |
| 业务确认状态 | 内容是规格值、决定、批准、状态变更 | 不进记忆；转去起草对应的领域候选，按原档位办理 |
| 敏感性 | 带客户标识 → 只能进同一客户的范围；与工作无关的个人信息（健康、家庭等）→ 不提议 | 收窄范围或不提炼 |
| 冻结 | 涉及已冻结对象的内容 → 只能作为“变更讨论”类观察，并提示走变更流程 | 不产生约定类条目 |

**关口二：值不值得（模型判断加规则兜底）**

| 内容特征 | 去向 |
|---|---|
| 能从业务系统现读的动态状态（谁负责、到哪一步、数值是多少） | 不记，只留对象引用 |
| 一次性请求、短期计划（“下周三前先别动图纸”） | 只留工作状态，带到期时间；需要多人知道时建议建任务 |
| 本人明确的长期交代（“以后”“每次”“记住”） | 个人候选 |
| 团队约定、客户关注点 | 范围候选 |
| 决策的理由和取舍 | 范围候选（决策背景），挂正式决定 |
| 未核实的猜测、归因、概括 | 默认只留工作状态；本人明确要求记下时，成为“观察”候选，可信状态为“有人这样说” |
| 有业务结果支撑的经验 | 案例记录 → 知识候选（M4） |
| 已有等价条目 | 补充证据，不新增 |
| 本人明确纠正旧条目 | 修订或替代候选 |

**关口三：做什么操作（确定性规则）**

主张键 = 种类 + 主语对象 + 谓词 + 适用条件。只有主张键相同，才可能是“同一件事”。

| 与已有条目的关系 | 操作 |
|---|---|
| 没有相同主张键的有效条目 | 新建候选 |
| 主张键相同、内容等价 | 补充证据（同一根来源不重复计数） |
| 主张键相同、内容更具体 | 修订（追加新版本） |
| 主张键相同、内容矛盾、新内容的生效时间更晚或相同 | 替代：旧条目的失效时间 = 新条目的生效时间，旧条目保留可查 |
| 主张键相同、内容矛盾、新内容的生效时间更早 | 作为历史版本插入，不改变当前有效条目 |
| 主张键相同、内容矛盾、先后无法判断 | 标冲突：两条并存，都标“有争议”，通知确认人 |
| 主张键不同、文字相似（不同 Build、不同型号、不同客户） | 都保留，不合并；在确认卡上提示“相似但适用条件不同” |
| 本人或确认人否定 | 撤回（保留记录和原因） |

#### 5.6.3 规则和模型怎么分工

| 交给确定性规则 | 交给模型 | 永远不交给模型 |
|---|---|---|
| 关口一全部 | 判断一句话里有没有值得记的内容 | 权限和范围 |
| 主张键计算、时间先后比较 | 起草条目文字，建议种类、作用域、适用条件 | 业务确认状态 |
| 找相似条目（词重叠、同范围、向量近邻），只用于提示 | 指出可能相关的旧条目和关系 | 对已确认条目执行替代、撤回、删除 |
| 证据独立性计数（按根来源） | 起草合并后的文字 | 把可信状态从“有人这样说”升为“已核实” |
| 数值保真检查（派生文字里的每个数字和单位必须出现在引用的来源片段里） | — | — |
| 状态转换 | — | — |

模型的全部输出都是提议。提议变成有效记忆，要么经人确认，要么属于已取得资格的 T0 类别。

#### 5.6.4 关键流程伪代码

```python
def admit(run, draft):                                   # 关口一
    src = locate_in_owner_words(run, draft.trigger)      # 逐字找到，且在页面资料分界线之前
    if src is None:
        return reject("触发来源不是本人原话")
    if overlaps(draft.text, run.page_material, run.tool_results, run.ai_outputs):
        return reject("内容来自不可信材料或小Pai自己的回答")
    if run.memory_off or policy.closed(run.tenant) or run.entry == "dingtalk":
        return reject("本次不进记忆")
    if not readable_now(draft.scope) or (draft.realm == "scope" and not writable_now(draft.scope)):
        return reject("作用域不可读或不可写")
    if suppression_hit(run.requester, fingerprint(draft), src) and not fresh_explicit(src, draft):
        return reject("本人要求遗忘过")                    # 遗忘之后本人重新明确交代的照常放行
    if is_business_fact(draft):                          # 规格值、决定、批准、状态
        return route_to_domain_candidate(draft)          # 走原档位，不进记忆
    return classify(draft)

def classify(draft):                                     # 关口二
    if draft.readable_from_domain:
        return keep_reference_only(draft.subject_ref)
    if draft.one_off or draft.short_term:
        return work_state_only(draft, until=draft.until)
    if draft.epistemic in ("reported", "inferred") and not draft.explicit_remember:
        return work_state_only(draft)                    # 猜测默认不出本任务
    return choose_operation(draft)

def choose_operation(draft):                             # 关口三
    key = claim_key(draft.kind, draft.subject_ref, draft.predicate, draft.applicability)
    with advisory_lock(draft.scope, key):                # 同一件事的写入排队
        current = active_item(draft.scope, key)
        near = similar_items(draft)                      # 只用于在确认卡上提示
        if current is None:
            op = "create"
        elif equivalent(current, draft):
            op = "add_evidence"
        elif unknown_order(current, draft):
            op = "mark_conflict"
        elif draft.valid_from >= current.valid_from:
            op = "supersede"
        else:
            op = "insert_history"                        # 补录的旧信息不改当前
        return store_candidate(op, draft, hints=near)    # 一律先存为候选
```

#### 5.6.5 候选怎么核验、怎么晋升

| 候选 | 谁确认 | 条件 |
|---|---|---|
| 个人条目 | 本人，一次点击 | 可改文字和作用域；7 天不处理即过期 |
| 范围条目：约定、关注点、决策背景 | 对该范围有写权限的成员，T1 | 确认卡显示内容、受众、适用条件、相似旧条目；生成回执 |

#### 5.6.6 同步、后台、自动与审核、阈值

**同步写（和运行结果或用户操作在同一事务）**：工作状态、情景投影、候选入库、使用清单、本人或成员的确认。确认提交后，下一次运行开始时就能读到。

**后台写**：分词索引、向量、失效检查、重复检测、近况缓存、简报重建、经验起草、程序性信号汇总。

**自动生效与需要审核的边界**：

| 自动生效 | 需要一次确认 | 需要具名批准 |
|---|---|---|
| 工作状态、情景、使用清单（确定性） | 个人条目（本人） | 设计规则发布（T2） |
| 任务笔记（带核对过的引用，只在本任务内） | 范围条目的约定、关注点、决策背景（T1） | 技能包和提示词发布 |
| 标“可能过期”“待复核”（确定性规则） | 替代或撤回他人确认过的条目（T1） | — |
| 完全重复的证据合并 | 可信状态升级 | — |
| 已取得资格的“观察”和“补充证据”（T0） | — | — |
| 派生物的构建和重建 | — | — |

后台整理发出的“疑似不符”提示和常驻升降建议不在这张表里：它们不改变任何条目，采纳与否都由人操作，按上表“需要一次确认”的对应行办理。

**阈值不凭空指定**。下面这些数现在都是初始值：相似度门槛（词重叠 0.34）、新近度半衰期（30 天）、置顶和回执加权、被纠正降权、常驻预算、主动提议的触发次数、候选过期天数。校准方法：

- 评测集按时间线切成调参集和验收集，互不重叠。
- 相似度门槛：用人工标注的“是否同一件事”条目对，在调参集上选让误合并率为零、漏检率最低的值。
- 半衰期和加权：在调参集上看 recall@5，尤其是“很久以前但仍有效”的题。
- 常驻预算：画“任务完成度对常驻 token 数”的曲线，取拐点。
- 主动提议和触发词表：打开前先在回放会话上测误提议率（提议被忽略或被判为不该提的比例），高于调参时定下的上限就收窄词表。
- 选定后冻结，在验收集上只报告、不再调。

#### 5.6.8 四项特别检查

| 风险 | 目标架构怎么防 | 现状 |
|---|---|---|
| 普通表达被固化成个人偏好 | 触发词只认“面向小Pai 今后行为”的明确说法；候选必须本人确认；打开前测误提议率 | 确认机制已有；触发词表偏宽（X6）；整条路现在关着 |
| 小Pai 的回答被再提取成“已证实的事实” | 关口一拒绝内容来自 AI 输出的条目；证据链接的来源类型里没有“AI 回答”；小Pai 生成的条目不能给其他条目当证据 | 页面资料的重叠检查已有；对 AI 输出的重叠检查没有（现在不需要，因为提议必须引用本人原话） |
| 同一来源被反复摘要后当成多个独立证据 | 每条证据记根来源，计数按不同的根来源；派生物不能作为来源 | 没有证据计数机制（现在也没有需要计数的地方） |
| 记忆写入绕过正式规格、冻结点、变更流程 | 关口一把事实类内容转去领域；记忆不进证据区；“事实冲突时采信记忆的次数”是零容忍指标 | 已有：记忆只进约束区和背景区并标“不是业务事实”；AT-74 已登记 |

### 5.7 数据模型

条目契约，个人和范围两张物理表共用同一套字段（范围表多出回执和确认人）。字段名是建议，实施时按迁移规则定。

**条目身份 `memory_items`**

| 字段 | 含义 | 约束 |
|---|---|---|
| `id`、`tenant_id` | 记忆 ID、租户 | 行级权限按租户 |
| `realm` | 个人 / 范围 | 决定落在哪张表 |
| `owner_id` | 个人条目的主人 | 个人表必填，服务器从请求身份绑定 |
| `category_id`、`product_id`、`proposal_id`、`project_id` | 范围条目挂靠的业务对象 | 范围表品类必填；可见性继承挂靠对象的受众 |
| `kind` | 偏好 / 口径 / 叫法 / 背景 / 约定 / 关注点 / 决策背景 / 观察 | 固定枚举 |
| `claim_key` | 主张键：种类 + 主语对象 + 谓词 + 适用条件的摘要 | 同范围内同一主张键最多一条当前有效（部分唯一索引） |

**版本 `memory_item_versions`（只追加）**

| 字段 | 含义 | 约束 |
|---|---|---|
| `revision` | 版本号 | 每条目内连续 |
| `statement` | 主张的文字 | 个人 ≤200 字，范围 ≤300 字 |
| `subject_ref` | 主语对象：类型、ID、版本 | 可空；有则读时比对当前版本 |
| `value` | 涉及数值时：原文、数值、单位分开存 | 原文必存，照抄不改写 |
| `applicability` | 适用条件：对象引用和版本范围、客户标识、型号或变体、Build、阶段、工况说明 | 范围条目的经验类、决策背景类必填至少一项 |
| `source_authority` | 来源权威性：业务记录 / 已发布规则 / 核实答案 / 原件 / 人的陈述 / 讨论 / 小Pai 生成 | 由服务器按证据链接算出，不由模型填 |
| `epistemic` | 可信状态：有人这样说 / 已核实 / 推断 / 有争议 | “已核实”要求 §5.6.5 的条件；小Pai 生成的不能直接是“已核实” |
| `confirmation` | 业务确认状态：讨论 / 提议 / 本人或成员确认 / 已关联正式记录 | “已关联正式记录”必须带 `formal_ref`（对象类型、ID、版本） |
| `lifecycle` | 生命周期：候选 / 有效 / 已替代 / 已撤回 / 已过期 / 已停用 | 状态机见 §6.3 |
| `generated_by` | 生成方式：人写 / 小Pai 起草人确认 / 系统投影 / 小Pai 写 | — |
| `model_confidence` | 模型自报的把握 | 可空；只用于候选队列排序，不参与任何放行判断 |
| `occurred_at` | 事情发生的时间 | 可空 |
| `recorded_at` | 记下的时间 | 数据库时钟 |
| `valid_from`、`valid_to` | 生效起止 | 替代时由服务器写 `valid_to` |
| `review_due_at` | 复核日期 | 范围条目必填，缺省 90 天 |
| `sensitivity` | 普通 / 客户私有 / 个人 | 客户私有只在同一客户范围装载 |
| `created_by`、`confirmed_by`、`receipt_id` | 起草人、确认人、回执 | 范围表必填 |
| `request_key`、`request_sha256` | 请求编号与内容摘要 | 同编号不同内容被拒 |

来源权威性、模型把握、业务确认状态是三个字段，互不推导。一条“小Pai 生成、模型很有把握”的条目，确认状态仍然是“提议”。

**证据链接 `memory_evidence`（只追加）**

| 字段 | 含义 |
|---|---|
| `item_id`、`revision` | 支撑哪条、哪版 |
| `source_type`、`source_id`、`source_version` | 来源：运行 / 讨论帖 / 业务事件 / 回执 / 原件 / 业务对象，及其版本 |
| `locator`、`quote_sha256` | 片段定位（轮次、页、段、单元格）和片段摘要；不存片段正文，展示时按当前权限现读 |
| `root_source_id` | 根来源。同一份原件被多次总结，根来源相同 |
| `stance` | 支持 / 反对 / 只是背景 |

**关系 `memory_relations`**：`from_item`、`to_item`、`type`（替代 / 冲突 / 重复 / 细化 / 派生自）、建立人、回执。冲突是两条之间的关系，不是单条上的标记。

**遗忘抑制 `memory_suppressions`**：`owner_id`、`fingerprint`（规范化文字加主张键的带密钥摘要，不可还原）、来源片段引用（运行 ID 加片段摘要）、时间。**不含正文。**

**派生物登记 `derived_artifacts`**：`kind`（关键词索引 / 向量 / 近况缓存 / 简报）、对象、`source_watermark`（来源 ID 和版本集合的摘要）、`sources`、构建器版本、嵌入配置版本、状态（当前 / 过期 / 已清除）。

### 5.8 生命周期

```text
            ┌── 忽略 / 7 天过期
候选 ──确认──▶ 有效 ──同主张键的新版本生效──▶ 已替代（保留可查）
              │   ├──确认人或本人否定──────▶ 已撤回（保留记录和原因）
              │   ├──valid_to 到期────────▶ 已过期
              │   ├──范围条目停用──────────▶ 已停用（保留版本历史）
              │   └──个人条目删除──────────▶ 清除正文，只留删除记录和抑制指纹
              │
              └ 两个计算出来的标记（不是状态，读时判断）：
                  可能过期：引用对象的当前版本 ≠ 记下时的版本
                  待复核：超过复核日期
```

“有争议”是可信状态，不是生命周期：一条有争议的条目仍然有效，只是降到背景区并标注。

### 5.9 权限

| 规则 | 做法 |
|---|---|
| 个人条目只有本人可读可写 | 行级权限：所有者 = 当前用户，且写入者是真人本人 |
| 范围条目跟随挂靠对象 | 行级权限直接连业务对象的可见性，不存权限副本；对象受众一收窄，条目当场不可见 |
| 记忆不是权限 | 记忆不扩大任何读取范围；模型传来的作用域不作数 |
| 读两次 | 检索 SQL 里过滤一次；内容发给模型之前按当前权限再复核一次 |
| 引用的对象撤权 | 条目的依赖清单里有不可读对象 → 对这个读者隐藏，不透露它存在 |
| 管理员 | 能关功能、看数量，看不到个人条目内容 |
| 出站 | 记忆随运行发给模型，按运行绑定的数据类别判定并记回执；带客户标识的条目计入客户类别 |

### 6.2 事件

记忆模块发出的事件（和条目写入在同一事务进入发件箱）：

| 事件 | 载荷 | 消费方 |
|---|---|---|
| `memory.item.activated` | 条目 ID、版本、范围、主张键 | 索引、向量、简报重建 |
| `memory.item.superseded / retracted / retired` | 条目 ID、版本、原因 | 索引清理、简报重建、通知用过它的进行中运行 |
| `memory.item.forgotten` | 条目 ID（无正文） | 清索引、清向量、清简报里的引用、写抑制 |
| `memory.conflict.raised` | 两条条目 ID | 通知确认人 |

记忆模块消费的业务事件：

| 业务事件 | 记忆侧动作 | 是否调用模型 |
|---|---|---|
| 定义或规格改版、变更生效 | 引用旧版本的条目标“待复核”；相关派生物作废 | 否 |
| 来源撤回、原件撤权 | 依赖它的证据链接失效；只靠它支撑的条目降为“有人这样说”并标待复核；派生物作废 | 否 |
| 成员离开项目、受众收窄 | 无需动作（行级权限当场生效）；作废按人缓存的上下文 | 否 |
| G0 评审结束、问题关闭、项目关闭 | 起一个“经验沉淀”自动化运行，产出候选 | 是（只产出候选） |
| 会话归档或删除 | 情景、索引、向量同步处理 | 否 |

每个事件带对象 ID、对象版本、事件类型、时间。每个消费方按（事件 ID，消费方）去重，各自幂等，一个失败只重试自己。

### 6.3 状态转换的守卫

| 转换 | 谁能触发 | 守卫 |
|---|---|---|
| 候选 → 有效 | 本人（个人）；有写权限的成员（范围）；有资格的小Pai（仅观察、补证据） | 候选未过期；作用域当前可读可写；期望版本号匹配 |
| 有效 → 已替代 | 新版本确认时由服务器 | 主张键相同；新 `valid_from` ≥ 旧 `valid_from` |
| 有效 → 已撤回 | 本人；确认人或对象负责人 | 必须写原因 |
| 有人这样说 → 已核实 | 具名核实人；系统规则（已关联到已发布业务记录） | 独立根来源数量满足；小Pai 生成的证据不计 |
| 任意 → 有争议 | 服务器（检测到冲突关系）；成员提出 | 冲突另一方存在且有效 |
| 有效 → 清除（个人） | 只有本人 | 同时写抑制指纹和删除记录 |

小Pai 的身份在任何转换里都不能把条目从“提议”推进到“确认”，也不能执行替代、撤回、清除。

### 6.4 核心流程伪代码

**确认并替代（同一事务）**

```python
def confirm(actor, candidate, expected_revision, request_key):
    with transaction():
        advisory_lock(candidate.scope, candidate.claim_key)
        replay = find_by_request_key(actor, request_key)
        if replay: return replay if replay.digest == digest(candidate) else conflict()
        require(candidate.revision == expected_revision)
        require(readable_now(candidate.scope) and writable_now(actor, candidate.scope))
        current = active_item(candidate.scope, candidate.claim_key)
        new = append_version(candidate, lifecycle="active", confirmed_by=actor)
        if current and candidate.op == "supersede":
            require(new.valid_from >= current.valid_from)   # 补录的旧信息走 insert_history
            append_version(current, lifecycle="superseded", valid_to=new.valid_from)
            relate(new, current, "supersedes")
        write_receipt_if_scope(new)                          # 范围条目：回执同事务
        outbox("memory.item.activated", new)
    # 提交后：下一次运行组装时即可读到；索引由后台补，读路径会现场扫描未索引的条目
```

**遗忘**

```python
def forget(owner, item_id, expected_revision, request_key):
    with transaction():
        item = load_own(owner, item_id, expected_revision)
        fp = hmac(tenant_secret, normalize(item.statement) + item.claim_key)
        insert_suppression(owner, fp, source_spans=item.evidence_spans())   # 不含正文
        purge_versions_and_candidate(item)                                  # 正文立即清除
        insert_deletion_record(owner, item_id)                              # “某时删了一条”
        mark_derived_purged(sources_include=item_id)
        outbox("memory.item.forgotten", item_id)
    # 进行中带入了这条的运行：下一次模型调用前停下（已有）
    # 后台任何提炼任务：写候选前先查抑制指纹；来源片段命中“不再提炼”的也跳过
```

**后台派生物：来源变了就不落库**

```python
def rebuild(artifact):
    w0, sources = snapshot_sources(artifact)     # 读来源及其版本，算水位
    output = build(sources)                      # 可能调用模型，耗时
    with transaction():
        w1 = current_watermark(artifact)
        if w1 != w0:
            return requeue(artifact)             # 来源在构建期间变了：丢弃结果，重排
        if not citations_resolve(output, sources) or not numbers_match(output, sources):
            return reject(artifact)              # 有一句对不上来源，整版不发布
        publish_new_version(artifact, output, watermark=w0)
```

### 6.5 并发与一致性：每种机制保证什么

| 机制 | 保证 | 不保证 |
|---|---|---|
| 只追加版本加期望版本号 | 两个人同时改同一条，后到的被拒并提示刷新，不会互相覆盖 | 不防止两个人各建一条意思相同的新条目 |
| 主张键部分唯一索引加事务级建议锁 | 同一范围、同一主张键只有一条当前有效；替代是串行的 | 主张键不同但意思相近的重复，要靠相似提示和人判断 |
| 请求编号加内容摘要 | 重试不产生重复写；同编号不同内容被拒 | 不识别“两个不同请求其实是一回事” |
| 条目、回执、发件箱同一事务 | 业务写入和事件要么都有、要么都没有 | 派生物不在这个事务里，是最终一致 |
| 发件箱加按（事件，消费方）去重 | 事件至少送达一次，消费幂等 | 不保证跨对象的事件顺序；所以派生物用水位核对，不依赖顺序 |
| 来源水位比对后再发布 | 过期的后台结果永远不会成为当前版本 | 不保证重建多久完成 |
| 读时复核（行级权限、依赖清单、生命周期） | 不管索引和缓存多旧，返回给模型的每一条在此刻都是可读且有效的 | 已经发给模型的内容收不回；所以进行中的运行在下一次模型调用前复核，命中即停 |
| 运行内冻结 | 一次运行里看到的记忆前后一致 | 运行期间别人确认的新条目，这次运行看不到，下一次才有 |

### 6.6 失效怎么传播

原则：**正确性靠读时复核保证，派生物的清理只影响召回和存储，不影响是否泄露。**

| 来源变化 | 条目 | 索引与向量 | 近况与简报 | 运行中的上下文 | 执行历史里的副本 |
|---|---|---|---|---|---|
| 业务对象改版 | 标“可能过期”或“待复核”，降到背景区 | 不动 | 作废重建 | 冻结不变；下次运行生效 | 不处理（是当时的真实记录） |
| 原件撤回、对象撤权 | 对失去权限的读者隐藏 | 后台清向量 | 作废；重建时不含该来源 | 下一次模型调用前停下 | 按保留期清除 |
| 条目被替代或撤回 | 旧版本保留可查，不再装载 | 旧版本退出索引 | 作废重建 | 下次运行生效 | 不处理 |
| 个人条目被遗忘 | 正文清除 | 立即清除 | 个人条目不进团队简报，无需处理 | 下一次模型调用前停下 | 按保留期清除（X3：Temporal 历史保留期需与此对齐） |
| 嵌入模型更换 | 不动 | 新旧两套并存，重嵌完成并通过检索评测后切换；一次查询只用一套 | 不动 | 不动 | 不动 |

### 6.7 九个具体问题

1. **新版本替代旧版本，同时能追溯历史？** 替代不删旧版本，只给旧版本写失效时间。`memory.search` 带 `as_of` 时返回那个时点有效的版本。
2. **后来补录的旧信息覆盖当前事实？** 替代的守卫比较的是生效时间，不是记录时间。补录条目的生效时间早于当前条目，就只能作为历史版本插入。
3. **同项目不同 Build、同产品不同型号被误合并？** 适用条件是主张键的一部分。Build 不同，主张键就不同，系统不会当成同一件事；相似提示会注明“适用条件不同”。
4. **用户纠正后多久生效？** 本会话：下一轮（纠正写进工作状态，和确认在同一事务）。其他会话：下一次运行开始时。已在进行的其他运行：这次不变；被删除的条目会让它在下一次模型调用前停下。
5. **多人、多运行并发更新？** 见 §6.5 前三行。
6. **后台摘要做完时来源已经变了？** 水位比对不一致就丢弃重排（§6.4）。
7. **来源修改、删除、撤权后，派生物怎么同步？** 见 §6.6。每个派生物在登记表里记了它用过的来源，所以能按来源反查出所有受影响的派生物。
8. **用户要求遗忘后，后台任务又从旧记录里把它提炼回来？** 三道防线：抑制指纹（同样内容不会从旧记录里再被提议）；来源片段标“不再提炼”；个人条目本来就只能由本人原话触发加本人确认，后台任务没有写个人条目的路径。
9. **个人记忆删除和必须保留的业务历史怎么划界？**

   | 内容 | 本人要求遗忘时 |
   |---|---|
   | 个人条目、个人候选、它们的索引和向量 | 立即清除 |
   | 本人的会话记录 | 需要“删除会话”功能（现在没有，C9）；删除时情景、索引、向量同步清除 |
   | 运行回执、审计、出站回执 | 保留（I17：删除不能抹去受控历史） |
   | 由本人“分享到项目”而产生的范围条目 | 是独立的业务记录，不随个人条目删除；可以由本人或负责人停用 |
   | 本人在项目讨论里的发言 | 属于项目记录，按项目的规则，不属于个人记忆 |

### 6.8 检索与上下文构建

**请求怎么分流**

| 用户在问什么 | 先去哪 | 再去哪 |
|---|---|---|
| 现在是多少、现在到哪了、谁负责 | 领域读取（当前版本） | — |
| 当时是多少、冻结时的规格 | 领域读取（指定版本或 as_of） | 情景（当时讨论了什么） |
| 为什么这么定、当时还考虑过什么 | 正式决定记录 | 决策背景条目 → 情景 → 讨论串 |
| 我们一般怎么做、客户在意什么 | 范围约定和关注点 | 已发布规则 |
| 以前遇到过类似的吗 | 企业检索（相似历史、已发布规则） | 经验候选（标“未评估适用性”） |
| 文件里怎么写的 | 企业检索（原件） | — |
| 我上次做到哪了、接着做 | 未完成工作目录（常驻） | 情景 → 读回会话 |

**对象怎么准确定位**：优先级是 @ 选中的对象 ＞ 运行绑定的范围 ＞ 编号通道识别的完整型号和料号 ＞ 本人叫法换成的标准词 ＞ 语义检索。同名产品靠对象 ID 区分，名称相同不合并。定位不唯一时，问一个澄清问题，不猜。

**怎么组合四种检索**：先用结构化条件过滤（范围、种类、有效期、适用条件），再在过滤后的集合里做关键词、编号精确匹配、向量三路召回并融合，最后对命中的对象做一跳关系扩展（两端都过权限）。

**型号、数值、单位、日期、版本**：这些只走精确通道。条目里的数值原文、数值、单位分开存；检索时编号和版本做精确匹配；向量相似度只用来找“说的是不是同一个话题”，不用来判断“是不是同一个值”。

**权限什么时候生效**：检索 SQL 里就过滤，所以排序器和模型看到的候选集已经是当前用户可读的；发给模型之前再复核一次。小集合（个人记忆）直接精确检索，不走近似索引，避免“先取近邻再过滤”造成的漏召回。

**当前事实和历史事实**：默认查现在。问题里有明确时点（“冻结时”“上个月”“B1 那轮”）时，小Pai 传 `as_of` 或指定版本；返回的每条都带有效区间，回答里写明“截至某时”。

**跨项目经验**：三个条件见 §5.3 第 4 条。

**没有记忆、证据不足、冲突未解决**：

- 没有有效记忆 → 回到领域和企业检索；都没有 → 明说“没有找到”，并区分“没查到”和“业务上不存在”。
- 只有未核实的观察 → 可以提，但说明“这是某人某日的推测，未核实”。
- 冲突未解决 → 两边都给，说明各自来源，问一个澄清问题或建议谁来裁定。

**故障和滞后**：记忆服务不可用 → 运行照常，只用领域和企业检索，信封里写明“本次未读取记忆”，回答里说明。索引滞后 → 现场扫描未索引的条目（已有做法）。向量不可用 → 标“仅关键词”，不表现成零结果。

**上下文里放哪**

| 位置 | 内容 | 上限（初始值） | 超了先裁谁 |
|---|---|---|---|
| 冻结前缀 | 系统策略、工具定义、技能目录 | — | 不裁 |
| 运行信封 · 证据 | 当前对象的正式约束（当前版本、冻结状态） | 按技能合同 | 改为目录加按需读 |
| 运行信封 · 约束区 | 固定偏好；个人口径和叫法；范围约定 | 个人 1,000；范围约定占范围预算的优先部分 | 先裁全局条目，留本范围的；约定只留置顶的；不整体去掉 |
| 运行信封 · 背景区 | 未完成工作目录 300；范围近况 400；关注点、决策背景、观察（与约定合计 800）；最近情景目录 300 | 合计约 1,800 | 最先裁：情景目录 → 近况 → 观察 → 关注点 |
| 末尾 | 工作状态（目标、约束、焦点对象、未完成、待确认、关键证据引用、不确定项）≤1,500；当前问题 | — | 约束和焦点对象不裁；装不下就停并说明 |
| 循环内 | 工具结果（含 `memory.search` 的返回） | 单条 4,000 | 较早的换成句柄 |

- 压缩后必须留下的：当前目标、未完成动作、待确认事项、关键证据的引用、不确定项。这些都在工作状态里，由服务器维护，不靠模型摘要。
- **什么时候主动加载，什么时候让小Pai 自己查**：每次都会用到、而且很短的（偏好、约定、未完成目录）主动加载；只在某些问题上才用到的（背景、情景详情、简报）让小Pai 按需查，信封里告诉它“还有 N 条没带，可以查”。
- **为什么用了这条**：每条进入上下文的记忆在使用清单里记一行：条目 ID、版本、区、原因（范围匹配 / 置顶 / 检索命中及查询词和排名）。界面上“用到了 N 条记忆”点开就是这张表。
- 历史对话、文档、工具结果、记忆各自保持身份标签。任何一种被检索到或被摘要过，都不会获得改系统规则、权限或审批要求的能力。

### 6.9 后台整理、经验学习与程序记忆

**几个说法在本稿里各指什么**（2026-11-12 补充）：

| 说法 | 原文的意思 | 本稿里对应什么 |
|---|---|---|
| consolidation（整理合并） | 去重、合并、清理过期内容 | 下表的“维护”：不调用模型，自动生效；合并后的文字由模型起草、人确认 |
| reflection（反思） | 从纠正和失败里总结改进 | “经验沉淀”和“程序性汇总”，都只产出候选 |
| dreaming | Anthropic、Letta 的说法：离线回看记录，修正笔记、建知识表示、决定预先加载什么 | 三件事分别对应下表的“条目核对”“范围简报”“常驻升降建议” |
| sleep-time compute（闲时算力） | 把整理挪到回答路径之外 | 所有调用模型的整理都在后台工作流里；回答路径不新增模型调用 |

不采用的两种做法：Agent 自己改写记忆且不经人（Letta 的 dreaming 默认如此）；Agent 自己重写提示词（LangGraph 文档里的反思）。小Pai 的整理任务没有任何一条能直接改有效条目的文字、状态或常驻位置。

**是否采用后台整理**：采用，但拆成下面七类任务，产出状态不同。

| 任务 | 触发 | 处理范围 | 输入水位 | 产出 | 自动生效？ |
|---|---|---|---|---|---|
| 维护（不调用模型） | 业务事件；每日定时 | 受影响的条目和派生物 | 事件编号 | 标可能过期和待复核；相似条目对；索引和向量；抑制执行 | 是 |
| 范围近况 | 读取时现算；慢了再改成事件触发预算 | 一个范围 | 最近事件 | 确定性摘要 | 是 |
| 范围简报（调用模型） | 该范围有新确认的条目、已关闭的问题或新决定，且超过最小间隔 | 一个范围 | 条目和业务事件的版本集合 | 逐句带引用的简报页 | 作为派生物自动发布，前提是每句的引用都能解析、数字都对得上（§6.4）；只进背景区，按需读 |
| 经验沉淀（调用模型） | G0 结束、问题关闭、项目关闭 | 触发对象及其关联记录 | 对象版本 | 范围候选、知识候选 | 否，候选 |
| 程序性汇总 | 每日定时 | 近 30 天的纠正、拒绝、评测失败、工具错误 | 时间窗 | 技能修订候选 | 否，候选 |
| 条目核对（先规则，后模型） | 条目引用的来源出了新版本；复核日期临近；被带入次数多而久未核对 | 有证据链接的有效范围条目 | 条目版本加来源版本 | “疑似不符”提示，发给确认人 | 否，只是提示；不改条目 |
| 常驻升降建议（不调用模型） | 每周定时 | 个人条目按本人自己的运行统计；范围条目按该范围的运行统计 | 时间窗 | “建议置顶 / 取消置顶 / 缩小作用域 / 归档”，发给本人或确认人 | 否，只是建议 |

**关键规则**：

- **回到原始来源核验**。整理任务的输入只能是原始记录、条目和业务对象，不能是上一次整理的产出。简报每次从来源重建，不是在旧简报上改。这是控制“越总结越走样”的主要手段。
- **“有人这样说”和“已被证实”分开**。从讨论和对话里来的内容，可信状态是“有人这样说”；只有关联到已发布的业务记录，或经具名核实，才是“已核实”。整理任务不能升级可信状态。
- **一次成功不推广，一次失败不归因**。单个案例只能生成“案例记录”，适用条件锁定在那个型号、Build、工况上。晋升为“候选方法”要求：至少两个相互独立的案例（不同 Build 或不同项目）有业务结果回执支撑，并且列出已知的反例。
- **防止互相引用造成虚假印证**。证据按根来源计数；小Pai 生成的内容、派生物、引用了记忆的回答，都不算来源。
- **保留什么**。保留可核验的行动、结果和一句简明的依据。不保存模型的思考过程，也不以它为前提。
- **版本、审计、回滚**。每次整理是一次有回执的自动化运行；产出带版本；简报保留最近若干版，回滚就是把“当前”指回上一版；候选被采纳后的条目按运行可撤回。

**条目核对**（2026-11-12 补充）

- 问题：现有机制只在“引用的对象出了新版本”时把条目标为待复核。条目的文字从一开始就和来源对不上，或者来源内容没变但条目写偏了，发现不了。
- 做法分两步。第一步不调用模型：证据链接指向的来源是否还存在、还可读；条目里的数值和单位是否出现在引用的片段里；条目与主语对象的当前值是否直接冲突。第二步才调用模型，只问一个问题：引用的片段是否支持这条说法。回答必须摘出片段里的原句，服务器核对这句确实在片段里。
- 产出：一条“疑似不符”提示，分四种：来源里找不到这个说法；数值或单位与来源不同；与业务对象当前值冲突；来源已不可读。提示连同摘出的原句发给确认人，由人决定修订、撤回或忽略。这就是 P84 第 6 项“小Pai 只报告冲突，由服务器存为提示并通知作者，AI 身份不改记忆的状态”的后台版本。
- 不做的事：不改条目文字；不改可信状态（不会因为核对通过就升为“已核实”，那需要具名核实人）；不处理个人条目（个人条目是本人的交代，没有“对不对得上来源”的问题；叫法指向的对象是否还在，已有确定性检查）。
- 核对的先后：按“被带入的次数 × 距上次核对的时间”排队，先核对用得多又久未核对的。这是 Anthropic 文中提出的设想，原文没有实测，本稿把它当初始做法，由 §8.4 的消融决定去留。

**常驻升降建议**（2026-11-12 补充）

- 问题：哪些条目每次都带上，现在按固定规则定（作用域匹配、置顶、最近确认优先）。常驻的内容会进每一次运行，写偏一条就影响每一次回答，所以这一层要小、要准；但没有任何机制根据实际使用情况回头调整它。
- 只用确定性信号，不问模型“你用没用这条”：

  | 信号 | 来自哪里 | 指向什么建议 |
  |---|---|---|
  | 一条没有常驻的条目经常被 `memory.search` 搜出来 | 使用清单 | 建议置顶，或把作用域从某项目放宽 |
  | 一条常驻条目 90 天里既没被带入也没被搜到 | 使用清单 | 建议归档 |
  | 一条全局条目只在某一个项目的运行里出现 | 使用清单 | 建议把作用域缩到那个项目 |
  | 带入这条的运行被本人纠正，或本人点过“这次别用”“这条过期了” | 运行反馈、§7.3 的操作 | 建议取消置顶或修订 |
  | 常驻预算经常装不下（每次都有条目被挤掉） | 组装记录里的“未带入条数” | 建议清理：列出最久没用的几条 |

- 产出只是建议，出现在“我的记忆”或范围的备忘区，由本人或确认人点一下才生效。不自动升降。
- 与 N12 的关系：统计的对象是本人已经确认过的条目被用了多少次，不从对话里学习新的偏好，不形成画像。个人条目的统计只算本人自己的运行，只给本人看，管理员看不到。

**节奏与预算**（2026-11-12 补充）

| 任务 | 是否调用模型 | 最小间隔（初始值） | 没有变化时 |
|---|---|---|---|
| 维护、范围近况、常驻升降建议 | 否 | 事件触发或每日、每周定时 | 水位没变就不跑 |
| 条目核对 | 第二步调用 | 同一条目两次核对至少隔 30 天，来源出新版本时不受此限 | 条目和来源的版本都没变就跳过 |
| 范围简报 | 是 | 同一范围两次重建至少隔 24 小时 | 来源水位没变就不重建 |
| 经验沉淀、程序性汇总 | 是 | 由业务事件或每日定时触发，同一事件只跑一次 | — |

- **并发**：同一范围同一类任务同时只有一个在跑。工作流编号由范围和来源水位算出，重复的启动请求被拒。
- **费用**：调用模型的整理都是自动化运行，每次有自己的运行预算和回执。费用单列为“记忆整理”，和后台索引的预算放在同一处管理，租户管理员看得到用量。
- **预算不够时**：只停调用模型的任务，先停范围简报，再停条目核对，经验沉淀最后停（它由业务事件触发，次数少）。不调用模型的维护照常运行。暂停如实显示：简报页标“已暂停更新，内容截至某时”，不拿旧内容冒充最新。
- **出站**：每次调用按运行绑定的数据类别判定并记出站回执（P26）。这几类任务和 P88 的系统自动化规则同样办理：租户预置，管理员可以停用。带客户标识的范围只在同一客户范围内整理，不跨客户汇总。
- **身份与范围**：按 P57，规则负责人取触发对象或该范围的负责人，读写不超过其当前范围，每次运行重新核对。
- 上面的间隔都是初始值，按 §5.6.6 的方法在调参集上校准。

**从案例到技能的晋升阶梯**

```text
案例记录        一次有业务结果的经历。适用条件 = 那一次的型号、Build、工况。
   │  条件：≥2 个独立案例，结果有回执，列出反例
   ▼
候选方法        知识候选（T0，须资格）。带适用性假设。只作线索，不能当依据。
   │  条件：适用性评估判定“适用”（对目标配置和用途，由具名的人或确定性引擎判断）
   ▼
已发布规则      设计规则（T2，具名发布）。带生效期、适用条件。可作依据引用。
   │  条件：这条规则是“做法”而不是“事实”，并且在多个场景重复被用到
   ▼
技能修订候选    把规则写进技能包或场景配方。
   │  条件：技能负责人审核；golden-case 和回归题评测通过（评测集不可由这个流程修改）
   ▼
受控技能        新补丁版本；已有的 T0 资格重审。
```

撤回是每一级都有的：来源撤回或对象改版 → 规则标“需复核”；规则撤回 → 引用它的技能版本标记并进入修订；技能出现关键错误 → 资格暂停，降回一次确认。

## 7. 端到端业务示例与用户体验

两个示例里的人名、项目、编号都是为说明而设的。

### 7.1 示例一：个人习惯，从一句话到被遗忘

| 时间 | 发生了什么 | 系统怎么处理 | 处理后的状态 |
|---|---|---|---|
| 11-10，项目 F64 的会话 | 用户：“把这周的周报整理一下，以后给我表格形式的周报。” | 原话存进会话记录。运行收尾时过三关：① 触发片段“以后给我表格形式的周报”能在本人原话里逐字找到，不在页面资料里，没开不进记忆，不是业务事实；② 属于明确的长期交代；③ 主张键（口径，周报，格式）下没有已有条目 → 新建候选 | 工作状态多一条原话约束，**这次的周报就按表格出**。出现一张候选卡：“要记住这条吗？以后周报用表格形式。作用域：全局 / 仅本项目” |

| 12-15 | 用户：“以后周报给我表格。” | 这是遗忘之后本人重新做的明确交代，不受抑制限制，照常出候选卡；确认后旧的抑制指纹解除 | 新条目 N2 |

### 7.2 示例二：团队的决策背景，从口头同意到正式变更

| 时间 | 发生了什么 | 系统怎么处理 | 处理后的状态 |

## 8. 评估与验收方案

### 8.1 原则

- 评测题从业务时间线上截取：一个项目上的业务事件和多名成员的会话交织，加一份权限快照。
- 按事件顺序回放。每道题只能看到它时间点之前的事件，不能用到未来信息。
- 时间线分成调参集和验收集，按整条时间线切，不按题切，防止同一条时间线两边都有。
- 能用规则判的不用模型判。需要模型评审的指标，先有人工标注子集校准；试点期只有一名标注人时，这类指标只观察、不作门槛。
- 新题一律是候选，你确认后才进题集。

### 8.3 基线

四组加一个上限组，在同一评测集上跑：

| 组 | 设置 |
|---|---|
| 基线 0：无跨会话记忆 | 关掉个人条目、情景回忆、范围条目、简报。保留会话内的工作状态，保留完全相同的业务读取和企业检索工具 |
| 基线 1：原始历史检索 | 不做任何提炼。给一个按本人权限搜索自己全部会话原文（原话加回答）和可读讨论串的工具 |
| 基线 2：当前实现 | 今天的 M1 加 M2a |
| 目标架构 | 本稿 |
| 上限：理想记忆 | 把人工标注的正确记忆直接注入，跳过写入和召回 |

控制变量：

- 同一个模型和版本。
- 同一份可见数据（同一权限快照）。
- 同一批任务。
- 可比的上下文预算：聚焦上限相同；基线 1 取回的历史片段和其他组的记忆用同样的 token 上限。
- 有随机性的指标每格至少跑 5 次，报告均值和波动。

怎么读结果：

- 目标 − 基线 0 = 记忆的净收益。小于等于 0 说明记忆在添乱。
- 目标 − 基线 1 = 提炼和治理相对“直接搜历史”的增益。如果很小，说明账本和整理不值得做那么重。
- 目标 − 基线 2 = 本稿相对现状的增益。
- 上限 − 目标 = 写入和召回造成的损失。
- 上限 − 基线 0 = 这个业务里记忆价值的天花板。

### 8.4 消融

每次在目标架构上只关一样：

| 关掉什么 | 要证明的增益 | 主要看哪些题 |
|---|---|---|
| 后台整理里调用模型的部分（经验沉淀） | 事件触发的沉淀让后续项目少踩坑 | 跨项目经验类题、T22 |

| 情景索引里的回答摘要 | 决策依据和接续任务更容易找到 | T01、T02 |
| 任务笔记 | 跨会话长任务不重复劳动 | 多会话研究类任务 |
| 条目核对 | 写偏的条目能被发现并改正，且提示里的误报不多 | T27；被植入错误条目的时间线 |
| 常驻升降建议 | 按建议调整后，同样的常驻预算下约定遵守率和任务完成率更高 | T28；长时间线（条目逐渐变多）上的前后对比 |
| 单类记忆：个人条目 / 范围条目 / 情景 | 哪类在帮忙、哪类在添乱 | 全部 |

某一项的增益不为正：从目标架构里去掉，或在对应场景的配方里降预算。

### 8.5 指标定义

| 类别 | 指标 | 算法 |
|---|---|---|
| 写入 | 写入精确率 | 标注为“该记”的候选数 ÷ 产生的候选数 |
| 写入 | 写入召回率 | 成为候选的“该记”内容数 ÷ 标注为“该记”的内容数 |
| 写入 | 错误固化数 | 生效条目里，标注为讨论、假设、草稿的条数 |
| 写入 | 未确认生效数 | 没有确认记录却生效的条数（零容忍） |
| 写入 | 重复率 | 标注为同一件事的有效条目对数 ÷ 有效条目数 |
| 写入 | 关键事实遗漏率 | 后续任务需要但没被记下、也无法从业务系统读到的内容占比 |
| 检索 | recall@k、precision@k | 记忆和证据分开算 |
| 检索 | 关键证据覆盖率 | 回答所需的关键来源里，被取到的比例 |
| 时态 | 时点正确率 | 当前题答了当前值、历史题答了当时值的题数 ÷ 总题数 |
| 生效 | 纠正生效延迟 | 确认提交 到 新运行首次装载该版本 的时间，p50、p95 |
| 生效 | 撤权后读取次数 | 撤权提交之后仍返回相关内容的次数（零容忍） |
| 遗忘 | 删除残留数 | 删除后在条目、候选、索引、向量、简报、新运行上下文任一处出现的次数（零容忍） |
| 遗忘 | 重新生成数 | 删除后产生内容相同候选的次数（零容忍） |
| 整理 | 核对检出率、误报率 | 被植入的不符条目里收到提示的比例；收到提示的条目里实际一致的比例 |
| 整理 | 自动改动数 | 整理任务在没有人操作的情况下改变条目文字、状态或常驻位置的次数（零容忍） |
| 整理 | 建议采纳率 | 被本人或确认人采纳的升降建议数 ÷ 发出的建议数；长期很低说明信号选错了 |
| 任务 | 任务完成率 | 按评分规程判定完成的任务数 ÷ 任务数 |
| 任务 | 重复澄清次数 | 问了历史上已经回答过的问题的次数 |
| 任务 | 错误业务动作数 | 起草或执行了不该有的领域候选或命令的次数 |
| 忠实 | 记忆被当证据引用次数 | 零容忍 |
| 忠实 | 事实冲突时采信记忆次数 | 零容忍 |
| 性能 | 记忆组装耗时、首字延迟 | p50、p95 |
| 性能 | 上下文占用 | 记忆 token ÷ 输入总 token |
| 可靠 | 降级告知率 | 降级运行里如实说明的比例；伪零结果次数（零容忍） |

### 8.6 失败怎么处理

- 零容忍项任何一条失败：阻断发布，先修。
- 质量项下降：说明原因，由你决定是否接受。
- 某个组件消融增益不为正：去掉或降预算，不带着上线。
- 每条失败生成一道回归用例候选，你确认后入库。
- 有限的测试全部通过，只能说“在这批用例上没有发现失败”，不能说系统不会出错。

数据与上线的正确性：

- **迁移**：现有个人条目能无损映射到新契约（有效 → 有效；种类一一对应；确认状态 = 本人确认；生效起点 = 确认时间）。迁移期间新旧两处都能读，核对一致后切换。原始记录和情景表不动。
- **灰度**：每个新能力挂在租户记忆策略的开关上，先在试点租户开。提示词变更走 Prompt A/B。“经验沉淀”和观察类 T0 走资格流程。
- **回滚**：派生物随时可以丢弃重建；条目只追加，回滚就是把“当前”指回上一版；配方回滚是技能包版本回退；任何回滚都不删原始记录。
- **不变的纪律**：迁移按真实 head 单调编号；golden-case 不由自动化写入；AI 身份对业务表零直接写；记忆不进冻结前缀。
