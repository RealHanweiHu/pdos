## 0. 结论

1. **对外只有一个 Agent：小Pai。**
   - 内部只有一套运行时：Temporal 负责长等待、定时和重试；LangGraph 负责 Agent 本身的推理循环和检查点。
   - 同时有多个任务在跑，必要时拆出受隔离的只读子任务。
   - 不做多个专业 Agent 互相协作、群聊或投票。
2. **专业能力是工具和技能包，不是 Agent**（用户 2026-10-08 定：不再按原工程六领域 Agent 的方式组织）。
   - 现有 7 个 AgentKey、45 个登记能力，逐步拆成工具和技能包，由小Pai 按需调用。
   - AgentKey 退出运行时概念。技能包按工作内容组织，例如 RFQ 抽取、竞品对比、失败归并；不再按六个领域划分。
   - 权限来自领域对象和写操作登记，不来自 Agent 归属。
3. **小Pai 接入统一的工具注册表。**
   - 包括读工具、研究工具、计算工具、带档位的领域命令，以及经管理员允许的 MCP 连接器（§4.3）。
   - 对话成为正式的修改通道，即 DC-11 §11.3 的要求。
4. **已实现的持久执行边界保留为外层**（AGENTS.md 不可协商项 6）。
   - 现在的"两节点 LangGraph 外壳"只是承载旧入口的过渡做法。
   - 新增一张真正的 Agent 图，从小Pai 的公开研究开始迁移。
5. **先做的事**：
   - 先修剩余 P0 和几处 P1 硬伤（§11 阶段 0），不等运行时迁移；
   - 产品线先迁，事件类能力后迁；
   - 被替代的自研治理代码最后删。

## 2. 目标拓扑

### 2.1 四层

| 层 | 数量 | 说明 |
|---|---|---|
| 用户面 Agent | 1：小Pai | 唯一对话入口。用户说目标，不选 Agent。后台任务的结果也署名小Pai，并标明触发来源和所用 Skill |
| 运行时与 AI 身份 | 1 套运行时；每个租户 1 个 AI 身份 | 权限按每次运行绑定：请求者、范围、档位、预算、cancel_epoch。不按 Agent 人格授权 |
| 任务（Run） | 多个并发 | 对话请求、持续委托、自动化规则。自动化规则可由领域事件、定时、相对里程碑或手动触发。都是同一张图加载不同的 Skill |
| 子任务 | 按需 | 只有两种：广度只读研究的并行展开；隔离读取不可信内容。见 §6 |

### 2.2 何时拆子任务

| 情况 | 做法 |
|---|---|
| 能拆成互不依赖的只读子问题，每个都要读大量原文 | 并行子任务。子任务只交回结构化结果 |
| 读取网页、客户邮件、RFQ 等不可信内容 | 隔离子任务。不给写工具，只交回带原文片段的字段 |
| 写同一个对象，或结论互相约束、需要整体取舍 | 主 Agent 顺序做 |
| 需要不同专业视角 | 加载 Skill，不新建 Agent |
| 需要独立复核 | 用确定性校验（逐字核对引用、引擎复算），或交给人。不让另一个模型投票 |

### 2.3 不做

- 自主 Agent 群聊、多席位辩论进正式结论。现有 `debate_runtime` 不纳入主线。
- 给用户暴露"品质 Agent""产品 Agent"之类的选择。
- 让 LangGraph 的 interrupt 或 workflow 跑完代表业务批准。这是 10/02 目标架构 §03.1 的要求。

## 3. 运行时结构

### 3.1 分层

```text
入口：小Pai 消息 / 页面按钮 / 领域事件 / 定时（Outbox）
  → 领域 API：鉴权、范围绑定、幂等键；写 Run 与回执
  → DurableRuntime.submit → Temporal AgentWork（已实现）
      → Activity：pdos_execute_agent_graph（心跳、超时、崩溃转对账）
          ├─ legacy 处理器：现有 31 个入口（两节点外壳，迁移期保留）
          └─ agent 处理器（本方案新增）：Agent 图，见 §3.3
      → 等待 signal：人回答问题、T1 确认、专家答复、G0 结果
        领域事务提交后经 Outbox 发出
  → 领域命令：唯一写入口，与 ActionReceipt、Audit、Outbox 在同一事务
```

### 3.2 状态归属

沿用 10/02 目标架构 §3：

| 存储 | 拥有 | 不拥有 |
|---|---|---|
| 领域库 | 正式事实、版本、批准、回执 | 执行位置 |
| Temporal 持久库 | 执行位置、定时器、等待、重试 | 业务真值 |
| LangGraph 检查点（PostgresSaver，独立库） | 一次运行内的消息、工具结果、证据池引用 | 批准 |
| 运行时作业库 `pdos_agent_runtime` | 作业引用、事件流、对账标记 | 业务数据原文 |

### 3.3 Agent 图

```text
prepare_context        按 Skill 声明组装上下文（见 §8）
  → model              原生工具调用；输出要么是工具调用，要么是最终结构化结果
  → route
      ├─ 工具调用 → tools   只读工具可并行；写工具串行并带幂等键
      │              → model（循环；轮次和工具次数有上限）
      ├─ 需要人输入 → interrupt（Activity 返回 needs_input；workflow 等 signal；
      │              用 Command(resume=…) 在同一个 thread 继续）
      └─ 最终结果 → verify → finalize
verify                 schema、引用逐字核对、数值交引擎复算、档位与范围复核
finalize               写结果与回执；上限用尽时强制收尾，保留已完成部分，不整段丢弃
```

- 每个会话对应一个 LangGraph thread。同一会话的证据池跨轮复用，只存快照引用和定位，不存原文副本。
- 研究的广度展开用 LangGraph 的 `Send` 起子图，见 §6。
- 现有的两节点外壳只作为 legacy 处理器保留，新能力不再接入。

### 3.4 模型网关改造

1. **原生工具调用和结构化输出**：
   - OpenAI 兼容协议用 `tools` 加 `response_format`/JSON schema；
   - Anthropic 原生协议用 `tools` 加 `cache_control`；
   - 消息只往后追加，系统提示和工具定义保持前缀稳定（AGENTS.md 不可协商项 4）。
2. **重试回传错误**：重试时把上次输出和校验错误一起回传给模型。超长输出按截断处理，不整次判失败。
3. **先验证 MiniMax-M3**：在阶段 0 用 golden 探针核对它的原生工具调用和 JSON schema 遵从度。
   - 不达标时，保留 JSON 文本模式作为适配器内部的降级路径，对外接口不变；
   - 同时把"工具调用能力"列入模型资格评测项。
4. **供应商错误重试**：遇到 429 和 5xx 按退避重试，使用现有但从未启用的 `max_backoff_seconds`。

### 3.5 预算、计量与取消

- **取消**：预留和结算放在 Activity 内。客户端取消、Temporal 取消与供应商错误分开识别。
  - 取消时按预留上限做"估算结算"并释放名额；
  - 不再产生永久占用的 unknown。这一条同时修掉 P0-2。
- **未知用量**：保留结算时限，过期转为估算并标注，不补零。
- **计量包到期**：不允许拖垮整个网关。试点期改用不过期的本地估算，或改为延迟校验、失败可降级（P0-3）。
- **授权与计费解耦**：工具授权不再依赖 `budgeted` 模式，避免再次出现"模型能回复、搜索不能跑"。
- **费率**：费率表接入后才计价。在此之前费用明确显示为未知，不再伪装成已有成本数据。

## 5. Skill

### 5.1 技能包：三要素加渐进披露（用户 2026-10-07 定）

参照 Linear Agent 的公开做法：单个 Agent，技能包由三要素组成，按上下文预先加载，运行中也可以自己加载。

**每个技能包由三部分组成：**

| 要素 | 内容 | 例（`competitor_comparison`） |
|---|---|---|
| 工具 | 这个技能可以调用的工具，引用 §4 的 ToolSpec，并带上各自的档位 | `category.competitors`、`evidence.search`、`research.fanout`、`calc.spec_compare`、`proposal.item.patch`（T0） |
| 数据语义 | 相关对象、字段和状态的含义：单位与测试工况、规格字典的参数版本，以及"实测、宣传、推断、未知"的区别、什么能算作证据 | 竞品指标必须引用参数 ID 和版本；不同工况、币种或日期不算同口径；未知不画点 |
| 使用原则 | 什么时候用、方法步骤、边界与禁止事项、失败时怎么处理 | 先确认参数口径一致再比较；样本量不足要标出；价格要注明币种、日期，以及零售价还是促销价 |

**治理元数据**沿用目标架构 §06.2 的 SkillVersion 字段：
- key、version、purpose；
- input_schema、output_schema；
- context_requirements、allowed_operations；
- evidence_policy、failure_policy；
- budget、model_capability_requirements；
- evaluation_suite、owner。

**渐进披露分三层：**

1. **目录**：固定系统提示里只放技能目录，即名称加一句话说明，保持前缀稳定（AGENTS.md 不可协商项 4）。
2. **按上下文预载**：服务器根据当前入口，在第一轮就附上相关技能的完整内容。"入口"包括所在页面、对象、会话范围和触发事件。例如：
   - 在提案页，预载 `proposal_drafting` 和品类数据语义；
   - 在品类对话里，预载 `category_framing`；
   - 由事件触发时，预载对应的技能。
3. **运行中自加载**：Agent 用 `skill.load(name)` 加载其他技能，技能内容作为消息追加。服务器校验当前用户和范围能否使用这个技能；加载记录写入运行回执。

**工具列表与提示缓存**：
- 工具定义整体保持稳定，以便命中提示缓存；
- 技能加载决定的是"允许调用哪些工具、按什么原则调用"，服务器拒绝调用未加载技能的写工具；
- 工具数量大到影响选择准确度时，再引入"按需检索工具"，不在运行中改写工具列表。

**存放方式**：
- 技能包是版本化的配置文件，随代码发布；
- **不写进数据库 CHECK 约束或触发器**，改提示词或使用原则不需要迁移；
- 运行记录里保存所用技能包、模型和工具的完整版本组合。

**适用范围**（用户 2026-10-08 确认）：
- 小Pai 是系统里唯一的 Agent。对话、页面按钮、事件触发、定时和持续委托，都由同一个运行时、同一张 Agent 图加载技能包执行。
- 不另设领域 Agent；技能包按工作内容组织，不按六个领域分组。

## 6. 研究子任务与不可信内容隔离

- **`research.fanout` 的输入和执行**：
  - 输入是一组子问题，按品牌或来源类型划分：官网规格、独立评测、电商评论。
  - 每个子问题在子图里运行 `single_source_research`，只有 search 和 read 两个工具，没有任何写工具。
- **子任务输出台账行**：

  | 字段 | 含义 |
  |---|---|
  | brand、model | 品牌、型号 |
  | parameter_id、version | 规格字典里的参数及版本 |
  | value、unit、condition | 数值、单位、测试工况 |
  | quote | 原文片段 |
  | snapshot_id、locator | 快照和定位 |
  | status、error | 状态：ok / partial / unavailable；以及错误 |

- **原文核对**：`quote` 必须是快照正文的子串，由确定性代码核对。
- **主 Agent 只看台账，不看原始网页。** 失败和覆盖情况的说明由代码根据台账生成，不让模型复述。这能修掉"429 归错品牌"一类问题。
- **读取改进**：
  - Firecrawl 改要 markdown，并使用页面元数据里的标题；
  - 支持 PDF；
  - 按问题挑相关段落，允许续读（offset）；
  - 保留 Firecrawl 的原始错误，不被直连回落覆盖；
  - 遇到 429 按 Retry-After 退避，同站读取共享限速。
- **出站过滤**：查询词发出前，与会话中的私有实体比对，包括客户名、型号、附件名和私有原文片段，命中则拦截或改写。是否允许把客户资料发给模型，待 §13 拍板。
