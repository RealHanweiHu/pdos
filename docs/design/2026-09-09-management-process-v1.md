# 研发管理流程 v1.1：四专业协作与 ID 立项专项

日期：2026-09-09。用户澄清：“我现在没有将整个流程跑起来。我需要你用系统将我的管理流程规定好”；随后明确“我独立开发系统，业务由多人协作”。本轮依据这一方向，沿用既有 NPD 七阶段、实体、权限和 Gate，整理管理规则并接入项目页面。系统开发及验收由用户负责；实际项目按业务角色分工，不把所有研发工作默认分配给用户本人。

## 1. 管理目标与当前做法

团队打开项目时，应知道当前在哪个阶段、优先做什么、由谁负责、在哪里登记，以及下一次评审要检查什么。资料在执行过程中逐步形成；不要求先拿出一个已经跑完的项目，才能建立流程。

先用空白项目或明确标注的示例验证规则、入口、状态变化和阻塞保护；项目启动后，真实资料用于验证实际效果与校准指标。已有 D14-02 报告继续作为导入回放材料，D14-04 的产品类型与照明排除继续有效。不得把示例或旧项目结果写成新项目实测结果。

## 2. 项目主线

新想法或客户要求先进入需求池，评估后形成开发案例，批准后转项目。项目负责人在启动时落实负责人、业务成员和产品类型，按既有 NPD 七阶段推进：

| 阶段 | 管理目标 | 本阶段应逐步形成的记录 | 谁组织交接 |
|---|---|---|---|
| 概念与立项 | 明确做什么、为何做、是否可行 | 需求与范围、技术/成本/交期风险、立项决策 | 产品负责人提供业务依据，项目负责人组织研发评估 |
| 规格与计划 | 约定目标、验证方法和分工 | 规格版本、负责人/期限/依赖、项目测试模板与差异 | 项目负责人协调，产品/研发/品质共同核对 |
| 设计与评审 | 形成可制作的设计输入 | ID 冻结记录、结构/硬件/嵌入式文件、BOM/固件版本、评审问题及样机输入 | 研发牵头，品质及制造相关人员参与 |
| EVT 工程验证 | 验证核心功能和技术方案 | 试制批次、唯一可识别样机、配置、功能报告、问题和复测 | 研发提供样机与设计依据，品质组织验证 |
| DVT 设计验证 | 核对完整规格与可靠性 | 拟定型配置、整机/可靠性/适用认证证据、差异处置和定型结论 | 品质组织验证，研发解决问题，各相关负责人评审 |
| PVT 试产验证 | 验证制造、检验与交付准备 | 冻结 BOM、SOP/治具/检验引用、试产数据、转产交接清单 | 项目负责人组织制造、研发、品质及接收方 |
| 量产稳定与移交 | 完成稳定观察与持续维护交接 | 质量反馈、遗留任务接收、最终版本索引、移交结论和复盘 | 项目负责人协调，各接收方确认维护责任 |

同一管理主线下，自行车泵、汽车泵、帐篷泵等分别选择测试模板。项目差异要写明适用依据、排除理由与确认记录；新增功能或客户特殊要求经 AI/人工形成建议，再审阅并应用。具体性能、可靠性、良率及观察期限不凭空填统一数值，应在各项目规划时约定。

## 3. 团队职责和交接规则

| 业务职责 | 对什么负责 | 交接时必须讲清楚 |
|---|---|---|
| 产品/业务负责人 | 需求、使用场景、范围、客户承诺 | 哪个需求版本、如何判定满足、什么发生了变化 |
| 项目负责人 | 任务分配、依赖、日期、风险协调、阶段评审 | 交给谁、何时完成、前置条件、完成证据及当前阻塞 |
| 研发负责人/执行人 | 设计、样机配置、技术判断与整改 | 具体版本、受影响对象、变更原因及需要怎样复验 |
| 品质/验证人员 | 验证计划、记录核对、问题验证、质量结论 | 验证对象与版本、原始结果、判据、失败项和复验结论 |
| 制造/供应相关人员 | 工艺、物料与试产准备、制造反馈 | 实际就绪情况、版本引用、缺项、交接接收人与证据 |
| 评审人与接收方 | 判断本阶段结论和接收后续责任 | 通过/暂缓/退回/条件放行的理由，以及条件任务的责任/期限/证据 |

“制造/供应相关人员”是业务职责，不等同于新增账号权限角色；实际操作继续使用现有权限矩阵和项目成员授权。项目启动时再指派具名人员，一个人可兼任允许兼任的职责；高/严重 Issue 的独立验证约束、Gate 政策和 AI 接受/应用双动作不被“独立开发系统”取消。

## 4. 每天怎么用

1. 每位成员先看“我的工作”，处理本人到期、阻塞、待验证和待审事项。
2. 在原任务/问题/测试记录中更新结果，附证据或引用；沟通可以在线下进行，结论回到对应记录。
3. 项目负责人按固定节奏检查延期、依赖、风险和下阶段准备；具体会议频率在项目启动时约定。例会结论落到责任明确的任务、问题或决策。
4. 阶段工作完成后进入“Gate·交付物”，检查实际阻塞和签核状态，再提交评审；不以一句“基本完成”代替记录。

## 5. 四条贯穿流程的操作规则

**任务与交接**：任务有唯一负责人、截止日期、前置依赖和清楚的完成描述。前置未完成表示等待前置，不滥用 blocked；实际受阻写明阻塞原因。交接要有接收方和版本/证据引用，不能只发送文件却不说明用途。

**测试与问题**：先确认计划和测试对象，再记录执行结果；上传报告只是导入草稿。核对后确认，失败由对应负责人整改，指定验证人按关闭标准复验。问题按分析→措施→验证→关闭推进，无证据不得假定已解决；重新出现时按已有重开流程处理。

**需求与设计变更**：冻结后变化先记录原因、影响对象、版本、成本/日期/验证影响，再由有权限的人决定。批准后更新相应版本和任务，保留旧记录；不覆盖原报告，不让 AI 直接改正式业务结论。

**阶段评审**：评审前按阶段操作清单人工核对，再看系统实际 readiness。已有 Gate 必需条件不能由条件放行绕过；条件事项必须有责任人、期限和关闭证据。项目只有在当前 Gate approved 后才能按相邻阶段推进。最终阶段评审、业务移交和项目状态关闭分别留痕。

## 6. 已接入系统的位置与执行边界

项目工作区 → 概览·控制塔 → “现在做什么”：对已有 NPD v1 项目，根据实际当前阶段显示职责、应形成的记录和三个优先动作，按钮进入工作项、工程·变更、试制·测试·质量、文档、决策或 Gate。可展开完整七阶段主线及多人协作规则。未知流程/版本不套用 NPD v1 文案；不改动已存在的项目数据或阶段。

本轮新增的是版本化操作指引与页面入口。清单明确标注“评审前由负责人核对”，不使用未绑定业务记录的完成勾选框，不声称这些文字项都已自动检查或自动生成任务。实际硬闸仍由已有服务端 Gate readiness 和项目状态机执行，例如适用阶段 Build/样机/审核报告缺失、失败/阻塞测试、必需交付物和签核阻塞。应依据 Gate 实际返回结果判断，而非仅依据这份操作指引。

多产品线完整配置化模板、任务自动生成、转产交接模板细化等仍按 V0-6/V1-B6 逐项落地，不把指引页面算作全部功能完成。产品真实符合性、真实业务效果及各阶段 Exit 仍需后续实际运行与用户裁决。

## 7. 后续验收顺序调整

先检查“流程规则明确 → 系统入口可操作 → 关键约束有效”，再由真实项目执行形成资料，最后做业务效果验收。下一项应围绕一个阶段的实际操作闭环补齐系统缺口，优先规划阶段的任务分工和项目模板配置；不再反复要求用户先提供完整项目历史材料。

执行依据：[原执行计划](2026-08-09-preview-execution-plan.md)、[V0/V1 联合合同](2026-09-08-v0-v1-acceptance-and-pilot-contract.md)、[项目类型模板合同](2026-09-08-project-type-test-template-contract.md)。本条记录用户新近明确的工作方向，不追认 V0/V1 或生产出口。


## 8. ID、结构、硬件与嵌入式：2026-09-09 用户补充

用户明确研发包含 ID、结构、硬件与嵌入式；任务依赖必须清楚；ID 周期占比较大，需要在立项阶段单列确认。此处沿用七阶段，在概念/立项阶段增加 ID 专项计划确认，进入方案阶段后再做 ID 冻结，不新增一个串行阶段。

### 8.1 立项阶段先确认 ID 计划

ID 是工业设计，包含外观、操作体验、尺寸包络及 CMF（颜色、材料与表面工艺）。在立项阶段评审前，项目负责人组织产品、ID、结构、硬件、嵌入式负责人核对：

1. **来源与范围**：全新 ID、沿用修改或客户提供；指定输入版本及边界。沿用/客户提供也须做适用性与接口核对，不直接跳过确认。
2. **责任与资源**：具名 ID 负责人、内外部设计资源、预算、产品/客户最终确认人，以及各专业接收人。系统开发者身份不代替这些职责。
3. **周期构成**：设计工作量、方案评审轮次、客户反馈等待、外观样制作和修改缓冲分别估算；区分工作日与自然日，不能仅给一个笼统截止日期。
4. **关键节点**：启动、方向确认、外观样确认、ID 冻结的目标日期；关联结构空间/板框、PCB、EVT 样机等后续任务。
5. **未确定项**：明确待谁确认、何时得到答案、影响哪些日期；不能把空白或口头“差不多”标成已确认。

立项确认的是 ID 计划、投入与决策安排，并非要求立项时已经完成 ID 设计。ID 方案冻结需留下图档/外观样、关键尺寸、CMF、操作布局版本、产品/客户确认及结构/硬件可行性结论。

### 8.2 依赖按具体交付物建立

每个任务写明唯一负责人、前置任务、前置输入版本、开始/截止日期、完成交付与接收人。模板中的负责人是业务专业，实例化时必须替换为具名成员。任务不以“研发完成”笼统汇总四专业进度。

- **可以并行**：规格/架构明确后，结构布局、电路选型和嵌入式架构预研与 ID 方案同时开展；按已确认接口在开发板上开发固件基础功能。
- **需要等待输入**：结构空间/板框正式发布依赖 ID 冻结和共同接口约束；PCB 依赖板框和器件/接口约束；板级联调同时依赖目标样板与基础固件。
- **分别汇合**：板框发布后结构详细设计与 PCB 可并行；整机设计评审汇合 ID、结构、硬件和板级联调成果，之后制作 EVT 整机样机。
- **评审仍独立**：任务完成不等于阶段 Gate 批准。PVT 交接准备任务完成后，正式 ERP 交接仍等待 PVT Gate。

### 8.3 ID 周期与延期管理

在进度评审中单列 ID 各节点的原计划、最新预测、实际完成、偏差原因及确认人。ID 较长时优先检查它是否位于本项目关键路径；不能预设所有项目的关键路径永远都是 ID。

ID 延期或冻结后修改时，按依赖链定位结构板框、PCB、联调和样机等受影响工作，分别评估返工、成本、资源与目标日期；经项目负责人及接收方确认后修订计划，保留原日期与变更理由。已有输入足够的预研继续开展；不能机械地把所有任务一起顺延。当前系统没有据此自动计算关键路径或自动改排期。

### 8.4 本轮系统落点与边界

项目概览已增加立项 ID 专项核对、四专业协作说明，以及本阶段/完整 20 项依赖基线；每项列出前置、交付和接收专业。页面与模拟脚本共同读取版本化 JSON，避免两套依赖漂移。

在隔离模拟中，这 20 项已通过真实任务 API 建成具名任务与真实依赖，验证并行工作、输入未就绪的开工拦截、ID 专项决策与延期记录。日常项目页面目前展示模板指引，尚未提供一键实例化和完整 ID 表单，也没有新增“ID 计划缺项禁止立项”的服务端硬闸。现有 Task 对 done/skipped 均视为依赖终态，因此“ID 冻结必须人审且不可跳过”的强制控制仍待实现；本次模拟仅走 done 并保留证据。

两个既有模拟缺口（提前结项、Quality 逐次测试录入权限）继续保留；本轮按用户补充优先细化四专业与 ID，不因此声称这些缺口已修复。验证见 [四专业与 ID 验证记录](../reports/2026-09-09-id-disciplinary-validation.md)。
