# NPI 框架与小Pai自主建立项目任务（设计草案 v0.2）

日期：2026-11-01。**状态：设计草案；§10 P33 已由用户确认（2026-11-01），原文见设计确认稿，v1.1 已加注；未实施，未改代码或迁移。**

依据：[完整目标架构 v1.1](2026-10-08-pdos-complete-target-architecture-v1.1.md) §03.2、§03.4–§03.6、§03.13、§06.5、§06.12、附录 A；[DC-11 写入分级政策](2026-09-20-ai-direct-write-tier-policy.md) §3、§6、§7、§11；[S5 项目工作合同](2026-10-18-pdos-next-s5-project-work-contract.md)；技能包 `pdos-next/server/pdos_next/skill_packages/work_management.md`。

## 1. 起因

用户 2026-10-31 至 11-01 提出三点：

1. 小Pai 应能自动根据品类写 NPI 开发任务、分发工作、设置截止日期和项目节点；
2. 模板要避免臃肿，并能按项目调整，例如“轮胎充气泵、帐篷充气泵等有不同的任务”；
3. “agent 可以根据品类自己创建任务，只需要遵循 NPI 的基本框架即可。”

本草案按第 3 点收口：**只固定 NPI 基本框架，任务由小Pai 按品类和项目自主建立与维护。**

## 2. 现状核对（2026-10-31）

### 2.1 模板

| 来源 | 新品（NPD） | 说明 |
|---|---|---|
| pdos-next 读取的 `assets/cehub/deliverable-guide-manifest.json` | 81 个任务 + 15 个门禁项 | `domain/work_management/templates.py` 的 `catalog()` 不区分模板版本，把 CEHub 2026-07 v1（55 个）、v2（53 个）、v3 三代任务合在一起；六类项目合计 325 个交付物、687 个检查项 |
| CEHub v3（`~/Desktop/ce-project-hub/shared/npd-v3.ts`，可选参考） | 轻量 15–22，标准 25–32 | 已有档位与电池、认证、软件、模具四个附加包；完整档与标准档任务相同；每阶段有出口条件与必交成果 |

v3 放进 pdos-next 后还有三处重复：7 个“评审 (Gate N)”被写成任务，而 pdos-next 的阶段评审与决定是独立对象；概念阶段的立项论证、可行性评估、立项评审已由品类研究、立项提案和 G0 完成；部分同一负责人的工作被拆成多个任务。

### 2.2 小Pai 的项目工作权限

| 操作 | 现行档位 | 限制 |
|---|---|---|
| `work.task.create` | T0（需资格） | 来源只认已登记原件、精确 G0 待决项或模板条目 |
| `work.plan.propose` | T0（需资格） | 只生成候选 |
| `work.plan.apply`、`work.stage.adopt`、`work.stage.milestone.bind` | T1 | 项目负责人本人一次确认 |
| `work.task.assign` | T1 | 项目负责人本人一次确认 |
| `work.baseline.approve`、`work.stage.decide` | T2 | AI 只准备材料 |
| 修改、取消单个任务 | 无命令 | 只能按运行整次撤回 |

`work_management` 尚无任何租户的 T0 资格；项目只有负责人字段，没有团队与角色；真实工作日历未接通；阶段模板没有服务器接口。

## 3. 思路

**框架规定“每个阶段必须达成什么”，小Pai 决定“为此要做哪些任务”。**

这与 v1.1 一致：§03.2 规定模板管进入条件、交付成熟度、责任和评审，“不是按日历自动推进的检查表”；§03.4 要求工作按结果定义。原来写在任务清单里的经验改写进两处：品类资料（小Pai 的输入）和框架检查（代码执行的底线）。

## 4. NPI 基本框架（固定，由人维护）

框架按项目类型版本化（v1.1 §03.13），由用户或项目管理部门维护，小Pai 不改。首个框架为新品；派生、JDM、翻新、OBT、变更按同一方式另定，实施时以 CEHub v3 对应类型整理，经用户确认后启用。

### 4.1 新品阶段与出口成果

出口成果与数值门槛沿用 CEHub v3，可调整。概念阶段由品类研究、立项提案和 G0 完成，不在项目内。

| 阶段 | 必须达成的出口成果 | 阶段节点（人决定） |
|---|---|---|
| 规划 | 完整规格冻结；初版 BOM 与关键供应商明确 | 计划基线（G1） |
| 设计 | ID 外观、结构 3D、电子原理图与 Layout、BOM v1.0；关键料件规格冻结；DFM/DFA 检查闭环；BOM 成本对比目标 | 设计冻结评审 |
| EVT | EVT 样机；功能/性能测试报告（主要功能通过率 ≥95%，无未关闭 P0/P1） | EVT 评审 |
| DVT | DVT 样机；可靠性测试报告（全部通过，无未关闭 P0/P1） | DVT 评审 |
| PVT | 作业指导书；良率报告（整机直通率 ≥95%）；EOL 100% 测试能力验收；包装与物流验证报告 | PVT 评审 |
| 量产移交 | 首批量产良率稳定、客户放行；售后无未闭环重大问题 | 项目关闭评审 |

**轻量路径**（无电池、无新模、常规风险）：EVT 与 DVT 合为“样机验证”，出口成果合并。路径由型号属性按固定规则判定，不由模型判断。

### 4.2 条件成果（按型号属性触发）

| 触发条件 | 增加的出口成果 | 能否去掉 |
|---|---|---|
| 含锂电或受压腔体 | 规划：电芯厂审核或复用确认；设计：安全 FMEA 与保护电路评审；PVT：UN38.3、MSDS、电池安全认证报告 | 红线，不能去掉 |
| 有目标市场认证要求 | DVT：认证报告 | 红线，不能去掉 |
| 含固件或 App | DVT：软件完整测试报告 | 可去掉，须写理由 |
| 需要开新模 | DVT：模具 T1 样品 | 可去掉，须写理由 |

另有三项永久红线，沿用 CEHub v3：EOL 100% 测试能力、PVT 评审、首批量产放行。

### 4.3 任务四要素

每个任务必须有：

1. 一个负责角色；
2. 一个交付物，对应某项出口成果或其前置；
3. 工期，可以是范围或“未知”；
4. 来源：框架出口成果、品类资料、型号定义当前版或 G0 待决项。

## 5. 小Pai 自主做什么

| 时机 | 小Pai 做的事 | 要不要人确认 |
|---|---|---|
| 项目建立（G0 批准后） | 按框架、品类资料、型号定义和 G0 待决项，选定阶段路径并生成全部任务：名称、负责角色、交付物、检查项、依赖、工期范围、来源，绑定阶段节点 | 不用。直接写入项目，署名小Pai，可整次撤回 |
| 分派 | 按项目团队角色分派 | 不用。受派人承接时才形成本人承诺 |
| 排日期 | 估工期，优先用同品类历史实际用时；日期由排期引擎按日历和依赖算出 | 不用。这是计划日期，不是承诺 |
| 运行中 | 根据测试失败、设计变更、会议决定、延期等，增加、拆分、合并、改派或取消**自己建且尚未被承接**的任务 | 不用 |
| 运行中 | 修改**已被承接**的任务的范围或日期 | 要。承接人一次确认 |
| 计划基线（G1）前 | 计划随时由小Pai 维护 | 不用 |
| 计划基线（G1）后 | 偏离基线时显示差异并起草调整方案 | 重设基线由负责人具名决定 |

**品类差异的来源**：参数字典、测试模板、法规目录、品类知识和同品类历史项目。能并入已有任务的内容加为检查项；需要单独负责人、单独工期，或者下游依赖它的成果时，才新建任务。

**项目团队与角色**：是领域事实，由项目负责人维护；小Pai 可起草名单，负责人一次确认。模型不提供人员职责事实（不可协商项 2）。角色无人或对应不唯一时，作为例外交负责人。成员、角色、负载与交接的完整设计见[项目团队、驾驶舱与 @提及](2026-11-01-project-team-cockpit-mentions-design.md)（P34）。

## 6. 框架检查（代码执行，不靠模型）

小Pai 每次生成或修改任务后，由代码检查：

1. 每项出口成果（含触发的条件成果）至少有一个任务产出它；
2. 红线成果必须有任务，且不能标为不适用；
3. 每个任务满足 §4.3 四要素；
4. 依赖无环，阶段节点不作为任务；
5. 没有依据的工期标为“未知”，不得编精确值（v1.1 §03.5）。

不通过的结果不生效。小Pai 自行修改；两次仍不通过，作为例外交给项目负责人。

## 7. 仍由人负责

- **阶段评审决定、计划基线批准**：具名决定，属于 DC-11 §7 不可让渡的人裁决最小集。
- **个人承诺日期**：承接人本人承接时作出（v1.1 §03.5、§03.6）。
- **框架本身**：阶段、出口成果、红线与门槛。
- **项目团队与角色**：负责人维护。
- **例外**：框架检查两次不通过、角色找不到人、小Pai 要改已承接的任务。

## 8. 例：同一框架下的两种充气泵

以下是示意，实际任务由小Pai 按品类资料生成。

| 出口成果 | 轮胎充气泵（锂电无线、数显自动停机） | 帐篷/气垫充气泵（锂电、大流量低压、带抽气） |
|---|---|---|
| 规划：关键供应商明确 | 气泵机芯（气缸/电机）选型与供应商确认 | 风机/叶轮选型与供应商确认 |
| 设计：电子原理图与 Layout | 压力传感与自动停机电路设计；固件设计 | 电机驱动与充放气切换电路设计；无固件，不建软件任务 |
| EVT：功能/性能测试报告 | 压力精度与自动停机标定测试；气嘴兼容测试（Schrader/Presta） | 风量与充气/抽气双向测试；多种气门适配测试 |
| DVT：可靠性测试报告 | 连续工作温升与热保护测试；跌落测试 | 户外防水防尘测试；连续工作温升测试 |
| 品类依据 | 品类种子 `auto-tire-inflator`：31 个参数、31 个测试项、43 条法规条目 | 尚无品类；按用途划界应另建，建成前任务更少、工期多为“未知” |

两者的出口成果完全相同，任务各不相同。

## 9. 质量保障：用资格和指标，不用清单

- **上线前**：基线前的项目计划本质是草稿，按 v1.1 §06.12 草稿类技能包的试点资格办理。用户本人审阅 10–20 个覆盖不同品类的合成或自有项目计划，按“租户 × 技能包 × 模型版本”记录。评估维度：出口成果覆盖、红线、任务四要素、品类差异是否合理、未知是否保留、任务粒度。
- **运行中**：跟踪撤回率、人工修改率和框架检查失败率；超过阈值自动降回一次确认（DC-11 §6.3）。
- **沉淀**：同一品类反复出现的任务，小Pai 建议写进品类资料，由用户批准后生效；不自动改框架。

### P33 NPI 框架约束下由小Pai自主建立与维护项目任务（用户 2026-11-01）

- 起因：用户 2026-10-31 至 11-01 提出“agent 可以根据品类自己创建任务，只需要遵循 NPI 的基本框架即可”，并要求模板不臃肿、可按项目调整（轮胎充气泵与帐篷充气泵任务不同）。现行规则下，任务来源只认原件、G0 待决项与模板条目；计划应用、阶段启用、里程碑绑定与分派均须项目负责人一次确认；没有修改或取消单个任务的命令；模板目录混合 CEHub 三代版本，新品有 81 个任务和 15 个门禁项可选。
- 采纳：
  1. **框架**：项目模板由任务清单改为 NPI 基本框架，按项目类型规定阶段、出口成果、条件成果与红线、阶段节点；框架版本化，由用户或项目管理部门维护，小Pai 不改框架。首个框架为新品，其余项目类型逐一经用户确认后启用。
  2. **任务来源**：框架出口成果、当前品类资料（参数字典、测试模板、法规目录、品类知识）、型号定义当前版和 G0 待决项，均可作为 `work.task.create` 的来源。每个任务记录所服务的出口成果与来源引用。成果标为已交付仍须有实际原件。
  3. **基线前计划自动生效**：计划基线批准前，小Pai 按框架生成的项目计划（阶段路径、任务、依赖、工期、计划日期和里程碑绑定）以 T0 直接生效，涉及 `work.stage.adopt`、`work.plan.apply`、`work.stage.milestone.bind` 的此一情形；署名小Pai，可整次撤回。阶段路径由型号属性按固定规则判定。基线批准后，计划变更以候选呈现差异，重设基线仍为 T2。
  4. **按角色分派**：小Pai 可按项目团队角色把任务分派给对应成员（`work.task.assign` 的此一情形为 T0）。分派不等于承接，受派人本人承接时才形成承诺。项目团队与角色由负责人维护；角色无人或对应不唯一时作为例外交负责人。
  5. **自主维护**：新增 T0 命令，小Pai 可修改、拆分、合并、改派或取消自己建立且尚未被承接的任务。已承接任务的范围或日期变更须承接人一次确认（T1）；已提交或已验收的任务不改。
  6. **框架检查**：每次生成或修改后，由确定性代码检查出口成果覆盖、红线、任务四要素、依赖无环和无依据工期为未知；不通过不生效，两次不通过交负责人作为例外。
  7. **资格**：基线前项目计划按 v1.1 §06.12 草稿类技能包办理试点资格，以用户本人对 10–20 个覆盖不同品类的项目计划的审阅记录为依据，按“租户 × 技能包 × 模型版本”记录。运行中撤回率、人工修改率或框架检查失败率超过阈值时，自动降回一次确认。
- 不改变：DC-11 §7 人裁决最小集（阶段决定、基线批准等仍为 T2）；个人承诺须本人作出（v1.1 §03.5、§03.6）；阶段不按日历自动推进（§03.2）；AI 身份写入、溯源与撤回（DC-11 §11）；模型不提供权限与人员职责事实（AGENTS.md 不可协商项 2）；未取得资格的租户中，上述动作退回现行一次确认。
- v1.1 同步（确认后）：附录 A 为 `work.task.assign`、`work.plan.apply`、`work.stage.adopt`、`work.stage.milestone.bind` 加注此情形档位，并登记新增的任务维护命令；§03.13 加注框架；§06.5 示例加注。S5 项目工作合同与 `work_management` 技能包的来源规则随实施更新。
- 判据：
  - G0 批准后无需人工操作，项目即有完整计划，且框架检查全部通过；
  - 缺少任一红线成果对应任务的计划不生效；
  - 受派人承接前没有承诺记录；
  - 小Pai 不能未经承接人确认就修改已承接任务；
  - 基线批准后小Pai 不能直接改变基线；
  - 未取得资格的租户中，上述动作走一次确认；
  - 整次撤回能撤销小Pai 生成的计划，已被人修改或承接的条目逐条列为未撤回并说明原因。

## 11. 建设项

建议顺序：

1. **框架配置**：新品阶段、出口成果、条件成果、红线与门槛，版本化；停用混合三代模板的任务目录（`templates.py`）。
2. **框架检查器**（§6）。
3. **项目团队与角色**：新领域对象与迁移。
4. **任务维护命令**：修改、拆分、合并、改派、取消，限小Pai 建且未承接的任务。
5. **阶段节点服务器接口**：接现有阶段评审与决定命令。
6. **`work_management` 技能包改版**：按框架生成计划的使用原则、来源规则与输出 schema。
7. **真实工作日历**：现传入日历会被拒绝；接通前计划日期按什么日历计算，实施时确定并在页面标注。
8. **资格评测集**：10–20 个覆盖不同品类的合成项目，供用户审阅。

## 12. 未决与风险

- **门槛数值**：通过率 ≥95%、直通率 ≥95% 沿用 CEHub v3，是否适用当前产品线待用户确认。
- **跨项目可比性**：各项目任务不同，跨项目比较与健康度按出口成果和阶段计算，不按任务名称。
- **新品类质量**：品类资料少时，小Pai 生成的任务更少、未知更多；框架检查只保证不缺底线成果，不保证品类差异充分。
- **其他项目类型**：派生、JDM、翻新、OBT、变更的框架尚未整理。
